<objective>
Move the three host-side shell scripts into `.claude/skills/vice-session/resources/`, make
them work from either location, and have any use of the skill's Node modules deploy them
into `tools/` automatically.

Purpose: quick-260730-oga moved the Node half of this setup into the skill and deliberately
left the shell half in `tools/`, with SKILL.md telling anyone exporting the skill to
"copy the scripts alongside". That instruction is the bug: a skill that only works if you
also remember to copy three files from somewhere else is not exportable, and the person who
forgets gets a client with nothing to talk to and no error explaining why. This change makes
the skill carry both halves, keeps `tools/` as a disposable deployment target the host's
existing muscle memory still hits, and removes the second tracked copy so the two can never
drift.

The load-bearing detail: the scripts currently derive the repo root as one level up from
their own file. That is right from `tools/` and wrong from `resources/` — off by three
levels, landing on `.claude/skills/.vice-supervisor`, a directory nothing writes to. Nothing
would error; the container would just read a permanently empty epoch file and restart
detection would quietly stop working. This is the same failure class `repo-root.mjs`'s header
comment exists to document, and it is why D-6 is not optional polish.

Output: three scripts relocated with `git mv` (history preserved) plus one new shared
`lib/repo-root.sh`; a new `install-resources.mjs` that fires once per process from any entry
point, never overwrites, never throws, and explains the host launch on stderr; an `install`
verb; ten new tests; and the two documents whose description of the host/container split this
change invalidates.
</objective>

Create `.claude/skills/vice-session/install-resources.mjs`.

State the hosting choice in its header — D-3 asks for it explicitly. The check lives in a
DEDICATED module, triggered from `repo-root.mjs`, for two reasons. First, `repo-root.mjs` is a
pure path resolver, and inlining filesystem-writing side effects into it would make every
importer of a path function also a file writer. Second and decisive: the installer needs the
repo root, so hosting the logic inside `repo-root.mjs` and importing back would be a module
cycle, and in that cycle this module evaluates while `repo-root.mjs`'s `const HERE` is still in
its temporal dead zone — every entry point would die with
`Cannot access 'HERE' before initialization`. The cycle is avoided structurally: this module
takes the repo root as an ARGUMENT and imports nothing from `repo-root.mjs`. Put that in a
comment, because the obvious "cleanup" a later reader will attempt is to add that import.

Export:

- `RESOURCES_DIR` — this module's own sibling `resources/` directory, resolved from
  `import.meta.url`.
- `installTargetDir(root)` — `join(root, "tools")`.
- `resourceEntries()` — recursive walk of `RESOURCES_DIR` returning the relative path of every
  regular file. A walk, not a hardcoded list, so a file added to `resources/lib/` later deploys
