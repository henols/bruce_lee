**FINDING 1 — boot is sub-second.** Computed from the nanosecond `launched_at`/`ready_at` fields
in the broker's own `.vice-supervisor/spares/*.json` records, read live before shutdown:

| Port | launched_at (ns) | ready_at (ns) | elapsed |
|---|---|---|---|
| 6541 | 1785658461697376099 | 1785658462352542811 | 0.655 s |
| 6542 | 1785658462399346879 | 1785658463038645810 | 0.639 s |
| 6543 | 1785658820902732602 | 1785658821608383711 | 0.706 s |

These are **upper bounds**: `ready_at` is stamped when `maintain_spares()` observes
`probe_ready()` succeed, and passes run every `VICE_BROKER_POLL_MS=500`, so up to ~0.5s of each
figure is poll latency rather than boot. True boot is somewhere in ~0.14–0.71s. The safe claim
is "sub-second, roughly 0.65s measured, true value at or below that" — never a bare figure
presented as the boot time itself.

**FINDING 2 — the grant-timeout conclusion is retracted.** Corrected arithmetic over a
serialised depth-1 boot queue at ~0.7s per boot:

| Wave width | Last agent waits | Under the 25s ceiling |
|---|---|---|
| 5 | ~2.8 s | fine |
| 10 | ~6.3 s | fine |
| 16 (= current `VICE_BROKER_MAX`) | ~10.5 s | fine |
| ~36 | ~25 s | the actual cliff |

The 25s deadline caps waves at roughly 36 agents, more than double `VICE_BROKER_MAX=16`. The
timeout was never the binding constraint; `VICE_BROKER_MAX` is. Raising the timeout stays a mild
robustness improvement (headroom for a slow or contended host) and nothing more.

**FINDING 3 — the log prints `(0s)`.** `maintain_spares()` computes elapsed seconds with integer
division (`elapsed_s=$((elapsed_ns / 1000000000))`), so every sub-second boot renders as `(0s)`
— visible in all four log lines above. The only human-readable boot figure in the system rounds
the true value to zero, reading as "instant, or unmeasured", while full nanosecond precision sat
unused in the JSON. This is why nobody had a number to contradict an 8s guess.

**FINDING 4 — qpq's host validation PASSED.** Serialised warming works on the host: four
launches, strictly one per pass, each reaching `ready` before the next began, **zero SEGV, zero
exit-1, zero exit-0 races** — the 2026-08-01 outage's failure mode (three simultaneous boots:
one SEGV, one exit 1, one exit 0) did not recur. The grant was instant from a warm spare
(`granted request … -> port 6540 (from ready spare)`). Floor restoration works (`launched port
6543` immediately after). Clean reap on signal: `^C` → `reap saw 4 recorded instance(s),
terminated 4` → protocol state purged; 4 = 3 spares + 1 grant.

**FINDING 5 — defect 4 reproduced, and the deployment shape is fragile.** The `^C` reaped all
four instances including this session's granted one. That is **by design** — qpq reversed the
contract deliberately, because orphans cost more than an interrupted session. The contract is
not the defect. The fragility is that the broker runs in the **foreground** with no detached
mode, so a stray Ctrl-C, a closed terminal or a SIGHUP from an ending SSH/VS Code session
destroys every active session's emulator. Downstream: two consecutive `mcp__vice__vice_ping`
calls then returned byte-identical `ECONNREFUSED` against the cached grant
(`req-132346-1785658820506-ed4707b4`, port 6540, epoch 3, pid 3493998), reproducing **defect 4**
(proxy caches a dead grant for the session's life, no re-request path) — previously seen once,
now witnessed a second time, with the new fact that a *deliberate* shutdown poisons a session
exactly as a crash does. Supporting host artifacts, read live: `.vice-supervisor/6540/supervisor.log`
showed `caught signal, shutting down` / `terminating child pid 3493998` / `clean shutdown`,
proving the emulator was signalled rather than crashed; `.vice-supervisor/6540/logs/x64sc-20260802-081421.log`
truncates mid-line inside `MCP-Tools: Handling tools/ca`, showing x64sc was killed while serving
a request.

**FINDING 6 — the atomic-write temp leak.** `write_json_atomic()` runs
`mktemp "$VICE_POOL_DIR/.broker.XXXXXX"`, chmods 600, writes, then `mv`s to the final path. If
the process dies between `mktemp` and `mv`, the temp survives — and `purge_protocol_state()`
removes only `spares/ grants/ requests/ leases/`, `broker-instances.json` and `broker.json`,
never `.broker.*`. Observed: `.vice-supervisor/.broker.bXkF8L`, 0 bytes, mode 600, dated
2026-08-01 22:53, surviving the entire 2026-08-02 lifecycle (start, 4 launches, a grant, a
purging shutdown) untouched. Inert — nothing globs `.broker.*`; it is neither `*.json` in a
protocol dir nor a numeric port dir — so the cost is unbounded accumulation plus a misleading
artifact for anyone inspecting the pool dir mid-outage, the same class of harm as the stale
`usage()` text that misdirected a live debugging session in defect 2. Severity **minor**, and
that severity was the assistant's suggestion, not confirmed by the user. Suggested fixes: sweep
`.broker.*` in `purge_protocol_state()`; better, use a deterministic per-target temp name
(`"$final_path.tmp"`) so a retry overwrites instead of accumulating, bounded by construction —
and note that Node's `writeFileSync` + `renameSync` with a fixed `.tmp` suffix plus exit cleanup
makes it structurally impossible, which is a point for the rewrite.
