## THE CALL: option (c), the middle split

Move `inPowerOnPatternBlock` and `sharesSingleBitDriftOrigin` into the skill. Keep `classifyRunSet`
and `REPORT_ZONES` in `tools/recover.mjs`.

**The executor does not re-litigate this.** The reasoning below is the spec; implement it.

### Why not (a), move all four

`REPORT_ZONES` contains `$0400-$CB66 program image`. `$CB66` is *danish's* measured
program-image ceiling — `01-01-SUMMARY.md:124` records it as "~51 KB of loaded game code and
data" for that release, and `recovery/danish/NOTES.md:133` reports against the same boundary.
That is a release-specific constant, which fails layer B's stated criterion ("no concept of a
release") outright. `classifyRunSet` consumes it directly at `recover.mjs:367`.

So moving `classifyRunSet` is not a move. It is either (i) dragging `$CB66` into a skill whose
name promises genericity — the exact failure the seam note used to reject folding `recover.mjs`
into `vice-session` ("a Bruce Lee skill wearing a generic name"), or (ii) redesigning
`classifyRunSet` to take zones as a parameter. The todo authorises a move, not a redesign, and
forbids behaviour change; (ii) is an API change with real regression surface against a gate that
currently reports exact numbers. Rejected.

### Why not (b), leave all four

Two independent facts defeat it.

**`popcount` is duplicated across the seam today.** `recover.mjs:342` defines a local
`popcount` inside `sharesSingleBitDriftOrigin`; `ram-compare.mjs:26` defines a module-level one
with a byte-identical body. The drift-measurement primitive had to be re-derived on the far side
of the boundary. That is not a stylistic nit — it is the boundary telling you it is in the wrong
place. Option (c) deletes the copy; option (b) preserves it.

**`inPowerOnPatternBlock`'s entire justification is a C64 machine fact.** Its docstring is about
never-written RAM holding the power-on `$00`/`$FF` pattern. Nothing in it mentions this game,
this release, or this gate. `sharesSingleBitDriftOrigin` likewise reasons purely about DRAM
drift physics, and it exists specifically to correct an overcounting bug that `classifyRuns` —
already in the skill — documents about itself. Under (b), the skill's own domain knowledge lives
outside the skill, and the fix to the skill's own documented limitation lives outside the skill.

### How 01-01's argument is upheld, not overruled

01-01's principle is **accepted**: the skill offers a capability, the project layers policy, and
policy belongs to the project. The disagreement is narrower than the principle — it is about
*which of the four symbols contain policy*. 01-01 drew the line around all four; the line
actually falls between the third and the fourth.

Test: does the symbol *decide* anything, or does it *measure*?

- `inPowerOnPatternBlock` → returns a fact about 16 neighbouring bytes. No N, no threshold, no
  accept/reject. **Measurement.**
- `sharesSingleBitDriftOrigin` → returns a fact about a value set. Exhaustive, no cutoff, no
  tunable. **Measurement.**
- `classifyRunSet` → holds `N >= 3`, holds the `sharedOrigin || patternBlock` **disjunction**,
  and holds the release-specific zone table. **Policy.**

And the policy is demonstrably live, not merely nominal: `drift-discriminator-resolved.md`
records that a **stricter** formulation (per-bit majority against the consensus of N) was
considered and rejected — it rejects `$DA7B`, which the disjunction accepts by positing an
unobserved origin. A different consumer of this skill could legitimately prefer the stricter
rule, or demand both clauses rather than either, or demand N>=5. That is exactly what makes the
disjunction policy. 01-01's line was right; it was drawn one symbol too wide.

### How the "two captures" evidence is honoured

The todo's strongest point stands: the skill advertises "prove **two** captures are equivalent"
while 01-01 measured 93 bytes identical in runs 1+2 that differed in run 3, so two runs cannot
call a byte stable. The skill was advertising the weaker half of its own capability.

Option (c) fixes that without claiming the skill owns the N. Both moved predicates are
*run-set shaped* by signature — `inPowerOnPatternBlock(images, addr)` takes an array of images,
`sharesSingleBitDriftOrigin(values)` takes an array of per-run values. After the move the skill
ships every measurement needed to adjudicate N captures for any N; the project keeps *which* N
and *which* combination of clauses it accepts. The description is corrected to cover repeated
captures rather than exactly two, which is the honest statement of what the skill now offers.

### The decision predicts a testable consequence

If these predicates really belong in an import-free module, moving them should unlock coverage
that was awkward or impossible through `classifyRunSet` — window boundaries at exactly `+/-8`,
address clamping at `$0000`/`$FFFF`, the byte-excluded-from-its-own-window rule, per-image
disagreement, and 256-case origin sweeps. Task 2 writes those tests **first**. If they turn out
to be reachable just as cleanly through `classifyRunSet`, the decision was weaker than argued —
so the plan produces evidence for its own call rather than only rhetoric.
</decision>

`sharesSingleBitDriftOrigin(values)`:

  versus `$10` is two bits apart. This is the case the pairwise rule got wrong.

  8-bit spread.
- `[0xaa]` is true; a single observation is always within one flip of itself.
- Exhaustive positive sweep, all 256 values of `v`: `[v, v ^ 0x01, v ^ 0x02]` is true, since `v`
  itself is an origin. This makes the "all 256 candidates, no search cutoff" claim checkable
  instead of asserted.
- Exhaustive negative sweep, all 256 values of `v`: `[v, v ^ 0x07]` is false. Three bits apart
  means no single origin can sit within one flip of both. Note in a comment that `[v, v ^ 0x03]`
  is deliberately NOT used here because it IS true — origin `v ^ 0x01` reaches both — which is
  the whole point of the shared-origin reframe and would make the sweep a false negative test.

`inPowerOnPatternBlock(images, addr)`:
- The window is exactly `addr-8` through `addr+8` inclusive, with `addr` itself excluded. A
  neighbour of `0x33` planted at exactly `addr-8` returns false; the same at exactly `addr+8`
  returns false; the same at `addr-9` or `addr+9` returns true, because it is outside the window.
- The byte at `addr` being `0x33` in every image still returns true — drift is precisely what
  made it stop being `$00` or `$FF`, so it is excluded from judging itself.
- A `0x33` planted in only ONE of three images returns false; every image is checked, not just
  the first.
- `addr = 0x0000` and `addr = 0xffff` return a boolean without throwing; out-of-range window
  indices are skipped.
- An all-`$00`/`$FF` neighbourhood returns true.

All of the above run over 65536-byte buffers with no emulator and no I/O, which is the property
the import-free header claims and is the empirical payoff the decision predicted.
