## Decisions Made

- **The mode-restriction gap was fixed, not silently ported forward.** See key-decisions above and the Deviations section below for the full account.
- **`containerizeRecord()`'s `alias` option made required.** No real caller (`vice-proxy.mjs`'s `containerizeGrant()`) or any test in the suite ever invokes it with `urlFields` non-empty and no `alias`; the outer options parameter also lost its permissive `= {}` default for the same reason. Zero behavior change for any real caller, matching Plan 03's `resourcesStatus()` precedent exactly.
- **No discriminated-union return invented for the incident-record writers.** `vice-broker.mts`'s `WriteResult` idiom fits a function with a genuine ok/fail branch; `writeIncidentRecord()`/`finaliseIncidentRecord()` have none (they always succeed or let a real fs exception propagate, unchanged from the original). Introducing a fabricated always-`ok:true` wrapper would have been a behavior-shape change disguised as "following the precedent."
- **`IncidentRecordInput`'s fields typed mostly `unknown`, not narrow scalars.** `renderIncidentRecord()` only ever passes these through `yamlScalar()` or a template literal, never a type-specific operation; narrowing to `string`/`number` would assert a contract the runtime does not enforce and would have forced an unsound cast when `finaliseIncidentRecord()` spreads `parsed` (whose dynamic keys come back `unknown` from `ParsedFrontmatter`'s index signature).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical Functionality] incident-record.mjs's atomic write never actually restricted the written file's mode**
- **Found during:** Task 2, while reading the pre-conversion `incident-record.mjs`'s `writeAtomic()` against PLAN.md's task text ("restrict its mode before any content lands... must come through unchanged") and PATTERNS.md's "Atomic write (tmp -> chmod 600 -> content -> rename)" section, which lists `incident-record.ts`'s writer under "Apply to."
- **Issue:** The actual pre-conversion function was `writeFileSync(tmp, content)` then `renameSync(tmp, path)` -- no `chmodSync` step, and no empty-write-first step. Cross-checked against the two siblings the file's own header comment claims atomicity parity with (`vice-broker-client.mjs`'s `writeJsonAtomic()`, `resources/vice-broker.sh`'s `write_json_atomic()`): neither of those chmod either. Only `vice-broker.mts` (the Phase 01.6 TS tracer) and `install-resources.ts` (Plan 03) actually do the full tmp-empty -> chmod 0600 -> content -> rename sequence. The plan's "must come through unchanged" framing was inaccurate about this file's actual state -- it described a newer, tighter pattern as if it were already this file's status quo.
- **Fix:** Added `writeFileSync(tmp, "")` then `chmodSync(tmp, 0o600)` before the content write, matching `vice-broker.mts`/`install-resources.ts`'s exact idiom. Updated `writeAtomic()`'s own doc comment to accurately describe the now-tightened sequence and why it diverges from the two named siblings, rather than leaving a comment that claimed parity with functions that still lack the step.
- **Files modified:** `.claude/mcp/vice/incident-record.ts`, `.claude/mcp/vice/incident-record.test.ts` (two new tests), `.planning/RE-FINDINGS.md`
- **Verification:** New test `T-01.6.1-08: the written record's mode is not group- or world-readable` asserts `statSync(path).mode & 0o077 === 0` directly after a write; a second new test asserts the same after `finaliseIncidentRecord()`'s re-render. Both pass live. Full suite re-run immediately after: 254/254, fail 0.
- **Committed in:** `0ceb419` (Task 2's commit)
