## Accomplishments

- Removed the last hardcoded-extension read in the tree: `load-order.test.mjs`'s Part 1 guard used to read `join(HERE, "install-resources.mjs")` by literal name. Replaced with `resolveModuleByStem()`, a by-stem resolver over `listModuleFiles()`'s own enumeration that throws loudly on zero matches (subject renamed away) or two matches (both extensions transiently on disk mid-rename) rather than silently checking a stale copy -- proven RED-then-GREEN live (both new-behavior tests failed with `ReferenceError` before the resolver existed, then passed once implemented).
- Converted the three cycle-slice source modules to `.ts` with named `interface`/`type` declarations per `vice-broker.mts`'s idiom, `isPlainObject()` narrowing of `install-resources.ts`'s manifest `JSON.parse()` result instead of casting, and the never-throw two-layer try/catch discipline preserved exactly (proven by `install-resources.test.ts` still reporting `pass 19, fail 0`, including the untracked-file-protection case).
- Repointed every real consumer specifier in the tree to the three new `.ts` paths -- `vice-probe.ts`'s own bare side-effect import (a consumer RESEARCH's own count had missed), `containerpath.mjs`, `incident-record.mjs`, `vice-broker-client.mjs`, `vice.mjs`, `vice-sync.mjs`, `vice-proxy.mjs`/`.test.mjs`, `containerpath.test.mjs`, and both test files converted in Task 3 -- and verified the hub (`vice-proxy.mjs`, 2,441 lines) still loads cleanly in a fresh Node process, not merely that grep found no stale specifier.
- Cleared Wave 1's scoped `@ts-expect-error` on `host-scripts.test.ts`'s import of `install-resources` -- it would otherwise have become a loud, self-cancelling `TS2578` ("unused directive") error the moment `install-resources.ts` landed, exactly as that Wave's SUMMARY predicted.
- Converted the three test files (`repo-root.test.ts`, `install-resources.test.ts`, `load-order.test.ts`) with typed helper functions throughout, leaving every regression-corpus string literal -- including load-order's 29 legacy `.mjs`-specifier-shape literals -- exactly as written, since those exist to prove the extraction regexes still catch every shape a rename could produce.
- Discovered and fixed a **second** hardcoded-name gap in `load-order.test.mjs` that Task 1's own scope (Part 1's real-file read only) did not cover: Part 2's module-enumeration sanity test asserted `moduleNames.includes("repo-root.mjs")` etc. by literal name. Rewrote it to use Task 1's own `resolveModuleByStem()` (see Deviations).

## Decisions Made

- **Part 2's hardcoded-name gap fixed via Task 1's own resolver, not a separate mechanism.** Task 1's scope was Part 1's real-file read only; Part 2's enumeration sanity test hardcoded the same three filenames a second time and would have failed the moment Task 2 landed. Reusing `resolveModuleByStem()` there (rather than inventing a second by-stem helper) keeps one resolution mechanism in the file.
- **Hazard-header quoted literals kept byte-identical.** `install-resources.ts`'s and `hostpath.ts`'s header comments quote the forbidden import (`"./repo-root.mjs"`) as an anti-pattern illustration, mirrored verbatim by `load-order.test.ts`'s own regression corpus. Per the plan's explicit "port verbatim" instruction, that quoted string was left unchanged; every OTHER prose mention of the three renamed files (in these same files and in every other touched file) was updated to `.ts` so the surrounding documentation stays accurate.
- **`resourcesStatus()` typed with a required `root` parameter**, dropping its original `= {}` default. Nothing in the tree calls this exported-but-unused function with zero arguments; the old default only deferred an inevitable crash (`join(undefined, "tools")`) to a different line. No behavior change for any real caller.
