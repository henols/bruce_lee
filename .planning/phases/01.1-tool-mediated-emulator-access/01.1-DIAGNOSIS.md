# Phase 01.1 — Diagnosis: why the current emulator path fails

**Date:** 2026-07-31
**Task:** 01.1-01/T1

## Purpose

The premise that motivated this phase — "the claim that `vice-session` does not work has never
been diagnosed, only asserted" — is checked here directly, with live evidence, before any code is
written. This diagnosis separates two questions that the existing memory note
(`vice-session-skill-is-dead.md`) conflates: (1) is the host emulator reachable from this
container right now, and (2) is the Bash-mediated design itself defective. These are independent
facts, and only one of them is this phase's actual justification.

## The verdict rule

Stated up front, exactly as the plan requires:

- DNS fails to resolve, **or** a port connects but no MCP response is ever routable →
  `structurally-unreachable`
- DNS resolves and every port refuses immediately →
  `host-not-running`
- A `vice_ping` round-trip succeeds →
  `reachable`

## Probe evidence (run live, this session, 2026-07-31)

### Probe 1 — DNS resolution

Command:

```bash
getent hosts host.docker.internal
```

Observed output:

```
172.17.0.1      host.docker.internal
```

DNS resolves. Container networking to the host gateway is intact.

### Probe 2 — raw TCP connect on ports 6510, 6511, 6512

Command (run once per port, via bash's `/dev/tcp` redirection):

```bash
timeout 5 bash -c 'exec 3<>/dev/tcp/host.docker.internal/6510'
timeout 5 bash -c 'exec 3<>/dev/tcp/host.docker.internal/6511'
timeout 5 bash -c 'exec 3<>/dev/tcp/host.docker.internal/6512'
```

Observed output, all three, immediately (well under the 5s timeout — no hang):

```
bash: connect: Connection refused
bash: line 1: /dev/tcp/host.docker.internal/6510: Connection refused
exit_code=1

bash: connect: Connection refused
bash: line 1: /dev/tcp/host.docker.internal/6511: Connection refused
exit_code=1

bash: connect: Connection refused
bash: line 1: /dev/tcp/host.docker.internal/6512: Connection refused
exit_code=1
```

This is the distinction the whole diagnosis rests on: an **immediate `Connection refused`** on
every port, not a hang or a slow timeout. Refused means nothing is listening on the other end —
the TCP stack itself answered instantly. A timeout would instead mean something unroutable
(a firewall silently dropping the packet, or a genuinely broken network path), which is the
`structurally-unreachable` case. That is not what was observed.

Command:

```bash
node .claude/skills/vice-session/scripts/vice.mjs ping

Observed output (full session, timed):

```

warn: vice_ping transport failure (attempt 2/5), reconnecting in 5000ms: transport error calling initialize: fetch failed

`vice.mjs ping` exhausted its full 5-attempt reconnect ladder (2s + 5s + 12s + 30s backoff between
attempts) and failed after ~49 seconds, matching the documented "~50s ladder" in `vice.mjs`'s own
header comment (lines 212-227) and in `STATE.md`'s history. This is exactly the "dead host looks
like a hang" symptom `RESEARCH.md` and this task's `<read_first>` list flagged in advance — the
50-second wait is the retry ladder working as designed against an unreachable endpoint, not the
proxy (or the transport module) malfunctioning.

### Supervisor state files

Checked:

```bash
ls -la .vice-supervisor/
ls .vice-supervisor/epoch.json .vice-supervisor/registry.json .vice-supervisor/session.json
```

Observed:

```
ls: cannot access '.vice-supervisor/': No such file or directory
```

The `.vice-supervisor/` directory itself does not exist. No supervisor, pool, or session has
written anything in this container instance's lifetime. This is consistent with — and further
corroborates — "nobody has started the host emulator side of this setup," rather than "something
crashed mid-run and left partial state."

## Applying the rule

DNS resolves (Probe 1). Every one of the three pool ports refuses immediately, not a timeout
(Probe 2). Per the stated rule, this is:

**Reachability verdict:** host-not-running

`vice.mjs ping`'s exhausted retry ladder (Probe 3) is the expected downstream consequence of that
verdict, not independent evidence of a different failure mode — a transport-level "fetch failed"
against a refused connection is exactly what the retry ladder is built to eventually give up on.

## Halt rule

Only `structurally-unreachable` stops this phase. That verdict was **not** reached here, and the
distinction matters concretely: `structurally-unreachable` would mean either DNS itself is broken,
or a port connects but no MCP response is ever routable through it — in either case, the proxy
being built in Task 2 would fail identically to the current path, on an infrastructure fact no
amount of new code could route around, and continuing to build would mean building on an
unexamined assumption (ROADMAP criterion 1, § Risks).

`host-not-running` is the opposite kind of fact: it says the network path and the DNS resolution
are both fine, and the only missing piece is a process that has not been started on the host side.
That is an **availability fact about the host**, not a defect in the proxy's design, and it does
not stop the build. `01.1-RESEARCH.md`'s § Validation Architecture establishes exactly why: the
proxy's entire observable surface, on the stdio side, is a set of `stdin`/`stdout` JSON-RPC frames,
and that surface is fully testable with a `node:http` stand-in server standing in for the host —
zero live emulator required. Task 2 of this plan proceeds on that basis.

## Correcting the "non-functional" framing

The project memory note `vice-session-skill-is-dead.md` (originSessionId
`543a18a5-b7ec-49aa-8dc3-e800d55c1b19`, modified 2026-07-31T13:19:13.580Z) states: "The
`vice-session` skill (`.claude/skills/vice-session/`) is **non-functional** and slated for
removal." That wording is stronger than the evidence supports, and this section corrects the
record rather than inheriting it.

**The Bash-mediated path is working, heavily-used, load-bearing code.** Three real recovery
captures — RECOVER-01, RECOVER-02, RECOVER-03 (plans 01-01 through 01-03, per `STATE.md`'s own
history) — executed successfully through exactly this path: `vice.mjs`'s `call()` /
`withReconnect()` / `readEpoch()` / `assertSameMachine()` / `serverInfo()` functions, invoked via
`node .../vice.mjs ...` from Bash. Along the way this code:

- survived **six real host VICE MCP outages** in one session (two needed a manual host restart,
  four self-recovered via the retry ladder demonstrated live in Probe 3 above);
- correctly distinguished a genuine mid-session machine restart from a transient transport blip,
  via the epoch mechanism (`readEpoch()`/`assertSameMachine()`), voiding runs whose identity could
  not be proven rather than silently writing garbage;
- correctly enforced the `vice_disk_list` deny-list at every call site, with zero accidental
  invocations across the whole session.

None of that is the behaviour of non-functional code. What is currently unreachable is the *host
process this session happens to need* — a fact this diagnosis's own Probes 1–3 established live,
today, independent of any defect in `vice.mjs` itself.

**The phase's actual justification is a hazard/enforcement gap, not brokenness.** The current
architecture is Bash-mediated *by design* (`tools/README.md`'s own recorded decision D-5): every
emulator call is a hand-assembled shell invocation, `node .../vice.mjs call TOOL '{...}'`, rather
than a real `mcp__vice__*` tool call. That means:

- there are no schemas and no tool-name completion — an agent has to know or look up the exact
  JSON shape every tool expects;
- there is no structural enforcement point — the three known hazards (`vice_disk_list` refusal,
  epoch-based restart detection, the pause-on-state-read discipline) are each implemented
  correctly *inside* `vice.mjs`, but nothing stops a caller from bypassing `vice.mjs` entirely and
  reaching the host directly, or from misremembering a rule that lives only in a skill doc or a
  project memory file rather than being enforced by the tool surface itself.

"Worth fixing" is the accurate claim here. "Broken" is not, and this document deliberately states
that distinction plainly rather than restate the memory file's stronger wording.

## Disposition

Verdict is `host-not-running`, which does not halt the phase. Task 2 (the tracer proxy) proceeds,
built and verified against a `node:http` stand-in server per `01.1-RESEARCH.md`'s Validation
Architecture — no live host emulator is required for anything in this plan. Success criterion 3
(fresh-session, live `mcp__vice__*` proof) remains gated on a human starting the host side, exactly
as `01.1-RESEARCH.md` and `ROADMAP.md`'s own risk section anticipated; that gate lives in a later
plan (`01.1-04`), not this one.
