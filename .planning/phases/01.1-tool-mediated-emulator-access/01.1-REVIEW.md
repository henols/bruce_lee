# Phase 01.1: Code Review Report

**Reviewed:** 2026-07-31T00:00:00Z
**Depth:** standard
**Files Reviewed:** 28
**Status:** issues_found

## Summary

Reviewed the vice-proxy stdio MCP server, the relocated `vice-mcp-selector` transport/pool/session/probe modules, the host-side shell launchers, the `c64-ram-capture` skill, and the three `tools/*.mjs` library consumers. The never-throw discipline in `vice-proxy.mjs` is genuinely solid (verified against its own test suite: uncaughtException/unhandledRejection handlers, the single `process.exit(` on the stdin end/close path, and every `tools/call` outcome degrading to a well-formed `isError` result). The epoch-based restart detection and the never-cache-a-negative-result invariant both hold up under inspection.

Two real defects were found that undercut load-bearing safety properties this phase is explicitly built around:

1. A path-traversal gap in the proxy's own "refuse an out-of-workspace absolute path" security control — the check operates on the raw, unresolved string rather than a normalized path, so a lexical `..` sequence can pass the "inside the workspace" test while still resolving outside it once handed to the host.
2. `voidRun()`'s evidence-note write is not directory-safe — if a machine restart is detected before the run has reached the point where `dumps/` is guaranteed to exist, the write throws and replaces the informative "the emulator restarted" diagnosis with a raw ENOENT, silently discarding the evidence note this mechanism exists to guarantee.

Three further issues degrade robustness or quality without being immediately incorrect-behavior-causing: the live-refreshed tool manifest advertises protocol-method-shaped pseudo-tools alongside the real `vice_*` surface; the `vice_disk_list` deny-list is enforced identically (and therefore not independently) at both layers with no name normalization; and a boot-detection retry loop in `c64-ram-capture` cannot actually retry because the state reads it depends on pause the machine.

## Critical Issues

### CR-01: Path-traversal bypass of the workspace-boundary refusal in `rewritePathsIn`/`isInsideWorkspace`

**File:** `.claude/skills/vice-mcp-selector/scripts/vice-proxy.mjs:424-426, 437-449`
**Issue:** `isInsideWorkspace()` compares the raw argument string against the resolved workspace root using a plain prefix test, with no `path.resolve()`/`path.normalize()` applied to the argument first:

```js
function isInsideWorkspace(absPath, root) {
  return absPath === root || absPath.startsWith(root.endsWith("/") ? root : root + "/");
}
```

`rewritePathsIn()` calls this directly on the untouched string value from `arguments`:

```js
if (!value.startsWith("/")) return value;
if (!isInsideWorkspace(value, root)) {
  throw new PathOutOfWorkspaceError(...);
}
try {
  return hostPath(value);   // still the UNRESOLVED string
} catch (e) { ... }
```

An argument such as `"/workspaces/bruce_lee/../../../etc/passwd"` lexically **starts with** `root + "/"` (`/workspaces/bruce_lee/`), so `isInsideWorkspace()` returns `true` and the refusal never fires — even though the path resolves well outside the workspace once its `..` segments are honored by the filesystem. The unresolved string (still carrying the `..` segments) is then handed to `hostPath()` and, if translated, forwarded to the host VICE MCP server as a `path` argument (e.g. for `vice_disk_attach`, `vice_display_screenshot`, or any future path-taking tool) — this is exactly the directory-traversal class the review scope calls out, and it defeats the one refusal this file's own header describes as closing off "the container path escaping translation" case.

**Fix:** Resolve the argument before comparing, and translate the resolved form, not the raw one:

```js
function isInsideWorkspace(absPath, root) {
  const resolved = resolve(absPath); // `resolve` is already imported in this file
  return resolved === root || resolved.startsWith(root.endsWith("/") ? root : root + "/");
}

// in rewritePathsIn():
if (!value.startsWith("/")) return value;
const resolvedValue = resolve(value);
if (!isInsideWorkspace(resolvedValue, root)) {
  throw new PathOutOfWorkspaceError(...);
}
try {
  return hostPath(resolvedValue);
} catch (e) { ... }
```

### CR-02: `voidRun()` can throw ENOENT and silently discard the evidence note it exists to guarantee

**File:** `.claude/skills/c64-ram-capture/scripts/ram-capture.mjs:345-374` (called from `tools/recover.mjs:319-337`)
**Issue:** `voidRun()` writes its evidence note unconditionally once either `binPath` or `capturePath` is non-null, with no directory-existence check:

```js
export function voidRun({ binPath, capturePath, reason, ... } = {}) {
  if (!binPath && !capturePath) {
    return { voidedArtifacts: [], notePath: null };
  }
  ...
  const notePath = `${binPath || capturePath}.VOID.json`;
  writeFileSync(notePath, JSON.stringify({...}, null, 2) + "\n");   // no mkdirSync first
  return { voidedArtifacts, notePath };
}
```

`tools/recover.mjs`'s `recover()` only creates the containing `dumps/` directory once it reaches its success path (`mkdirSync(dumpsDir, { recursive: true })`, line 269) — well after `reset()`, `boot()`'s gate-walk/`attachAndStart()`, and the early part of `capture()` have already run. A `MachineRestartedError` raised anywhere before `boot()`'s own `screenshot()` call (which is the thing that incidentally creates `dumps/` today, as a side effect of writing the boot screenshot) — e.g. during `reset()`'s `vice_checkpoint_delete`/`vice_machine_reset` calls, or during `attachAndStart()` — reaches `recover()`'s `catch` block with `dumps/` not yet on disk. `voidRun({ binPath, capturePath, ... })` is called with non-null `binPath`/`capturePath` (both computed unconditionally at the top of `recover()`), skips its "nothing to void" early return, finds neither artifact exists (fine, no-op rename), and then calls `writeFileSync(notePath, ...)` against a path whose parent directory does not exist — throwing `ENOENT`. This exception is not caught anywhere in `voidRun()` or in `recover()`'s `catch` block, so it propagates and replaces the intended, informative `"recover(...): the emulator restarted mid-capture -- this run is VOID..."` message with a bare filesystem error, and — more importantly — the `.VOID.json` note is never written. This defeats the explicit design goal stated in this same file's header ("a voided run is itself evidence, not just a discarded one") in exactly the failure mode (a host/emulator restart) this project has been hard-blocked by six times already.

**Fix:** Make the note write directory-safe:

```js
import { dirname } from "node:path"; // add to the existing node:path import

// inside voidRun(), before writeFileSync(notePath, ...):
mkdirSync(dirname(notePath), { recursive: true });
```

## Warnings

### WR-01: Live-refreshed tool manifest advertises non-emulator protocol methods as callable tools

**File:** `.claude/skills/vice-mcp-selector/scripts/tools-manifest.json:5-51`, `.claude/skills/vice-mcp-selector/scripts/refresh-manifest.mjs:46-51`, `.claude/skills/vice-mcp-selector/scripts/vice-proxy.mjs:168-217`
**Issue:** The committed manifest (freshly regenerated by this phase's own `refresh-manifest.mjs` run) contains, alongside the 59 real `vice_*` tools, four entries that are not emulator tools at all — `initialize`, `notifications_initialized`, `tools_list`, `tools_call` — mirroring the underlying JSON-RPC method names verbatim. `refresh-manifest.mjs` writes whatever `serverInfo()`'s `tools/list` call returns with no filtering beyond the existing `DENY_LIST`, and `vice-proxy.mjs`'s `readManifestTools()`/`handleToolsList()` likewise only filters `DENY_LIST`, not shape/prefix. The result: an agent's tool list shows `mcp__vice__initialize`, `mcp__vice__tools_call`, etc. as if they were ordinary emulator tools. Calling any of them forwards to the host's `tools/call` with that literal name (e.g. `name: "tools_call"`), which is not how a normal `vice_*` tool invocation looks — at best this wastes a round trip and returns a confusing host-side error; it is also an unaudited edge of the deny-list's threat model, since neither layer of `DENY_LIST` enforcement has any reason to expect a tool literally shaped like a JSON-RPC method passthrough, and nothing here can rule out (without live testing, which this review is barred from doing) that such an entry behaves as a generic dispatch wrapper on the host side. Also note this silently inflates the "63 tools" figure the project treats as ground truth (CLAUDE.md's "exact 63-tool surface... matches, tool-for-tool") — only 59 of the 63 are real `vice_*` tools.
**Fix:** Filter the manifest to tool names matching the documented surface (e.g. `t.name.startsWith("vice_")`) in `refresh-manifest.mjs` before writing, and defensively again in `vice-proxy.mjs`'s `readManifestTools()` (the same "second, independent layer" pattern already used for `DENY_LIST`), so a snapshot generated by any means can't leak protocol-method-shaped pseudo-tools into the agent-facing surface.

### WR-02: `DENY_LIST` enforcement has no name normalization, so its "two independent layers" share one blind spot

**File:** `.claude/skills/vice-mcp-selector/scripts/vice.mjs:106, 477-482`, `.claude/skills/vice-mcp-selector/scripts/vice-proxy.mjs:604-609`
**Issue:** Both enforcement points use `Array.prototype.includes()` for exact-string matching against `DENY_LIST = ["vice_disk_list"]`, with no trimming or case-folding:

```js
// vice.mjs
if (DENY_LIST.includes(toolName)) { throw new ViceError(...); }
// vice-proxy.mjs
if (DENY_LIST.includes(name)) { return isErrorText(...); }
```

These are described in both files' comments as "independent layers," but for the specific class of bypass the review scope calls out — a name that normalizes to the forbidden one (padding, case variation) — they are not independent at all: they use the identical matching rule, so whatever slips past one slips past the other by construction. Whether Claude Code itself would ever send such a variant is a separate question (it echoes names verbatim from `tools/list`), but nothing in this code defends against a hand-crafted or replayed JSON-RPC frame naming e.g. `"Vice_Disk_List"` or `"vice_disk_list "`, which would reach the host untouched by either check.
**Fix:** Normalize before comparing in both places (`name.trim().toLowerCase()` against a lower-cased `DENY_LIST`), so the two layers actually diverge in what they'd need to fail simultaneously for a bypass to occur.

### WR-03: `attachAndStart()`'s boot-detection retry loop cannot detect delayed progress

**File:** `.claude/skills/c64-ram-capture/scripts/ram-capture.mjs:156-176`
**Issue:**

```js
await call("vice_execution_run", {});   // the only resume in this function

let moved = false;
for (let i = 0; i < 5 && !moved; i++) {
  const postRegs = await call("vice_registers_get", {});
  moved = postRegs.PC !== preRegs.PC;
}
if (!moved) {
  // falls back to a scripted LOAD"*",8,1 + RUN
  ...
}
```

Per this project's own established finding (see `vice-sync.mjs`'s header and this codebase's project memory: "most VICE MCP state reads pause the emulator, and do not resume it"), `vice_registers_get` pauses the machine. The loop resumes the machine exactly once, before the loop starts, and then calls a pausing state-read up to five times with no resume in between. After the first iteration, the machine is paused and stays paused for the remaining iterations — so `postRegs.PC` on iterations 2–5 will read back the identical value already observed on iteration 1 (`i=0`). If the real autostart/disk-load progress takes longer than the network round trip of that single first read, this loop can never see it move — it burns four extra, useless round trips and then falls back to the keyboard-driven `LOAD"*",8,1`/`RUN` path even when the native autostart would have succeeded given a genuine second resume. This changes the recorded boot `method`/`fallbackUsed` fields and switches the entry-point search onto a different, timing-sensitive path than the one that would otherwise have been used — a real risk to the reproducibility story this skill is built around.
**Fix:** Resume between checks, not just once before the loop:

```js
let moved = false;
for (let i = 0; i < 5 && !moved; i++) {
  const postRegs = await call("vice_registers_get", {});
  moved = postRegs.PC !== preRegs.PC;
  if (!moved) await call("vice_execution_run", {});
}
```

## Info

### IN-01: "Session" is an overloaded term across three unrelated concepts in this phase

**File:** `.claude/skills/vice-mcp-selector/scripts/vice-proxy.mjs:260-268` (module-local `viceSession`), `.claude/skills/vice-mcp-selector/scripts/vice.mjs:297-364` (`beginSession()`/`currentSession`, the identity-tracking session), `.claude/skills/vice-mcp-selector/scripts/vice-session.mjs` (the pool-lease `session acquire`/`release`/`status` CLI concept)
**Issue:** Three genuinely different things are all named "session" in this codebase: the proxy's own per-process epoch baseline, `vice.mjs`'s identity-tracking session object returned by `beginSession()`, and `vice-session.mjs`'s pool-lease session (a completely different, TTL-based cross-invocation concept). None of these are bugs individually, but the shared vocabulary makes it easy for a future change to one to be mistakenly assumed to also affect another (e.g. confusing the proxy's `ensureViceSession()` with a `vice-session.mjs` lease).
**Fix:** Consider renaming the proxy's local state (e.g. `epochSession` or `restartTracker`) to reduce the chance of a maintainer conflating it with the pool-lease `session` concept `vice-session.mjs` already owns that name for.
