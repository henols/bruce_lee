# Phase 01.1: Tool-Mediated Emulator Access - Research

**Researched:** 2026-07-31
**Domain:** Model Context Protocol (stdio server + HTTP client proxy) inside Claude Code; Node.js process lifecycle; existing VICE-access tooling migration
**Confidence:** MEDIUM — the wire protocol and Claude Code mechanics are HIGH (official docs, cited below); the phase's own diagnosis question (research question 1) resolved with a live, reproducible finding; but end-to-end verification of the *built* proxy is blocked by the same environmental fact this research surfaced (see Summary).

## Summary

The premise that motivated this phase — "the claim that `vice-session` does not work has never been diagnosed — only asserted" — is now diagnosed. It is **not the state described by the memory file** (`vice-session-skill-is-dead.md`: "non-functional"). Reading `vice.mjs`/`vice-session.mjs`/`vice-pool.mjs` and `STATE.md`'s own history shows the current path is heavily used, working, load-bearing code: three real recovery captures (RECOVER-01/02/03, plans 01-01..01-03) executed through it, with a battle-tested retry ladder, an epoch-based restart detector, and a deny-list — surviving six real host outages along the way. `tools/README.md` records the empty `.mcp.json` as a **deliberate D-5 decision**, not an accident or a defect: registering `mcp__vice__*` directly would bypass the deny-list, epoch check and lease discipline that only exist inside `vice.mjs`'s seam today. So "why does the current path fail" has two different, non-conflated answers: (1) **right now, at research time, the host process is simply not running** — confirmed live below, a plain `ECONNREFUSED` on every pool port, not a hang, not a Bash-vs-tool problem; this is an availability fact about the host, not a code defect, and it will make the built proxy fail *identically* until a human starts the host side; (2) **independent of availability, the architecture is Bash-mediated by design**, which is a real, worth-fixing DX/enforcement gap (no schemas, no tool names, hazards advisory-in-practice-only-because-nobody-else-can-call-them) — but "worth fixing" is a different claim from "broken," and the plan should say so plainly rather than inherit the memory file's stronger wording.

The practical consequence for planning: **1.1's own success criterion 3 (fresh-session proof that `mcp__vice__*` tools work) cannot be executed by this phase alone right now** — it needs a human to start the host emulator first, on top of the human-in-the-loop `.mcp.json` approval step findings 1/2/3/10 already require. This is not a new blocker introduced by the design; it is the same fact recorded in `STATE.md`'s "HARD BLOCKER" entry recurring. The plan should include an explicit, narrow checkpoint for this rather than assume reachability.

The build itself is smaller than the design note implies once one architectural fact is established: **`vice.mjs`'s existing module is not being replaced, it is being reused.** Its `call()`/`rpc()`/`withReconnect()`/`readEpoch()`/`assertSameMachine()`/`serverInfo()` functions already implement the exact HTTP-client-to-host half of what the proxy needs (JSON-RPC over `fetch`, SSE-body parsing, a 50s reconnect ladder, the `vice_disk_list` deny-list, epoch-based restart detection). The **only new code** is the stdio-server-facing half: answer `initialize`/`tools/list`/`tools/call` over newline-delimited JSON-RPC on stdin/stdout, delegating every real call into the existing `call()`. This reframes "write an MCP server" into "write a ~150-line stdio adapter in front of code that already has six real outages' worth of hardening." It also reframes the removal in success criterion 8: this is a **migration**, not a deletion — five files (`tools/recover.mjs`, `tools/chip-state.mjs`, `tools/watch-loads.mjs`, `.claude/skills/c64-ram-capture/scripts/ram-capture.mjs`, its test file) import `vice-session/scripts/{vice.mjs,vice-pool.mjs,vice-sync.mjs}` directly as a **library**, not through the CLI, and none of them go through Claude Code's MCP layer at all — they are plain Node processes invoked by `node tools/recover.mjs ...`. Retiring "Bash-mediated agent access" (what criterion 8 actually targets) and retiring "the transport module these five files import" are different questions with different answers; conflating them would either strand five working scripts or leave a half-migrated skill.

**Primary recommendation:** Build `vice-proxy.mjs` as a thin stdio-JSON-RPC-to-MCP adapter that *imports* the relocated `vice-session` transport module (rather than re-implementing HTTP/retry/epoch logic), relocate that module (and the five files that import it) into the new `vice-mcp-selector` skill in the same change, and treat success criterion 3's fresh-session verification as a human checkpoint gated on the host emulator actually running — because right now, it demonstrably is not.

### Locked Decisions (from the design note's Phase 1.1 column and ROADMAP.md)

- One static `.mcp.json` entry: `{"mcpServers":{"vice":{"command":"node","args":[".claude/skills/vice-mcp-selector/scripts/vice-proxy.mjs"]}}}` — no `url` field, never rewritten at runtime.
- The proxy forwards to a **fixed** host port. No leasing, no broker, no on-demand launch — that is 1.2's scope, explicitly excluded here.
- `initialize` and `tools/list` must be answered **without acquiring an emulator** (finding 6: spawn is eager). Acquisition (in the 1.1 sense: the first real host round-trip) is deferred to the first `tools/call`.
- Hazards enforced **in code**, each with a regression test that fails if the guard is removed: `vice_disk_list` refused; epoch re-checked every forwarded call; oversized output handled (chunked or raised limit) rather than silently truncated.
- The proxy must **never exit** and must **never cache a negative result** — every failure mode answers in a valid MCP frame, and the call after a fix "just works" with no session restart (finding 7: stdio servers are never auto-reconnected).
- Three-state diagnostics (never started / dead-or-hung / alive-but-failed), each quoting the translated **host** path via `hostpath.mjs`, each explicitly forbidding the old `vice.mjs` scripts as a workaround.
- Removal of `vice-session` and the Bash-mediated call path happens **only after** criterion 3 (fresh-session proof) passes — never before.
- Host-side launch machinery (`vice-pool.sh`/`vice-supervisor.sh`) is **not touched** in 1.1.

- What the epoch check is *for* now that fresh boots are the 1.2-future expectation — narrows to mid-session-restart detection only; not this phase's problem to resolve fully since 1.1 has no fresh-boot lifecycle yet (every emulator behind the fixed port is exactly as long-lived as it is today).
- Which fixed port, and who launches the emulator on it during 1.1 — the existing pool (`tools/vice-pool.sh start 3`, default ports 6510-6512) or a bare `x64sc -mcpserver` invocation.

### Pattern 1: Delegate, don't reimplement, the host-facing half

**What:** `vice-proxy.mjs` imports `call`, `serverInfo`, `readEpoch`, `DENY_LIST`, `beginSession`/`assertSameMachine` from the relocated `vice.mjs`, rather than opening its own `fetch()` to the host.
**When to use:** Always, for this phase — this is the single biggest scope-reduction available. `withReconnect()`'s 50-second backoff ladder and SSE-body parsing are exactly the kind of code a lifecycle spike would otherwise have to re-derive and re-battle-test from zero.
**Example:**
```js
// vice-proxy.mjs (new) -- delegating tools/call to the existing seam
import { call, DENY_LIST } from "./vice.mjs"; // relocated, unchanged

async function handleToolsCall(name, args) {
  if (DENY_LIST.includes(name)) {
    return { content: [{ type: "text", text: `${name} is permanently forbidden — see CLAUDE.md's hazard note.` }], isError: true };
  }
  try {
    const result = await call(name, args); // reuses the retry ladder + epoch check already built
    return { content: [{ type: "text", text: JSON.stringify(result) }], isError: false };
  } catch (e) {
    return { content: [{ type: "text", text: e.message }], isError: true }; // NEVER rethrow past this point
  }
}
```
*(Illustrative sketch, not a drop-in — `call()`'s current return shape and error types should be checked against exactly during implementation.)*

### Pattern 2: Three-tier response for every `tools/call`

**What:** every path through the handler — success, tool-level error, transport error, protocol error — ends in a JSON-RPC **result** with `content`/`isError`, never a JSON-RPC **error** object, *except* for genuinely protocol-level problems (unknown method, malformed params) per the spec's own two-category error model.
**When to use:** for every tool call; this is what makes success criterion 6 true structurally rather than by discipline.
**Example (per official MCP spec, `[CITED: modelcontextprotocol.io/specification/2025-06-18/server/tools]`):**
```json
{"jsonrpc":"2.0","id":4,"result":{"content":[{"type":"text","text":"Failed to fetch weather data: API rate limit exceeded"}],"isError":true}}
```
vs. a genuine protocol error (unknown tool name — this one SHOULD be a JSON-RPC error, not an `isError:true` result):
```json
{"jsonrpc":"2.0","id":3,"error":{"code":-32602,"message":"Unknown tool: invalid_tool_name"}}
```

### Anti-Patterns to Avoid

- **Registering the emulator's endpoint directly as a second, unguarded path.** `tools/README.md` already made and documented this exact decision (D-5) for the *current* Bash path; the proxy is what makes it safe to expose as MCP tools, precisely because every hazard funnels through one file. Do not create a second entry point that bypasses the proxy "for convenience."
- **Re-implementing HTTP retry/SSE parsing inside the new proxy file.** This is the module `vice.mjs` already is; duplicating it doubles the surface that can drift and re-introduces bugs `vice.mjs`'s six real outages already found and fixed.
- **Treating `.mcp.json`'s `url` field guidance as relevant here.** 1.1 registers a `command`-based stdio entry with no `url` at all — the env-var-expansion-in-`url` question (finding 9) is entirely 1.2/broker territory (an HTTP-type server entry), not 1.1's.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| HTTP JSON-RPC client to the host, with retry/backoff | A new `fetch()` wrapper in `vice-proxy.mjs` | Import `vice.mjs`'s `call()`/`rpc()`/`withReconnect()` | Already hardened against 6 real host outages; re-deriving this is pure risk with no upside. |
| `vice_disk_list` refusal | A second deny-list | Import `vice.mjs`'s `DENY_LIST` constant | One list, one place; the project's own D-5 rationale for the current seam applies unchanged to the proxy. |
| Epoch-based restart detection | New logic reading `.vice-supervisor/<port>/epoch.json` | Import `readEpoch()`/`assertSameMachine()` | Already handles the "epoch file present but not valid JSON" and "absent supervisor" cases correctly (`readSession()`'s sibling logic in `vice-session.mjs` shows the same defensive pattern applied twice already — reuse rather than triplicate it). |
| Host path translation for diagnostic messages | Re-deriving `/proc/self/mountinfo` parsing | Import `hostPath()` from `devcontainer-host-path/scripts/hostpath.mjs` | `install-resources.mjs` already does exactly this for its own host-launch instructions — same call, same pattern, proven. |
| Newline-delimited JSON-RPC stdio framing | A hand-rolled byte-buffer parser with ad-hoc edge cases | A minimal, spec-literal line-buffer split on `\n`, one `JSON.parse` per line | The spec is small and explicit here (cited below) — this is the one piece of *new* protocol code this phase needs, and it should be minimal and spec-literal rather than "smart." |

**Key insight:** almost everything success criterion 5 (hazards in code) asks for already exists as tested code in this repo under a different file name. The main engineering risk in this phase is the ~150 lines of *new* stdio-framing glue, not the hazard logic.

## Common Pitfalls

### Pitfall 1: Conflating "the host is down" with "the design is wrong"
**What goes wrong:** building/debugging the proxy against a host that simply is not running produces the exact same symptom (`ECONNREFUSED`) a defective proxy would produce, and it is tempting to "fix" the proxy in response.
**Why it happens:** the memory file's "non-functional" framing primes exactly this misreading, and `ECONNREFUSED` looks identical whether the cause is "nobody started x64sc" or "the proxy's client code is broken."
**How to avoid:** before debugging the proxy's transport code, independently confirm host reachability with the same three-command check used in this research (DNS resolve, raw TCP connect, `vice_ping` round-trip) — if all three fail identically to what is recorded below, the fix is "start the host," not "read the proxy code again."
**Warning signs:** every port in the pool (6510/6511/6512) refusing identically, `.vice-supervisor/{epoch,registry,session}.json` all absent (no supervisor has written anything this session).

### Pitfall 2: Rebuilding the retry ladder from scratch
**What goes wrong:** a fresh implementation of "connect to the host over HTTP" re-derives the SSE-vs-plain-JSON body parsing, the 50-second backoff schedule, and the deny-list from zero, without the six real-outage data points that shaped the existing one.
**Why it happens:** the design note frames the proxy as "simultaneously an MCP server and an MCP client," which reads as "build both halves," when only one half is actually new.
**How to avoid:** import, don't reimplement (Pattern 1 above).
**Warning signs:** a PR that touches `fetch()`/retry logic inside `vice-proxy.mjs` itself rather than only inside a thin call to the relocated `vice.mjs`.

### Pitfall 3: An uncaught throw anywhere in the stdio read loop
**What goes wrong:** one unhandled exception (malformed input line, a rejected promise with no `.catch`, or — the specific, *documented* failure in the official SDK itself — an `EPIPE` on `stdout.write()` when Claude Code closes the pipe abruptly) crashes the process, and per finding 7, Claude Code never restarts a dead stdio server. The session's emulator access is then gone for good, silently, for the rest of the session.
**Why it happens:** Node's default behavior for `uncaughtException`/`unhandledRejection` (since Node 15+, unhandled rejections crash by default too) is to log and exit; a plain `stdout.write()` with no `'error'` listener on the stream throws synchronously on `EPIPE`.
**How to avoid:** top-level `process.on('uncaughtException', ...)` and `process.on('unhandledRejection', ...)` handlers that log and continue (never re-throw, never call `process.exit()`); an `'error'` listener on `process.stdout` specifically for `EPIPE`; every per-line JSON parse and every tool-call handler wrapped so a bad frame produces a JSON-RPC parse-error *response*, not a crash.
**Warning signs:** this is exactly the shape of a filed, confirmed defect in the *official* `@modelcontextprotocol/typescript-sdk` — issue #1564, "Unhandled 'EPIPE' in 'StdioServerTransport' causes fatal process crash on client disconnect" `[CITED: github.com/modelcontextprotocol/typescript-sdk/issues/1564]`. Even the reference implementation got this wrong at least once; treat it as the single highest-value defensive check to test explicitly (see Validation Architecture).

### Pitfall 4: Assuming the fixed-port emulator behind the proxy is idle-safe
**What goes wrong:** every state-reading `vice_*` call pauses the emulated CPU and does not resume it (an established, measured project finding, `[VERIFIED: STATE.md 2026-07-30, cross-checked in memory vice-mcp-pauses-on-state-read]`). A proxy that reads state for diagnostics (e.g., probing liveness) without re-issuing `vice_execution_run` afterward silently starves whatever else is using that same fixed-port instance.
**Why it happens:** this behavior is easy to forget when writing new diagnostic code, since it does not surface as an error — the machine just runs at ~0.7% speed instead of 100%.
**How to avoid:** use `vice_ping` (measured non-pausing) for any proxy-side liveness probe, never a state-reading call; if the proxy adds its own polling for a broker-absent check in a later phase, follow the same discipline `vice-probe.mjs` already established for exactly this reason.
**Warning signs:** a "hung" emulator that is actually running at 0.7% speed rather than truly stopped — this project has already spent real debugging time on this exact confusion once (per `STATE.md`).

## Code Examples

### `initialize` handshake (per official spec, `[CITED: modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle]`)

Request from Claude Code:
```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{...},"clientInfo":{"name":"claude-code","version":"..."}}}
```
Server (the proxy) response — version negotiation rule: **if the server supports the client's requested version, echo it back exactly; otherwise respond with the newest version the server itself supports** (the client then disconnects if it can't accept that):
```json
{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18","capabilities":{"tools":{"listChanged":false}},"serverInfo":{"name":"vice","version":"1.0.0"}}}
```
The existing project's own client code (`vice.mjs`'s `ensureInitialized()`) sends `protocolVersion: "2024-11-05"` to the *host* server — a different, older wire negotiation entirely, between the proxy (as client) and the host VICE MCP server. Do not confuse the two handshakes; the proxy is a server on one side of `initialize` and a client on the other, with independently negotiated versions.

Then, before any `tools/list`/`tools/call`, the client sends (no response expected — it's a notification):
```json
{"jsonrpc":"2.0","method":"notifications/initialized"}
```

### `tools/list` response shape (per spec, `[CITED: modelcontextprotocol.io/specification/2025-06-18/server/tools]`)
```json
{"jsonrpc":"2.0","id":1,"result":{"tools":[{"name":"vice_memory_read","description":"...","inputSchema":{"type":"object","properties":{"address":{"type":"string"},"size":{"type":"integer"}},"required":["address"]}}]}}
```
`vice_disk_list` must be **absent** from this array entirely (see research question 4 below) — `vice.mjs`'s own `serverInfo()` already filters it out of its returned payload, so re-serializing that payload into this shape inherits the omission for free.

### Wire framing (per spec, `[CITED: modelcontextprotocol.io/specification/draft/basic/transports]`)
> "At its core, MCP is just JSON-RPC 2.0 over newline-delimited streams... Messages are delimited by newlines, and MUST NOT contain embedded newlines... the server MUST NOT write anything to its stdout that is not a valid MCP message."

This last clause matters concretely here: any `console.log()`/debug print anywhere in the reused `vice.mjs` module (it has several, e.g. `console.error` warnings — those are fine, `stderr` is not part of the framed channel — but any stray `console.log` would corrupt the stdio stream). Audit the relocated module for any `console.log` call and convert to `console.error` before wiring it into the proxy.

## Security Domain

`security_enforcement: true`, `security_asvs_level: 1` in `.planning/config.json`. This phase's attack surface is unusual for ASVS purposes: it is a **local, loopback-only, single-developer devcontainer tool**, not a networked multi-user application — most ASVS categories (authentication, session management for human users, access control between users) do not apply in the conventional sense. The categories that do apply concern **input validation of untrusted host-written files** and **not creating a new unguarded privileged pathway**.
