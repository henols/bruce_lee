# Phase 01.1 Plan 02: Snapshot-Backed Discovery, Deny-List Enforcement & Continuation-Based Output Cap Summary

**Converted the three known emulator-access hazards (`vice_disk_list`, mid-session host restarts, oversized results) from rules a caller had to remember into structural proxy-seam code, each with a regression test that fails when its guard is removed.**

## Performance

- **Duration:** ~18 min
- **Started:** 2026-07-31T14:59:21Z (base commit for this wave)
- **Completed:** 2026-07-31T15:16:08Z
- **Tasks:** 3 (all completed)

## Accomplishments

- `tools/list` now answers from a committed, offline-readable snapshot (`tools-manifest.json`) with zero HTTP traffic, proven by a request counter incremented inside the stand-in server, including three distinct failure modes (missing file, invalid JSON, wrong shape) that all degrade to a well-formed empty list rather than a fetch, throw, or hang.
- `refresh-manifest.mjs` is the one and only writer of that snapshot: a small operator-invoked CLI that calls the host's `serverInfo()`, honours `VICE_TOOLS_MANIFEST`, and never overwrites a good snapshot with a partial one on failure (verified live against an unreachable endpoint).
- `vice_disk_list` is now unreachable from two independent layers: filtered out of every `tools/list` response at read time (catching a snapshot generated by any means, not just `refresh-manifest.mjs`), and refused at `tools/call` before any network attempt — each with its own test, and the test file's header comment states explicitly which test fails if which layer is removed.
- Every forwarded `tools/call` brackets itself with a plain `readEpoch()` comparison before and after the call. A changed epoch refuses (or discards a mid-call result) with a loud error naming both epoch values, then re-baselines immediately so the very next call forwards normally — proven by a three-call sequence (baseline, refused drift, successful re-baselined call) that also asserts the drifting call never reached the stand-in host.
- A single module constant (`OUTPUT_CHAR_CAP`, default 500000, overridable via `VICE_MAX_RESULT_CHARS`) backs both the `_meta["anthropic/maxResultSizeChars"]` declaration on every tool and the actual size check — one number, one definition. Oversized results split into cap-sized chunks served across an explicit `vice_result_continue` continuation, proven byte-for-byte reassembly-equal to the stand-in server's original payload with exactly one host request total across the whole sequence.
- Decision D-D deliberately keeps the epoch check narrow: no call to `assertSameMachine()`, no probe of `vice_checkpoint_list` anywhere in executable code (verified with the plan's own comment-excluding grep), since a state-reading probe would pause the emulated CPU without resuming it and the proxy arms no checkpoints of its own to probe with.

## Decisions Made

- **D-C, D-D, D-E** resolved exactly as the plan specified (committed snapshot + refresh script; epoch check narrowed to `readEpoch()` only, no `assertSameMachine()`/checkpoint probe; `_meta` ceiling plus proxy-side continuation, no truncation branch). See the frontmatter `key-decisions` for the concrete reasoning captured at execution time.
- **The output-cap constant was introduced in task 1's commit rather than deferred to task 3.** Task 1's own action text requires the `_meta` declaration to reference "the module constant introduced in task 3" — since both sites must read the exact same number, the constant had to exist from task 1's first commit; task 3 only added the *enforcement* logic that reads it, not a second definition.
- **The synthetic `vice_result_continue` tool descriptor was drafted alongside `OUTPUT_CHAR_CAP` in task 1 but deliberately moved out before that commit**, once it became clear that advertising a tool `tools/call` couldn't yet serve would leave task 1's commit, taken alone, in an inconsistent state (a tool discoverable but not callable). It now lands in task 3's commit together with the handler that actually serves it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Two task-1 tests needed updating for the always-present synthetic tool**
- **Found during:** Task 3, immediately after adding `vice_result_continue` to every `tools/list` response
- **Issue:** Task 1's own tests (`"tools/list reads the committed snapshot with no emulator"` and `"tools/list survives a missing or corrupt snapshot"`) asserted an exact tool count / an exactly-empty `tools` array. Once task 3 made `vice_result_continue` unconditionally present in every response, both assertions started failing — not because task 1's behaviour regressed, but because task 3 legitimately changed what "the tools array" contains.
- **Fix:** Updated both assertions to account for the synthetic tool: the snapshot-read test now expects 3 tools (2 fixture + 1 synthetic) instead of 2, and the corrupt-snapshot test now asserts the tool *names* array equals `["vice_result_continue"]` instead of asserting the whole array is `[]` — preserving the original intent ("no manifest-derived tools leak through on a broken snapshot") while accommodating the tool that isn't manifest-derived at all.
- **Files modified:** `.claude/skills/vice-mcp-selector/scripts/vice-proxy.test.mjs`
- **Verification:** Full suite (`node --test vice-proxy.test.mjs`) — all 11 tests pass, including both updated task-1 tests.
- **Committed in:** `11015e1` (task 3's commit, since the change was caused by and landed alongside task 3's behaviour change)
