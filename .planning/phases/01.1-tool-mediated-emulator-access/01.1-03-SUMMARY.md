# Phase 01.1 Plan 03: Never-Throw Hardening, Three-State Diagnostics & Path Translation Summary

**vice-proxy.mjs now fails fast (~1s, not ~50s) on an unreachable emulator with three pairwise-distinct diagnoses, cannot be killed by any hostile input, never caches a negative result, and rewrites every forwarded container path to its host form at the one seam that sees every call.**

## Accomplishments

- Closed every remaining path by which `vice-proxy.mjs` could stop answering: `handleMessage()` now validates message SHAPE before deciding whether an `id` excuses silence -- a value that parsed as JSON but isn't a well-formed request/notification (a bare number, an object with no `method`) is always answered with `-32600`, never silently treated as an unrecognised notification. The two `process.exit(0)` call sites (stdin `end`/`close`) collapsed into one shared `shutdown()`, so the file now has exactly one `process.exit(` occurrence, matching the source-assertable invariant the plan requires.
- Proved the never-cache-a-negative-result property with a single-process down-then-up test: the same child process, same pid, answers `isError:true` against nothing listening and then `isError:false` the moment a real server starts on that port -- no restart, no cached failure. This same test dropped from ~49s to ~114ms once task 2's pre-flight probe landed, directly demonstrating the fail-fast improvement.
- Added a pre-flight `probeInstance()` liveness check to `tools/call`, ordered after the deny-list refusal and epoch comparison and before delegating to the resilient transport. An unreachable host now classifies into exactly one of three states -- never started (refused, no epoch record), dead or hung (refused-with-epoch-present, timed out, or something answered but wasn't recognisably VICE), or alive-but-failed (the host answered, but this particular call failed) -- each with its own message, its own absolute host path (via `hostPath()`/`SET_ENV_HINT`, degrading exactly like `hostLaunchInstructions()` does), and language that forbids the shell-fallback workaround without ever pairing a module name with a CLI verb (plan 01.1-04's own durable gate matches that exact pattern).
- Moved container-to-host path translation off every caller's discipline and into the one seam that sees every forwarded call (decision D-G): a recursive, depth-bounded walk over `params.arguments` rewrites any string beginning with `/` that resolves inside the workspace via `hostPath()`, refuses outright (naming the argument's position, the offending value, and the workspace root) when it resolves outside, and leaves everything else -- relative strings, hex addresses, tool names, numbers -- byte-identical. `devcontainer-host-path` becomes a third, unmodified consumer.
- `SKILL.md` gained a "Paths" section in `mcp__vice__*` vocabulary, naming no file under `scripts/`; the pre-existing "Polling while the machine runs" section (decision D-F: the discipline stays documented, not absorbed into the proxy) needed no changes.
- Six pre-existing tests (spanning plans 01.1-01 and 01.1-02) had their request-count assumptions updated to account for the new probe traffic -- see Deviations below for the full account.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Six pre-existing tests' request-count assertions did not account for the new pre-flight probe's own network traffic**
- **Found during:** Task 2, immediately after wiring `probeInstance()` into `handleToolsCall()`
- **Issue:** `probeInstance()` performs its own full `initialize`+`vice_ping` handshake against the host on EVERY forwarded, non-deny-listed, non-drift-refused `tools/call` -- by design, since it must never share cached state with the resilient transport. This means every successful forwarded call now costs one extra `tools/call`-method request at the stand-in server (the probe's own ping) on top of the real call. Five tests from plans 01.1-01/01.1-02 asserted exact `tools/call` request counts that assumed no probe existed (`toolCallsSeen.length === 1` in the tracer test; `1`/`2`/`3` in the three epoch/oversized-result tests), and would have failed not because behaviour regressed but because task 2 legitimately added a second, harmless network round trip per call.
- **Fix:** Updated the affected assertions to the correct new counts (tracer: 1→2; epoch-drift test: 1/1/2 → 2/2/4; missing-epoch test: 3→6). For the two continuation tests, the real target tool was ALSO named `"vice_ping"`, making the probe's ping and the real oversized call indistinguishable to the stand-in server -- retargeted those two tests' real call to `"vice_memory_read"` and taught `startBigPayloadServer` to answer `vice_ping` with a small, recognisable ping payload distinct from the oversized `targetTool` payload, so the probe correctly reports the host alive instead of misclassifying the oversized non-JSON blob as "not VICE".
- **Files modified:** `.claude/skills/vice-mcp-selector/scripts/vice-proxy.test.mjs`
- **Verification:** Full suite (`node --test vice-proxy.test.mjs`) — all 17 tests pass after the fix, including all six updated pre-existing tests.
- **Committed in:** `ce97710` (task 2's commit, since the change was caused by and lands alongside task 2's behaviour change)

**2. [Rule 1 - Bug] The out-of-workspace path-refusal test could not literally assert "request counter unchanged" given the plan's required call ordering**
- **Found during:** Task 3, while writing the path-translation test
- **Issue:** The plan's action text explicitly orders the pre-flight liveness probe BEFORE the path-rewriting pass. This means an out-of-workspace path refusal (e.g. `/etc/passwd`) still triggers the probe's own harmless `vice_ping` network round trip before the translation logic ever runs and refuses the call -- so a literal `assert.equal(requests.length, requestCountBefore)` would spuriously fail even though the SENSITIVE path itself never reaches the host, which is the actual security property criterion 9 cares about.
- **Fix:** Wrote the assertion to directly check the property that matters: no request among everything the stand-in server received carries `arguments.path === "/etc/passwd"`. This is robust to the probe's own traffic and proves the load-bearing guarantee (the out-of-workspace argument never reaches the host) rather than a raw, order-sensitive request-count delta.
- **Files modified:** `.claude/skills/vice-mcp-selector/scripts/vice-proxy.test.mjs`
- **Verification:** `node --test --test-name-pattern="path translation" vice-proxy.test.mjs` passes.
- **Committed in:** `3128b3f` (task 3's commit)
