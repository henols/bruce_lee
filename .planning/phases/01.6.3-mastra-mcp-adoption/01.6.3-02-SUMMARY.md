# Phase 01.6.3 Plan 02: The @mastra/mcp Seam Swap (Tracer) Summary

**`vice-proxy.ts`'s hand-rolled JSON-RPC wire layer is gone, replaced by `@mastra/mcp`'s `MCPServer` + `startStdio()`, with `tools/call` answered by a hand-built `CallToolRequestSchema` override (not `MCPServer`'s own dispatch) to preserve this file's exact `{content, isError}` contract and the deny-list's pinned refusal text — proven on `vice_ping` plus the three synthetic tools, with the full pre-swap test suite run and every failure classified.**

## Accomplishments

- Deleted the entire hand-rolled JSON-RPC wire layer named in the plan's `must_haves` (`writeMessage`/`respond`/`errorResponse`/`handleInitialize`/`handleToolsList`/`handleMessage`/`handleLine`/the stdin loop/`ProtocolError`/`SUPPORTED_PROTOCOL_VERSIONS`), replaced by `new MCPServer({ name: "vice", version: PROXY_VERSION, tools })` + `await server.startStdio()`.
- Added `rawJsonSchemaAsStandardSchema()` (the minimal, permissive `StandardSchemaWithJSON` adapter for a raw manifest schema), `buildViceTool()` (wraps a `ToolDefinition` + runner into a Mastra `Tool` via `createTool()`), `toolCallResultToWire()` (a lossless `ToolCallResult` -> `CallToolResult` pass-through), and `forwardToVice()` (the retained body of the old `handleToolsCall()`, trimmed of name/args extraction and the deny-list check, every downstream function — `ensureBrokerLease()`, `ensureViceSession()`, `checkEpochAndRebaseline()`, `probeInstance()`, `rewriteArguments()`, `call()`, `renderSeamHazardAnnotations()`, `wrapPossiblyChunked()` — reused completely unchanged).
- Installed a `CallToolRequestSchema` override via `server.getServer().setRequestHandler(...)` immediately after `startStdio()` resolves, with zero `await` between the two calls (the documented, load-bearing ordering this plan's own "Ground truth" section derived from reading `@mastra/mcp`'s and the SDK's compiled source directly). The override enforces the deny-list first (unconditionally, before any tool lookup), then dispatches to the registered tool's `execute()`, building the wire response itself rather than trusting `MCPServer`'s own success/failure wrapping.
- Registered `vice_ping` (the tracer's one real forwarding tool, deliberately narrowed via `TRACER_MANIFEST_TOOL_NAMES`) plus the three proxy-local synthetic tools (`vice_result_continue`, `vice_recycle`, `vice_diagnose`), each reusing its existing unchanged handler.
- Proved every plan `must_have` with real spawned-process tests: the tracer round trip, both deny-list layers (construction-time absence from `tools/list` AND call-time refusal with zero host requests), and a deep-equal assertion that `vice_ping`'s wire `inputSchema` is byte-for-byte the manifest's own raw schema through the full `createTool()` -> `MCPServer` -> `standardSchemaToJSONSchema()` round trip.
- Ran the full pre-existing `vice-proxy.test.ts` suite against the swap (104 tests) and classified every failure: fixed the two genuine wire-level changes (a malformed/schema-invalid stdin line now draws no response at all, and `tools/call` with a missing `params.name` now yields `-32603` instead of `-32602`), and confirmed the remaining nine failures are exactly the disclosed "tool not yet registered" gap (`vice_memory_read`, `vice_disk_attach`, `vice_checkpoint_add` — all Plan 03's job), with zero genuine regressions.

## Decisions Made

- **`tools/call` answered by a hand-built override, never `MCPServer`'s own dispatch.** Confirmed by reading `@mastra/mcp/dist/index.js`'s `CallToolRequestSchema` handler directly (~line 35158-35330): its success path always returns `{isError: false, content: [{type:"text", text: typeof result === "string" ? result : JSON.stringify(result)}]}`, collapsing a chunked result's second content item and ignoring any `isError` field the tool's own `execute()` returned; its failure path prepends `"Error: "` to a thrown error's message. Neither shape matches this file's own `{content, isError}` contract, and the `"Error: "` prefix would break a pre-existing test pinning the deny-list's exact refusal text verbatim. The override is installed via `server.getServer().setRequestHandler(CallToolRequestSchema, ...)` immediately after `await server.startStdio()` — confirmed by reading `Protocol.setRequestHandler`'s own contract (`shared/protocol.js` ~line 890, "this will replace any previous request handler for the same method," a plain overwrite) and `StdioServerTransport.start()` (called inside `connect()`), which wires its `'data'` listener synchronously before `startStdio()`'s promise resolves — so with zero `await` between the two calls, the override is guaranteed in place before Node could ever deliver a queued `'data'` event to the SDK's own (about-to-be-overwritten) handler.
- **`tools/list` is left to `MCPServer`'s own `ListToolsRequestSchema` handler, unmodified.** This is the one piece of genuine library value this swap adopts. Traced the schema-conversion path precisely: `tool.parameters` (the `Tool` instance's own field) resolves through `CoreToolBuilder.getParameters()` to the exact `StandardSchemaWithJSON` object this plan's `rawJsonSchemaAsStandardSchema()` constructs (untouched, since `toStandardSchema()` returns an already-conforming schema unchanged); `MCPServer.convertSchema()` then calls `standardSchemaToJSONSchema(schema)`, which calls `schema["~standard"].jsonSchema[io]({target, libraryOptions})` — our own implementation returns the manifest's raw schema verbatim regardless of `target`/`io`, so the wire output is proven byte-for-byte identical to the manifest's own schema, not merely assumed from documentation.
- **Registered manifest-tool scope deliberately narrowed to `vice_ping` only.** `TRACER_MANIFEST_TOOL_NAMES = new Set(["vice_ping"])` filters `readManifestTools()`'s output before registry construction — a disclosed, temporary functionality gap this plan's own objective names explicitly. Plan 03 removes the restriction; the mechanism (`buildViceTool()`, `forwardToVice()`) needs no change to register the remaining ~43 tools.
- **`tsconfig.json` gains `skipLibCheck: true`.** `@mastra/core@1.55.0` bundles `dist/_types/@ai-sdk_*` and `dist/_types/@internal_ai-sdk-v4/` internal declaration files with real, independently-confirmed cross-version inconsistencies (`ProviderV3`/`LanguageModelV3` referenced but not exported by the vendored `@ai-sdk/provider`; `zod/v4`'s `ZodObject`/`ZodArray` generic-arity and `objectUtil`/`objectOutputType`/`objectInputType` export mismatches) — none of which this project's own source triggers or is affected by; they surface purely because TypeScript's default `skipLibCheck: false` walks every transitively-imported `.d.ts`, and this plan is the first time anything in this repo imports from `@mastra/mcp`/`@mastra/core`. Verified the fix masks nothing of ours: `tsc --noEmit --skipLibCheck` produces zero diagnostics for this project's own files with or without the flag in isolation.

## D-01 finding (the mismatch this plan was built to test)

`01.6-RESEARCH.md` §B rated the `@mastra/mcp` integration a mismatch at HIGH confidence; this plan's job was resolving that mismatch cleanly or showing its exact shape on one tool, where the cost of being wrong is one commit, not forty-six. Honest account, as the autonomy contract requires:

**What resolved cleanly:** `tools/list`'s schema-conversion dispatch is now genuinely `MCPServer`'s own code, not a hand-rolled equivalent — the one piece of real, adopted library value, proven byte-for-byte identical to the pre-swap wire output. Broker leasing, epoch tracking, the liveness probe, path rewriting, `call()`, and chunking all continue working completely unchanged, just re-entered from a new top-level caller. The swap is genuinely narrower in code volume: `handleInitialize`/`handleToolsList`/`handleMessage`/`handleLine`/the stdin loop/`ProtocolError` (roughly 140 lines of hand-rolled protocol plumbing) are gone.

**What stayed narrower than the ROADMAP criterion's headline implies:** `tools/call` — the method that matters most for this proxy's own hazard discipline (the deny-list, the exact refusal wording, the `{content, isError}` contract) — is NOT actually handled by `MCPServer`. It is intercepted and answered entirely by this plan's own override, for the precise reason recorded in "Decisions Made" above. So "adopt `@mastra/mcp`" resolves to "adopt its `tools/list` schema-conversion dispatch, and its `StdioServerTransport`/`Protocol` wire transport, while keeping full hand-written control of the one JSON-RPC method this proxy's threat model most depends on." This is a legitimate, working outcome — not a failure of the swap — but it is a narrower adoption than "swap the wire layer for `@mastra/mcp`" reads as a headline. Plan 03 inherits this same shape for the remaining ~43 tools: no new architecture is needed, because the override's own dispatch (a plain `tools[name]` lookup) scales to any tool count without change.

## Issues Encountered

- **A JSON-RPC wire-level narrowing this plan's own "Ground truth" section did not call out in advance**, discovered while running Task 2's full-suite verification: the SDK's own `StdioServerTransport`/`Protocol` (read directly from `@modelcontextprotocol/sdk`'s compiled source this session) route a `JSON.parse` failure OR a `JSONRPCMessageSchema` zod-validation failure to an internal `onerror` handler only — no wire response is written for a malformed raw line, a bare JSON value, or a well-formed-looking object missing its `method` field. The retired hand-rolled `handleLine()`/`handleMessage()` pair always answered each of these with an explicit `-32700`/`-32600` JSON-RPC error. This is not a crash and not a hang (confirmed: the process stays alive and answers the next well-formed request normally, and `Protocol.connect()`'s own wiring chains any `onerror` handler so nothing escapes as an uncaught exception) — it is a genuine behavioral narrowing in *whether* a caller sending one of these three malformed shapes gets an explicit refusal versus silence. Documented and pinned in both `"stdout carries only valid JSON-RPC messages"` and `"never-throw: malformed and hostile input is answered, not fatal"` rather than left unaddressed.
- **A second, narrower wire-level detail**: `tools/call` with a missing `params.name` now yields `-32603` (`InternalError`) instead of the retired `-32602` (`InvalidParams`). Traced to `setRequestHandler`'s own wrapping (`Protocol.setRequestHandler`, `shared/protocol.js` ~line 886-893): every registered handler — including this plan's own override — is wrapped with `parseWithCompat(CallToolRequestSchema, request)` before being invoked, and a validation failure there throws a plain `ZodError` with no numeric `.code` field, which `_onrequest`'s own error-to-response mapping (`Number.isSafeInteger(error['code']) ? error['code'] : ErrorCode.InternalError`) falls back to `InternalError` for. Still a well-formed, non-crashing JSON-RPC error either way; pinned to the new exact code in `"never-throw: malformed and hostile input is answered, not fatal"`.
