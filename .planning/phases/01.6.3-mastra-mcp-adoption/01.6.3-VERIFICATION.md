### The Deny-List Gap — Explicit Verdict

**Verdict: the gap is genuinely pre-existing and NOT widened by this swap.** This was the load-bearing
claim to check, and it holds up under direct code comparison, not just narrative:

- The pre-swap `handleToolsCall()` (retired in commit `a27628b`, read directly via
  `git show a27628b~1:.claude/mcp/vice/vice-proxy.ts`) contained: `const name = ... params.name`,
  then `if (DENY_LIST.includes(name)) { ... }` — an outer-name-only check.
- The post-swap `CallToolRequestSchema` override (`vice-proxy.ts:2976-2996`) contains the structurally
  identical shape: `const name = request.params.name; if (DENY_LIST.includes(name)) { ... }`.
- `call()`'s own internal guard (`vice.ts:632`, `DENY_LIST.includes(toolName)`) was never touched by
  either plan of this phase.
- A dedicated live test (`vice-proxy.test.ts:4638`, "known, pre-existing, NOT widened: tools_call's own
  nested vice_disk_list argument is not refused at this layer and reaches the stand-in host") proves —
  not asserts from memory — that `tools_call` carrying `{name: "vice_disk_list", ...}` as a nested
  argument reaches the stand-in host byte-for-byte, exactly matching what a bare pre-swap `call()`
  would have done.
- What the swap did change: full-manifest registration (Plan 03) made `tools_call` itself newly
  *reachable* through this proxy's own dispatch (Plan 02's tracer had only registered `vice_ping` +
  3 synthetics). Reachability of the carrier tool is not the same as widening the guard's blind spot —
  the guard's shape (outer-name-only) is unchanged, before and after.
- Filed correctly at
  `.planning/todos/pending/2026-08-05-generic-surface-deny-list-gap-tools-call-nested-vice-disk-list.md`,
  which itself documents the provenance argument above, and attributes ownership to Phase 01.4
  criterion 3 rather than closing it here.

This is an honest, evidenced "unwidened" — the phase does not silently absorb a widened gap under a
reused "pre-existing" label.
