## Ground truth this plan is built on (read the compiled library source, not the docs)

Verified this session by `npm pack`-ing `@mastra/mcp@1.15.0`, `@mastra/core@1.55.0` and
`@modelcontextprotocol/sdk@1.30.0` into a scratch directory and reading the shipped `.d.ts`/`.js`
directly (no install, no lifecycle scripts — the same zero-risk method `01.6.3-APPROVALS.md`
already used for the telemetry finding). Re-verify against the versions actually installed by Plan
01 rather than trusting these line numbers to still be exact — libraries change between minor
releases.

- **`MCPServer` constructor** (`@mastra/mcp/dist/server/server.d.ts`): takes
  `{ name, version, tools, agents?, workflows?, resources?, prompts?, id?, ... }`, where `tools` is
  `ToolsInput = Record<string, ToolAction | VercelTool | ...>`. `createTool()` (from
  `@mastra/core/tools`) is the documented, idiomatic constructor for a `ToolAction`:
  `createTool({ id, description, inputSchema, execute, mcp: { _meta } })`.
- **`startStdio()`** (`server.js`, ~line 35750): `this.stdioTransport = new StdioServerTransport();
  await this.server.connect(this.stdioTransport);` — nothing else. Registers no signal handlers,
  never calls `process.exit()`. `getServer()` returns the underlying
  `@modelcontextprotocol/sdk` `Server` instance for advanced use — this is public, documented API,
  not a private-field reach-in.
- **`StdioServerTransport`** (`@modelcontextprotocol/sdk/dist/cjs/server/stdio.js`): only registers
  `'data'`/`'error'` listeners on `process.stdin` — no `'end'`/`'close'` handlers, no signal
  handlers. This file's own existing teardown region (SIGINT/SIGTERM/SIGHUP, `stdin.on("end"/
  "close")`) is therefore untouched and remains the only code observing those events — it stays
  exactly as it is.
- **`Protocol.setRequestHandler(schema, handler)`** (`@modelcontextprotocol/sdk`'s
  `shared/protocol.js`, ~line 890): "Note that this will replace any previous request handler for
  the same method" — a plain overwrite, no exception thrown on re-registration. This is the
  documented seam this plan uses: call `mcpServer.getServer().setRequestHandler(CallToolRequestSchema,
  ourOverride)` **synchronously, immediately after `await server.startStdio()` resolves, with no
  `await` in between** — `StdioServerTransport.start()` (called inside `connect()`) has already
  wired its `'data'` listener by the time `startStdio()`'s promise resolves, but Node does not
  deliver a queued `'data'` event until the next turn of the event loop, so the override is
  guaranteed to be in place before the SDK's own `CallToolRequestSchema` handler could ever run for
  a real incoming message, as long as nothing awaits between the two calls.
- **The exact mismatch, read directly in `@mastra/mcp/dist/index.js`'s `CallToolRequestSchema`
  handler (~line 35158-35330):** on success, it always returns
  `{ isError: false, content: [{ type: "text", text: typeof result === "string" ? result :
  JSON.stringify(result) }] }` where `result` is whatever your tool's `execute()` returned — it does
  **not** look at any `isError` field on that return value. On a thrown error, it returns
  `{ content: [{ type: "text", text: \`Error: ${error.message}\` }], isError: true }` — note the
  **prepended `"Error: "`**. Neither shape matches this file's own `ToolCallResult` contract
  (`{content: {type:'text',text}[], isError: true|false}`, used by `isErrorText()`,
  `wrapPossiblyChunked()`, `handleRecycle()`, `handleDiagnose()`, `handleResultContinue()`) — a
  `wrapPossiblyChunked()` result with a second content item (a chunk marker, or a trailing path
  note) would be silently collapsed to one JSON-stringified blob, and every `isErrorText(...)`
  refusal would gain an unwanted `"Error: "` prefix if returned through `execute()` and left to
  `MCPServer`'s own dispatch. **This is why `tools/call` is intercepted (see Task 1), not left to
  `MCPServer`'s own handler** — `execute()` remains a real, working implementation for every tool
  (so `MCPServer.executeTool()` and a from-`tools/list` fallback both still work correctly, just
  with the "Error: " prefix / single-item collapse if ever reached that way), but the *primary* path
  this proxy is proven against builds the wire response itself, preserving today's exact envelope.
- **`createTool()`'s `inputSchema`** wants a Standard Schema (Zod, or anything satisfying
  `@standard-schema/spec`'s `StandardSchemaV1`/`StandardJSONSchemaV1`), not a raw JSON Schema
  object — confirmed by reading `@mastra/schema-compat`'s `toStandardSchema()`, which converts an
  *already-standard* schema (Zod etc.) into one that also carries JSON-Schema-conversion, and does
  not accept a bare JSON-Schema object as input. This project's tool definitions (from
  `tools-manifest.json` via `readManifestTools()`) are raw JSON Schema, sourced from the HOST's own
  MCP server — there is no reason to convert them to Zod (the proxy has never validated argument
  shape itself; the host does). Task 1 writes a minimal, permissive adapter satisfying the
  `StandardSchemaWithJSON` interface directly (`~standard.validate` always succeeds — matching
  today's zero-validation-at-the-proxy behavior exactly — and `~standard.jsonSchema.output()`/
  `.input()` both return the manifest's own raw schema verbatim, so the wire `tools/list` output is
  byte-identical to today's).
- **`DENY_LIST` (`vice.ts`) has exactly one entry, `"vice_disk_list"`, and is enforced at THREE
  layers today**, not two: `handleToolsList()`'s discovery-time filter, `handleToolsCall()`'s
  call-time refusal, and `call()`'s own internal refusal (`vice.ts` line ~632) — the deepest layer,
  **outside** the code this plan touches, and untouched by this swap regardless of what happens at
  the wire layer above it. This plan's job is preserving layers 1 and 2 exactly, not proving layer 3
  (which no change here can weaken).
