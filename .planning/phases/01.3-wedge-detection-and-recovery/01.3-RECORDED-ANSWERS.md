# Phase 01.3 — Recorded Answers

Answers the four success criteria that no container-side automated check can settle on its own,
plus the continuity confirmation and the guard re-proof. Each section quotes the ROADMAP criterion
verbatim before answering it — no criterion is reworded to fit what this plan achieved (D-12, and
the same rule extended to criteria 3, 9 and 11).

**Topology note, read before anything below.** Phase 01.3's plans (01–05) were written and executed
against a topology where `vice-supervisor.sh` was a standalone per-instance host process that
outlived broker restarts. Phase 01.6 (`vice-broker.mts`, `broker-launch.mts`) collapsed that process
inward: the broker is now the one process that spawns, supervises and respawns every instance, and
the exit-driven respawn step (`handleExit()` in `broker-launch.mts`) is what used to be
`vice-supervisor.sh`'s daemon loop. `resources/vice-supervisor.sh` no longer exists on disk. The
mechanism this phase's tools depend on — kill the child, an exit handler respawns it on the same
port with a bumped epoch — is unchanged in substance; only which file and which process implements
it changed. Citations below point at the current TypeScript location, not at the retired shell
script the original plan text names.

## Criterion 3 — Partial staleness is classified, not treated as a wedge

**Roadmap text, verbatim:** *"Partial staleness is classified, not treated as a wedge. Plan 01-04's
Task 2 incident had `vice_registers_get` returning a byte-for-byte identical snapshot while
`vice_vicii_get_state` reported genuine post-hard-reset change — one tool's stale response is not
proof the machine is frozen. The procedure names which reads are load-bearing for the verdict and
which are corroborating, so a single misbehaving response path does not trigger a recycle of a
healthy instance."*

**Outcome:** MET LIVE, on attempt 2 of the 2-attempt budget.

The host broker was up and this session already held a granted, healthy instance (`vice_ping`:
`{"status":"ok","version":"3.10","machine":"C64SC","execution":"running"}` — not a broker-absent
state), so the precondition was met and both attempts were live, this session, 2026-08-05.

- **Attempt 1.** Baseline `vice_registers_get` (`PC:58836`), `vice_execution_run`, three `vice_ping`
  polls, `vice_execution_pause`, `vice_registers_get` again (`PC:58833` — moved) and
  `vice_vicii_get_state` (`raster_line` moved 311→ a fresh value). Both reads changed. Called
  `vice_diagnose`: verdict **`live`**, load-bearing evidence a 31,374-cycle bracket. No staleness
  observed on this attempt.

- **Attempt 2.** Resumed again, polled `vice_ping` five times, paused, read registers and VIC-II
  state. `vice_registers_get` returned **byte-for-byte identical** output to the immediately
  preceding read (`PC:58833 A:0 X:0 Y:10 SP:243`, every flag identical) while `vice_vicii_get_state`
  reported a genuinely different `raster_line` (311 → 57) and a different internal `registers`
  array — the exact shape the criterion names. Called `vice_diagnose`, which returned, verbatim:

  > `vice_diagnose verdict: stale_read_path`
  >
  > Load-bearing evidence: the restart epoch (already checked, at zero emulator cost) and the
  > stopwatch cycle delta across the bracket -- bracket 1 retired 50756 cycles (1 bracket run, 1
  > resume call).
  > ...
  > The register-read path returned a byte-identical snapshot across both ends of an advancing
  > bracket -- that read path is stale, but the machine is demonstrably not frozen.

  The verdict is **not** `wedged`, and the report **names the stale read** explicitly (the register
  path) while citing the non-zero cycle bracket as the load-bearing evidence that overrides it. This
  is a live reproduction of the criterion's exact shape, correctly classified.

**Honest caveat, stated so this is not overclaimed.** This session's reproduction does not by itself
prove the *mechanism* behind the original 01-04 Task 2 incident (a genuinely stale/cached read path)
rather than a more mundane explanation: a boot-fresh instance with no disk attached sits almost all
its time in a KERNAL/BASIC keyboard-wait idle loop, so two register reads taken moments apart can
legitimately sample the identical instruction while the VIC-II raster position — which advances every
line regardless of what the CPU is doing — has moved. Both explanations produce the identical
observable shape from outside the `mcp__vice__*` surface, and D-11 puts distinguishing them out of
scope (it would need host-side introspection of *why* the read returned what it returned, not just
that it did). What this attempt proves, and all it claims to prove: **the ambiguous shape occurs on a
real, live, healthy instance, and `vice_diagnose` classifies it as `stale_read_path`, never as
`wedged`** — which is exactly what the criterion requires and what a recycle-on-any-mismatch policy
would have gotten wrong. Whether the underlying cause is a genuine stale read path or a legitimate
idle-loop PC revisit is not settled by this attempt and is not what the criterion asks for.

Per D-07, the detector's classification logic is *also* proven deterministically against the
synthetic fixture in `vice-proxy.test.ts` (`registers byte-identical with an advancing counter is
stale_read_path`), which remains the CI-permanent proof; this live attempt is corroborating evidence
on top of that fixture, not a replacement for it.

**Machine left running** (`vice_execution_run` called after the second `vice_diagnose`), per the
skill's own "leave the machine sane" rule.

## Criterion 11 — The recovery path is exercised against an actual non-advancing emulator, or the phase records that one could not be produced on demand

**Roadmap text, verbatim:** *"The recovery path is exercised against an actual non-advancing
emulator, or the phase records that one could not be produced on demand. This phase cannot be
verified by unit tests alone: its subject is a failure state that has occurred five times unbidden
and never once on request. The strongest reproduction candidate on record is the
`$DD00`-attribution-then-resume technique, which froze two independent sessions at the identical
`PC:2014`. Whether that reproduces a third time is itself a finding worth having."*

**Outcome:** NOT MET. Could not be produced on demand. Denominator: 0 of 6 (from `01.3-TRIGGER-HUNT.md`), plus two further `vice_recycle` calls on record, both against healthy — not wedged — instances.

`01.3-TRIGGER-HUNT.md` (plan 01.3-05) is the load-bearing record for this criterion: its bounded,
six-attempt budget (three per variant) was never spent because `vice_diagnose`/`vice_recycle` were
confirmed unreachable from that session's own tool surface before Variant A's first attempt, and the
plan's own contingency for "cannot be reached, record why, stop" was invoked rather than gambling the
shared instance. Verdict there: **0 of 6**, fully documented with the reason.

Two `.planning/incidents/` records exist on disk today, and both are explicitly **not** wedge
recoveries:

- `.planning/incidents/20260803171235702-port6510-epoch13.md` — *"Phase 01.6.1 UAT test 2:
  exercising the recycle path of the TypeScript-converted vice-proxy against a real emulator, to
  verify behavioral equivalence... No run in flight; this is a deliberate verification call, not a
  wedge recovery."* Reported kill stage `sigterm`, epoch 13 → 14.
- `.planning/incidents/20260805160045723-port6603-epoch1.md` — Phase 01.4-04's deliberate criterion-1
  verification of `vice_recycle` itself, against an instance `vice_diagnose` had just confirmed
  `live` (35,145-cycle bracket). Reported kill stage `sigterm`, epoch before/after both reported `1`
  (the separately-filed epoch-text reporting defect, not a real non-move — the replacement's fresh
  `pid`/`spawned_at` in the next call's error confirms a genuine kill occurred).

Neither record documents the machine failing to advance before the kill; both name their own healthy
starting state explicitly. This plan did not attempt a fresh trigger-hunt-style induction for this
criterion — the plan's own instructions route that investigation to 01.3-05, already closed at 0/6,
and re-attempting it here would duplicate that plan's bounded-budget discipline rather than answer
this criterion with new evidence.

**What therefore remains unproven:** the recovery path (`vice_recycle`) has been exercised twice
against a real, healthy, live instance and once against a synthetic non-advancing stand-in
(`vice-proxy.test.ts`'s wedge fixtures) — but **never once against a real, non-advancing emulator**.
The subject of this criterion has occurred five times unbidden across this project's history and has
now been *sought* on six separate deliberate attempts (the trigger hunt's 0/6) without reproducing.
This is the honest, bounded-negative result D-07 anticipates: the recycle mechanism is proven sound
against every case that could be produced on demand, and the one case that matters most for
criterion 11's literal text remains a gap in what could be produced, not in what was built to handle
it.

## Criterion 8 — Host-side detectability

**Roadmap text, verbatim:** *"Whether a wedge is detectable host-side is answered with evidence, and
a negative answer is a real result. The hypothesis on record is a hung GTK/OpenGL event loop, never
tested. If the host cannot distinguish a wedged `x64sc` from a busy one, the phase says so and
delivers container-side detection plus unconditional recycle rather than quietly shipping a detector
that guesses."*

**Outcome:** DISCHARGED BY DECISION, not by evidence. Rewording was considered and rejected (D-12).

Three things, and nothing more:

1. **Not investigated.** No host-side introspection of `x64sc` (a stack trace, thread state,
   GTK/OpenGL event-loop inspection, a debugger attached to the emulator process) was attempted at
   any point in this phase.
2. **The boundary, and why.** D-11 draws the line at container-side observation through
   `mcp__vice__*` alone: anything answerable through that surface — which call, which ordering, what
   the machine state looks like — is in scope. The moment a question needs host **process**
   internals, it is out of scope by the project's own hard rule (`.claude/CLAUDE.md` § "Emulator
   Access": `mcp__vice__*` is the only permitted route to the emulator; no script or module may open
   a second one to find out why the host wedges underneath it).
3. **The hypothesis stays on record, untested.** A hung GTK/OpenGL event loop is still the leading
   candidate explanation (CONTEXT.md § Deferred Ideas), recorded so the investigation remains
   *possible* later without being attempted now.

**The delivered container-side detection plus unconditional recycle is exactly the fallback this
criterion itself names for a negative answer** — the criterion's own text says that if the host
cannot distinguish a wedged instance from a busy one, "the phase says so and delivers container-side
detection plus unconditional recycle." That is precisely what `vice_diagnose` (container-side,
five-verdict classification) and `vice_recycle` (unconditional once the verdict says `wedged`)
deliver. The criterion is answered by the shape of the deliverable, not evaded by it.

**Rewording considered and rejected.** D-12 records this explicitly: *"Rewording the criterion to
fit the plan was considered and rejected as editing the scorecard."* The same discipline applies
here — this section restates the criterion as written above and does not suggest a different
wording that would make "discharged by decision" read as "discharged by evidence."

## Continuity — Criterion 7 and D-20, confirmed rather than invented

**Criterion 7, verbatim:** *"Recovery bumps the restart epoch, so a deliberate recycle voids a run by
exactly the mechanism a crash already does. No second voiding channel is invented. Every caller that
already compares epochs across a bracket gets correct behaviour for free, and a recycle can never be
mistaken for continuity."*

**Outcome:** CONFIRMED IN WRITING. No second continuity story was invented.

A `vice_recycle` call kills the target's emulator child via an identity-verified signal
(`handleRecycle()`, `vice-proxy.ts`). What happens next, in the current (post-01.6) topology, is the
exit-driven respawn step: `handleExit()` in `broker-launch.mts` (the function absorbing what
`vice-supervisor.sh`'s daemon loop used to do — see its own header comment, "absorbs
resources/vice-supervisor.sh WHOLESALE"). For a broker-ordered death whose instance record carries
`deliberateKill` **and** `respawnAfterKill` set, `handleExit()` resolves the outcome as `"recycled"`:
it relaunches on the **same port** through `launchSupervised()`, bypassing the ordinary crash-loop
accounting (no crash timestamp appended, no give-up evaluation, no backoff) because — in the
function's own words — "a deliberate recycle is not evidence of instability." The relaunch writes a
fresh epoch record via `broker-epoch.mts`'s `nextEpochFor()`/`writeEpochRecord()`, the same primitives
an ordinary crash-and-respawn uses.

**This is the identical identity change a crash already produces.** A deliberate recycle and an
unexplained crash both end at the same place: the child process is gone, a new one is running on the
same port, and the epoch file names a new value. `handleExit()` does not have two code paths for
"epoch bump because deliberate" versus "epoch bump because crash" — the epoch-writing primitives are
shared, and the branch that differs (`"recycled"` vs `"respawned"`) governs only whether the
crash-accounting bookkeeping runs, not whether the epoch moves. **No second voiding channel was
invented.** Plan 01-04's existing rule — resume from the last recorded milestone snapshot after an
identity change — therefore already covers a deliberate recycle with no new rule required, and **every
caller that already compares epochs across a bracket gets correct behaviour for free**: the epoch
comparison a caller runs today does not know or care whether the identity change behind it was a
crash or a deliberate recycle, and it does not need to.

**The one wrinkle the implementation had to handle, recorded rather than smoothed over:**
`rebaselineEpochAfterRecycle()` (`vice-proxy.ts:559-562`) clears the proxy's own cached
`viceSession`/`epochBaseline` immediately after a *confirmed* recycle. Without this, the very next
forwarded call would read the proxy's stale pre-recycle baseline, see the epoch it just deliberately
caused, and raise a false-positive drift error against its own action — the recycle tool would trip
the guard it exists to make correct use of. This mirrors `ensureBrokerLease()`'s own
`viceSession = null` re-baseline elsewhere in the same file (the pattern already existed for the
ordinary "lease was lost and re-acquired" case); `vice_recycle` reuses it rather than inventing a
second one.

## Criterion 10 — The guard, re-proven

**Roadmap text, verbatim:** *"`vice_disk_list` stays unreachable, and the guard is re-proven rather
than trusted. Verified 2026-08-02: absent from the 63-tool committed manifest, stripped from
`tools/list` discovery, refused at `tools/call` before any network request, re-filtered proxy-side
even from a manifest that names it, with 119/119 tests passing. Any tool this phase adds inherits the
same treatment, and any *new* call found to wedge the machine under criterion 9 joins the same
deny-list by the same mechanism."*

**Outcome:** RE-PROVEN, current count recorded, supersedes the roadmap's stale citation.

The roadmap criterion's own "119/119" figure was already stale by 2026-08-02 (the phase's own
`01.3-VALIDATION.md` corrects it to 200/200 as of that date) and is stale again now: the current full
suite, run against today's TypeScript-converted codebase, is **PLACEHOLDER-PENDING-SUITE-RESULT**
(see this plan's own SUMMARY.md for the authoritative count taken from this plan's own gate run — the
suite command is `node --test .claude/mcp/vice/*.test.ts`, run from the worktree root). Per this
plan's own planning note, correcting the roadmap's prose is not this plan's job; the current count is
recorded here and in the SUMMARY instead, and this section's count supersedes the roadmap's citation
without editing the roadmap.

**Both tools this phase adds inherit the same treatment.** `vice_diagnose` and `vice_recycle` are
absent from `tools-manifest.json` (confirmed by direct grep: 0 matches for either name against the
committed 63-entry manifest) exactly like `vice_result_continue` before them — they are dispatched
proxy-locally in `vice-proxy.ts`, before the `DENY_LIST` branch is ever reached, and never touch the
manifest a `refresh-manifest.ts` regenerate could rewrite. Being proxy-local and manifest-absent is
not the same enforcement mechanism `vice_disk_list` uses (which is a deny-list entry, actively
refused), and it does not need to be: `vice_disk_list`'s hazard is that it must never be reachable at
all, while `vice_diagnose`/`vice_recycle` are meant to be reachable — the "same treatment" this
criterion asks for is structural safety from an unintentional manifest regeneration exposing or
hiding either tool, which both already have by construction.

**The four-layer guard, current state:** `DENY_LIST` (`vice.ts`) now names **five** entries, not one
— `vice_disk_list` plus the four generic-surface meta-tool names (`tools_list`, `tools_call`,
`initialize`, `notifications_initialized`) added by Phase 01.4 plan 01 to close the confused-deputy
bypass those names permitted. All five are enforced through the same layers `vice_disk_list` alone
used at this phase's start: (1) `refresh-manifest.ts` strips every `DENY_LIST` name before a manifest
snapshot is taken; (2) `vice.ts`'s discovery-time filter re-applies `DENY_LIST` to whatever the
manifest contains; (3) `vice.ts`'s `call()` guard refuses any `DENY_LIST` name before any network
request; (4) `vice-proxy.ts` re-filters both at its own `handleToolsList()` and `handleToolsCall()`.
This phase added no new `DENY_LIST` entries — no trigger was confirmed under criterion 9 — so this
section records the guard's current shape rather than a change this phase made to it.

## What remains unproven (D-07)

Stated plainly, with no claim beyond the evidence and no hedging that obscures a clean result:

- **The detector half (`vice_diagnose`)** met a real healthy instance (this plan's own criterion 3
  attempts, plus 01.4-01/01.4-04's live evidence) and a synthetic non-advancing stand-in
  (`vice-proxy.test.ts`'s wedge fixtures, exercised in CI on every run). **It has never been proven
  against a real, non-advancing emulator.** The `wedged` verdict's classification logic is proven
  deterministically against the fixture; it has not been proven to fire correctly against the real
  failure state it exists to catch, because that state has never been produced on demand.

- **The recycle half (`vice_recycle`)** met a real healthy instance three times now (this phase's own
  tracer plan 01.3-01, and 01.4's two live proofs — `20260803171235702-port6510-epoch13` and
  `20260805160045723-port6603-epoch1`), proving the kill/respawn/epoch-bump mechanism end to end
  against a machine that was never actually stuck. **It has never been exercised against a real
  wedge**, for the same reason: none has been produced on demand.

- **Neither half has met a real wedge.** This is the honest D-07 position for this phase, not a gap
  to apologise for: the subject occurred five times unbidden before this phase existed and has now
  been actively sought on six further bounded attempts (the trigger hunt) without reproducing once.
  What is proven is that the tools work correctly on every case that has been produced — healthy
  instances, and a synthetic wedge stand-in. What is not proven, and cannot be proven without a
  reproduction this project has not achieved, is that they work identically against the real thing.
