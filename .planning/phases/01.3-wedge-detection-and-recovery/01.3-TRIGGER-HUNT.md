# Phase 01.3 Plan 05: The Bounded Trigger Hunt

Answers the question the roadmap refuses to assume away: is a specific call or ordering —
arming a stopping exec checkpoint, then resuming — causing the freeze recorded three times across
prior sessions? Answered within a fixed, stated denominator, entirely from inside the container.

## Setup

**Budget:** 6 attempts, three per variant. The budget is a **count, never a duration** — D-10
rejected time-boxing explicitly because wall-clock is never part of this project's loop. When the
budget is spent (or the hunt is blocked before spending it, as happened here), the recorded answer
is "could not reproduce/attempt in N attempts, here is exactly what was attempted," not a longer
or shorter number reached by extending the count silently.

**Variant A — the mid-routine shape.** Boot the release the two recorded stalls used (`saeger.d64`),
reach the same point in play (title → chamber 1 transition), arm a stopping exec checkpoint on the
store instruction immediately preceding the recorded freeze PC (`$07DB: STA $DD00`, immediately
before the frozen `$07DE`), let it hit, resume, then establish what happened mechanically.

**Variant B — the IRQ-entry shape.** On a screen with a live raster-split interrupt chain (danish's
title screen, the `$1103→$1574→$152C` chain from Incident 1), resolve the live handler entry, arm a
stopping exec checkpoint there, resume, and record the checkpoint's hit count. In one of the three
attempts, reproduce the recorded incident's exact ordering by issuing a machine reset while the
checkpoint is still armed.

**The D-11 boundary.** Anything answerable through `mcp__vice__*` is in scope: which call, which
ordering, what the machine state looks like at the freeze. The moment a question needs host process
internals — a stack trace, thread state, GTK/OpenGL introspection, a debugger on the emulator
process — the hunt stops and records the question rather than pursuing it. No script, module or
driver may open a second route to the host.

**The checkpoint-as-instrument-vs-suspect tension, decided up front.** A prior, currently
orphaned-branch finding (re-logged into `.planning/RE-FINDINGS.md` by this plan, see below)
establishes that arming a stopping checkpoint on the KERNAL default IRQ handler (`$EA31`) bounds a
resume to almost exactly one PAL frame (19,656 cycles, measured twice, bit-for-bit identical) — the
tightest known way to control elapsed game time per resume in this project. That is also, precisely,
the technique family this hunt is investigating as the freeze trigger (all three recorded freezes
share the shape "arm a stopping exec checkpoint, then resume"). Decision, recorded here before any
attempt was to be made: **this hunt would NOT use the frame-bounding technique as measurement
tooling for its own procedure.** Every checkpoint armed during an attempt is the checkpoint *under
investigation*, not a separate instrument — using a second, frame-bounding checkpoint on top of the
one being tested would confound which armed checkpoint (if either) caused an observed freeze, and
risks self-inflicting the very failure mode under study through a call the procedure did not intend
to test. Attempts are synchronised on checkpoint hits and cycle-bracket reads only, never on a
frame-bounding checkpoint used as a timing convenience. This decision was never exercised live in
this session (see Blocking Discovery below) but is recorded as the binding procedure for whoever
resumes this hunt.

## Blocking discovery: `vice_diagnose` and `vice_recycle` are unreachable this session

Before Variant A's first attempt, the precondition was checked and passed: `vice_ping` returned
`{"status":"ok","version":"3.10","machine":"C64SC","execution":"paused"}` — a healthy instance, not
one of the three broker-absent states.

Confirming the tools this plan's whole method depends on were reachable was the next step, and they
were not. Full reproduction, cross-checked against the source directly (not merely inferred), is
logged at `.planning/RE-FINDINGS.md` § "2026-08-02 — `vice_diagnose` and `vice_recycle` (and even the
older `vice_result_continue`) are unreachable from an agent session's own tool surface, even though
the running proxy's code has them fully wired" and filed as
`.planning/todos/pending/2026-08-02-vice-diagnose-and-vice-recycle-unreachable-from-agent-session.md`.
Summary of what was checked:

- `vice_ping` (a normal, directly-callable tool) works — the session's connection to
  `vice-proxy.mjs` is live and healthy.
- No directly-callable tool function named `vice_diagnose`, `vice_recycle`, or even the older,
  already-proven `vice_result_continue` exists in this session; a tool-schema search for any of the
  three finds nothing.
- The session's generic `tools_list`/`tools_call` escape hatch bypasses the synthetic-tool
  dispatch entirely: `tools_list` returns the raw manifest with `vice_disk_list` present (which
  must never appear in any `tools/list` response) and none of the three synthetic tools present;
  `tools_call({name:"vice_diagnose"})`, `tools_call({name:"vice_recycle"})` and
  `tools_call({name:"vice_result_continue"})` all three fail identically with the exact wording
  `vice-proxy.mjs`'s `aliveButFailedMessage()` emits when the **real host** rejects a forwarded
  call ("Tool not found") — meaning the literal name was forwarded straight to x64sc rather than
  intercepted proxy-side.
- Ruled out stale code directly: the running `vice-proxy.mjs` process's cwd is the main workspace
  checkout; that checkout's file has both tools fully wired at the identical line numbers as this
  worktree's own copy, and the file's mtime predates the process's start time. The code is correct;
  the gap is in how this session's tool surface was discovered, not in the implementation.

**Decision: do not attempt live reproduction without recovery.** D-05's whole sequencing rationale —
thin recycle tracer first, so the six-attempt budget is affordable — depends on `vice_recycle` being
able to restore a wedged instance in place. Without it reachable in this session, a genuine
reproduction of either variant would end the session with no recovery path, exactly the pre-01.3-01
status quo the phase exists to fix. Both recorded freeze shapes are the technique this hunt would be
attempting to reproduce on purpose; running it without the recovery net risks losing the shared
VICE instance — which later phase work (including this phase's own Wave 6) still needs — for a
result no better than "confirmed once, unrecoverably, with no denominator." A bounded negative with
a stated reason is the more valuable, and more honest, result available from inside this session.

No attempt in either variant was started. Per this project's rule against fabricating attempts, none
is recorded as attempted.

## Verdict

**Denominator: 0 of 6 attempts.** Neither Variant A (mid-routine, 0 of 3) nor Variant B (IRQ-entry,
0 of 3) was started. The budget is entirely unspent, and the reason is stated in full above: the two
tools this hunt's method depends on (`vice_diagnose` for a verdict, `vice_recycle` for recovery)
were confirmed unreachable from this session's own tool surface before the first attempt, and
proceeding without the recovery tool would have converted a bounded, six-attempt investigation into
an unbounded, unrecoverable gamble with a shared resource.

**Criterion 9's answer, for this session:** could not be attempted, for a reason fully documented
above and cross-referenced in `.planning/RE-FINDINGS.md` and
`.planning/todos/pending/2026-08-02-vice-diagnose-and-vice-recycle-unreachable-from-agent-session.md`.
This is a real result, not a gap papered over — the plan's own text anticipates exactly this shape
of outcome for the case where "the emulator cannot be reached at all," and generalizes cleanly to
the case actually hit here, where the emulator itself is reachable but the specific recovery
mechanism this hunt's safety case depends on is not.

**What remains unproven:** whether arming a stopping exec checkpoint and resuming is the freeze
trigger, in either the mid-routine or IRQ-entry shape. The correlation already on record (N=2
mid-routine, cross-session, identical PC; N=1 IRQ-entry, with the checkpoint-trap-vs-genuine-wedge
distinction still only partially resolved per Incident 1's own counter-evidence) stands exactly
where it was before this plan ran — neither strengthened nor weakened, because no new live evidence
was gathered against it. A future session should re-attempt this hunt only once `vice_diagnose` and
`vice_recycle` are confirmed reachable from that session's own tool surface — check both directly,
by name, before starting Variant A's first attempt, rather than assuming a healthy `vice_ping`
implies the rest of the surface is present.
