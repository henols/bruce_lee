# Phase 01.3 Plan 01: vice_recycle End-to-End Summary

**A destructive `vice_recycle` MCP tool that kills and respawns a session's own emulator in place via the existing supervisor respawn loop, with a repo-tracked incident record written before anything is killed, an identity-verified kill sourced only from the target's own epoch file, and every failure mode returning a well-formed, specifically-named result.**

- **Tasks:** 2/2 completed

## Accomplishments

- **Task 1 (tracer):** Wired one `vice_recycle` call end-to-end against a fabricated stub "x64sc" process: incident record write (D-17, before anything is killed) → recycle request → host-side `process_requests()` dispatch → `handle_recycle_request()` → identity-verified kill via a new `signal_vice_child_pid()` (parameterised sibling of `signal_recorded_pid()`, matched against the target's own epoch file's recorded `vice_bin`, never `$SUPERVISOR_SCRIPT`) → the supervisor's own unmodified respawn loop → a recycle ack naming the real kill stage → an epoch-bump check and readiness probe reported as two separate facts → epoch re-baselining so the next forwarded call doesn't false-positive its own drift guard.
- **Task 2 (hardening):** Closed every failure mode: identity mismatch, missing grant record, missing/truncated epoch file, no recorded pid, already-exited target (a *success*, not a failure), a malformed op-bearing request, an invalid target-id pattern (silently skipped, matching the existing invalid-id idiom — distinct from a well-formed-but-absent target, which acks). Added two structural guards: the network-call module set stays closed to `vice.mjs`/`vice-probe.mjs`, and neither synthetic tool (`vice_recycle`, `vice_result_continue`) ever reaches `tools-manifest.json` while both appear in a live `tools/list`.
- **Checkpoint follow-up:** Fixed a real contract inconsistency in `signal_vice_child_pid()` raised at the tracer checkpoint (same stage word, opposite exit code between the empty-pid guard and the genuinely-exited-pid branch), pinned with a dedicated unit-level test, and found+fixed a related real bug in `incident-record.mjs`'s `sanitiseInt()` (a `null` port/epoch was coercing to the number `0` via bare `Number(null)` instead of the literal `"unknown"`) while writing `incident-record.test.mjs`'s own coercion test.

## Decisions Made

See `key-decisions` in frontmatter. In brief: the recycle target pid is sourced exclusively from the target's own epoch file, never the grant's recorded `supervisor_pid`; an invalid target-id format is a silent skip (malformed request) while a well-formed-but-absent target is an acked failure; and `already_exited` is uniformly a success (exit 0) regardless of which guard produced it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `sanitiseInt()` in `incident-record.mjs` coerced a `null` port/epoch to the number `0` instead of `"unknown"`**
- **Found during:** Writing `incident-record.test.mjs`'s coercion test
- **Issue:** `Number(null) === 0` in JavaScript, so a genuinely-absent port/epoch (e.g. `handleRecycle()`'s own `preKillEpoch.present ? preKillEpoch.epoch : null` when no epoch was ever recorded) would silently render as `epoch0` in the incident filename instead of `epochunknown` — a misleading filename claiming a specific epoch that was never actually known.
- **Fix:** `sanitiseInt()` now excludes `null`/`undefined`/`""` explicitly, before the `Number()` coercion, returning `"unknown"` for all three.
- **Files modified:** `.claude/mcp/vice/incident-record.mjs`
- **Verification:** `incident-record.test.mjs`'s coercion test asserts `port: null` and `epoch: null` both resolve to `"unknown"` in the filename
- **Committed in:** `83e540e` (Task 2 commit)

**2. [Rule 1 - Bug] `signal_vice_child_pid()`'s empty/null-pid guard returned exit 1 while printing the same `already_exited` word the genuinely-exited-pid branch returns 0 for**
- **Found during:** Orchestrator checkpoint review after Task 1's tracer commit
- **Issue:** The function's own header comment states every `already_exited` outcome is a success ("the machine being gone is the goal... returns 0 exactly like a genuine kill"), but the empty/null-pid branch contradicted that by returning 1. Unreachable in practice (`handle_recycle_request()` guards against an empty pid earlier, writing its own `pid_lookup_failed` ack first), but a real contract inconsistency that would silently mislead any future caller that skipped that earlier guard.
- **Fix:** Changed the empty/null-pid branch's `return 1` to `return 0`, and updated the header comment to state the uniform rule explicitly.
- **Files modified:** `.claude/mcp/vice/resources/vice-broker.sh`
- **Verification:** New unit-level test extracts the function body via `sed` (the same idiom this file's own acceptance criteria already use to inspect function bodies) and asserts both the empty-string and literal `"null"` pid cases print `already_exited` and return exit 0
- **Committed in:** `83e540e` (Task 2 commit)

**3. [Rule 1 - Bug] An invalid/malformed recycle `target_id` was acking with `target_lookup_failed` instead of being silently skipped**
- **Found during:** Orchestrator checkpoint review, cross-referenced against the plan's own behavior spec ("a recycle request whose target id fails the id pattern is skipped with a logged reason and writes no file anywhere")
- **Issue:** `handle_recycle_request()` originally treated an empty/pattern-invalid `target_id` identically to a well-formed-but-absent one, writing an ack and deleting the request file for both. The plan's own spec requires the former to be a silent skip (matching `process_requests()`'s own invalid-`id` handling one level up), reserving the ack for a real, well-formed recycle attempt that failed to resolve.
- **Fix:** Split the branch: invalid/missing `target_id` now logs to stderr and returns with no file written anywhere (matching the existing invalid-id idiom); a well-formed but non-existent target continues to write a `grant_lookup_failed` ack, unchanged.
- **Files modified:** `.claude/mcp/vice/resources/vice-broker.sh`
- **Verification:** New test asserts no ack file and the request file left in place for an invalid target-id pattern
- **Committed in:** `83e540e` (Task 2 commit)

**4. [Rule 1 - Test-expectation fix] Two pre-existing `tools/list` assertions updated for the new synthetic tool**
- **Found during:** Task 1, running the full `vice-proxy.test.mjs` suite after adding `RECYCLE_TOOL` to `handleToolsList()`
- **Issue:** `RECYCLE_TOOL` joining `handleToolsList()`'s always-present synthetic-tool set is an intentional, required change (per this plan's own artifact list), but two pre-existing tests hard-coded the exact tool count/name list and broke as a direct, anticipated consequence.
- **Fix:** Updated both assertions to include `vice_recycle` alongside `vice_result_continue`.
- **Files modified:** `.claude/mcp/vice/vice-proxy.test.mjs`
- **Verification:** Full `vice-proxy.test.mjs` suite green afterward (54/54)
- **Committed in:** `ab55f1d` (Task 1 commit) — unavoidable at Task 1 commit time since Task 1's own acceptance criteria require the full pre-existing suite to pass
