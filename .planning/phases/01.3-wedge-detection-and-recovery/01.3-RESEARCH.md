## User Constraints (from CONTEXT.md)

### Locked Decisions

**Recovery surface and mechanism**

- **D-01:** Recovery replaces a wedged instance by **signalling the supervisor's `x64sc` child**, not by
  tearing down the broker grant. `vice-broker.sh:1020-1030` spawns `vice-supervisor.sh` per port, and that
  loop already respawns on child exit, collects crash evidence, and bumps `epoch.json`. So a deliberate
  recycle voids the run by the exact mechanism a crash already does — criterion 7 for free, no second
  voiding channel invented — on the same port, with the grant still valid. Reversibility: costly.
- **D-02:** **Tools only. No skill file is created.** The triage judgement lives in the tools' code and
  their descriptions, not in prose. `vice-mcp-selector/SKILL.md` was audited line-by-line, found to
  document hazards that code already enforced, and deleted outright (`db9eed3`). This overrides the source
  todo's own framing ("both — likely the honest answer") and the roadmap's presumed answer.
- **D-03:** **Two tools, split diagnose from recycle.** One tool runs the checks and returns a verdict with
  its evidence; a separate tool does the kill. A mode argument on one tool was rejected for putting a
  destructive action one typo from a diagnostic one. Recycle does **not** gate on a recent verdict.
- **D-04:** **The detector never runs automatically.** On-demand invocation only. Measuring liveness needs
  `vice_execution_run`, this project's leading crash suspect (D-1.2-F); a detector that resumed the machine
  on every call would multiply calls to the tool most correlated with host death.

**Sequencing and proof**

- **D-05:** **Thin recycle tracer first**, then the trigger hunt, then the full design. Breaks a circular
  dependency: criterion 9 wants the trigger investigation to report before the recovery design is fixed,
  while the risks note trigger-hunting is destructive and needs recovery in hand or it burns a session per
  attempt. Matches the tracer-first precedent from 01.1 and 01.2.
- **D-06:** **A confirmed trigger is blocked at the seam within this phase**, not deferred to a follow-on.
  See D-16 for the guard's shape — "blocked" means enforced at the seam, and the enforcement chosen is a
  warning, not a refusal.
- **D-07:** **Proof standard: synthetic for the detector, real kill for the recycle.** The detector's
  classification logic is proven deterministically against a stand-in that answers `ping` ok/running while
  its cycle counter never moves. The recycle is proven against a real healthy instance. The phase records
  honestly that neither half met a real wedge.
- **D-08:** **A wedge is exactly zero cycles across two consecutive brackets. There is no degradation
  threshold.** Any non-zero rate is returned as a measured cycles/s alongside the ~991,000/s baseline, with
  degradation flagged as an observation and never as a recovery trigger.

**Trigger investigation**

- **D-09:** **The hunt's subject is the armed-stopping-checkpoint family**, not the `$DD00` address.
  Retargeted during discussion once cross-reading all three incidents showed the common factor is a
  stopping exec checkpoint armed, then execution resumed — with the IRQ-handler-entry case (`$1103` shape)
  and the mid-routine case (`$07DE` shape) as its two variants.
- **D-10:** **A fixed attempt budget, named in the plan.** When it is spent, the recorded answer is "could
  not reproduce in N attempts, here is exactly what was attempted." Time-boxing was rejected — wall-clock is
  never part of this project's loop.
- **D-11:** **Container-side observation only.** Anything answerable through `mcp__vice__*` is in scope. The
  moment a question needs host process internals it stops and is recorded as an open question.
- **D-12:** **Criterion 8 is discharged by decision, and the phase says so.** D-11 means "is a wedge
  detectable host-side?" does not get answered by evidence. The deliverable is container-side detection
  plus recycle — exactly the fallback criterion 8 itself names for a negative answer.

**The checkpoint trap — a fourth state (new, from this discussion)**

- **D-13:** **There is a fourth state the roadmap does not list: a self-inflicted checkpoint trap.** An
  armed stopping exec checkpoint pins the PC because every resume re-enters the trap before useful work
  retires. The cycle bracket reads zero, `vice_ping` reports "running", the PC reads byte-identical every
  time. **This is not a wedge and must never be recycled as one.** Caveat, recorded rather than smoothed
  over: in incident 1, deleting the `$1103` checkpoint did NOT unfreeze it, and neither did a soft reset, a
  hard reset, nor an explicit single step. A checkpoint trap may be the onset without being the whole story.
- **D-14:** **The checkpoint-trap check runs FIRST, before any cycle bracket.** The diagnose tool enumerates
  armed checkpoints and resolves the live IRQ handler before it runs `vice_execution_run` at all. This
  modifies criterion 2's ordering. The IRQ handler is resolved by the documented two-read lookup —
  `$0314/$0315`, or `$FFFE/$FFFF` when `$01` has the ROMs banked out.
- **D-15:** **On a checkpoint trap the tool reports and does not remedy. No restart, no kill, nothing
  destructive.** Carries at minimum: which checkpoints are armed and their stop/continue flags; the live IRQ
  handler target and how it was resolved; the current PC and its relation to the armed checkpoint; an
  explicit statement that this is a self-inflicted stop, not a wedge. The agent then acts with tools it
  already has (`vice_checkpoint_delete`, `vice_checkpoint_toggle`, `vice_execution_step`) and reaches for
  recycle only when the cycle bracket says wedge with no checkpoint explanation.
- **D-16:** **The seam guard warns; it never refuses.** `vice_disk_list` is deny-listed because it has no
  legitimate use. A stopping checkpoint on an IRQ handler is core RE technique Phase 2 depends on — the
  call goes through and its result carries a hazard annotation naming the risk and the recovery. A planner
  must not read D-06 as authorising a refusal.

**Evidence capture and continuity**

- **D-17:** **The recycle tool captures evidence itself, before it kills.** The tool gathers criterion-4
  evidence (cycle brackets, PC, restart epoch, checkpoint enumeration, screenshot), writes the record, and
  only then signals the child. Structurally impossible to recycle without leaving a trail.
- **D-18:** **The incident record is repo-tracked under `.planning/`.** A committed record is greppable,
  survives a container rebuild, and can be cited by `RE-FINDINGS.md`. `.vice-supervisor/` is gitignored
  runtime state — a record written there is exactly as lost as no record at all. **This makes a tool write
  files, which no current `mcp__vice__*` tool does** — a genuine expansion of the proxy's remit, flagged in
  `.planning/seeds/ram-capture-as-proxy-tools.md`. Reversibility: costly.
- **D-19:** **Best-effort snapshot before the kill, never blocking.** Attempt a `.vsf` save and record
  whether it succeeded; a failed attempt is itself a finding. Costs one call and cannot stall the recycle.
- **D-20:** **Continuity reuses the existing rule unchanged.** A recycle bumps the epoch, the same identity
  change a crash produces, so plan 01-04's "resume from the last recorded milestone snapshot after an
  identity change" already applies. The phase confirms this in writing rather than inventing a second
  continuity story.

## Summary

This phase adds two MCP tools (`diagnose`, `recycle`) to an already-working three-layer stack —
`vice-proxy.mjs` (container-side Node MCP server) → `vice-broker.sh` (host-side bash daemon,
on-demand instance lifecycle) → `vice-supervisor.sh` (host-side bash, one per emulator instance,
owns the respawn loop and the `x64sc` child). All the pieces D-01 through D-22 assume already
exist and were read directly for this research; none of the three "open implementation questions"
turned out to be unanswerable, but one of them (question 1) turned up a real discrepancy that the
planner must design around rather than assume away.

**Primary recommendation:** build `diagnose` as a proxy-local tool (no new host capability, pure
composition of five already-existing `mcp__vice__*` reads) and build `recycle` as the **one place
this phase must add real host-side code**: a new request type in `vice-broker.sh`'s
`process_requests()` loop, because that loop today dispatches every request file identically
regardless of an `op` field that already exists in the request schema but is never read
(`resources/vice-broker.sh:1182-1238`). The pid to signal is **not** the `supervisor_pid` recorded
in every grant/spare record — it is the `x64sc` child pid, which is a field `readEpoch()` already
returns today for free (`vice.mjs:344-368`, the `.pid` field), but which is a **different pid**
from anything `signal_recorded_pid()`'s existing identity check verifies. Both facts are corrected
in detail in Key Finding 1 below, because CONTEXT.md's D-01/criterion-6 framing ("reused rather
than re-derived") needs a precise caveat: the *discipline* is reusable, the *function* is not,
unmodified.

## Key Finding 1 — Where the x64sc child pid lives, and why `signal_recorded_pid()` cannot be reused unmodified

**The answer to the phase's first open question.** Two separate facts, each confirmed by direct
code read:

**Fact A: `supervisor_pid`, recorded in every grant/spare JSON, is NOT the x64sc pid — it is the
supervisor script's own bash pid.** `launch_instance()` spawns `vice-supervisor.sh` itself with
`nohup ... & spawned_pid=$!` and writes that pid into the record as `supervisor_pid`
(`resources/vice-broker.sh:1028-1046`). `signal_recorded_pid()` — the function CONTEXT.md's D-01
says criterion 6 "reuses rather than re-derives" — verifies identity by checking `ps -o args=`
against **`$SUPERVISOR_SCRIPT`** (the path to `vice-supervisor.sh` itself:
`resources/vice-broker.sh:1436-1450`, the `case "$args" in *"$SUPERVISOR_SCRIPT"*)` branch). If you
signal that pid, `vice-supervisor.sh`'s own `on_signal()` trap fires
(`resources/vice-supervisor.sh:340-349`) — `terminate_child()` kills its x64sc child, then the
whole supervisor process **exits cleanly (status 0), and does not respawn**. That is a full
teardown of the (supervisor, x64sc) pair on that port, requiring a brand-new supervisor and a
brand-new grant to get a working instance back — exactly the "new port, new grant mid-flight"
outcome D-01's own reversibility note says the design must avoid.

**Fact B: the actual x64sc child pid is already exposed on the container side, for free, by code
that ships and is tested today.** `vice-supervisor.sh`'s respawn loop captures `child_pid=$!` right
after spawning `x64sc` and writes it into `epoch.json` as the `pid` field
(`resources/vice-supervisor.sh:388-391`, `write_epoch "$epoch" "$child_pid" ...`). Container-side,
`vice.mjs`'s `readEpoch()` already parses and returns this exact field
(`vice.mjs:344-368`, `pid: Number.isFinite(parsed.pid) ? parsed.pid : null`) — every session that
calls `beginSession()`/`assertSameMachine()` already has this value sitting in
`readEpoch(session.epochPath).pid`. `epoch_file` itself is already translated host→container by
`containerizeGrant()` (`vice-proxy.mjs:989-1042`, `pathFields: ["epoch_file", "supervisor_dir"]`)
and adopted at `useInstance({ ..., epochFile: containerized.epoch_file, ... })`
(`vice-proxy.mjs:1149-1150`). **No new read-side code is needed to obtain the x64sc pid.**

**Consequence for the plan:** `recycle`'s target pid is `readEpoch(activeEpochFile).pid`, not
anything in the grant record. But the *action* — signalling that pid — cannot happen
container-side (no route to a host pid). It must be a **new host-side broker capability**:

1. A new request `op` (e.g. `"recycle"`), naming the target instance (its epoch_file or port —
   the broker already resolves both host-side, no translation needed there).
2. `process_requests()` must actually **read and branch on** that `op` field — today it does not.
   `writeRequest()` (container side, `vice-broker-client.mjs:116-132`) already writes an `op` field
   into every request (`op = "acquire"` default) but `process_requests()`
   (`resources/vice-broker.sh:1182-1238`) never reads it — `extract_id_field()`
   (`resources/vice-broker.sh:646-648`) only ever extracts `"id"`, and every request file, without
   exception, is fed straight to `grant_from_spare()` / cold-launch. **This is new broker code, not
   an existing dispatch a new op-value slots into.**
3. The broker-side handler for `op:"recycle"` reads the **same** `epoch.json` (host paths, no
   translation needed — the broker already runs host-side) to get the current x64sc pid, verifies
   its identity (a check against `$VICE_BIN`/`x64sc`, structurally parallel to but **not the same
   check** as `signal_recorded_pid()`'s `$SUPERVISOR_SCRIPT` match — this is the "genuine
   parameterisation" the plan must add, not a reuse), then applies the identical
   SIGTERM→poll(`kill -0`)→SIGKILL escalation shape (`resources/vice-broker.sh:1452-1462`) — the
   **discipline** is exactly reusable, the **function body** is not, because its one hardcoded
   string is the wrong process name for this target.
4. Once the x64sc pid genuinely exits (not the supervisor), the supervisor's own `wait "$child_pid"`
   (`resources/vice-supervisor.sh:395`) returns with a real exit status, the crash-evidence block
   runs (`resources/vice-supervisor.sh:406-412`), and the **existing respawn loop** brings up a new
   `x64sc` on the **same port**, bumping `epoch` (`resources/vice-supervisor.sh:442`) — this part of
   D-01/D-07/D-20 is exactly correct and needs no new code at all.
5. **Confirmation channel for the recycle tool's own return value** is a planner discretion area,
   not settled here — the simplest option, reusing existing infra with zero new files, is to poll
   the (already-translated, already-readable) `epoch_file` for the epoch to increment past its
   pre-recycle value, bounded by an attempt budget; a dedicated ack file (`recycle-acks/<id>.json`,
   parallel to `grants`/`denials`) is the more explicit alternative and costs one more broker-side
   write path.

**Evidence:** direct read of `resources/vice-broker.sh` (`launch_instance` L997-1058,
`grant_from_spare` L1077-1147, `signal_recorded_pid` L1436-1464, `teardown` L1392-1418,
`process_requests` L1182-1238, `extract_id_field` L646-648), `resources/vice-supervisor.sh`
(`write_epoch` L289-306, respawn loop L377-443, `on_signal`/`terminate_child` L332-349),
`vice.mjs` (`readEpoch` L344-368), `vice-proxy.mjs` (`containerizeGrant` L989-1042,
`ensureBrokerLease` L1096-1159), `vice-broker-client.mjs` (`writeRequest` L116-132).
**Confidence: HIGH** — read directly, cross-checked against the live incident record's own
observed pid/epoch numbers in RE-FINDINGS.md, no execution needed to establish (this is a static
code-reading task, per the mandate).

## Key Finding 2 — Proxy-local vs broker-routed, resolved per tool

`RESULT_CONTINUE_TOOL` (`vice-proxy.mjs:236-252`) is the precedent for a **fully proxy-local**
synthetic tool: it is concatenated onto the manifest's tools array at `handleToolsList()`
(`vice-proxy.mjs:294-309`, `[...manifestTools, RESULT_CONTINUE_TOOL]`) and intercepted **before**
any deny-list/epoch/forwarding logic in `handleToolsCall()` (`vice-proxy.mjs:1161-1172`,
`if (name === "vice_result_continue") return handleResultContinue(args);`). This is a clean,
already-proven pattern for a tool that touches no host state.

- **`diagnose` fits this pattern exactly.** Every read it needs — `vice_checkpoint_list`,
  `vice_cycles_stopwatch`, `vice_registers_get`, `vice_memory_read`, `vice_display_screenshot` —
  is a normal forwarded `mcp__vice__*` call the proxy already knows how to make; `diagnose`'s own
  code is pure sequencing/classification over their results, run inside the proxy process, no new
  request/grant/lease protocol touched at all.
- **`recycle` does not fit this pattern**, because its action (signal a host pid) has no existing
  request shape to piggyback on (see Key Finding 1) — it needs a genuinely new
  request-write/broker-dispatch/host-action round trip, the shape `ensureBrokerLease()`
  (`vice-proxy.mjs:1096-1159`) already establishes for `acquire` (`writeRequest()` +
  `createLease()` + `pollGrant()`), but for a **new verb**, not the existing one. The container side
  already knows how to write a well-formed request file (`vice-broker-client.mjs:writeRequest()`)
  and poll a result file to a deadline (`pollGrant()` — reusable as a *pattern*, though its target
  directory is `grants`/`denials`, not whatever the recycle ack ends up being).

**What already exists between proxy and broker, concretely, for the planner to build on:**
`requests/<id>.json` (write), `grants/<id>.json` / `denials/<id>.json` (poll-to-deadline read),
`leases/<id>` (heartbeat/release). No `actions/` or `recycle/` directory exists yet — it is new
scope, correctly sized as "a new request op" rather than "a new protocol."

**Evidence:** `vice-proxy.mjs:236-252,294-309,1161-1172,1096-1159`; `vice-broker-client.mjs` (whole
file, esp. `writeRequest` L116-132, `pollGrant` L208-237). **Confidence: HIGH.**

## Key Finding 3 — Manifest reconciliation is a non-problem, by construction, if the pattern is followed

`refresh-manifest.mjs` is confirmed the **sole writer** of `tools-manifest.json`
(`refresh-manifest.mjs:1-56`) and unconditionally **overwrites** it with whatever the live host
`serverInfo()` handshake returns (`tools = info.tools`, then `writeFileSync`). It has zero
awareness of proxy-local tools and will never gain any — this is by design, per its own header
comment ("vice-proxy.mjs never imports this file").

This is **not a problem to solve**, because `RESULT_CONTINUE_TOOL` already proves the correct
answer: a proxy-local tool's definition lives **only in `vice-proxy.mjs`'s own source**, concatenated
onto the manifest-derived array at `handleToolsList()` read time
(`vice-proxy.mjs:294-309`). It is never written into `tools-manifest.json` at all, so a manifest
regenerate cannot drop it — there is nothing to drop. **`diagnose` (if proxy-local, per Key Finding
2) should follow this exact shape.** `recycle` is the harder case: it is proxy-local from the
*discovery* side (its tool definition is code, not manifest data) but has a **real host-side
counterpart** (the broker's new recycle-dispatch code) that a manifest refresh also cannot see —
and does not need to, since the host-side broker code lives in `resources/vice-broker.sh`, which
`refresh-manifest.mjs` never reads either (it only talks MCP `tools/list` to the host emulator
server, not to the broker).

**The existing `DENY_LIST` four-layer guard**, confirmed directly (re-proving criterion 10):
1. Write-time filter — `serverInfo()` in `vice.mjs` (`filterDenyList`-equivalent at
   `vice.mjs:540-557`) strips `DENY_LIST` names before `refresh-manifest.mjs` ever writes them.
2. Read-time re-filter — `handleToolsList()` in `vice-proxy.mjs:303`
   (`readManifestTools().filter((t) => !DENY_LIST.includes(t.name))`).
3. Call-time refusal before any network attempt — `handleToolsCall()` in `vice-proxy.mjs:1177-1182`.
4. `call()`'s own refusal one layer further down — `vice.mjs:494` (`if (DENY_LIST.includes(toolName))`).

Both layers 2 and 3 are proven with a **deliberately adversarial fixture** — a manifest that
*includes* `vice_disk_list` on purpose, to prove the runtime filter (not just the write-time one)
is what keeps it out (`vice-proxy.test.mjs:513-550`, `vice-proxy.test.mjs:487-511` for the
call-time refusal). **Any tool this phase adds should get the identical test shape**: a fixture
that deliberately includes the new tool/hazard to prove the *code*, not the data, is what
enforces it (`01.1 criterion 5`'s discipline, reused correctly here).

**Corrected test count for criterion 10:** ROADMAP.md's criterion 10 cites "119/119 tests
passing," verified 2026-08-02. Running the full suite today (`node --test .claude/mcp/vice/*.test.mjs`)
reports **200/200 passing** — the 119 figure predates the two same-day broker fixes
(`260802-ci3`, `260802-d6v`, per STATE.md's Quick Tasks table) that grew `vice-broker.test.mjs`
from 43→50 tests and added others. The planner should cite **200/200** (or whatever the count is
at plan time — re-run, don't trust either historical figure) as the re-proof baseline for
criterion 10, not the stale 119.

**Evidence:** `refresh-manifest.mjs` (whole file); `vice-proxy.mjs:294-309`; `vice.mjs:123,494,540-557`;
`vice-proxy.test.mjs:480-550`; live run of `node --test .claude/mcp/vice/*.test.mjs` in this
session — 200 pass, 0 fail. **Confidence: HIGH** (live-verified in this session).

## Key Finding 4 — No current `mcp__vice__*`-surfaced code writes anywhere under `.planning/`, or anywhere outside `.vice-supervisor/`

Directly searched (`grep -n "writeFileSync\|mkdirSync" .claude/mcp/vice/*.mjs`, excluding tests):
every write site in the whole `.claude/mcp/vice/` tree targets `.vice-supervisor/` (broker
protocol state — `requests/`, `leases/`, the atomic tmp-then-rename helpers in
`vice-broker-client.mjs:79-91` and `vice-pool.mjs`) or is `refresh-manifest.mjs`'s own
`tools-manifest.json` write, invoked by hand, never by the proxy. **Nothing today writes a
repo-tracked file under `.planning/`.** This confirms D-18's own framing exactly: the incident
record is a genuine, first-of-its-kind expansion of the proxy's remit, not an extension of an
existing pattern — the planner should treat "a tool writes a committed file" as new surface
needing its own test coverage (permissions, atomicity, idempotency of a repeated recycle writing a
second record), not as "just like the epoch file, but somewhere else."

**The atomic-write pattern to follow** (used identically in two places already):
`vice-supervisor.sh`'s `write_epoch()` (`resources/vice-supervisor.sh:289-306`, `mktemp` in the
same directory + `mv`) and `vice-broker-client.mjs`'s `writeJsonAtomic()`
(`vice-broker-client.mjs:79-91`, tmp file in the same target directory + `renameSync`). Both are
same-directory tmp-then-rename; the incident-record writer should be a third instance of the exact
same shape, on the container side (since `.planning/` is a container-visible, git-tracked path —
no host/container translation needed, unlike `epoch_file`).

## Key Finding 5 — D-16's warning annotation is a different code shape than `DENY_LIST`, not a variant of it

`DENY_LIST` refuses **before forwarding** — the call never reaches the host at all
(`vice-proxy.mjs:1177-1182`). D-16 requires the opposite: the checkpoint-arming call **must go
through** (it is core RE technique per D-16's own text), and the hazard is attached to the
**result**, not used to block the request. This means the interception point is the **same seam**
(`handleToolsCall()`, after `call()` returns a payload, before the proxy returns it to the agent)
but a **different branch**: detect "this call armed a stopping exec checkpoint whose address
resolves to the currently-live IRQ handler target" (requires the same two-read vector lookup as
`diagnose`'s checkpoint-trap check — see Key Finding 6) and append a warning block to the returned
`content`, never touching `isError`. There is no existing code to point to for this exact shape
(annotate-after-forward); it is new, and should get the same "test fails if the guard is removed"
treatment DENY_LIST already has (assert the annotation is present in a fixture call that arms
exactly this pattern, and assert it is **absent** for an ordinary non-IRQ checkpoint, so the
warning cannot become blanket noise on every checkpoint call).

**Evidence:** `vice-proxy.mjs:1161-1250` (the whole `handleToolsCall()` body, read to find the
return point after `call()`); no existing test or code implements a post-hoc annotation today —
confirmed by grepping for `annotat|hazard|warning` in `vice-proxy.mjs` (no hits other than doc
comments). **Confidence: HIGH that no such mechanism exists yet; MEDIUM on the exact detection
heuristic**, since "resolves to the currently-live IRQ handler" needs the same live `$01`/vector
read D-14 needs, not a static address list (an IRQ handler's address is a fact about the running
game image, not a fixed constant — the planner should treat "which address is the IRQ handler
entry" as *resolved live, every check*, not cached from a prior session).

## Key Finding 6 — The exact IRQ-handler resolution D-14 requires

From `.planning/RE-FINDINGS.md` § "2026-08-01 — the vector table: six pairs, and `$01` decides
which pair is live" (doc-derived, MEDIUM confidence, not yet exercised live against this project's
own image — the diagnose tool's first real run over a live wedge is what would promote this to
HIGH):

1. Read `$0314/$0315` (KERNAL IRQ vector, RAM, indirect — default `$EA31`).
2. Read `$01` (the 6510 port register) to determine whether the ROMs are banked in or out. **The
   hardware pairs (`$FFFE/$FFFF`) are only live when the ROMs are banked out via `$01`** — check
   `$01` before trusting either pair.
3. If ROMs are banked out, read `$FFFE/$FFFF` (hardware IRQ/BRK vector) instead — this is the pair
   actually dispatched by the CPU in that configuration.
4. A second, corroborating tell: read the handler's own first instruction. The KERNAL's
   register-save preamble means the KERNAL path is in use; a jump straight into game code means it
   is not (RE-FINDINGS.md § "IRQ source is settled by reading two enable masks" gives the
   supporting raster/CIA-enable-mask reads if a second confirmation is wanted: `$D01A`/`$D019` for
   raster, `$DC0D`/`$DD0D` for CIA timer).

D-14's exact requirement — "resolved by the documented two-read lookup — `$0314/$0315`, or
`$FFFE/$FFFF` when `$01` has the ROMs banked out" — matches this exactly; no correction needed,
only restatement with the tool calls: two `vice_memory_read` calls (address `$0314`, size 2; and
conditionally address `$FFFE`, size 2) plus one `vice_memory_read` (address `$01`, size 1).

**Evidence:** `.planning/RE-FINDINGS.md` lines ~290-325 (doc-derived, MEDIUM). **Confidence:
MEDIUM** — matches CONTEXT.md's own citation, not independently re-verified against a live wedge
in this research session (none is running; static analysis only, per the task's constraints).

## The checkpoint-trap correlation (D-13) — re-examined against the incident todos, with the caveat's weight assessed

Read directly, all four incident todos plus the relevant RE-FINDINGS.md entries:

- **Incident 1** (`2026-08-01-vice-registers-frozen-after-reset-during-01-04-task2.md`): froze

## Trigger-hunt cost and budget (D-09/D-10)

**What one attempt costs**, reconstructed from the incident record: each reproduction attempt
needs a fresh session (boot-fresh instance grant, per-session access model — a stalled session
cannot be reused, confirmed in RE-FINDINGS.md's "a stalled session cannot be repaired from inside
and has to be abandoned"), a full boot-to-gameplay sequence (attempt 4 re-derived this from
scratch and reached the trigger point in well under the session), one stopping checkpoint arm on
`$DD00` (or `$1103` for the IRQ-entry variant), one resume, then the confirmation cost: **two
independent `cycles_stopwatch reset→run→ping×N→read` brackets reading zero**, plus one
`vice_registers_get` read taken immediately after an explicit `vice_execution_pause`, to rule out
a merely-slow machine (the ~6,000/s degraded case, D-08). That is roughly 8-12 tool calls plus the
boot sequence per attempt, entirely container-side and requiring no host access — cheap in tool
calls, expensive in **needing a fresh session per attempt** since a stalled instance cannot be
reused for the next try until `recycle` exists (hence D-05's sequencing: recycle-tracer first).
Once `recycle` works, an attempt budget of order 5-10 is reasonable to name in the plan (D-10 only
requires the number be stated, not what it is) — each attempt after the first can reuse the same
session if `recycle` successfully restores a healthy instance on the same port.

**What:** A tool definition that lives entirely in `vice-proxy.mjs` source, concatenated onto the

`mcp__vice__*` calls, with no new host-side action.

### Pattern 2: Identity-verified host-side kill (the discipline to reuse, NOT the function)
**What:** SIGTERM, then poll `kill -0` every 200ms up to a wait ceiling, escalate to SIGKILL on
timeout — but ONLY after confirming, via `ps -o args=`, that the recorded pid still matches the
expected process's own invocation string.
**When to use:** Any host-side action that signals a pid recorded in a file that could have gone
stale (pid reuse).
**Example:**
```bash
# Source: .claude/mcp/vice/resources/vice-broker.sh:1436-1464 (signal_recorded_pid, existing)
# The recycle dispatch needs the SAME SHAPE but checking against $VICE_BIN ("x64sc"), not
# $SUPERVISOR_SCRIPT -- this is new code, parameterised, not a call to the existing function.
signal_recorded_pid() {
  local pid="$1" label="$2"
  kill -0 "$pid" 2>/dev/null || return 1
  case "$(ps -o args= -p "$pid" 2>/dev/null)" in
    *"$SUPERVISOR_SCRIPT"*) ;;   # <-- this literal is what must change for the x64sc target
    *) echo "refusing to signal $pid ..." >&2; return 1 ;;
  esac
  kill -TERM "$pid" 2>/dev/null || true
  # ... poll kill -0, escalate to SIGKILL after VICE_BROKER_KILL_WAIT_S ...
}
```

### Anti-Patterns to Avoid
- **Signalling `supervisor_pid` and calling it "the recycle."** It works, but it tears down the
  whole (supervisor, x64sc) pair and forces a fresh grant on a new port — exactly what D-01 says
  the design must NOT do (see Key Finding 1).
- **Calling `signal_recorded_pid()` unmodified against the x64sc pid.** Its identity check is
  hardcoded to `$SUPERVISOR_SCRIPT` and will always refuse (correctly, since a real x64sc pid never
  matches that string) — silently producing a no-op "recycle" that looks like it ran but never
  signalled anything.
- **Writing the new tools' definitions into `tools-manifest.json`.** `refresh-manifest.mjs` will
  silently drop them on the next regenerate (Key Finding 3) — define them in `vice-proxy.mjs` code
  only.
- **Assuming D-15's checkpoint-delete remediation always un-sticks a checkpoint trap.** Incident
  1's own log disproves this for at least one case (see the checkpoint-trap section above) — report
  the trap; do not promise the fix works.
- **Treating the IRQ-handler address as a fixed constant across sessions.** It must be resolved
  live every time (`$0314/$0315` vs `$FFFE/$FFFF`, decided by `$01`), never cached — a different
  game state (or a different game entirely, in future phases) can retarget it.

## Common Pitfalls

### Pitfall 1: Confusing `supervisor_pid` with the x64sc pid
**What goes wrong:** Recycling ends up tearing down and re-granting instead of an in-place respawn.
**Why it happens:** Both pids are recorded somewhere in the broker's files, and only close reading
of `write_epoch()`'s call site distinguishes them.
**How to avoid:** Always source the recycle target from `epoch.json`'s `pid` field (host-side, or
via `readEpoch()` container-side), never from a grant/spare record's `supervisor_pid`.
**Warning signs:** A "recycle" that leaves the proxy reporting a new port/new grant, or a session
losing its cached endpoint — that is a full teardown, not a recycle.

### Pitfall 2: Trusting D-15's remediation as a guaranteed fix
**What goes wrong:** The diagnose tool reports a checkpoint trap, the agent deletes the checkpoint
and resumes, and the machine is still frozen — because incident 1 already showed this exact
sequence fail.
**Why it happens:** The natural reading of D-15 ("the agent then acts... reaches for recycle only
when the cycle bracket says wedge with no checkpoint explanation") sounds like delete-and-resume is
the normal successful path.
**How to avoid:** Word the diagnose tool's checkpoint-trap report as an explanation, not a promise
of recoverability; the agent's next move (delete + resume, then a fresh cycle bracket to confirm)
is still correct, but the plan/tests should include the "still frozen after delete" case as a
possible, not exceptional, outcome — at which point it genuinely is indistinguishable from
criterion 8's "detectable host-side?" unknown and recycle is the fallback after all.

### Pitfall 3: Caching the IRQ handler address across diagnose calls
**What goes wrong:** A stale cached address silently resolves the wrong vector pair after a
disk swap, reset, or between two different games in a later phase.
**Why it happens:** It looks like a constant once resolved for one boot.
**How to avoid:** Re-read `$0314/$0315`/`$01`/`$FFFE-$FFFF` fresh on every `diagnose` call; the
resolution costs three cheap `vice_memory_read` calls, not worth memoising.
**Warning signs:** A diagnose report whose "live IRQ handler" field never changes across a hard
reset, when it structurally should be re-derived from the reset vector.

### Pitfall 4: Assuming the trigger hunt can run before recycle works
**What goes wrong:** A wedge is deliberately reproduced, and with no recycle path, the whole
session must be abandoned per-attempt (the current, pre-phase state) — burning a session per data
point.
**Why it happens:** It is tempting to start the trigger hunt first since it directly targets
criterion 9's highest-value evidence.
**How to avoid:** D-05's sequencing (thin recycle tracer → trigger hunt → full design) is not
merely a nice-to-have ordering, it is the only way an attempt budget (D-10) is affordable at all —
follow it.

## Security Domain

### Applicable ASVS Categories

This is internal developer tooling (an MCP server reachable only by this project's own agent
sessions, never by an external untrusted user), so most ASVS categories are not meaningfully
applicable. The relevant ones:

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no | Not a multi-user or network-exposed surface; the broker's own uid-parity precondition (`resources/vice-broker.sh`'s header comment) is the only relevant access boundary, unchanged by this phase. |
| V4 Access Control | yes, narrowly | The identity-verified-kill discipline (`ps -o args=` match before any `kill -TERM`) IS this project's access-control mechanism for a privileged host action — must be preserved exactly, parameterised correctly (Key Finding 1), never weakened to a bare pid kill. |
| V5 Input Validation | yes | Every broker-protocol file (`requests/`, `grants/`, `epoch.json`) is already treated as untrusted input (try/catch JSON.parse, no thrown exception on malformed content) — the new recycle request/dispatch code must follow the identical never-throw, never-trust posture already established (`readJsonMaybe()` in `vice-broker-client.mjs`, the JSON-shape validation in `vice-proxy.mjs`'s `readManifestTools()`). |
| V6 Cryptography | no | Not applicable — no secrets, no crypto in this surface. |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Pid reuse — a recorded pid is recycled by the OS onto an unrelated process before the kill fires | Tampering/Elevation (accidental, not adversarial, but the effect is the same: killing the wrong process) | The existing `ps -o args=` identity check, parameterised correctly per Key Finding 1 — never a bare `kill -TERM $pid`. |
| A malformed or half-written broker-protocol file (crash mid-write) | Denial of Service (self-inflicted) | Already mitigated by the atomic tmp-then-rename pattern; the new incident-record write and any new recycle-request/ack file must use the identical pattern, not a direct write. |
| A tool result silently discarding a kill's failure (e.g., SIGTERM sent, process still alive, but the tool reports success) | Repudiation (the record doesn't reflect what actually happened) | The recycle tool's return value must carry the actual outcome of the SIGTERM→poll→SIGKILL sequence (which stage succeeded), not just "requested" — mirrors D-17's evidence-before-action requirement extended to evidence-of-outcome. |
