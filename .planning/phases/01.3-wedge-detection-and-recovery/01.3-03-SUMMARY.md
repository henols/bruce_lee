# Phase 01.3 Plan 03: gatherWedgeEvidence() and the Full Incident-Record Evidence Section Summary

**One evidence gatherer, composed from plan 01.3-02's own cycle-bracket and IRQ-vector primitives, assembles criterion-4's full evidence set (bracket, registers, checkpoints, IRQ handler, screenshot, and a best-effort pre-kill snapshot) into a fixed-order incident-record section where a failed capture is always visibly a failure, never a silent gap.**

## Performance

- **Duration:** single session
- **Tasks:** 2/2 completed
- **Files modified:** 4 (2 code, 2 test)

## Accomplishments

- **Task 1 (the evidence gatherer and the record format):** Added `gatherWedgeEvidence()` to `vice-proxy.mjs` -- the one place criterion-4's evidence set is assembled, composed entirely from reads already forwardable through `call()`: one cycle bracket via `runCycleBracket()` (plan 01.3-02, never re-derived), the register snapshot, the full checkpoint enumeration (address, enabled flag, stop/continue), the resolved live IRQ handler via `resolveLiveIrqHandler()` (plan 01.3-02), and a screenshot written to a path in the incidents directory sharing the record's own stem. `captureStep()` wraps every step so a rejection, transport failure, or non-answering read degrades to an explicit `unavailable (<reason>)` entry rather than aborting the gather -- proven against a healthy stand-in, a stand-in that rejects only the screenshot, one that rejects only the checkpoint enumeration, and one that rejects every single read. The screenshot's path argument is explicitly translated via `rewriteArguments()` (the same helper the forwarded seam applies), proven by asserting the stand-in's actually-received argument is the translated host-form path, not the container path. `incident-record.mjs`'s `renderIncidentRecord()` gained a fixed-order `## Evidence` section and an `evidence_complete` frontmatter flag; `incidentAssetStem()`/`incidentAssetPath()` factor the filename-building rule `incidentRecordPath()` already used, so the screenshot and the record can never drift onto two different naming rules.
- **Task 2 (the snapshot attempt and the ordering guard):** Added `captureSnapshotAttempt()` -- the LAST capture step before the record write, calling `vice_snapshot_save` with a name (not a path) built from the same timestamp/port/epoch stem, recorded as *accepted* rather than *verified* (T-01.3-11: the capability takes a name resolved host-side, so nothing container-side can confirm a file landed). Wired `gatherWedgeEvidence()` and `captureSnapshotAttempt()` into `handleRecycle()` immediately before the (unchanged) `writeIncidentRecord()` call, and extended the tool's success text to name the snapshot outcome alongside the existing record path, kill stage, both epochs and readiness verdict. Strengthened the plan 01.3-01 filesystem-ordering test to assert the evidence section is already *complete* (not merely present) at the moment the request file appears, and added a region-scoped structural test asserting `writeIncidentRecord(` precedes `writeRecycleRequest(` inside `handleRecycle()`'s own source -- manually verified to fire by temporarily reversing the two calls (the structural test failed as expected; the filesystem-ordering test alone did NOT catch the reorder, because its 20ms poll granularity is too coarse to observe a synchronous back-to-back call reorder -- this is exactly why the plan calls for the structural guard as the real mechanism), then reverted before this commit.
- **258/258 tests pass** across the whole `.claude/mcp/vice/*.test.mjs` suite (244 baseline + 14 new: 6 in `incident-record.test.mjs`, 8 in `vice-proxy.test.mjs`), no flake observed on the final run.

## Decisions Made

See `key-decisions` in frontmatter. In brief: the snapshot's evidence wording is deliberately weaker than the screenshot's ("accepted" vs "saved to") because only the screenshot's path is one the container can verify was even attempted correctly; the screenshot and snapshot share one filename-building rule (`incidentAssetStem()`); a single capture-step deadline covers every evidence step uniformly rather than special-casing the snapshot; and `finaliseIncidentRecord()` carries the evidence section forward as already-rendered text rather than re-deriving it from structured data it never has in hand.

## Issues Encountered

- The initial two-recycles-at-the-same-port-and-epoch test hung, because leaving `epoch.json` genuinely unchanged across both recycle calls also starves `handleRecycle()`'s own post-kill "epoch moved" wait loop (bounded by the ~30s `RECYCLE_ACK_TIMEOUT_MS`, unrelated to the incident-record filename concern the test cares about). Fixed by bumping `epoch.json` before each recycle's ack (so its own post-kill wait resolves fast) and resetting it back to 1 before the next recycle's own `preKillEpoch` read -- preserving "same epoch_before for both recycles" as the actual property under test.
- An early regex assertion (`/RAM KERNAL IRQ vector pair/`) in two new tests didn't match production's actual wording (`"the RAM IRQ vector pair"`, no "KERNAL"); corrected to match the real string `resolveLiveIrqHandler()` renders.
