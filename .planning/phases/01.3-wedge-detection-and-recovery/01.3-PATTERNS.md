### `diagnose` tool — add to `.claude/mcp/vice/vice-proxy.mjs` (controller, request-response)

**Analog:** `RESULT_CONTINUE_TOOL` and its wiring, same file.

**Tool definition pattern** (`vice-proxy.mjs:236-252`):
```javascript
const RESULT_CONTINUE_TOOL = {
```

`diagnose` should follow this exact literal-object shape: a plain object with `name`, `description`, `inputSchema`,
defined at module scope near `RESULT_CONTINUE_TOOL`, not generated dynamically.

**Discovery-time wiring** (`vice-proxy.mjs:294-309`):
```javascript
function handleToolsList() {
```

**Call-time dispatch, BEFORE deny-list/lease/epoch logic** (`vice-proxy.mjs:1161-1172`):

**D-14 ordering requirement inside `handleDiagnose()`:** enumerate armed checkpoints and resolve the live IRQ

**Analog for the container→host round trip:** `ensureBrokerLease()`'s existing `writeRequest()` +
`createLease()` + poll-to-deadline shape (`vice-proxy.mjs:1096-1159` per RESEARCH.md Key Finding 2) — reusable
as a *pattern*, not literally, since its target directories are `grants`/`denials`, not whatever the recycle
ack ends up being (planner discretion, RESEARCH.md Open Question 1 recommends starting with epoch-polling).

**`writeRequest()`'s existing `op` parameter** (`vice-broker-client.mjs:116` onward):
```javascript
export function writeRequest({ id, op = "acquire", sessionId = null, clientPid = null } = {}) {
  // ... id MUST already be a newRequestId() output -- validated here (T-01.2-01) ...
  writeJsonAtomic(join(dir, `${id}.json`), dir, record);
```

This already accepts an `op` field — the write-side plumbing for `op:"recycle"` is nearly free. **The gap is
entirely on the read side**, per Key Finding 1.

**The gap — `process_requests()` never reads `op` today** (`resources/vice-broker.sh`, `process_requests()`):
```bash
process_requests() {
  local req_file id total_now port in_flight
  [ -d "$REQUESTS_DIR" ] || return 0
  if [ "$(count_launching)" -gt 0 ]; then in_flight=1; else in_flight=0; fi
  for req_file in "$REQUESTS_DIR"/*.json; do
    [ -e "$req_file" ] || continue
    id="$(extract_id_field "$req_file")"
    if [ -z "$id" ] || ! is_valid_request_id "$id"; then
      echo "vice-broker: skipping request $(basename "$req_file") -- invalid or missing id: \"$id\"" >&2
      continue
    fi
    if grant_from_spare "$id"; then continue; fi
    if [ "$in_flight" -eq 1 ]; then ...; continue; fi
    total_now="$(count_total)"
    if [ "$total_now" -ge "$VICE_BROKER_MAX" ]; then deny "$id" "..."; continue; fi
    if ! port="$(next_free_port)"; then deny "$id" "..."; continue; fi
    if launch_instance "$port" "cold"; then in_flight=1; else deny "$id" "$LAST_LAUNCH_ERROR"; fi
  done
}
```
`extract_id_field()` extracts only `"id"`; every request file, without exception, is fed straight into the
acquire path (`grant_from_spare()` / cold-launch). **This is new branch code, not an existing dispatch a new
op-value slots into** — the plan must add an early `op="$(extract_op_field "$req_file")"`-style read and a
branch (`if [ "$op" = "recycle" ]; then handle_recycle "$id" "$req_file"; continue; fi`) before the existing
acquire logic runs.

**Identity-verified kill — discipline to copy, function body NOT reusable unmodified**
(`resources/vice-broker.sh`, `signal_recorded_pid()`):
```bash
signal_recorded_pid() {
  local pid="$1" label="$2"
  [ -n "$pid" ] && [ "$pid" != "null" ] || return 1
  kill -0 "$pid" 2>/dev/null || return 1
  local args
  args="$(ps -o args= -p "$pid" 2>/dev/null || true)"
  case "$args" in
    *"$SUPERVISOR_SCRIPT"*) ;;
    *)
      echo "vice-broker: refusing to signal pid $pid for $label -- ps reports \"$args\", which does not match $SUPERVISOR_SCRIPT (possible pid reuse)" >&2
      return 1
      ;;
  esac
  kill -TERM "$pid" 2>/dev/null || true
  local waited_ms=0 limit_ms=$((VICE_BROKER_KILL_WAIT_S * 1000))
  while kill -0 "$pid" 2>/dev/null; do
    if [ "$waited_ms" -ge "$limit_ms" ]; then
      echo "vice-broker: pid $pid ($label) did not exit within ${VICE_BROKER_KILL_WAIT_S}s of SIGTERM -- sending SIGKILL" >&2
      kill -KILL "$pid" 2>/dev/null || true
      break
    fi
    sleep 0.2
    waited_ms=$((waited_ms + 200))
  done
  return 0
}
```
**Constraint, load-bearing (RESEARCH.md Key Finding 1 / Anti-Patterns):** the `case "$args" in *"$SUPERVISOR_SCRIPT"*)`
match is the wrong identity check for a recycle target. `supervisor_pid` (this function's usual target) is the
**bash pid of `vice-supervisor.sh` itself** — signalling it tears down the whole (supervisor, x64sc) pair and
forces a brand-new grant on a new port, which is exactly what D-01 says the design must NOT do. The recycle
target is the **x64sc child pid**, obtained from `epoch.json`'s `"pid"` field (written by `write_epoch()` in
`vice-supervisor.sh`, read container-side by `readEpoch().pid` in `vice.mjs` — see below). A new sibling
function (not a call to `signal_recorded_pid()` unmodified) is needed with the identity check parameterised
against `$VICE_BIN` (e.g. `x64sc`), not `$SUPERVISOR_SCRIPT` — same SIGTERM→poll→SIGKILL escalation shape,
different match string, different label semantics.

**Where the x64sc pid already comes from, container-side, for free** (`vice.mjs:344-368`):
```javascript
export function readEpoch(path = activeEpochFile) {
  const absent = { present: false, epoch: null, spawned_at: null, pid: null, path };
  let raw;
  try { raw = readFileSync(path, "utf8"); } catch { return { ...absent, reason: "epoch file absent" }; }
  let parsed;
  try { parsed = JSON.parse(raw); } catch { return { ...absent, reason: "epoch file present but not valid JSON" }; }
  if (parsed === null || typeof parsed !== "object" || !Number.isInteger(parsed.epoch)) {
    return { ...absent, reason: "epoch file present but its \"epoch\" field is not a finite integer" };
  }
  return {
    present: true,
    epoch: parsed.epoch,
    spawned_at: typeof parsed.spawned_at === "string" ? parsed.spawned_at : null,
    pid: Number.isFinite(parsed.pid) ? parsed.pid : null,   // <-- the x64sc child pid
    path,
  };
}
```
No new read-side code needed here — this is the never-throw, never-trust posture every broker-protocol file
read already follows, and the recycle tool's own JSON reads (request/ack files) should match it exactly.

**Where the pid is written, host-side** (`resources/vice-supervisor.sh`, `write_epoch()`, atomic
tmp-then-rename — the pattern D-18's incident record must also follow):
```bash
write_epoch() {
  local this_epoch="$1" pid_field="$2" log_field="$3" dry_run_field="$4"
  local tmp
  tmp="$(mktemp "$VICE_SUPERVISOR_DIR/.epoch.XXXXXX")"
  {
    printf '{\n'
    printf '  "epoch": %s,\n' "$this_epoch"
    printf '  "spawned_at": "%s",\n' "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
    printf '  "pid": %s,\n' "$pid_field"
    printf '  "supervisor_pid": %s,\n' "$$"
    printf '  "vice_bin": "%s",\n' "$(json_escape "$VICE_BIN")"
    ...
  } >"$tmp"
  mv "$tmp" "$EPOCH_FILE"
}
```
Called at `write_epoch "$epoch" "$child_pid" "\"logs/x64sc-$ts.log\"" "false"` right after the respawn loop
captures `child_pid=$!` — this is the concrete site RESEARCH.md's Key Finding 1 Fact B refers to.

## Shared Patterns

### Never-throw, never-trust JSON reads
**Source:** `readJsonMaybe()` in `.claude/mcp/vice/vice-broker-client.mjs:96-109`; `readEpoch()` in
`.claude/mcp/vice/vice.mjs:344-368`; `readManifestTools()` in `.claude/mcp/vice/vice-proxy.mjs`.
**Apply to:** every new file this phase reads (request files, ack files, epoch.json) and any file the incident
writer reads back to confirm its own write.
```javascript
function readJsonMaybe(path) {
  let raw;
  try { raw = readFileSync(path, "utf8"); } catch { return null; }
  try {
    const parsed = JSON.parse(raw);
    return parsed && typeof parsed === "object" ? parsed : null;
  } catch { return null; }
}
```

### Atomic writes: tmp file in the same directory, then rename
**Source:** `write_epoch()` in `.claude/mcp/vice/resources/vice-supervisor.sh:288-306` (bash, `mktemp` +
`mv`); `writeJsonAtomic()` in `.claude/mcp/vice/vice-broker-client.mjs:86-91` (Node, `randomUUID()` tmp name +
`renameSync`).
**Apply to:** the incident record write (D-18), and any new recycle-request/ack file.
```javascript
function writeJsonAtomic(targetPath, tmpDir, data) {
  mkdirSync(tmpDir, { recursive: true });
  const tmp = join(tmpDir, `.tmp-${process.pid}-${randomUUID()}`);
  writeFileSync(tmp, JSON.stringify(data, null, 2) + "\n");
  renameSync(tmp, targetPath);
}
```

## Contradictions Between Code and CONTEXT.md (report, don't smooth over)

1. **D-01/criterion-6 says `signal_recorded_pid()` is "reused."** The code shows this is only true for the
   *discipline* (SIGTERM→poll→SIGKILL after an identity check) — the function's actual identity check is
   hardcoded to `case "$args" in *"$SUPERVISOR_SCRIPT"*)`, which will always fail (correctly) against a real
   x64sc pid, silently producing a no-op "recycle" if called unmodified. A parameterised sibling function is
   required. (`resources/vice-broker.sh:1442-1447`, RESEARCH.md Key Finding 1.)
2. **D-01's premise that "criterion 7 is satisfied for free"** is correct only if the recycle target is the
   x64sc child pid from `epoch.json`, never `supervisor_pid` from a grant/spare record — signalling
   `supervisor_pid` tears down the whole (supervisor, x64sc) pair and forces a new grant on a new port, which
   is the exact outcome D-01's own reversibility note says must be avoided. The two pids live in different
   places and are easy to conflate (RESEARCH.md's own Pitfall 1).
3. **D-15's remediation guidance ("delete the checkpoint, resume, reaches for recycle only when the cycle
   bracket says wedge with no checkpoint explanation") reads as if delete-and-resume normally works.**
   Incident 1's own step log (`.planning/todos/pending/2026-08-01-vice-registers-frozen-after-reset-during-01-04-task2.md`)
   shows checkpoint delete → resume → still frozen; soft reset → still frozen; hard reset → still frozen;
   single step → still frozen, in that exact order — CONTEXT.md's own D-13 caveat says this explicitly ("may
   be the onset without being the whole story"), but D-15's text alone could be read as promising a fix. The
   plan should word the diagnose tool's checkpoint-trap report as an explanation, not a guarantee of
   recoverability (RESEARCH.md Pitfall 2).
