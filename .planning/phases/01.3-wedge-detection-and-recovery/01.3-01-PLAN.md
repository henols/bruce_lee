<objective>
Prove the whole `vice_recycle` path end-to-end on one slice: capture a record, ask the host to kill
the emulator's x64sc child, watch the supervisor bring it back on the same port, confirm the epoch
moved, and hand the caller a truthful account of what happened.

Purpose: D-05 makes this first because it breaks a real circular dependency. The trigger hunt
(criterion 9) is destructive and needs a working recovery path or it burns a session per attempt,
while the roadmap wants the hunt to report before the recovery design is fixed. A deliberate kill of
a *healthy* instance is fully observable, so the recycle half can be proven now without waiting for
a wedge that has never appeared on request.

Output: a destructive `vice_recycle` MCP tool served proxy-local, a new `recycle` request verb the
host broker actually dispatches on, a parameterised identity-verified kill aimed at the x64sc child
rather than the supervisor, an ack file that records which kill stage fired, and the first
repo-tracked file any `mcp__vice__*` tool has ever written.
</objective>

instead. This is a recorded choice, not an omission.

**Three places where the code contradicts what CONTEXT.md assumed. Corrected here, in the open.**

1. **`signal_recorded_pid()` cannot be reused unmodified.** CONTEXT.md § Reusable Assets says
   criterion 6 is "satisfied by reuse, not re-derivation." Its identity check is hardcoded to match
   `$SUPERVISOR_SCRIPT` (`resources/vice-broker.sh` ~L1443-1450), which is the wrong process name for
   an x64sc target and would always refuse — a silent no-op recycle that looks like it ran. What is
   reusable is the SIGTERM to poll to SIGKILL **discipline**. Criterion 6 is still satisfied, by a
   parameterised sibling, not by calling the existing function. Task 1 adds that sibling.
2. **The recycle target pid is NOT the recorded supervisor pid.** Every grant and spare record's
   recorded supervisor pid is `vice-supervisor.sh`'s own bash pid (`resources/vice-broker.sh`
   ~L1028-1046). Signalling it fires the supervisor's own signal trap
   (`resources/vice-supervisor.sh` L332-349), which kills the child and then **exits cleanly with no
   respawn** — the opposite of D-01. The real x64sc pid is the `pid` field of `epoch.json`, written by
   `write_epoch()` (`resources/vice-supervisor.sh` L289-306, called at L391) and already returned
   container-side by `readEpoch().pid`. CONTEXT.md § Integration Points flagged this as "planning must
   confirm how that is obtained"; it is now confirmed. Conflating the two pids is the highest-severity
   failure mode in this phase and is carried as `T-01.3-04` in the threat register below, not as a
   comment.
3. **`process_requests()` ignores the `op` field entirely today** (`resources/vice-broker.sh`
   L1182-1238) — `extract_id_field()` extracts only the id, and every request file without exception
   is fed to the acquire path. Recycle needs a genuinely new host-side dispatch branch, not an
   existing verb to extend. Task 1 budgets for it.

**Planner discretion, resolved.** Recorded here so no downstream agent has to re-decide:

- **Tool names:** `vice_recycle` and `vice_diagnose`, both `vice_`-prefixed to match every existing
  entry including the proxy-local `vice_result_continue`.
- **Recycle confirmation channel: a dedicated `recycle-acks/<id>.json`, plus an independent epoch
  check.** RESEARCH § Open Questions recommended epoch-polling alone as the cheaper option, and
  assumption A3 named its narrow misattribution race. Two things overrule that recommendation. The
  repudiation mitigation `T-01.3-03` requires the tool to report *which stage of the kill sequence
  fired*, which an epoch bump cannot tell anyone. And an identity refusal produces no epoch bump at
  all, so epoch-polling alone would report a refusal as an indistinguishable timeout. The ack says
  what the host did; the epoch says the machine actually came back. Both are required, and A3's race
  disappears as a side effect.
- **Incident record path and format:** `.planning/incidents/<UTC-compact>-port<N>-epoch<M>.md`,
  markdown with a YAML frontmatter block. Markdown because RE-FINDINGS.md will cite it and a human
  reads it; frontmatter because the same file then greps as structured data without inventing a
  second format. `.planning/incidents/README.md` states that these files are never archived — unlike
  the four stall todos they replace, which move to `todos/completed/` — which is why they get their
  own directory rather than joining the todo lifecycle.

    `handle_recycle_request()` reads the target id, validates it against the id pattern, resolves
    `$GRANTS_DIR/<target_id>.json`, and reads that record's port and epoch file path. It then reads
    the x64sc pid and the recorded vice binary name out of **that epoch file** — this is the single
    source of the target pid, and the grant record's recorded supervisor pid is deliberately never
    read here, because that pid is the supervisor script's own bash pid and signalling it fires the
    supervisor's signal trap, killing the pair with no respawn. Every failure along that chain
    (missing grant record, unreadable epoch file, absent pid) writes an ack with an outcome naming
    exactly which lookup failed and returns without signalling anything — which is D-21's requirement
    that the recycle path be correct when the broker's records disagree with reality. On success it
    records the pre-kill epoch value, calls `signal_vice_child_pid`, and writes the ack.

    `signal_vice_child_pid()` takes the pid, the expected binary name and a label. It is a
    **parameterised sibling** of `signal_recorded_pid()`, not a call to it: same guard order (empty or
    the literal null returns non-zero; `kill -0` failure returns the already-exited stage), same
    `ps -o args=` identity check, same SIGTERM then 200ms `kill -0` poll up to
    `VICE_BROKER_KILL_WAIT_S` then SIGKILL escalation, same loud refusal wording on a mismatch. The
    one difference is the match string: the value read from the epoch file's recorded binary field,
    never the supervisor script path. Verifying against the value the supervisor itself wrote is
    strictly stronger than a hardcoded name, because the epoch file states which binary that instance
    was actually launched with. It prints one of `already_exited`, `identity_refused`, `sigterm` or
    `sigkill` on stdout so the caller can put the real stage in the ack.

    `write_recycle_ack()` goes through the existing `write_json_atomic()` helper and emits every field
    in the ack table in "Artifacts this phase produces". Delete the request file after acking, exactly
