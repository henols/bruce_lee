# Phase 01.3: Wedge Detection and Recovery - Context

**Gathered:** 2026-08-02
**Status:** Ready for planning

<domain>
## Phase Boundary

An agent that suspects the emulator is stuck can establish **mechanically** whether it is, tell the
look-alike states apart, and — where the state warrants it — recover through `mcp__vice__*` and
nothing else. Today the only exit is abandoning the session, which has halted plan 01-04 across at
least three attempts.

Delivers: **two MCP tools** (a read-only diagnose call and a destructive recycle call), a bounded
**trigger investigation** into whether a specific call or ordering causes the freeze, and a durable
**incident record** written before anything is killed.

Not in this phase: a skill file; root-causing `x64sc`/GTK/OpenGL internals; host-side wedge
detection; intra-session parallelism; any change to `vice-pool.sh`'s classic port-keyed lease.

**The discussion materially reshaped the phase.** The roadmap's framing assumed three states
(crashed-and-respawned / wedged / degraded-but-live) and a recovery-centric deliverable. Cross-reading
the four incident todos during this discussion produced a **fourth state — a self-inflicted checkpoint
trap — that is cheaper to detect, more likely to be the actual recorded cause, and recoverable in-session
with no kill at all.** See D-13 through D-16. Planning should treat detection as the phase's centre of
gravity and recycle as the fallback, which is the inverse of the roadmap's emphasis.

</domain>

<decisions>
## Implementation Decisions

### Recovery surface and mechanism

- **D-01:** Recovery replaces a wedged instance by **signalling the supervisor's `x64sc` child**, not by
  tearing down the broker grant. [vice-broker.sh:1020-1030](.claude/mcp/vice/resources/vice-broker.sh#L1020-L1030)
  spawns `vice-supervisor.sh` per port, and that loop already respawns on child exit, collects crash
  evidence, and bumps `epoch.json`. So a deliberate recycle voids the run by the exact mechanism a crash
  already does — **criterion 7 for free, no second voiding channel invented** — on the same port, with the
  grant still valid. — **Reversibility:** costly — the whole epoch/continuity story, criterion 7's
  no-second-channel rule, and the "grant survives a recycle" property all rest on this. Switching to broker
  teardown later means the session gets a new port and a new grant mid-flight, which the proxy's cached
  endpoint does not currently expect.

- **D-02:** **Tools only. No skill file is created.** The triage judgement lives in the tools' code and
  their descriptions, not in prose. This follows a live project precedent rather than a preference:
  `.claude/skills/vice-mcp-selector/SKILL.md` was audited line-by-line, found to document hazards that
  code already enforced, and **deleted outright** (`db9eed3`). Prose that describes behaviour code could
  enforce has rotted here before. This **overrides the source todo's own framing** ("both — likely the
  honest answer") and the roadmap's presumed answer; the override is deliberate.

- **D-03:** **Two tools, split diagnose from recycle.** One tool runs the checks and returns a verdict with
  its evidence; a separate tool does the kill. The diagnostic call is read-mostly and safe to make freely;
  the destructive one stays a deliberate, separate act — on a surface where `vice_disk_list` already proved
  a single call can kill the host. A mode argument on one tool was rejected for putting a destructive action
  one typo from a diagnostic one. Recycle does **not** gate on a recent verdict (rejected as sharing state
  and introducing another tuned staleness constant).

- **D-04:** **The detector never runs automatically.** On-demand invocation only. Measuring liveness needs
  `vice_execution_run`, which **D-1.2-F** already identifies as this project's leading crash suspect; a
  detector that resumed the machine on every call would multiply calls to the tool most correlated with
  host death — the detector would cause the failure it exists to catch. Both a session-start auto-bracket
  and proxy-side passive hinting were considered and rejected.

### Sequencing and proof

- **D-05:** **Thin recycle tracer first**, then the trigger hunt, then the full design. This breaks a
  circular dependency the roadmap sets up but does not resolve: criterion 9 wants the trigger investigation
  to report *before* the recovery design is fixed, while the risks section notes trigger-hunting is
  destructive and needs recovery in hand or it burns a session per attempt. The smallest working recycle —
  signal the child, epoch bumps, tools answer — is provable against a *healthy* instance, because a
  deliberate kill is fully observable without needing a real wedge. Matches the tracer-first precedent from
  01.1 and 01.2.

- **D-06:** **A confirmed trigger is blocked at the seam within this phase**, not deferred to a follow-on.
  Criterion 9 says a confirmed trigger changes the deliverable; this makes that literal. **See D-16 for the
  guard's shape** — "blocked" here means enforced at the seam, and the enforcement chosen is a warning, not
  a refusal.

- **D-07:** **Proof standard: synthetic for the detector, real kill for the recycle.** The detector's
  classification logic is proven deterministically against a stand-in that answers `ping` ok/running while
  its cycle counter never moves — the exact recorded signature, testable in CI forever. The recycle is proven
  against a real healthy instance. The phase **records honestly that neither half met a real wedge**, and what
  therefore remains unproven. This is the answer to criterion 11, whose subject has occurred five times
  unbidden and never once on request.

- **D-08:** **A wedge is exactly zero cycles across two consecutive brackets. There is no degradation
  threshold.** Any non-zero rate is returned as a measured cycles/s alongside the ~991,000/s baseline, with
  degradation flagged as an observation and **never** as a recovery trigger. This keeps the ~6,000/s
  documented hazard a distinct state without inventing a tuned constant — the same trap this project already
  rejected once when the drift discriminator's block-fill heuristic scored 134/137 and was refused anyway
  because "tuning until green manufactures the false confidence this work exists to prevent."

### Trigger investigation

- **D-09:** **The hunt's subject is the armed-stopping-checkpoint family**, not the `$DD00` address. Initially
  scoped to the `$DD00`-resume shape (two hits at an identical PC), then **retargeted during discussion** once
  cross-reading all three incidents showed the common factor is *a stopping exec checkpoint armed, then
  execution resumed* — with the IRQ-handler-entry case (`$1103` shape) and the mid-routine case (`$07DE` shape)
  as its two variants. This is the hypothesis that covers all three incidents rather than the two that happened
  to share an address.

- **D-10:** **A fixed attempt budget, named in the plan.** When it is spent, the recorded answer is "could not
  reproduce in N attempts, here is exactly what was attempted." A negative with a stated denominator is a real
  result; an open-ended hunt is how a tooling phase eats a week. Time-boxing was rejected — wall-clock is never
  part of this project's loop, and making an exception here would be the wrong place to start.

- **D-11:** **Container-side observation only.** Anything answerable through `mcp__vice__*` is in scope — which
  call, which ordering, what the machine state looks like at the freeze. The moment a question needs host
  process internals (stack traces, thread state, GTK/GL introspection, a debugger on `x64sc`) it stops and is
  recorded as an open question. A checkable line that matches the only-permitted-route rule.

- **D-12:** **Criterion 8 is discharged by decision, and the phase says so.** D-11 means "is a wedge detectable
  host-side?" does not get answered by evidence. The phase records: not investigated, boundary drawn at
  container-side observation, here is why. The deliverable is container-side detection plus recycle — which is
  **exactly the fallback criterion 8 itself names for a negative answer**. Rewording the criterion to fit the
  plan was considered and rejected as editing the scorecard.

### The checkpoint trap — a fourth state (new, from this discussion)

- **D-13:** **There is a fourth state the roadmap does not list: a self-inflicted checkpoint trap.** An armed
  stopping exec checkpoint pins the PC because every resume re-enters the trap before useful work retires. The
  cycle bracket reads zero, `vice_ping` reports "running" (VICE's execution flag flips before the trap fires),
  and the PC reads byte-identical every time because the machine genuinely never moved. **This is not a wedge
  and must never be recycled as one** — recycling here destroys a healthy instance.

  **Evidence from cross-reading the incident record** (this correlation had not been drawn before 2026-08-02):
  - Incident 1 (`vice-registers-frozen-after-reset`): the freeze began *immediately after* an exec+stop
    checkpoint was armed at **`$1103`, an IRQ-handler entry**, on a title screen with a confirmed live
    raster-split IRQ chain `$1103→$1574→$152C`. The tell is that the `$1103` checkpoint reported
    `hit_count: 0` after multiple resume/poll cycles — on an IRQ-driven screen where it should fire every
    frame. A checkpoint that cannot register a hit on an address the machine must be executing means the
    machine was not getting there.
  - Incidents 3 and 4: both froze at `PC:2014` (`$07DE`), the instruction immediately after `STA $DD00` —
    exactly where a **stopping checkpoint on that store had just parked the machine** before execution was
    resumed.

  **Caveat, recorded rather than smoothed over:** in incident 1, deleting the `$1103` checkpoint did *not*
  unfreeze it, and neither did a soft reset, a hard reset, nor an explicit single step. So a checkpoint trap
  may be the **onset** without being the whole story — it may be what tips VICE into a state it cannot leave.
  Planning must not assume delete-and-resume always works.

- **D-14:** **The checkpoint-trap check runs FIRST, before any cycle bracket.** The diagnose tool enumerates
  armed checkpoints and resolves the live IRQ handler before it runs `vice_execution_run` at all. It is the
  cheapest check, it needs no resume to reach a verdict, and it keeps a healthy instance from being killed
  for a self-inflicted stop. This **modifies criterion 2's ordering**: the cycle bracket remains the definitive
  liveness test, but it is no longer the first move. The IRQ handler is resolved by the documented two-read
  lookup — `$0314/$0315`, or `$FFFE/$FFFF` when `$01` has the ROMs banked out.

- **D-15:** **On a checkpoint trap the tool reports and does not remedy. No restart, no kill, nothing
  destructive.** It names the problem so the agent can solve it and understand what happened. The report is
  explanatory, not a verdict code, and carries at minimum:
  - which checkpoints are armed, at what addresses, and which stop vs continue
  - the live IRQ handler target and how it was resolved (which vector pair, and the `$01` value that decided)
  - the current PC and its relation to the armed checkpoint that explains why it is not moving
  - an explicit statement that this is a self-inflicted stop, not a wedge, and that recycling would destroy a
    healthy instance

  The agent then acts with tools it already has — `vice_checkpoint_delete`, `vice_checkpoint_toggle`,
  `vice_execution_step` — and reaches for recycle only when the cycle bracket says wedge **with no checkpoint
  explanation**.

- **D-16:** **The seam guard warns; it never refuses.** `vice_disk_list` is deny-listed because it has no
  legitimate use. A stopping checkpoint on an IRQ handler is **core RE technique that Phase 2's exhaustive
  trace depends on** — refusing it, even with an opt-in override, would obstruct the exact work this project
  runs on. Same seam, different remedy: the call goes through and its result carries a hazard annotation
  naming the risk and the recovery. This is how D-06's "block at the seam" is to be implemented; a planner
  must not read D-06 as authorising a refusal.

### Evidence capture and continuity

- **D-17:** **The recycle tool captures evidence itself, before it kills.** Capturing is not optional and not
  a step an agent under pressure can skip: the tool gathers the criterion-4 evidence (cycle brackets, PC,
  restart epoch, checkpoint enumeration, screenshot), writes the record, and only then signals the child.
  Structurally impossible to recycle without leaving a trail. The alternative arrangement — the agent captures,
  following instructions — is the one that **already produced four evidence-free todos**.

- **D-18:** **The incident record is repo-tracked under `.planning/`.** The whole point is that the trail
  outlives the session, and the four stall todos it replaces live in `.planning/todos/`. A committed record is
  greppable, survives a container rebuild, and can be cited by `RE-FINDINGS.md`. **`.vice-supervisor/` is
  gitignored runtime state — a record written there is exactly as lost as no record at all.**

  **This makes a tool write files, which no current `mcp__vice__*` tool does.** That is a genuine expansion of
  the proxy's remit, flagged as the main open question in
  `.planning/seeds/ram-capture-as-proxy-tools.md`. Planning must treat it as a design decision with a stated
  rationale, not as an incidental implementation detail. — **Reversibility:** costly — once incident records
  are committed at a path, `RE-FINDINGS.md` entries and todos will cite it, and the proxy's file-writing remit
  becomes precedent for the capture tools that seed anticipates.

- **D-19:** **Best-effort snapshot before the kill, never blocking.** Attempt a `.vsf` save and record whether
  it succeeded; if the wedged machine will not answer, note that and move on. A wedge that reproduces once is
  the only chance to inspect the machine at the freeze, and **a failed attempt is itself a finding** about what
  a wedged instance can still do. Costs one call and cannot stall the recycle.

- **D-20:** **Continuity reuses the existing rule unchanged.** A recycle bumps the epoch, which is the same
  identity change a crash produces, so plan 01-04's "resume from the last recorded milestone snapshot after an
  identity change" already applies. The phase **confirms this in writing** rather than inventing a second
  continuity story. Every caller that already compares epochs across a bracket gets correct behaviour for free.

## Existing Code Insights

### Reusable Assets
- **`vice-supervisor.sh`'s respawn loop + `write_epoch()`** — D-01 uses this as the recovery mechanism rather
  than building one. Killing the `x64sc` child produces respawn, crash evidence and an epoch bump with no new
  code on the recovery side.
- **`signal_recorded_pid()` in `vice-broker.sh`** — identity-verified kill, already written and already used by
  `grant_from_spare()`'s failed-probe path. Criterion 6 is satisfied by reuse, not re-derivation.
- **`RESULT_CONTINUE_TOOL` in `vice-proxy.mjs`** — a synthetic tool served entirely proxy-local that appears in
  `tools/list` "exactly like a real tool so an agent can discover it". The working precedent for how a new tool
  gets exposed.
- **`probe_ready()` in `vice-broker.sh`** — proves readiness by a real MCP round-trip rather than a socket probe.
  The same "bookkeeping is not evidence" discipline the diagnose tool needs.
- **`vice_checkpoint_list`, `vice_cycles_stopwatch`, `vice_registers_get`, `vice_memory_read`,
  `vice_display_screenshot`** — every read D-14 and D-17 need already exists as a tool. The diagnose tool
  composes existing calls; it does not need new host capability.

### Established Patterns
- **Tracer-first plan sets** (01.1-01, 01.2-01) — one thin slice end-to-end with the hard-to-retrofit parts
  present in the first commit. D-05 follows this.
- **Atomic writes are tmp-file + `rename()` in the same directory**, never in place — used by `write_epoch()`
  and `write_json_atomic()`. Any incident record written under D-18 should follow it.
- **Hazards are enforced in code with a test that fails if the guard is removed** (01.1 criterion 5). D-16's
  warning annotation should carry the same test discipline even though it warns rather than refuses.
- **Every claim carries Evidence and Confidence on the HIGH/MEDIUM/LOW scale**, and promotion happens by
  re-logging with live evidence, never by editing a grade in place.

### Integration Points
- **The broker → supervisor seam** is where D-01 acts. `launch_instance()` records `supervisor_pid` and
  `epoch_file` per port in `spares/$port.json`; the recycle tool needs the child `x64sc` pid, which is the
  supervisor's child rather than the recorded supervisor pid — planning must confirm how that is obtained
  through the permitted route.
- **`tools-manifest.json` + `refresh-manifest.mjs`** — the manifest is the single source `tools/list` is served
  from and is the only writer. Two new tools have to land there coherently, and `refresh-manifest.mjs`
  regenerates from the *host* server, which will not know about proxy-local tools.
- **This phase unblocks plan 01-04's remaining live play-through and Phase 2's exhaustive trace** — both long
  unattended emulator sessions, which is exactly where an unrecoverable wedge is most expensive.

<specifics>
## Specific Ideas

- **"Report back what the problem is, but do not solve it."** The user's framing for the checkpoint-trap state,
  and it generalises: the diagnostic surface explains, the agent decides, and every mutating act stays a
  separate deliberate call. This is why D-03's split exists and why D-15 refuses to auto-delete a checkpoint.
- **The report must be understandable, not just actionable.** The stated goal is that the agent "can solve it
  by itself and understand what happened" — so the checkpoint-trap output names the vector pair it read, the
  `$01` value that decided which pair was live, and why the PC is pinned. A verdict code would satisfy the
  criterion and miss the point.
- **Prefer a mechanism that already exists over a new one.** D-01 and D-20 both take this shape — the epoch
  bump and the milestone-snapshot resume rule are reused rather than paralleled, which is what "no second
  voiding channel" means in practice.
- **A negative with a stated denominator is a real result.** D-10 and D-12 both. "Could not reproduce in N
  attempts, here is what was attempted" and "not investigated, here is the boundary and why" are deliverables,
  not gaps.
- **Do not manufacture a threshold.** D-08 refuses a degradation cut for the same reason the drift discriminator
  refused a block-fill heuristic that scored 134/137 — a tunable constant gets tuned until green.
- **Resilience over scope.** The user's stated aim for the whole VICE MCP. It decided D-21/D-22: harden the path
  this phase owns, and decline to inherit a partly-stale defect list it cannot verify.
