# Phase 01.3 Plan 04: The D-16 Seam Hazard Annotation and the SEAM_HAZARDS Table Summary

**Arming a stopping exec checkpoint now goes through to the host unchanged and comes back carrying a hazard note (shape, evidence, diagnostic, recovery, residual) -- structurally the OPPOSITE of the vice_disk_list deny-list refusal at the same seam, expressed as a data-driven SEAM_HAZARDS table so plan 01.3-05's confirmed trigger is one entry away, never new plumbing.**

## Performance

- **Duration:** single session
- **Tasks:** 2/2 completed
- **Files modified:** 2 (both code: `vice-proxy.mjs`, `vice-proxy.test.mjs`)

## Accomplishments

- **Task 1 (the seam warns and never refuses):** Added `CHECKPOINT_ARMING_TOOLS` (today: `vice_checkpoint_add` alone, with the toggle/group re-enable residual documented as a comment on the set), per-session suppression state (`seamHazardSeen`/`seamHazardEpochKey`, cleared via a synchronous local `currentEpoch()` read on an observed epoch change -- never a forwarded call), and `annotateCheckpointHazard(name, args, payload)`: returns nothing unless the capability is in the arming set, the call's own arguments express an exec operation with the stop flag set (schema defaults: both `true` when absent), and the forwarded call already succeeded. Wired into `handleToolsCall()` by merging the note into the payload's text BEFORE `wrapPossiblyChunked()` runs (T-01.3-15: an oversized result still carries the note inside its own chunking), never touching `isError` or routing through `isErrorText` (D-16, T-01.3-12). The annotation text names the armed shape and address (or states the address as unparseable rather than silently skipping), cites the two recorded freeze variants, points to `vice_diagnose` for live handler resolution, gives the recovery ordering (diagnose first, recycle only on a wedge with no checkpoint explanation), and states the toggle/group residual.
- **Task 2 (the hazard set is a table):** Refactored task 1's single hazard into `SEAM_HAZARDS` -- an array of `{ id, capabilities, detect, render }` entries walked generically by `renderSeamHazardAnnotations()`, which `handleToolsCall()` now calls instead of the single hard-wired function. `detectCheckpointArmingHazard()`/`renderCheckpointArmingHazard()` carry task 1's own logic, split into the table's detect/render shape. Added two structural guards: a completeness test walking the table and requiring every entry to carry a detector, a renderer, and at least one test in the file naming its `id`; and a disjointness test asserting no capability named by any `SEAM_HAZARDS` entry also appears on `DENY_LIST`. A `VICE_SEAM_HAZARDS_TEST_FIXTURE` env-gated fixture entry (matched against `vice_ping`, an existing universally-forwardable tool, rather than a synthetic capability name) proves the walk is genuinely data-driven: a synthetic second entry is detected and annotated with zero changes to the production entry. A source-region guard on `detectCheckpointArmingHazard`/`renderCheckpointArmingHazard` carries task 1's own no-`isErrorText`/no-forwarded-call invariants forward past the refactor.
- **Both guard-removal demonstrations performed and reverted before their respective commits:** task 1's annotation append was temporarily short-circuited to `undefined`, which failed the 4 tests depending on it; task 2's completeness structural test was demonstrated by temporarily adding an untested table entry, which failed exactly that one test. Both reverted (confirmed clean via `grep` for the temporary markers) before committing.
- **268/268 tests pass** across the whole `.claude/mcp/vice/*.test.mjs` suite (258 baseline + 10 new: 6 in task 1, 4 in task 2), no flake observed on the final run. `vice_disk_list` remains absent from `tools/list` and refused at `tools/call`, unaffected by either task.

## Decisions Made

See `key-decisions` in frontmatter. In brief: the guard deliberately never resolves the live IRQ handler at arm time (three reasons recorded in the plan, all still binding); the annotation merges into the raw text before chunking rather than appending as a trailing content item, trading the path-note's byte-isolation guarantee for surviving inside an oversized chunked result; `CHECKPOINT_ARMING_TOOLS` excludes the toggle/group re-enable paths by design, with the residual stated in both the code comment and the annotation text; and `SEAM_HAZARDS`'s `capabilities` field exists only for the disjointness test, never for dispatch, so the walk always costs one array pass regardless of match.

## Deviations from Plan

None - Rule 1-4 auto-fixes. Two test-fixture corrections were made while writing the tests themselves (not deviations from the plan's own design, but bugs in my first draft of the fixtures, caught immediately by running the suite before committing):

1. Several test fixtures initially omitted a `vice_ping` handler in their `respond()` function. `handleToolsCall()` runs a pre-flight `vice_ping` liveness probe before forwarding any real call (plan 01.1-03), so a fixture answering only the tool under test caused every call -- including the one under test -- to fail with a "dead or hung" error. Two tests (the "continue-only/disabled/non-exec" negative case and the "rejects" case) initially passed anyway for the wrong reason (a `doesNotMatch(/vice-proxy hazard/)` assertion is satisfied equally by "no annotation" and by "an unrelated error with no annotation"). Fixed by adding `vice_ping` handling to every fixture that needs a genuinely successful call, and by re-verifying the "rejects" test isolates the rejection to the `vice_checkpoint_add` call specifically (not the probe).
2. The "annotation makes no additional forwarded calls" test initially counted ALL `tools/call` requests, which double-counted the seam's own pre-flight `vice_ping` probe alongside the arm call itself (2, not 1). Fixed to count only `vice_checkpoint_add` calls via the file's existing `forwardedCallsNamed()` helper, matching the property actually under test (the annotation itself issues zero calls, not that the whole seam issues exactly one).

These were caught and fixed before either task's commit, verified by the final clean test runs recorded above.
