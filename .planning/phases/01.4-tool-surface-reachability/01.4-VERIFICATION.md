## Judging the live-confirmation reasoning (criterion 3)

`01.4-LIVE-EVIDENCE.md`'s new section reports, from a session opened after the broker restart:

- Exactly four `mcp__vice__*` entries reported unavailable in that session's tool surface —
  `tools_call`, `tools_list`, `initialize`, `notifications_initialized`. These are precisely the four
  meta-tools `01.4-01` added to `DENY_LIST` (the fifth, `vice_disk_list`, was already closed on the
  named path and is reported separately, still absent).
- A schema request naming three tools explicitly returned `vice_ping`'s schema and returned **neither**
  `tools_list` **nor** `tools_call` — i.e., the two denied meta-tools were not merely "deferred and
  unloaded" (the ambiguous shape that caused the previous stale-snapshot confusion), they were absent
  from the server's own tool definitions when asked for by name alongside a control tool that did
  answer.
- `vice_ping` itself answered normally: `{"status":"ok","version":"3.10","machine":"C64SC",
  "execution":"paused"}`.
- No dangerous call (`vice_disk_list`, nested or otherwise) was made at any point.

**The load-bearing step, as instructed, is the ruling-out of the alternative explanation (a dropped
connection rather than a filtered surface).** I find this sound rather than merely asserted:

1. A dropped/disconnected `mcp__vice__` server would remove **every** tool under that prefix, not a
   selective four. The evidence instead shows a clean split — exactly the DENY_LIST-sized set missing,
   everything else (demonstrated by `vice_ping`) present and functioning.
2. The missing set is not "some tools" but **precisely** the set `01.4-01` added to `DENY_LIST`, with
   no more and no fewer — a coincidence of that specificity is a materially weaker explanation than "the
   filter that names exactly these four tools is doing exactly this."
3. This is a stronger test than the prior run's ambiguous one. The prior stale-snapshot problem was that
   a *listing* of deferred tool names still named the denied ones — consistent with either "not yet
   loaded" or "not actually filtered." Here, a targeted schema request for the denied names, made
   alongside a request for a control name that did resolve, came back empty for the denied names
   specifically — that is what construction-time filtering (`vice-proxy.ts:3011`, "if
   DENY_LIST.includes(def.name) continue") predicts, and what a live-but-still-serving-everything
   session would not produce.
4. The one thing that would still leave me unsatisfied — every tool including `vice_ping` disappearing,
   or the four missing tools including something *not* on `DENY_LIST` — did not happen. Both would have
   pointed at "disconnected" or "wrong filter," and neither is reported.
5. The safety discipline held: the evidence of closure was obtained without ever issuing the one call
   that would have been the hazard, which is consistent with everything else this phase has recorded
   about how this mechanism must be tested.

I accept the ruling-out. Criterion 3 is now closed on both paths (named-path closure was never in
question; the generic-dispatch path's own client-visible effect is now observed, not merely proven in
isolated code), from a session whose schema snapshot genuinely postdates the fix — the exact gap the
prior verification named.
