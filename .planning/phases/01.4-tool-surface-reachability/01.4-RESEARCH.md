## Summary

This phase does not need new library research — it needs **forensic reading of code that already
exists and is already correct**, plus recognition that two of its five criteria are properties of
the **harness** (Claude Code itself), not of `vice-proxy.mjs`. The central, load-bearing fact,
confirmed **live and in writing already** in this project's own `.planning/RE-FINDINGS.md`
(2026-08-02 entries) and `.planning/phases/01.3-wedge-detection-and-recovery/.continue-here.md`:
**Claude Code takes a snapshot of an MCP server's callable-tool schema once, at that session's own
MCP initialization, and never refreshes it — not on a broker restart, not on a host restart, not
mid-session no matter how long the session runs.** `vice-proxy.mjs`'s `handleToolsList()` is
proven correct by a live, fresh-session `ToolSearch` call that successfully loaded
`mcp__vice__vice_diagnose` and `mcp__vice__vice_recycle` by exact name. The reason criterion 1's
268/268-green suite coexists with an agent session that cannot see three tools is exactly this
gap between what the tests exercise (a bespoke stdio JSON-RPC test client that always speaks to a
freshly-spawned, current-code process) and what a real session exercises (Claude Code's own
tool-discovery/caching layer, which no in-container test can reach).

Independent of that mechanism, this research also found — and directly verified by reading
`vice-proxy.mjs`, `vice.mjs` and `tools-manifest.json` — the **exact, code-level cause of
criterion 3's `vice_disk_list` breach**, requiring no live probing at all: `tools-manifest.json`
contains four entries (`initialize`, `notifications_initialized`, `tools_list`, `tools_call`) that
are the **host's own JSON-RPC method names, re-exposed by the host as ordinary, forwardable
tools**. `vice-proxy.mjs`'s deny-list guard (both layers) and its three proxy-local synthetic-tool
dispatch (both layers) check only the **outer** `params.name` of a `tools/call` request. `tools_call`
is a manifest tool whose own schema is literally `{name: string, arguments: any}` — "call a tool by
name" — so invoking `mcp__vice__tools_call({name:"vice_disk_list"})` sails past every guard
(the outer name is `"tools_call"`, never `"vice_disk_list"`) and is forwarded verbatim to the host,
which answers it as a real, unfiltered `tools/call` against its own registry. The same mechanism
explains `tools_list` returning a 64-tool set **with `vice_disk_list` present** and the three
synthetic tools **absent**: it forwards the literal string `"tools_list"` to the host, which
answers with its own raw, un-deny-listed inventory (the host has never heard of the deny-list, and
has never heard of the three proxy-only synthetic tools either, since those exist only inside
`vice-proxy.mjs`).

**Primary recommendation:** Fix criterion 3 by removing `tools_call`/`tools_list` (and, for the
same reason, `initialize`/`notifications_initialized`) from the forwardable tool surface entirely
— deny-list them at the exact same seam `vice_disk_list` already uses, since an agent has no
legitimate reason to call a tool literally named `tools_call` when Claude Code's own native
`tools/call` protocol method already reaches every real tool correctly and safely. Resolve
criterion 2 by writing up the confirmed session-snapshot mechanism as a **documented session-shape
constraint** (a synthetic tool added mid-session is unreachable for the rest of that session; a
fresh session sees current code) rather than attempting a code fix — there is no code fix available
inside this repo, and the fix already recorded and proven is "start a fresh session." Criterion 1
follows automatically once criterion 2's constraint is documented and criterion 3's forwarding hole
is closed, because the tools were never broken — only unreachable via a stale snapshot or a bypass
route. Criterion 4 is upstream (`anthropics/claude-code#13898`-class), already mitigated locally
(the `tools:` line was removed from `gsd-executor.md`), but that mitigation lives in a **gitignored,
untracked file** and needs a durability check, not a redesign. Criterion 5 has a fully-scoped
rewrite plan already written (`de-architecture-agent-visible-proxy-messages.md`); execute it as
specified.

### Pattern 1: Deny-list a tool at the proxy seam, not by trying to fix the host

**What:** `DENY_LIST = ["vice_disk_list"]` in `vice.mjs`, checked in three independent places
(`call()`, `handleToolsList()`'s discovery filter, `handleToolsCall()`'s call-time refusal) — see
`vice-proxy.mjs:2141-2149` and `vice.mjs:120-123,493-499`.
**When to use:** Any capability that must never reach the host, or (per this research's finding)
any tool name whose own semantics let it re-invoke an arbitrary other tool name (a generic
dispatcher). The existing pattern is proven, tested, and load-bearing — extend it, don't invent a
parallel mechanism.
**Example:**
```javascript
// Source: .claude/mcp/vice/vice.mjs:120-123 (current, verified in this session)
export const DENY_LIST = ["vice_disk_list"];

// Proposed extension (criterion 3) — same shape, applied to the generic-dispatch
// tools captured verbatim from the host's own tools/list response:
export const DENY_LIST = ["vice_disk_list", "tools_call", "tools_list"];
// NOTE: DENY_LIST's existing three call sites already do everything needed once these
// names are added — no new logic, just three more entries in an existing list. Verify
// "initialize" and "notifications_initialized" the same way; if they are equally
// forwardable and equally useless to an agent, add them too rather than leaving a
// partial fix. (Their inputSchemas take no meaningful arguments today, so their blast
// radius is smaller, but "smaller" is not "zero" if the host's implementation changes.)
```

### Pattern 2: Proxy-local synthetic tool dispatch runs BEFORE deny-list and BEFORE forwarding

**What:** `handleToolsCall()` checks `name === "vice_result_continue"`, then
`name === RECYCLE_TOOL.name`, then `name === DIAGNOSE_TOOL.name`, each returning directly — none of
these ever reach `call()` or the network. See `vice-proxy.mjs:2116-2139`.
**When to use:** Any future proxy-local-only tool (one that has no host-side existence at all).
**Example:**
```javascript
// Source: .claude/mcp/vice/vice-proxy.mjs:2116-2139 (current, verified in this session)
if (name === "vice_result_continue") {
  return handleResultContinue(args);
}
if (name === RECYCLE_TOOL.name) {
  return handleRecycle(args);
}
if (name === DIAGNOSE_TOOL.name) {
  return handleDiagnose(args);
}
// Layer 1: call-time deny-list refusal, before any forwarding logic
if (DENY_LIST.includes(name)) {
  return isErrorText(/* ... */);
}
```
This ordering is already correct and does not need to change for this phase — the gap is not in
this dispatch table, it is in what happens when `name` is itself a tool that can name a *different*
tool inside its own `arguments`.

### Anti-Patterns to Avoid

- **Treating a healthy `vice_ping` as evidence that any OTHER tool is reachable.** Already recorded
  as a project anti-pattern (`.continue-here.md` Anti-Pattern 1) — a live transport connection and
  a complete tool schema are independent facts. `vice_ping` succeeding proves the session's MCP
  connection is alive; it proves nothing about whether `vice_diagnose`/`vice_recycle` are present
  in that session's own tool surface.
- **Reaching for `mcp__vice__tools_list`/`tools_call` as a fallback probe when a named tool seems
  missing.** This is exactly the anti-pattern that produced the misleading "64-tool" observation in
  the recorded incident — the generic tools bypass `handleToolsList()`/`handleToolsCall()` entirely
  and answer from the host's own, unfiltered, un-synthetic-aware registry. The correct probe is a
  by-name `ToolSearch` (or equivalent) call, never the generic path.
- **Restarting the broker, the host, or redeploying resources to try to make a newly-added
  synthetic tool appear.** Already tried and recorded as not helping
  (`.continue-here.md` Anti-Pattern 3) — the broker does not hold the tool list; the client's
  session-scoped snapshot does, and nothing server-side can invalidate it.
- **Assuming a green `node --test .claude/mcp/vice/*.test.mjs` run says anything about session-level
  tool reachability.** The test harness speaks raw JSON-RPC directly to a freshly-spawned child
  process — it structurally cannot exercise Claude Code's own client-side tool-discovery/caching
  layer, which is exactly where this phase's real bug lives (criteria 2, 3-via-tools_list, 4).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Detecting whether a specific session's tool surface is stale | A custom "tool staleness checker" tool inside vice-proxy.mjs | A documented pre-flight discipline: before depending on a proxy-local synthetic tool in a plan, do a by-name `ToolSearch`/schema-load check first, and stop-and-report if it fails, per `.continue-here.md`'s own "Required first action" | The staleness lives entirely in the CLIENT (Claude Code), which the proxy cannot introspect or signal from the server side. No server-side code can fix a client-side snapshot problem — this needs a documented human/agent discipline, not more code. |
| Recursively validating nested tool-call arguments for every possible generic-dispatch shape | A generic "deep argument scanner" that walks `arguments` looking for anything resembling a tool name | Deny-listing the generic-dispatch tools themselves (`tools_call`/`tools_list`) at the existing `DENY_LIST` seam | The generic scanner is unbounded scope (what counts as "looks like a tool name"? what about a tool that takes an array of names? a tool that takes a base64-encoded name?) and fragile. Removing the generic-dispatch surface from what's forwardable closes the whole class in one line, with zero false-negative risk from a cleverer nested shape. |

**Key insight:** Every hazard this phase closes shares one shape with the already-solved
`vice_disk_list` problem: a capability that must never reach the host is closed by refusing it *at
the proxy seam*, comparing an exact tool name, never by trying to make the host behave differently
or by trying to out-think every way a caller might phrase the same request. The fix for criterion 3
is not a new mechanism — it is two more entries in a list that already works.

## Common Pitfalls

### Pitfall 1: Mistaking "the test suite is green" for "the live session works"
**What goes wrong:** A plan ships code changes, the 268 (or more, after this phase) tests pass, and
the phase is declared done — while the actual agent session still cannot see the tools.
**Why it happens:** The test suite necessarily speaks to a bespoke, freshly-spawned child process
over raw JSON-RPC (see `vice-proxy.test.mjs:3456` for the exact shape) — it is, by construction, a
"fresh session" every single time. It can prove the server is correct; it cannot prove or disprove
anything about Claude Code's own client-side snapshot/caching behaviour, because that layer is not
exercised by directly speaking JSON-RPC to a child process.
**How to avoid:** Per the roadmap's own explicit framing, this phase's verification is **a live
session call and nothing else** for criteria 1, 2 and 4. Do not let a passing test suite stand in
for that check.
**Warning signs:** A plan's "Definition of Done" lists only `node --test` passing, with no live
`ToolSearch`/named-tool-call step against a fresh session.

### Pitfall 2: Fixing criterion 2 as if it were a code defect
**What goes wrong:** Time spent looking for a bug in `handleToolsList()`/`handleToolsCall()` to
explain why the synthetic tools are missing from a session — there isn't one; the function is
already proven correct (both by the passing structural test and by a live, fresh-session
`ToolSearch` call recorded in `.planning/RE-FINDINGS.md`).
**Why it happens:** The natural instinct when three tools are unreachable is to look at the code
that serves them. In this specific case the code is fine; the gap is a documented,
already-confirmed property of the harness (session-scoped tool-schema snapshot, never refreshed).
**How to avoid:** Treat criterion 2 as a **documentation and process** deliverable — record the
constraint (a synthetic tool added mid-session is unreachable until the next fresh session) in
`CLAUDE.md` § Emulator Access and/or a project note, and add the by-name pre-flight check as a
standing discipline for any plan that depends on a proxy-local synthetic tool.
**Warning signs:** A plan proposes changing `handleToolsList()`'s logic, adding caching-busting
code, or adding a "refresh" tool to solve criterion 2 — none of these can reach a client-side
snapshot from the server side.

### Pitfall 3: Fixing the generic-dispatch hole by hardening instead of removing
**What goes wrong:** Adding logic to `handleToolsCall()` that inspects `arguments.name` when
`name === "tools_call"` and re-runs the deny-list check against it — this closes today's exact
hole but leaves the underlying problem (an unrestricted generic dispatcher exists as a forwardable
tool at all) unaddressed for any future host-side quirk shaped differently.
**Why it happens:** Recursive-inspection feels like the "more correct" fix because it preserves
`tools_call`/`tools_list` as usable tools.
**How to avoid:** Recognise that `tools_call`/`tools_list` serve **no legitimate purpose** as
agent-callable tools in this project — Claude Code's own native `tools/call`/`tools/list` protocol
methods already reach every real capability correctly, safely, and by name. Removing them from the
forwardable surface (deny-listing them) is strictly safer and requires no ongoing maintenance.
**Warning signs:** A plan's fix for criterion 3 adds new conditional branches inside
`handleToolsCall()` rather than adding entries to `DENY_LIST`.

### Pitfall 4: Assuming the `gsd-executor.md` fix from 2026-08-01 is still in place without checking
**What goes wrong:** Criterion 4 is treated as already closed because `STATE.md` records a
"RESOLVED" entry from 2026-08-01 — but `.claude/agents/gsd-executor.md` is **gitignored and
untracked** (verified this session: `git check-ignore -v` matches `.gitignore:72: .claude/*`;
`git ls-files` returns nothing for it), so nothing about it is guaranteed to survive a fresh clone,
a GSD reinstall (`npx @opengsd/gsd-core@latest --claude --local`), or any process that regenerates
`.claude/agents/` from a template.
**Why it happens:** A "RESOLVED" entry in `STATE.md` reads as closed, but the underlying artifact
it describes is explicitly *not* durable by the project's own git configuration.
**How to avoid:** This phase must **live-verify** (dispatch a real `gsd-executor` subagent, confirm
`mcp__vice__vice_ping` succeeds in its turn) rather than trust the historical record, and should add
a lightweight, repeatable check (e.g. a container-side assertion the phase's own verification runs,
or a note in the plan's own acceptance criteria) that specifically re-reads
`.claude/agents/gsd-executor.md`'s frontmatter and confirms no `tools:` key is present, immediately
before declaring criterion 4 met.
**Warning signs:** A plan cites `STATE.md`'s 2026-08-01 entry as sufficient evidence without a
fresh, live dispatch in *this* phase.

// Source: .claude/mcp/vice/tools-manifest.json (committed, read directly this session)
{
  "name": "tools_call",
  "description": "Call a tool by name",
  "inputSchema": {

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| Confused-deputy via a generic "call a tool by name" dispatcher (`tools_call`) forwarding a deny-listed name inside its own arguments | Elevation of Privilege | Deny-list the generic dispatcher itself at the same seam that already blocks the specific forbidden tool — do not attempt to teach the seam every possible way a caller might phrase the same underlying request |
| A stale client-side cache masking a server's true current capability set | (Not classic STRIDE — an availability/integrity-of-information gap) | Document the constraint explicitly and require a live by-name check before depending on a newly-added capability within the same session that added it |
| An agent-visible error message describing internal topology instead of an available action | (Not classic STRIDE — a usability/safety gap: a model may attempt to "fix" something it cannot reach, or hallucinate an unavailable capability) | Rewrite every agent-visible string to lead with the next action the agent (or the human it should escalate to) can actually take, per the existing `de-architecture-agent-visible-proxy-messages.md` todo |
