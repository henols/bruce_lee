**`call()` guard — lines 486-499 (refusal is lines 493-499, the deny check is the first
statement in the function body, deliberately):**
```javascript
/**
 * Call a vice_* tool by name and return its parsed JSON result.

 * Refuses any tool on DENY_LIST before any network request is made -- this
 * check is the first line of the function body, deliberately, so the deny
 * list is enforced even if a future edit reorders the rest of the function.

export async function call(toolName, args = {}, opts = {}) {

        `(see CLAUDE.md's hazard note). Refusing to serialise this request.`
    );
  }
  ...
```
Note the refusal message is worded specifically for the "crashes the host" hazard
(`vice_disk_list`'s reason). If `tools_call`/`tools_list` are added to this same `DENY_LIST`,

themselves — they bypass guards when forwarded). A plan should decide explicitly whether to
reuse this array with its current message (inaccurate for the new entries) or split a sibling
list/message, per RESEARCH.md's own noted option ("DENY_LIST... OR a sibling
NEVER_FORWARD_LIST").

## 2. `.claude/mcp/vice/vice-proxy.mjs` — `handleToolsList()` and `handleToolsCall()`

**`handleToolsList()` — lines 353-368 (full function):**
```javascript
function handleToolsList() {
  // Two independent transforms applied at READ time, not write time, so a
  // stale or hand-edited snapshot can never leak either property:
  //   1. re-filter DENY_LIST -- refresh-manifest.mjs's serverInfo() call
  //      already filters at write time; this is the second, independent
  //      layer that catches a snapshot generated by any other means.
  //   2. stamp the same output-size ceiling this proxy enforces onto every
  //      tool, not a curated subset -- the host's tool set is not this
  //      repo's to enumerate.
  const manifestTools = readManifestTools().filter((t) => !DENY_LIST.includes(t.name));
  const tools = [...manifestTools, RESULT_CONTINUE_TOOL, RECYCLE_TOOL, DIAGNOSE_TOOL].map((t) => ({
    ...t,
    _meta: { ...(t._meta || {}), "anthropic/maxResultSizeChars": OUTPUT_CHAR_CAP },
  }));
  return { tools };
}
```
Adding `tools_call`/`tools_list` to `DENY_LIST` makes this filter (line 362) remove them from
discovery automatically — no separate edit needed here for the discovery half of criterion 3.

**`handleToolsCall()` — lines 2109-2154+ (the full dispatch chain, in order):**
```javascript
async function handleToolsCall(params) {
  const name = params && params.name;
  if (!name || typeof name !== "string") {
    throw new ProtocolError(-32602, "tools/call requires params.name to be a non-empty string");
  }
  const args = params && typeof params.arguments === "object" && params.arguments !== null ? params.arguments : {};

  // The synthetic continuation tool: entirely a proxy-local concern, served
  // before any deny-list or epoch logic and NEVER forwarded to the host.
  if (name === "vice_result_continue") {
    return handleResultContinue(args);
  }
  if (name === RECYCLE_TOOL.name) {
    return handleRecycle(args);
  }
  if (name === DIAGNOSE_TOOL.name) {
    return handleDiagnose(args);

  // Layer 1: call-time deny-list refusal, before any forwarding logic and
  // before any network attempt. Independent from handleToolsList()'s
  // discovery-time filter -- removing either one leaves the other standing.
  if (DENY_LIST.includes(name)) {
    return isErrorText(
      `${name} is permanently forbidden -- it is known to crash the shared host VICE MCP server. ` +
        `Recovery requires a manual, host-side restart. This refusal is permanent; retrying will not help.`
    );
  }

  const leaseResult = await ensureBrokerLease();
  ...
```
**This is the exact expression the defect lives in: `params.name` (line 2110) is the ONLY name
ever checked against `DENY_LIST`.** `params.arguments.name` (the nested name inside a
`tools_call` request) is never inspected anywhere in this chain — it flows into `args` (line
2114) and is forwarded verbatim to the host once `call(name, args)` is reached below line 2154.
A plan extending the deny-list to include `"tools_call"`/`"tools_list"` closes this at the OUTER
name (line 2144's existing check now also matches when `name === "tools_call"`), which is the
approach RESEARCH.md recommends (Pattern 1, Pitfall 3) — not a new nested check.

Also note the refusal text at line 2145-2148 says "it is known to crash the shared host VICE MCP
server" — same accuracy caveat as `vice.mjs`'s message above; a plan reusing this exact branch
for `tools_call`/`tools_list` inherits wording that doesn't fit their actual hazard (bypass, not
crash) unless it's revised.

## 5. `.claude/mcp/vice/refresh-manifest.mjs` — regeneration mechanics

**Full file is 60 lines; the load-bearing fact is lines 25-44:**
```javascript
async function main() {
  const path = manifestPath();
  // serverInfo() performs the host handshake (initialize + tools/list) and
  // already strips DENY_LIST names before returning (vice.mjs's own
  // documented choke point) -- vice-proxy.mjs's tools/list handler applies
  // the SAME filter again at read time, so a snapshot generated by any other
  // means is still safe, but this refresh path inherits the omission for
  // free.
  let info;
  try {
    info = await serverInfo();
  } catch (e) {
    console.error(`refresh-manifest: could not reach the host VICE MCP server (${e && e.message ? e.message : e}) -- manifest at ${path} left UNCHANGED. A partial or empty manifest is never written over a good one on failure.`);
    process.exitCode = 1;
    return;
  }
  const tools = Array.isArray(info?.tools) ? info.tools : [];
  ...
}
```
**Implication for the plan:** `serverInfo()` (in `vice.mjs`, not shown here but referenced) is
what calls the host and gets its raw `tools/list` answer; the doc comment states it "already
strips DENY_LIST names before returning." This means **once `tools_call`/`tools_list` are added
to `DENY_LIST` in `vice.mjs`, the next `refresh-manifest.mjs` run will automatically omit them
from the regenerated manifest** — a hand-edit to `tools-manifest.json` alone would NOT survive
the next refresh (the host will keep reporting these 4 meta-methods in its own raw `tools/list`
forever; only `DENY_LIST`-based filtering at read/refresh time removes them durably). **The fix
therefore belongs in `vice.mjs`'s `DENY_LIST`** (single source of truth), not in a manual edit to
`tools-manifest.json`, and not solely in `refresh-manifest.mjs`. `vice-proxy.mjs`'s own
`handleToolsList()` filter (item 2 above) is a second, independent belt-and-braces layer over
whatever manifest is on disk — both layers should end up filtering the same extended list.

**JSON-RPC child-process harness (lines 148-199, `startProxy()` + `nextMessage()`):**
```javascript
function startProxy(env) {
  const child = spawn(process.execPath, [PROXY_PATH], {
    env: { ...process.env, ...env },
    stdio: ["pipe", "pipe", "pipe"],
  });
  const messages = [];
  let consumed = 0;
  let outBuf = "";
  child.stdout.setEncoding("utf8");
  child.stdout.on("data", (chunk) => {
    outBuf += chunk;
    let idx;
    while ((idx = outBuf.indexOf("\n")) !== -1) {
      const line = outBuf.slice(0, idx);
      outBuf = outBuf.slice(idx + 1);
      if (line.trim().length === 0) continue;
      let parsed;
      try { parsed = JSON.parse(line); } catch (e) { parsed = { __parseError: e.message, __raw: line }; }
      messages.push(parsed);
    }
  });
  const stderrChunks = [];
  child.stderr.setEncoding("utf8");
  child.stderr.on("data", (chunk) => stderrChunks.push(chunk));
  function send(msg) { child.stdin.write(JSON.stringify(msg) + "\n"); }
  async function nextMessage(timeoutMs = 8000) { /* polls `messages`/`consumed` until one arrives or times out */ }
  ...
}
```

test("vice_disk_list is refused at tools/call with no request made", async () => {

    await proxy.nextMessage();

    const resp = await proxy.nextMessage();

    assert.match(resp.result.content[0].text, /vice_disk_list/);
