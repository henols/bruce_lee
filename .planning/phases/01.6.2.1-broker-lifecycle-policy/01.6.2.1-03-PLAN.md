**Add D-20's direct FIFO assertion.** Inject N entries (use N = 5, enough that a reversal or a sort
would be unmistakable and a coincidence implausible) into the pending-acquire queue in a known order,
each recording its own identifier when its attempt runs, then drain. Assert the recorded order equals
the injection order exactly. Then extend it to the requeue path, which is where an ordering bug would
actually live: make one middle entry report itself unsettled on the first drain so it is requeued,
inject a later-arriving entry during that same drain, and assert the requeued entry is **not**
overtaken by the newcomer on the following drain. That second half is the property
`drainPendingAcquires()`'s own comment claims and nothing asserts.

**Add the structural no-re-ordering gate.** Read `broker-control.mts` from disk, isolate the queue's
own region, strip comment lines, and assert no order-mutating construct appears in it — no sort, no
reverse, no index-shuffling splice beyond the documented front-drain. **Comment-stripping is
mandatory and this is the exact file that proves why:** the region's own header comment contains the
words this gate greps for, so an unstripped count is self-invalidating and would pass or fail for the
wrong reason. Follow `broker-launch.test.ts`'s landed structural gates for the stripping idiom, and
scope the read to the queue region rather than the whole module so an unrelated future sort elsewhere
in the file does not produce a false failure. Demonstrate the gate's discriminating power: temporarily
insert an order-mutating call into the region, observe RED, remove it, observe GREEN; record both.

**Do not add an end-to-end FIFO test, and here is the reason, recorded rather than left implicit.**
Arrival order at the broker is not controllable from a test that uses separate TCP connections — the
landed disconnect-while-queued test says so in its own comment and deliberately avoids assuming which
of two sends arrives first. An end-to-end test that asserted grant order would therefore be asserting
connection-setup jitter, and would be flaky by construction. D-20's specified proof is an
**injection**-level assertion, which is what this task authors; the arrival→queue link is covered by
the structural gate plus `enqueueAcquire()`'s single append-to-back implementation. This is an
instrument choice with evidence, not a reduction of D-08's scope.

**Do not modify `broker-control.mts`.** The queue already exists and is correct; CONTEXT is explicit
that this task is a test, not an implementation. If a genuine ordering defect is found, stop and

Commit this task on its own (D-11).
