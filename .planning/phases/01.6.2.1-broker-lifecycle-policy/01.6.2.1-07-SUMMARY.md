**Closed the concurrent-acquire race (CR-01) that let selectWarmInstance() hand a grant to an
instance a sibling had already dropped and killed, and the cross-session-kill blast radius that
opened in handleRelease() -- via a map-membership identity recheck and a GrantRecord.pid identity
check, each proven by a RED-then-GREEN regression test.**

## RED-First Discipline (Task 1)

Per this phase's own established discipline (`01.6.2.1-01-SUMMARY.md`), the CR-01 regression test
was written and run against the UNMODIFIED `selectWarmInstance()` before the fix was applied. Observed
RED failure:

```
✖ CR-01: two overlapping selectWarmInstance() walks over one shared ready candidate -- the first
  caller's failed probe drops+kills it before the second caller's probe resolves true, so both fall
  through to fresh cold launches instead of the second reusing the dropped record

  AssertionError [ERR_ASSERTION]: race-b's own cold-spawn factory must be invoked exactly once

  0 !== 1

  actual: 0
  expected: 1
  operator: strictEqual
```

This is exactly the failure the finding predicted: the second caller's own `selectWarmInstance()`
walk (unfixed) returned the stale, already-deleted record as a "winner" via the state-only recheck,
so its cold-launch arm was never reached. After applying the fix (broadening the recheck to also
verify map membership by identity), the SAME test went GREEN, along with every pre-existing test in
`vice-broker-acquire.test.ts` and `broker-launch.test.ts`.

## Decisions Made

- **The CR-01 test's own retry-on-`launch_in_flight` deviation** (documented in `key-decisions`
  above): once both concurrent callers correctly fall through to a cold launch (the fix's own
  correct outcome), whichever reaches `acquirePortAndLaunch()` first legitimately holds the
  single in-flight-launch slot and the other is refused `launch_in_flight` -- a REAL, PRE-EXISTING,
  CORRECT guard (criterion C) unrelated to CR-01, which `handleAcquire()`'s own cold-launch arm
  cannot bypass (it always uses the production `nextFreePort()`, with no injectable allocator).
  Confirmed empirically: without a retry, the test deterministically failed with
  `{ok:false, reason:"launch_in_flight"}` for the second caller. The test now retries the refused
  caller, mirroring the exact behaviour `handleAcquire()`'s own header comment documents for the
  real control plane. This does not weaken the test's discriminating power against CR-01 itself --
  the retry only ever engages AFTER both callers have already correctly reached the cold-launch
  arm, which is the fix's own success condition; against the UNFIXED code, the test fails much
  earlier (the assertion that each caller's own spawn factory is invoked exactly once), before the
  retry logic is ever exercised.
- **WR-02 deferred, not fixed** -- per the plan's own explicit instruction, recorded as a todo with
  both fix options rather than picked-and-implemented, since fixing it now risks destabilising the
  existing grant-time-probe-failure log-ordering test for a bound that does not currently bite at
  this project's own default warm floor (1).
- **`handleRelease()`'s mismatch-path log line writes directly to `process.stderr`** rather than
  through an injectable `log` parameter, matching `handleRelease()`'s own pre-existing (unparameterised)
  logging posture -- the new tests assert the resulting STATE, not the log line's exact text.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The CR-01 regression test's literal mechanics needed a retry loop the plan's action text did not specify**

- **Found during:** Task 1 (writing and first running the CR-01 regression test against the FIXED
  code, to confirm GREEN)
- **Issue:** The plan's action text specifies calling `handleAcquire("race-a", ...)` and
  `handleAcquire("race-b", ...)` once each, back to back, then `Promise.all`-ing both, expecting
  BOTH to report `ok: true` with each caller's own cold-spawn factory invoked exactly once. Against
  the FIXED code, this deterministically produced `{ok:false, reason:"launch_in_flight"}` for the
  second caller -- not a CR-01 regression, but a collision with `acquirePortAndLaunch()`'s own
  pre-existing, correct single-in-flight-launch guard (criterion C), which `handleAcquire()`'s
  cold-launch arm cannot bypass (it always calls the PRODUCTION `nextFreePort()`, with no
  injectable allocator in `HandleAcquireDeps`). Traced via explicit microtask-ordering analysis and
  confirmed by direct observation of the failure (`{ok:false, reason:"launch_in_flight"}`) before
  concluding this was a legitimate, unrelated serialisation rather than a fix defect.
- **Fix:** Wrapped each caller's `handleAcquire()` call in a small retry helper that re-invokes the
  SAME call when (and only when) the outcome is `{ok:false, reason:"launch_in_flight"}`, mirroring
  the exact behaviour `handleAcquire()`'s own header comment documents for the real control plane
  ("broker-control.mts's own attemptAcquire()/enqueueAcquire() queue the request and retry it later
  rather than refusing it"). This test calls `handleAcquire()` directly, bypassing that
  control-plane retry layer, so it performs the same retry itself.
- **Files modified:** `.claude/mcp/vice/vice-broker-acquire.test.ts`
- **Verification:** The test passes GREEN with the retry in place; without it, the SAME test fails
  deterministically with `launch_in_flight` (confirmed by removing the retry temporarily during
  investigation and observing the failure, then restoring it).
- **Committed in:** `5aff2e2` (Task 1 commit)
