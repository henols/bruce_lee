# Phase 01.6.2.1: Code Review Report

**Reviewed:** 2026-08-04T00:00:00Z
**Depth:** standard (with cross-file call-chain tracing on the acquire concurrency path, per explicit review instruction)
**Files Reviewed:** 15
**Status:** issues_found

## Summary

This phase's core deliverable — `handleAcquire()`/`selectWarmInstance()` in `vice-broker.mts`
consulting the warm pool before cold-launching, with a grant-time re-probe and a
recorded-state recheck meant to prevent a double-grant under concurrent acquires — is
extensively unit- and end-to-end tested, and the tests that exist all pass against the stated
scenarios. However, tracing the actual concurrency guarantee the code claims (`selectWarmInstance()`'s
own header comment: "no await between selection and the grant-recording step... proven under
two concurrent acquires") against what the recheck literally tests turned up a real gap: the
recheck only detects a candidate that a *sibling acquire already granted*, not one that a
*sibling acquire already dropped-and-killed after a failed grant-time probe*. Because the
drop path never changes `record.state` (it only deletes the map entry and marks
`deliberateKill`), a second, concurrent `selectWarmInstance()` walk holding the same stale
object reference can still hand back a candidate that is being torn down by another request,
producing an orphaned grant whose port can later be reassigned out from under it — including,
in the worst case, a later `release()` on the stale grant killing an unrelated live instance
that has since taken over the same port number. This is the highest-risk finding in this
review and is filed as a BLOCKER.

Four further, lower-severity issues were found: an acquire-time capacity check that can refuse
a request even when an idle, ready instance could satisfy it without exceeding the ceiling; a
grant-time probe failure that blocks the *whole* acquiring request behind a synchronous,
multi-second `verifiedKill()` wait per failed candidate; a cold-launch failure path
(`pid === null`) that reports an error to the caller while leaving the broken instance record
in `state.instances` to be cleaned up only indirectly, later, by crash supervision; and a
module-level mutable variable in the warm-launch epoch-writing path that is currently safe only
because of an invariant enforced elsewhere, with no local guard of its own.

The env-var alias drop (`VICE_BROKER_SPARES` → `VICE_BROKER_WARM_FLOOR`), the 1s probe timeout
default, and the two mirrored warm-floor/ceiling readers were all specifically checked for
drift and are consistent with each other and with the project's stated intent; none of those
are filed as findings.

## Critical Issues

### CR-01: `selectWarmInstance()`'s post-probe recheck does not detect a candidate a concurrent acquire already dropped and killed, allowing a double-managed/orphaned grant and a later cross-session kill

**File:** `.claude/mcp/vice/vice-broker.mts:371-405` (the recheck at line 386; the drop path at lines 392-402); consumed by `handleAcquire()` at `.claude/mcp/vice/vice-broker.mts:435-493`. The generated artifact carries the identical logic at `.claude/mcp/vice/resources/vice-broker.mjs:278` (`selectWarmInstance`) and `:319` (the `atCapacity` gate) — do not edit that file; the fix belongs in the `.mts` source above.

**Issue:**

`handleAcquire()` has no mutual-exclusion around `selectWarmInstance()` — the module-level
`inFlight` guard (`broker-launch.mts`) only serialises the *cold-launch* path
(`acquirePortAndLaunch`), and `broker-control.mts`'s `attemptAcquire()` calls `onAcquire()`
(i.e. `handleAcquire()`) independently per connection with no queuing until a launch is
already in flight. So two acquire requests arriving on two different TCP connections can run
two concurrent `selectWarmInstance()` walks over the same `state.instances` map at once.

`selectWarmInstance()`'s own header comment states the reason the design is safe under two
concurrent acquires: "a candidate's own probe response cannot change because a sibling acquire
granted it first, but its RECORDED state does, the instant that sibling's synchronous grant
step runs -- and that recorded state is the only signal this function is willing to trust."
That reasoning is correct for the *grant* path (`record.state` becomes `"granted"`
synchronously in `handleAcquire()`, so a sibling's post-probe recheck
`if (record.state !== "ready") continue;` correctly rejects an already-granted candidate).

It is **not** correct for the *drop* path. When a grant-time probe fails
(`vice-broker.mts:388-402`), the candidate is removed from `state.instances` via
`state.instances.delete(record.port)`, and `markDeliberateDeath(record, false)` sets
`deliberateKill`/`respawnAfterKill` — but **`record.state` itself is never changed**; it
remains `"ready"` on the now-orphaned object. A concurrent `selectWarmInstance()` call that
snapshotted the same record (`Array.from(state.instances.values())` at line 379, taken before
the first call's delete) and is awaiting its own probe on the very same port can have its probe
resolve `true` (a real race under load — a slow/contended host is exactly the scenario
`CONTROL_ACQUIRE_TIMEOUT_MS` was just raised from 25s to 120s to tolerate), pass its own
recheck (`record.state !== "ready"` is still false, since it was never set to anything else),
and return this record as the winner at line 389 — even though the process behind it is
concurrently being SIGTERM'd/SIGKILL'd by the sibling call's `deps.kill(...)` at line 394.

`handleAcquire()` then does, with no further await:
```js
state.grants.set(requestId, { id: requestId, port: record.port, grantedAt: Date.now() });
record.state = "granted";
```
This records a grant for a port whose instance object is no longer in `state.instances` at
all. The caller is handed a `url`/`epochFile` pointing at a process that is being torn down or
is already dead. Worse, because the port is no longer in the map, `nextFreePort()` can
legitimately reallocate that same port number to a brand-new, unrelated instance. If the
holder of the orphaned grant later calls `release`, `handleRelease()`
(`vice-broker.mts:632-646`) looks up `state.instances.get(grant.port)` — which by then may be
the *new, unrelated* instance occupying that port — and kills **that** instance
(`markDeliberateDeath` + `verifiedKill`), even though it may be granted to, and actively used
by, a completely different session. This is a genuine cross-session data-loss/availability
risk, not merely a theoretical race: the project's own emulator-access rules single out exactly
this failure shape ("a session whose broker dies must be restarted, not resumed") as the class
of incident worth a mandatory startup banner.

No existing test exercises this scenario: `vice-broker-acquire.test.ts`'s two-candidate test
("a failed grant-time probe on the first of two ready records...") uses a single,
non-concurrent `handleAcquire()` call, and no test in `broker-launch.test.ts` or
`broker-control.test.ts` runs two `selectWarmInstance()`-driven acquires concurrently against a
shared candidate whose probe outcomes differ between the two callers.

**Fix:**

Recheck map membership, not merely the `state` field, before trusting a probe-live candidate —
this closes both the already-granted case (the map entry for that port is now a *different*
object, since a grant does not delete the record from `state.instances`... actually granting
does not remove the entry either, so the state-field check alone is fine for that case; the fix
below is needed specifically for the delete case) and the already-dropped case:

```js
async function selectWarmInstance(state, deps) {
  for (const record of Array.from(state.instances.values())) {
    if (record.state !== "ready") continue;

    const isReady = await deps.probe(record.port);

    // A sibling acquire may have granted OR dropped this exact candidate
    // while this probe was in flight. "Granted" changes record.state;
    // "dropped" removes the record from state.instances outright and never
    // touches record.state -- so map membership must be rechecked too, not
    // merely the state field.
    if (record.state !== "ready" || state.instances.get(record.port) !== record) {
      continue;
    }

    if (isReady) {
      return record;
    }
    ...
```
Add a regression test that drives two overlapping `selectWarmInstance()`/`handleAcquire()`
calls against one shared candidate, where the first caller's probe resolves `false` (drop path)
and the second caller's probe resolves `true` after the first has already deleted the record —
proving the second caller falls through to a cold launch instead of returning the deleted
record.

## Warnings

### WR-01: `atCapacity()` refuses an acquire before ever consulting the warm pool, denying requests the pool could satisfy at zero additional cost

**File:** `.claude/mcp/vice/vice-broker.mts:423-426`

**Issue:** `handleAcquire()`'s own header comment states the intent plainly: "`atCapacity()`
runs before EITHER arm, so a full host refuses before ever walking the pool or touching the
port allocator." `atCapacity()` (`broker-state.mts:342-349`) is `countTotal(state) >= ceiling`,
and `countTotal()` counts every instance regardless of state — `launching`, `ready`, *and*
`granted`. If the ceiling (`VICE_BROKER_MAX`, default 16) is reached while some of those
instances are idle, probe-live `ready` spares, a fresh acquire is refused with `at_capacity`
even though granting one of those spares would not create a new instance and would not push
`countTotal()` any higher. The ceiling exists to bound concurrent emulator *processes*, not to
bound how many of those processes may be *handed out*; refusing to hand out an already-existing
idle one is a real availability bug, not merely a documented tradeoff — the comment documents
*what* the code does, not why doing so at a busy-but-not-actually-full host is correct. No test
in this phase (or the pre-existing `broker-control.test.ts` `at_capacity` test, which only
checks the control-plane's own error-code wiring against a stubbed `onAcquire`) exercises "at
the ceiling, with a ready spare available."

**Fix:** Only let `atCapacity()` gate the cold-launch arm, e.g. check it after
`selectWarmInstance()` returns `null`, or thread it as a precondition on the
`acquirePortAndLaunch()` call rather than on `handleAcquire()`'s own entry:
```js
export async function handleAcquire(requestId, stateDir, state, deps = {}) {
  const winner = await selectWarmInstance(state, { probe, kill, log });
  if (!winner && atCapacity(state)) {
    return { ok: false, reason: "at_capacity" };
  }
  ...
```

### WR-02: A grant-time probe failure blocks the acquiring request behind a synchronous, per-candidate `verifiedKill()` wait, undermining the warm floor's own "fast grant" purpose

**File:** `.claude/mcp/vice/vice-broker.mts:392-402` (the `await deps.kill(...)` inside `selectWarmInstance()`'s loop); `verifiedKill()` itself at `.claude/mcp/vice/broker-kill.mts:123-158`.

**Issue:** Unlike `handleRelease()` (`vice-broker.mts:641-645`), which fires `verifiedKill()`
and explicitly does **not** await it ("fire-and-forget from the control listener's close
handler's own perspective"), `selectWarmInstance()`'s drop path *does* await
`deps.kill(...)` before moving on to the next candidate. `verifiedKill()` issues SIGTERM and
then polls every 200ms up to `killWaitS` (default `VICE_BROKER_KILL_WAIT_S`, 5s) before
escalating to SIGKILL and returning. If a candidate's probe fails because the underlying
process has genuinely wedged (not merely booting slowly), the acquiring request now waits up to
~5 seconds *per dead candidate* before the walk can continue to the next `ready` record or fall
through to a cold launch — turning what the warm floor exists to make a fast, in-memory grant
into a multi-candidate, multi-second serial teardown on the hot path of a single request. This
is bounded well inside the raised `CONTROL_ACQUIRE_TIMEOUT_MS` (120s), so it will not time out,
but it directly contradicts the design intent (fast grants from a pre-warmed pool) and is easy
to trigger simply by having more than one simultaneously-wedged spare.

**Fix:** Either kill a failed candidate fire-and-forget (matching `handleRelease()`'s own
posture) and continue the walk immediately, or cap the number of candidates a single acquire
will wait through before falling back to a cold launch regardless of how many `ready` records
remain unvisited.

### WR-03: A cold launch whose spawned child never gets a pid leaves its broken record in `state.instances`, cleaned up only indirectly via crash supervision, rather than at the point the failure is detected

**File:** `.claude/mcp/vice/vice-broker.mts:465-470`

**Issue:**
```js
if (!result.ok) {
  return { ok: false, reason: result.reason };
}
if (result.record.pid === null) {
  return { ok: false, reason: "internal" };
}
record = result.record;
```
`acquirePortAndLaunch()` → `spawnAndRecordInstance()` (`broker-launch.mts:132-159`)
unconditionally calls `deps.state.instances.set(port, record)` *before* returning, regardless of
whether `child.pid` came back non-null. When `pid === null` (e.g. the resolved `VICE_BIN` binary
doesn't exist and Node's `spawn()` fails to fork), `handleAcquire()` tells its caller `internal`
and returns — but the broken `"launching"` record it just rejected is still sitting in
`state.instances`, occupying a port and counting toward `countTotal()`/`atCapacity()`. Because
the cold-launch spawn factory always wraps `spawn` through `withCrashSupervision()`, an eventual
`"exit"` event on the failed child *should* still route through `handleExit()` and either
respawn-with-backoff or eventually give up — but that is an indirect, delayed cleanup path the
caller who was already told "internal error" has no visibility into, and it treats a
configuration failure (bad binary path) identically to a real crash, retrying it up to
`VICE_MAX_RESTARTS` times before the port is freed.

**Fix:** When `result.record.pid === null`, delete the just-created record from
`state.instances` (and best-effort verify it's actually gone, e.g. via `verifiedKill` with the
recorded — likely null/absent — pid) before returning `internal`, so the failure is fully
resolved at the point it is detected rather than deferred to crash supervision's retry/backoff
machinery.

### WR-04: `lastWarmLaunchLogRelPath` is module-level mutable state with no guard of its own; correctness depends entirely on an invariant enforced elsewhere

**File:** `.claude/mcp/vice/vice-broker.mts:603, 619` (declaration and write site)

**Issue:** `maintainWarmFloorForRealBroker()`'s `spawnFactory` closure stashes the freshly
opened log's relative path into a **module-scope** `let lastWarmLaunchLogRelPath = ""` (line
619), which the `onLaunched` callback then reads (line 614) to write the epoch record. This is
safe today only because (a) `maintainWarmFloor()` launches at most one instance per call, and
(b) `run()`'s own `passInFlight` guard ensures `maintainWarmFloorForRealBroker()` is never
invoked concurrently with itself. Neither invariant is enforced, checked, or even referenced
at the point this variable is declared — a future change to either (e.g. a second periodic
pass, or a direct external call to `maintainWarmFloorForRealBroker()` for diagnostics) would
silently corrupt this value with no compiler or runtime signal, exactly the "correct module,
never called correctly" failure shape this same phase's own commentary elsewhere calls out
(Defect 5). Contrast with the cold-launch path's `lastLogRelPath`, which is a `let` scoped
*inside* `handleAcquire()`'s own call and therefore cannot leak across calls.

**Fix:** Scope this the same way the cold-launch path does — pass a local variable (or a small
mutable object) into the closure created fresh on each call to `maintainWarmFloorForRealBroker()`
rather than closing over module state, removing the cross-call sharing risk entirely regardless
of how many invariants elsewhere currently happen to protect it.
