## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 -- Test-writing correctness] Corrected the priority test's own probe stub, which initially defeated the test for an unrelated reason**
- **Found during:** Task 2, writing the priority test
- **Issue:** A first draft used `makeWarmFloorDeps()`'s own default `probe: () => Promise.resolve(true)` for a scenario where an acquire's own cold launch had just landed a "launching" record before `maintainWarmFloor()` ran in the same pass. Because that stub resolves ready immediately, `maintainWarmFloor()`'s own step 1 (promote every launching instance whose probe now succeeds) promoted the freshly-landed acquire instance to `ready` within the same call, zeroing `countLaunching()` before step 2's gate was reached -- so the function proceeded to warm a second, genuinely unwanted spare. This is not a bug in `maintainWarmFloor()` (a real emulator does not boot and answer inside one synchronous pass); it was a test-authoring trap.
- **Fix:** Gave that one test's own `maintainWarmFloor` call a `probe: () => Promise.resolve(false)` stub (still booting within this pass), matching the same idiom the already-landed "a pass overlapping an in-flight launch produces no second spawn" test already uses for this exact scenario.
- **Files modified:** `.claude/mcp/vice/broker-launch.test.ts`
- **Verification:** Test passes; the discriminating-power demonstration (inverted pass order) confirms the test still fails for the RIGHT reason once the stub is corrected.
- **Committed in:** `9787fa2` (Task 2 commit)
- **Logged to RE-FINDINGS.md** (`5731536`) as a confirmation/hazard finding, since this is a trap any future test against `maintainWarmFloor()` in a similar scenario could re-hit.
