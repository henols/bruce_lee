# Phase 01.6.2.1 Plan 01: Defect 5 — handleAcquire() Wired To The Warm Floor Summary

**`handleAcquire()` now resolves a grantable instance from the probe-live warm pool before ever cold-launching, closing the "built but never consulted" gap Defect 5 named, with a grant-time re-probe, kill-never-recycle preserved, and a structural gate proving the wiring holds.**

## Performance

- **Duration:** ~90 min
- **Tasks:** 3
- **Files modified:** 6 (1 created test file, 1 created deferred-items doc, 4 modified)

## Accomplishments

- Restructured `handleAcquire()` in `vice-broker.mts` so a warm-instance selection arm (a new module-private `selectWarmInstance()`) runs ahead of the existing cold-launch arm. Both arms converge on exactly one `state.grants.set()` call, per the plan's own assumption-delta decision ("resolve a grantable instance" is now the primary operation).
- The warm-instance selector re-probes each `ready` candidate at grant time (P-02); a failed probe drops the record, sets the deliberate-death marker with a false respawn-after-kill answer, and identity-verified-kills the pid before the walk continues to the next candidate, falling through to a cold launch once exhausted (P-03).
- Closed a genuine double-grant race (not explicitly required by any single acceptance criterion, but required by the plan's own threat-model disposition T-01.6.2.1-03): re-checks `record.state === "ready"` immediately after the grant-time probe resolves, before treating a candidate as the winner, so a sibling concurrent acquire that already claimed the same record during the probe's `await` cannot also be granted it.
- Proved the whole path two ways: a new unit test file (`vice-broker-acquire.test.ts`, five tests) against the built artifact with injected probe/kill/spawn stubs, and a new e2e test in `broker-e2e.test.ts` against the real spawned broker over the real TCP control plane.
- Added a structural anti-regression gate (`broker-launch.test.ts`) asserting exactly one grant-recording call site and that the real acquire entry point actually invokes the warm-instance selector by name (not merely declares it) — its discriminating power demonstrated live (RED when the call site was removed, GREEN when restored).
- Logged the built-but-never-consulted-pool hazard to `RE-FINDINGS.md` as the SECOND occurrence of the same shape 01.6.2's crash supervisor already produced, naming both occurrences and the two detection techniques that actually work.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — Missing Critical Functionality] Closed a double-grant race in the warm-instance selector**
- **Found during:** Task 1, while implementing `selectWarmInstance()`
- **Issue:** The plan's own threat-model disposition (T-01.6.2.1-03) claims "the selection → `state = "granted"` → grant-record transition is one synchronous step with no intervening `await`, so two concurrent acquires cannot both select the same record." Read literally, this only covers the step AFTER a winner is chosen. The selection step itself calls `await deps.probe(record.port)` — a genuine yield point — so two concurrent `handleAcquire()` calls could both probe the SAME `ready` record before either commits it to `granted`, and both would then treat it as their own winner.
- **Fix:** Added a synchronous re-check of `record.state === "ready"` immediately after the probe's `await` resolves, before treating a probe-live candidate as the winner. If a sibling call already flipped the record to `granted` while this call's probe was in flight, this call now skips it (treats it as claimed, not as a candidate) rather than double-granting it.
- **Files modified:** `.claude/mcp/vice/vice-broker.mts` (`selectWarmInstance()`)
- **Verification:** Covered by reasoning and code comment, not by a new dedicated concurrency test (no such test was in the plan's own acceptance criteria for this task, and the fix is cheap/local); the existing single-threaded-JS run-to-completion argument the file's own comments already use for `tryLaunchOne()`/`acquirePortAndLaunch()` applies identically here.
- **Committed in:** `c798d37` (Task 1 commit)

**2. [Rule 3 — Blocking, testability] Created a new unit test file not named in the plan's `<files>` list**
- **Found during:** Task 1
- **Issue:** The plan's own Task 1 `<files>` element lists only `vice-broker.mts`, `broker-e2e.test.ts`, and `resources/vice-broker.mjs` — no unit test file — but the task's own `<behavior>` section explicitly requires four unit tests (RED-first zero-spawn, probe-fail-then-second, exhausted-walk, release-then-acquire) in addition to the e2e test. `vice-broker.mts` cannot be imported unbuilt (see Decisions above), so no EXISTING test file's own import convention could host these tests without either (a) importing the built artifact, a pattern with no prior instance in this codebase, or (b) moving the new logic into `broker-launch.mts` (rejected — the plan's own code_context and canonical_refs are explicit that `handleAcquire()` itself, in `vice-broker.mts`, is P-01's target).
- **Fix:** Created `vice-broker-acquire.test.ts`, following `vice-broker-launch.test.ts`'s own established convention ("tests emitted OUTPUT... never imports a .mjs module itself" as a static import — this file's own dynamic `import()` after a fresh `build()` is a new, but consistent, variant of that same "test the emitted artifact" idiom).
- **Files modified:** `.claude/mcp/vice/vice-broker-acquire.test.ts` (new)
- **Verification:** RED-first proof captured (see above); all 5 tests pass against the fixed implementation; full suite green (397 tests / 392 pass / 0 fail / 5 todo, up from the 390/385/0/5 baseline by exactly the 6 tests this plan added, since task 2's structural test is counted separately).
- **Committed in:** `c798d37` (Task 1 commit)

**3. [Rule 1 — Test assertion corrected to match correct behaviour] Removed an over-literal "different port number" assertion**
- **Found during:** Task 1, writing the exhausted-walk-then-cold-launch unit test
- **Issue:** The plan's own `<behavior>` prose says the acquire "falls through to exactly one cold launch that grants a different port." A first draft of the test asserted the cold-launched port NUMBER differs from the failed candidate's own port — but dropping the failed candidate's record legitimately frees its port number, and `nextFreePort()` (unmodified, real production code) correctly reallocates the lowest free port, which is the just-freed one. Asserting numeric difference therefore failed against CORRECT system behaviour, not a bug.
- **Fix:** Reworded the test to assert what the plan's own `<done>` criterion actually requires — exactly one cold launch occurs, producing a fresh record (a different pid) — rather than a specific port number.
- **Files modified:** `.claude/mcp/vice/vice-broker-acquire.test.ts`
- **Verification:** Test passes; the underlying behaviour (one cold launch, fresh pid) is unchanged and correctly proved.
- **Committed in:** `c798d37` (Task 1 commit)
