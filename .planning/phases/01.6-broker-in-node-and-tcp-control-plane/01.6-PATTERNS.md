## Pattern: The TDZ Load-Order Hazard (`install-resources.mjs` / `repo-root.mjs`)

Quoted verbatim — this comment must survive the port unchanged in meaning, and the forbidden action it
names must not be reintroduced by an agent that doesn't understand why:

```javascript
// HOSTING CHOICE (D-3): this check lives in a DEDICATED module, triggered
// from repo-root.mjs, for two reasons. First, repo-root.mjs is a pure path
// resolver, and inlining filesystem-writing side effects into it would make
// every importer of a path function also a file writer. Second and decisive:
// this module needs the repo root, and repo-root.mjs is where the repo root
// is computed -- hosting this logic INSIDE repo-root.mjs and importing it
// back from there would be a module cycle. In that cycle, this module would
// evaluate while repo-root.mjs's `const HERE` is still in its temporal dead
// zone, and every entry point would die with
// "Cannot access 'HERE' before initialization".
//
// THE CYCLE IS AVOIDED STRUCTURALLY: this module takes the repo root as an
// ARGUMENT and imports NOTHING from repo-root.mjs. Do not "clean this up" by
// adding `import { repoRoot } from "./repo-root.mjs"` here -- that importable
// convenience is exactly the cycle described above.
```
(`.claude/mcp/vice/install-resources.mjs` lines 6-18)

RESEARCH.md §E live-reproduced this crash and found the critical nuance: **a lazy call (from inside a
function body, invoked later) does NOT crash** — only a top-level-synchronous call does. This means a
runtime test cannot categorically catch a reintroduction of the forbidden import; only a static
source-text/AST check can. The concrete test to port/write (from RESEARCH.md §E(c)):

```typescript
test("install-resources.ts never imports from repo-root -- see its own header comment", () => {
  const src = readFileSync(new URL("./install-resources.ts", import.meta.url), "utf8");
  assert.ok(
    !/from\s+["']\.\/repo-root(\.[jt]s)?["']/.test(src),
    "install-resources.ts must not import from repo-root.ts -- this reintroduces the TDZ cycle..."
  );
});
```

**A genuine NEW risk TypeScript introduces here:** `import type { repoRoot } from "./repo-root.ts"` is
completely erased at compile/strip time (verified live) — a well-meaning contributor could believe
"it's just a type import, safe" and be right by accident, while a plain value import of the same
specifier reintroduces the hazard. The static check above must reject the import syntactically
regardless of `type` keyword presence — do not special-case `import type` as safe.

## Pattern: Identity-Verified Kill (Phase 01.3 criterion 6, reused not re-derived)

Lives today in `resources/vice-broker.sh` (`signal_recorded_pid()`, lines 1519-1548; also duplicated at
`teardown()`, lines ~1470-1500, and again at shutdown time, ~2044-2053). Exact discipline: `kill -0`
(liveness) → `ps -o args=` (identity match against `$SUPERVISOR_SCRIPT`, guards against pid reuse) →
`kill -TERM` → poll `kill -0` on a timeout → `kill -KILL` escalation. Excerpt:

```bash
signal_recorded_pid() {
  local pid="$1" label="$2"
  [ -n "$pid" ] && [ "$pid" != "null" ] || return 1
  kill -0 "$pid" 2>/dev/null || return 1

  local args
  args="$(ps -o args= -p "$pid" 2>/dev/null || true)"
  case "$args" in
    *"$SUPERVISOR_SCRIPT"*)
      ;;
    *)
      echo "vice-broker: refusing to signal pid $pid for $label -- ps reports \"$args\", which does not match $SUPERVISOR_SCRIPT (possible pid reuse)" >&2
      return 1
      ;;
  esac

  kill -TERM "$pid" 2>/dev/null || true
  local waited_ms=0 limit_ms=$((VICE_BROKER_KILL_WAIT_S * 1000))
  while kill -0 "$pid" 2>/dev/null; do
    if [ "$waited_ms" -ge "$limit_ms" ]; then
      echo "vice-broker: pid $pid ($label) did not exit within ${VICE_BROKER_KILL_WAIT_S}s of SIGTERM -- sending SIGKILL" >&2
      kill -KILL "$pid" 2>/dev/null || true
      break
    fi
    sleep 0.2
    waited_ms=$((waited_ms + 200))
  done
}
```
(`resources/vice-broker.sh` lines 1519-1548)

RESEARCH.md §D1 already worked out the TypeScript equivalent (reuse this, do not re-derive):

```typescript
import { execFileSync } from "node:child_process";

function isAlive(pid: number): boolean {
  try { process.kill(pid, 0); return true; } catch { return false; }
}

function identityMatches(pid: number, expectedSubstring: string): boolean {
  try {
    const args = execFileSync("ps", ["-o", "args=", "-p", String(pid)]).toString();
    return args.includes(expectedSubstring);
  } catch { return false; }
}

async function verifiedKill(pid: number, expectedSubstring: string, graceMs = 3000): Promise<void> {
  if (!isAlive(pid)) return;
  if (!identityMatches(pid, expectedSubstring)) {
    console.error(`refusing to signal pid ${pid} -- identity check failed (possible pid reuse)`);
    return;
  }
  process.kill(pid, "SIGTERM");
  const deadline = Date.now() + graceMs;
  while (isAlive(pid) && Date.now() < deadline) {
    await new Promise((r) => setTimeout(r, 100));
  }
  if (isAlive(pid)) process.kill(pid, "SIGKILL");
}
```

## Pattern: The Single `in_flight` Owner (`vice-broker.sh` `process_requests()`)

Excerpt (`resources/vice-broker.sh` lines ~1259-1273), the exact guard that exists because a
2026-08-01 defect launched three `x64sc` processes at once:

```bash
  # A single in-flight flag, initialised ONCE before the loop from
  # count_launching() -- the SAME counter maintain_spares() below also
  # consults, so the two launch paths (this cold-launch path and
  # maintain_spares' warm-spare path) can never disagree about whether a
  # boot is already under way. Two counters that could disagree is exactly
  # how the two launch paths raced each other back into the 2026-08-01
  # outage (three simultaneous x64sc launches); there is now exactly one.
  if [ "$(count_launching)" -gt 0 ]; then
    in_flight=1
  else
    in_flight=0
  fi
  ...
    if [ "$in_flight" -eq 1 ]; then
      echo "vice-broker: request $id -- a launch is already in flight, awaiting readiness before granting or denying" >&2
      continue
    fi
```

**Under an event loop this must NOT become an async mutex library.** RESEARCH.md §D2's recommended
Node idiom — a plain module-level boolean, checked and set synchronously with **no `await` between the
check and the set**:

```typescript
let launchInFlight = false;

async function tryLaunchOne(): Promise<void> {
  if (launchInFlight) return;      // synchronous check -- no await has run since the last set
  launchInFlight = true;           // synchronous set -- this pair cannot be interleaved
  try {
    await spawnOneInstance();      // the only place awaiting is allowed
  } finally {
    launchInFlight = false;
  }
}
```

**The risk to name explicitly in the plan:** any future edit that inserts an `await` between the check
and the set silently reintroduces the exact race this flag exists to prevent. A dedicated test firing
two concurrent launch requests and asserting exactly one spawn occurs is a Wave 0 gap (RESEARCH.md's
own list) — reproduce the 2026-08-01 scenario's shape with a stubbed spawn function, no real `x64sc`.

## Pattern: `--once` and `VICE_BROKER_PROBE_CMD` — the Seams Every Test Drives

Both are environment/argument-driven seams in `vice-broker.sh` today, confirmed present and load-bearing:

- **`--once`**: short-circuits the daemon's normal poll loop to exactly one pass, explicitly forbidden
  in combination with `--detach` ("there is nothing to detach"). Tests drive it via
  `execFileP("bash", [BROKER_SCRIPT, "--once", "--dry-run"], ...)` (`vice-broker.test.mjs` line 241).
- **`VICE_BROKER_PROBE_CMD`**: injectable readiness-probe seam, invoked as `"$VICE_BROKER_PROBE_CMD"
  "$port"` (`resources/vice-broker.sh` line 885). When unset and no `curl` exists, zero speculative
  spares are warmed and the reason is logged (line 1405).

**What preserving them means in TypeScript:** both must remain environment/argument-driven seams in
the compiled broker, not conditionally-compiled test-only code paths — `--once` maps to a
`process.argv` flag the broker parses exactly as bash does; `VICE_BROKER_PROBE_CMD` stays a
`process.env` read at the exact readiness-probe call site. This is a low-risk, straightforward port
(RESEARCH.md §D4, HIGH confidence) — the danger is an agent "simplifying" these into hardcoded
test-mode branches instead of preserving them as real seams.

## Pattern: Hand-Rolled JSON Helpers — Concretely What "Replaced by Real JSON" Means

`resources/vice-broker.sh` hand-rolls JSON because bash has no native JSON support. Example
(`json_escape()`, lines 561-566):

```bash
json_escape() {
  local s="$1"
  s="${s//\\/\\\\}"
  s="${s//\"/\\\"}"
  printf '%s' "$s"
}
```

and the atomic-write choke point every protocol file goes through (`write_json_atomic()`, lines
603-611):

```bash
write_json_atomic() {
  local final_path="$1" content="$2" tmp
  tmp="$final_path.tmp"
  : >"$tmp"
  chmod 600 "$tmp"
  printf '%s\n' "$content" >"$tmp"
  mv "$tmp" "$final_path"
}
```

These, plus `extract_id_field()`/`extract_op_field()`/`extract_target_id_field()` (grep-against-known-
shape field readers, since bash has no `jq` dependency) and `read_spare_field()`/`read_grant_field()`/
`read_epoch_field()` (lines 654-814), **all disappear entirely** once the broker is TypeScript —
`JSON.parse`/`JSON.stringify` replace every one of them. The planner should NOT expect a 1:1 function
mapping for this category; it collapses to native JSON calls, wrapped in the never-throw discipline
below. The one thing that must survive is the **atomicity discipline** (write to a deterministic
`.tmp` sibling, `chmod 600` before content, then rename) — port that as `fs.writeFileSync(tmp, ...)` +
`fs.renameSync(tmp, final)`, not as a bare `writeFileSync(final, ...)`.

## Shared Pattern: "Never Throw on Untrusted File Read"

Established project-wide discipline (confirmed by header comments in `vice-pool.mjs` and
`vice-broker-client.mjs`, and already cited in `01.2-PATTERNS.md`'s "Never-throw / never-cache-a-
negative-result" section per `vice-broker-client.mjs`'s own comment). Concrete instance
(`.claude/mcp/vice/vice-broker-client.mjs`, the `readJsonMaybe`-shaped helper near line 95-115):

```javascript
/** Read and JSON.parse `path`, treating any failure (missing file, partial
 * write, malformed JSON, non-object shape) as "not there yet" rather than
 * throwing -- matches vice-pool.mjs's readRegistry() posture exactly. */
function readJsonMaybe(path) {
  let raw;
  try {
    raw = readFileSync(path, "utf8");
  } catch {
    return null;
  }
  try {
    const parsed = JSON.parse(raw);
    return parsed && typeof parsed === "object" ? parsed : null;
  } catch {
    return null;
  }
}
```

**Apply to:** every converted file that reads a file the other side of the container/host trust
boundary writes (`vice-broker-client.ts`, the folded-in broker's own reads of anything the proxy
writes, `repo-root.ts`/epoch readers). **Failure mode to guard against explicitly in review:** an
agent-driven port that "cleans up" a try/catch it doesn't understand the purpose of — collapsing the
two-layer try (file-read failure vs. JSON-parse failure) into one, or replacing `return null` with a
thrown error because "TypeScript likes explicit errors," silently turns a designed degrade-gracefully
path into a crash path. RESEARCH.md's Security Domain section names this exact pattern under "Malformed/
half-written state file read as a crash-inducing input" (STRIDE: Denial of Service).
