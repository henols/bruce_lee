<decisions>
## Implementation Decisions

### MCP library adoption

- **D-01 [deferred]: Adopt the Mastra MCP packages, tracked in Phase 01.6.3 not here.** The developer's decision, taken *after*
  being shown RESEARCH.md §B's HIGH-confidence recommendation against it. The recommendation is
  overridden, not unread. **Owned by Phase 01.6.3** after the 2026-08-02 split. What it carries:
  - `@mastra/mcp`'s `MCPServer` peer-depends on `@mastra/core` (~59 MB unpacked, 33 direct
    dependencies — verified via `npm view`). This is the first runtime dependency this repo has ever
    had. Legitimacy verification is part of the work, not an assumption — both packages were flagged
    `[SUS]` on a weak "too-new" heuristic and need a blocking, non-auto-approvable human checkpoint.
  - Research measured that a generic MCP SDK replaces only ~150–300 of `vice-proxy.mjs`'s 2,441
    lines (~6–12%: JSON-RPC framing, `handleInitialize()`, the `handleToolsCall()` routing skeleton).
    The remaining ~88–94% — broker leasing, epoch/liveness, recycle/diagnose, deny-list enforcement,
    path rewriting, incident capture — is untouched by any SDK and must keep working across the
    swap. Plan the seam, not a rewrite.
  - **CORRECTION, 2026-08-02 (planner finding).** This decision originally read *"the dependency must
    be bundled/vendored into the emitted JS that `install-resources.mjs` deploys."* **That premise was
    factually wrong.** `install-resources.mjs` deploys only `resources/` — five shell scripts —
    and `vice-proxy.mjs` **never reaches the host at all**; the broker speaks the file protocol, not
    MCP. Criterion 3's host clause is therefore satisfiable *without* a bundler, via the check
    VALIDATION.md already states. The bundling deliverable is not dropped, it is **relocated** — see
    D-06.

- **D-04 [deferred]: The per-instance restart-epoch file survives as a second on-disk exception, written by the broker, contract unchanged — tracked in Phase 01.6.2 not here.**
  Raised by RESEARCH.md §D3 and decided in session; neither the design
  note nor the ROADMAP had named it. `readEpoch()`'s entire value is a liveness check costing zero
  MCP traffic, which requires *some* on-disk record — and today `vice-supervisor.sh`'s `write_epoch()`
  writes it, a process D-1 folds away. So C4's "state in one place" has **two** file exceptions:
  `broker.json` for discovery, the epoch file for zero-traffic liveness. Format, location and
  semantics unchanged; only the writer moves. Redesigning the epoch check is transport-shaped work
  and stays in Phase 01.7. **Owned by Phase 01.6.2.**

- **D-05: `vice.mjs`'s CLI is deleted along with the `vice-pool` subsystem.** A consequence of D-02
  that no source artifact had recorded: `vice.mjs:659–660` dynamically imports `resolveInstance` from
  `vice-session.mjs` and calls it for **every** CLI verb except `session`/`pool`/`install` — so
  `ping`, `call` and `tools` break on deletion too, not just the two obviously-doomed subcommands.
  Rather than rework them, the CLI goes with the subsystem it depends on. This is consistent with
  D-02's own reasoning and with `skill-docs.test.mjs`'s standing assertion that no module in this
  directory is named in any agent-facing doc — *"no exemption, not even `vice.mjs`"*. The same
  zero-consumers confirmation gate covers it. **Owned by Phase 01.6.**

- **D-06 [deferred]: Whether to bundle is decided inside Phase 01.6.3, not assumed now and not tracked here.** With D-01's original
  premise corrected, the question changed shape. Bundling no longer protects criterion 3's host
  clause — it protects a **container-side** property: today the vice MCP server starts with zero
  dependencies, so a fresh clone works on bare `node`. A runtime `@mastra/mcp` dependency ends that,
  and the failure mode is severe — **the agent loses all emulator access on a clone that has not run
  `npm install`.** Two defensible answers: bundle and keep the property, or drop it deliberately and
  wire `npm install` into container provisioning. Leaving it undecided is not defensible, so it is
  recorded as the open question 01.6.3 must answer before it swaps the seam.

### Scope of the conversion inventory

- **D-02: `vice-pool.mjs`, `vice-pool.sh` and `vice-session.mjs` are deleted outright**, along with
  their tests — not converted, not preserved inert. The developer's decision against research's
  more conservative reading. Research established (MEDIUM confidence) that these are a **separate,
  older `registry.json`/lease subsystem** built for Phase 1's non-MCP recovery pipeline, with zero
  live importers outside the module tree and its own tests; the broker's *real* pool is its own
  warm-spares mechanism (`SPARES_DIR` / `maintain_spares()`), which does fold into the one process
  as D-1 intends.
  - **Precondition the planner must schedule before the deletion lands:** promote "zero live
    consumers" from MEDIUM to HIGH. The container cannot see host-side automation or a documented
    manual workflow that invokes them. This is a gate task, not a formality — it is the one thing
    standing between this decision and silently stranding Phase 1's dormant recovery pipeline.

- **D-03: The Phase 01.2 `D-1.2-B` contradiction is resolved in writing, not left silent.**
  `D-1.2-B` states these files are *"left entirely untouched… 'superseded in intent' is not 'safe to
  delete'."* D-02 overrides it. The override, its reasoning (Phase 1's 2026-08-01 replan rewrote
  plan 01-04 to go through `mcp__vice__*` tools exclusively, removing the consumer D-1.2-B was
  protecting), and its date must be recorded where a later reader meets the old decision — a
  ROADMAP annotation and/or an amendment to
  `.planning/notes/one-process-broker-in-typescript.md`. A locked decision reversed without a
  record is the failure mode this project already names for confidence grades.
