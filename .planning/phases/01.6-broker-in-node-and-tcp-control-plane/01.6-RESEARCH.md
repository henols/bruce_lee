## Summary

This phase converts ~16,522 lines of the `.claude/mcp/vice/` MCP-proxy-plus-broker tree — 13 `.mjs`
source files (6,426 lines), 8 `.test.mjs` files (10,096 lines), and 3 host-side shell scripts
(`vice-broker.sh` 2,103, `vice-pool.sh` 611, `vice-supervisor.sh` 443 = 3,157 bash lines) — into a
single TypeScript application that runs as **one process** on the host, replacing three host
processes (broker daemon + per-instance supervisors + pool commands) with one, while changing **no
transport and no protocol** (that is Phase 01.7). The container gets its first-ever `package.json`
and `tsconfig.json`; the host still needs only `node` and never `tsc`/`npm`.

Two findings should reshape how the planner slices this work more than anything else in the
ROADMAP's own risk list:

1. **`vice-pool.mjs`/`vice-pool.sh` (1,364 lines) is NOT the broker's warm-spare pool.** It is a
   separate, older, non-MCP subsystem serving the still-unexecuted Phase 1 recovery pipeline
   (`vice-session.mjs`, and `vice.mjs`'s CLI-only, agent-forbidden `session`/`pool` subcommands).
   Phase 01.2 explicitly declined to touch it (`D-1.2-B`: "left entirely untouched... superseded in
   intent is not safe to delete"). The design note's own conversion-inventory table lists
   `vice-pool.sh` as one of the three scripts that "retires, logic absorbed" into the one-process
   broker — that is very likely wrong, or at minimum needs an explicit decision this research could
   not find recorded anywhere. See **§A1** below; this is the single highest-value open question for
   the first plan to resolve, because getting it wrong either strands the Phase 1 recovery pipeline
   or ships a needless, disruptive rewrite of code nothing currently asks to change.
2. **The largest test file in the whole conversion (`vice-broker.test.mjs`, 2,685 lines, 61 tests)
   verifies `resources/vice-broker.sh` by spawning it as a real bash subprocess and inspecting its
   on-disk `grants/`/`spares/`/`requests/` output.** Once broker state moves in-process (criterion 4),
   the mechanism nearly all 61 of those tests are built on stops existing. This is not a syntax-level
   port; it is a from-scratch test redesign representing roughly a quarter of the whole test-suite
   conversion by line count. See **§D3** and **§Validation Architecture**.

On the developer's Mastra proposal (**§B**): the recommendation is **do not adopt, at any phase** —
not "wrong phase, right idea." `@mastra/mcp`'s `MCPServer` class carries a hard peer dependency on
`@mastra/core` (an ~59 MB agent-orchestration framework: agents, workflows, memory, storage
adapters), and `vice-proxy.mjs` has none of the primitives that framework exists to serve — no
Mastra agents, tools, or workflows, just a stdio MCP server that forwards translated JSON-RPC calls
to a non-MCP host process. Even the official `@modelcontextprotocol/sdk` — the leaner, directly
matching-shaped option — would replace only the ~150-300 lines of generic JSON-RPC/stdio framing in
a 2,441-line file; the other ~90% (broker leasing, path translation, epoch/liveness checks,
diagnose/recycle logic, deny-list enforcement, incident capture) is project-specific code no SDK
touches. Recommendation, with confidence grade, is developed fully in §B6.

Container Node is v24.18.1, verified in this session to strip TypeScript types **natively and
unflagged** — `node file.ts` and `node --test file.test.ts` both work with zero flags today — but it
rejects `enum`, `namespace`, and constructor parameter-property syntax (`ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`
/ parse errors), all verified live. TypeScript itself is now at major version **7.0.2** (a Go-native
port, GA 2026-07-08) — a genuinely new fact this research surfaced, not previously in any project
document, with real tsconfig implications (`moduleResolution: "node"/"node10"` are dropped; use
`"bundler"` or `"nodenext"`).

**Primary recommendation:** run `tsc` in the container only, targeting the erasable-syntax-only
subset (enable `erasableSyntaxOnly: true` so `tsc` itself rejects what native stripping would reject),
emit committed, banner-marked JS under `resources/`, keep `install-resources.mjs`'s existing
copy-to-`tools/` mechanism unchanged, resolve the `vice-pool.mjs` question explicitly before writing
any plan, and treat `vice-broker.test.mjs`'s redesign — not its translation — as its own sized task.

### Verified-live: what Node v24.18.1's native TypeScript stripping does and does not accept

All four probes below were run in-container this session (scratchpad `.ts`/`.test.ts` files, `node`
executed directly with no flags). **Evidence: live execution. Confidence: HIGH** for every row.

| Construct | Result | Detail |
|---|---|---|
| `interface`, type annotations, optional params (`x?: number`), non-null assertion (`x!`), `as const` | **Works, unflagged** | Erased cleanly; `node file.ts` runs like plain JS. |
| `node --test file.test.ts` | **Works, unflagged** | `✔ basic (0.488456ms)`, correct pass/fail summary — the test runner composes with native stripping with zero extra config. |
| `import type { Foo } from "./nonexistent.js"` | **Works — erased before module resolution** | The nonexistent path is never even touched; confirms type-only imports vanish completely, which matters for §E's TDZ hazard (an `import type` reintroduction would be invisible to a runtime check but not to a source-text/AST check). |
| `enum Bar { A, B }` | **Fails**: `SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode` | |
| `namespace Foo { export const x = 1 }` | **Fails**: parse error, `Unexpected identifier 'Foo'` | |
| `constructor(public x: number, private y: number)` (parameter properties) | **Fails**: parse error at the `public` modifier | This is a genuinely common TS idiom; forbid it in the style guide for this phase's conversion or every class constructor becomes a hazard. |
| `--no-experimental-strip-types` | Explicitly disables stripping; then a bare `.ts` file fails with a plain `SyntaxError: Unexpected identifier` | Confirms stripping is **on by default** in v24.18.1, not merely available behind a flag. |

**Conclusion for §A2 (does the test suite compile, or run TypeScript directly?):** run tests
**directly against `.ts` source via native stripping** in the container (fast inner loop, verified
working today), and separately run `tsc --noEmit` (or full emit) as a **gate**, with
`erasableSyntaxOnly`-equivalent discipline enforced so the two paths can never silently diverge.
Deploy the `tsc`-emitted JS to the host (criterion 3 already requires this because the host `node`
version is unverified and unpinned). This resolves the design note's open question 2 concretely:
**tests run TS directly (container Node is new enough, verified); the host never runs TypeScript at
all, compiled or otherwise** — it only ever runs the emitted JS.

## A. The five open questions the design note deferred to planning

### A1. Is the `vice-pool.mjs`/`vice-pool.sh` split absorbed, or does the container-side half survive?

**Answer: it is very likely a THIRD, separate subsystem that should NOT be folded into the one-process
broker at all — this needs an explicit decision, not an assumption, before any plan is written.**

Evidence, read directly from source this session:

- `vice-pool.mjs` (container-side, 753 lines) is imported only by `vice-session.mjs` (`acquire`,
  `releaseLeaseByToken`, `refreshLease`, `instanceFor`, `poolDir`) and dynamically by `vice.mjs`'s
  CLI-only `pool` subcommand (`poolHealth`, `formatPoolHealth`, gated behind
  `process.argv[1] === SELF`, i.e. only reachable by running `vice.mjs` directly as a CLI — which is
  **explicitly forbidden** for any agent-facing skill/doc, per `skill-docs.test.mjs`'s own assertion
  "no module under this directory is named in any agent-facing doc — no exemption, not even
  `vice.mjs`"). **Evidence: source read + grep across `.claude/mcp/vice/`, `tools/`, `.claude/skills/`.
  Confidence: HIGH.**
- `vice-pool.mjs`'s own header comment says explicitly: "Container-side half of the VICE instance pool
  coordination layer... `tools/vice-pool.sh` (host-only) writes `registry.json` describing N
  supervised x64sc MCP instances." This registry/lease scheme is entirely independent of
  `broker.json`/`grants/`/`requests/`/`leases/`/`spares/` — different files, different directory
  layout, different consumer.
- `vice-broker.sh`'s own "warm spares" mechanism (`SPARES_DIR`, `maintain_spares()`, `spares/<port>.json`)
  is what Phase 01.2 built and what D-1's "the pool joins the broker" almost certainly *means* — this
  is genuinely broker-internal state and genuinely folds into the one process.
- `vice-pool.sh` (host, 611 lines) is a **different, older launcher** that starts N raw supervised
  `x64sc` instances into `registry.json` for the **non-MCP recovery pipeline** — Phase 1's own
  `tools/recover.mjs`/`chip-state.mjs`/`watch-loads.mjs` equivalents, none of which currently exist in
  the tree (searched, zero hits) because Phase 1's replan (2026-08-01) rewrote plan 01-04 to go through
  `mcp__vice__*` tools exclusively instead. **This strongly suggests `vice-pool.mjs`/`vice-session.mjs`
  may now have zero live consumers at all** — every current agent-facing path (the `vice-mcp-selector`
  proxy, `c64-ram-capture`, and the rewritten Phase 1 plan 01-04) goes through `mcp__vice__*` tools
  directly, never through `vice-pool.mjs`'s `acquire()`. **Evidence: exhaustive grep across `tools/`
  and `.claude/skills/` for any live import of `vice-session.mjs`/`vice-pool.mjs`; zero hits outside
  the vice-mcp module tree itself, its own tests, and historical planning docs. Confidence: MEDIUM** —
  absence-of-import is strong but not airtight proof of zero runtime use (a human operator could still
  invoke `vice.mjs pool`/`vice.mjs session` by hand from a terminal, which this grep cannot see).
- Phase 01.2's own planning record (`D-1.2-B`, ROADMAP) says point-blank: "`vice-pool.sh` and
  `vice-pool.mjs`'s classic port-keyed lease are left **entirely untouched**: they still serve the
  non-MCP recovery pipeline, whose Phase 1 plans 01-04…01-06 are unexecuted, so 'superseded in intent'
  is not 'safe to delete'." This directly contradicts the 01.6 design note's own conversion-inventory
  table, which lists `vice-pool.sh` as one of the three scripts that "retires, logic absorbed" into
  the one-process broker.

**What the first plan must do:** get an explicit developer decision on exactly this tension before
writing any conversion tasks that touch `vice-pool.mjs`/`vice-pool.sh`/`vice-session.mjs`. Three
honest options, none decided here:
1. **Convert them to TypeScript as inert, unused-but-preserved code** (satisfies D-2a's "all of
   `.claude/mcp/vice/` converts" literally, without deciding their fate) — cheapest, but converts
   ~1,467 lines (753 + 357 + associated tests) of code that may have zero live callers, for no benefit.
2. **Delete them outright**, on the finding that nothing reachable from an agent session uses them —
   requires confirming the "zero live consumers" finding above at HIGH confidence first (a targeted
   grep across any host-side automation, cron jobs, or documented manual workflows this container
   cannot see), and squares badly with D-1.2-B's explicit "not safe to delete" unless Phase 1's replan
   is treated as having superseded that reasoning.
3. **Leave them as `.mjs`, out of scope**, treating them as a fourth "separate concern, own lifecycle"
   bucket alongside `tools/*.mjs` and the skill scripts that D-2a already excludes — the most
   conservative reading, and arguably the most consistent with D-1.2-B, but it means "all of
   `.claude/mcp/vice/` converts" (as literally stated in the design note) is not quite true.

None of these is free, and guessing wrong either strands Phase 1's dormant recovery pipeline or ships
1,467 lines of needless rewrite. **This is the single highest-value decision to force before writing
Wave 1.**

### A2. Does the test suite compile, or run TypeScript directly?

**Answered above under Standard Stack** — tests run directly against `.ts` via container Node's native,
unflagged, verified-working stripping; the host never sees TypeScript in any form, only `tsc`-emitted
JS. `node --test` composes with `.test.ts` glob patterns exactly as it does with `.test.mjs` today
(verified live). The one discipline this buys nothing for free: `enum`/`namespace`/constructor
parameter properties must be avoided project-wide, or files using them will pass `tsc` but fail at

`erasableSyntaxOnly`-equivalent lint/compiler setting so this is caught mechanically rather than by
convention.

### A3. Where does `resources/` land in the build topology?

Read `install-resources.mjs` and `resources/vice-pool.sh`'s own header in full this session. Today:
`resources/` is the **tracked, hand-authored source of truth** for the three host shell scripts;
`install-resources.mjs` walks it (`resourceEntries()`, a real directory walk, not a hardcoded list)
and copies every entry to `<repo>/tools/`, which is **gitignored** and treated as pure deployment
output, never hand-edited. Two tiers exist today: authored-and-tracked (`resources/`) →
generated-and-gitignored (`tools/`).

**Post-conversion this must become three tiers**, not two:

1. **Authored TypeScript source** — a new directory (e.g. `.claude/mcp/vice/src/`, sibling to today's
   flat `.mjs` layout, or `.claude/mcp/vice/` itself reorganized with `.ts` extensions if the flat
   layout is kept — genuinely a planning decision, not researched here). This is where a human edits.
2. **`resources/` — generated, but TRACKED (committed to git).** `tsc` emits here. This is the
   directory-meaning inversion the design note calls out: today `resources/` is hand-edited source;
   tomorrow it is build output that happens to be committed (so the host deployment step,
   `install-resources.mjs`, keeps working unmodified — it only ever reads `resources/` as "whatever
   is there to copy," never caring whether a human or a compiler produced it).
3. **`tools/` — generated, gitignored, host deployment target.** Completely unchanged mechanism and
   unchanged meaning — `install-resources.mjs`'s walk-and-copy logic needs zero code changes, because
   it is already directory-listing driven (confirmed by reading the file: `walk()` is a real recursive
   `readdirSync`, not a hardcoded list).

**Three concrete layout options**, with tradeoffs (none chosen here — this is exactly the design
note's open question 3, still open):

| Layout | `install-resources.mjs` impact | Tradeoff |
|---|---|---|
| **(a) `src/` sibling directory, `tsc outDir` = `resources/`** | Zero code change — `resourceEntries()` already walks whatever is physically in `resources/` | Cleanest separation; requires `tsconfig.json`'s `include`/`rootDir` to point at `src/` and `outDir` at `resources/`, which is the standard tsc shape. **Recommended.** |
| **(b) In-place `.ts`→`.js` alongside each other in the same flat directory** | Zero code change, but `resourceEntries()`'s walk would need to skip `.ts` files (or they'd get "deployed" to the host, which never runs `tsc` and doesn't need them) | Avoids introducing a new top-level directory, but pollutes `resources/` with both source and output, and every `.gitignore`/walk-filter must be kept in sync by hand — more surface for exactly the "silent stale build" hazard the design note already worries about. **Not recommended.** |
| **(c) `tsc` emits to a build-only `dist/` directory, and a separate copy step moves `dist/` contents into `resources/` before `install-resources.mjs` runs** | Requires a NEW script/step, and now there are FOUR tiers instead of three | Adds a seam with no benefit over option (a) — `tsc`'s own `outDir` already does this move for free. **Not recommended** unless something concrete forces `dist/` to also hold non-deployed build artifacts (declaration files, source maps) that must not reach `resources/`; if so, prefer `declaration: false`/`sourceMap: false` in tsconfig instead of a second copy step, since the host never debugs this code and never needs `.d.ts` files. |

**What every layout must add regardless (criterion 3's explicit ask):**
- A **generated-file banner** at the top of every emitted file — see §F for exact wording.
- A **sync test** — build into a scratch directory and diff/hash-compare against the committed
  `resources/` tree, failing loudly if they differ (catches "developer edited `.ts`, forgot to
  rebuild, committed the stale `resources/`" — the single scenario this criterion exists to prevent).
- An update to `./.claude/CLAUDE.md`'s Emulator Access section, which today instructs editing
  `resources/` directly — see §F for the precise text change required.

### A4. Does the one-process design change how a wedged emulator is detected?

Read Phase 01.3's ROADMAP section and its own `01.3-PATTERNS.md`/`01.3-RESEARCH.md` directory in full.
**Collision surface, reported as findings, per the "flag it now" instruction (01.3 resumes last, after
01.6, 01.4, and 01.7):**

- Phase 01.3's own pause note (ROADMAP, verbatim): "this phase's recovery path was designed against a
  **separate supervisor process** holding the respawn loop, which 01.6 collapses into the broker.
  Re-read the design before resuming; it may no longer describe the machine." This research confirms
  that warning is accurate and specific, not generic caution: `vice_recycle`'s implementation today
  (per `.planning/notes/broker-control-plane-over-tcp.md`) is `writeRecycleRequest()` →
  `requests/<id>.json` with `op:"recycle"` → poll `recycle-acks/`, and the RECEIVING side is
  `vice-supervisor.sh`'s own respawn loop signalling itself — a process that, per D-1's own kernel
  fact, currently **outlives broker restarts**. Once that supervisor process is folded into the
  broker, a broker restart taking down its own recycle machinery mid-recycle is a new failure mode
  that did not exist when the supervisor was independent.
- `vice_diagnose`'s cycle-bracket liveness test (Phase 01.3 criterion 2: "reset the stopwatch, resume
  once, poll with `vice_ping`, read the stopwatch back") is **entirely container-side and MCP-mediated**
  — it never touches `vice-supervisor.sh` or the broker's internals at all, so this specific mechanism
  is **unaffected** by the one-process collapse. The parts that DO change are the ones that route
  through the file-based recycle-request protocol, which both retires its *implementation substrate*
  here (01.6, state consolidation) and its *transport* in 01.7.
- Phase 01.3's criterion 6 (identity-verified kill, `ps -o args=` against a recorded pid before

## D. The one-process runtime design in Node/TypeScript

### D1. Signal handling for catchable shutdown

Phase 01.3 criterion 6 and `vice-broker.sh`'s existing kill discipline (verified by direct source
read, lines ~1470-1610 and ~2044-2053) is: `kill -0 $pid` (liveness) → `ps -o args= -p $pid` (identity
match against the known script/binary path substring, guarding against pid reuse) → `kill -TERM` →
poll with a timeout loop → `kill -KILL` if still alive after the grace period. **This is the exact
spec to port, not re-derive** — the TypeScript equivalent is:
```typescript
// Reuses Phase 01.3 criterion 6's verified-kill discipline (bash source: vice-broker.sh
// lines ~1503-1541), not re-derived.
import { execFileSync } from "node:child_process";

function isAlive(pid: number): boolean {
  try { process.kill(pid, 0); return true; } catch { return false; }
}

function identityMatches(pid: number, expectedSubstring: string): boolean {
  try {
    const args = execFileSync("ps", ["-o", "args=", "-p", String(pid)]).toString();
    return args.includes(expectedSubstring);
  } catch { return false; }
}

async function verifiedKill(pid: number, expectedSubstring: string, graceMs = 3000): Promise<void> {
  if (!isAlive(pid)) return;
  if (!identityMatches(pid, expectedSubstring)) {
    console.error(`refusing to signal pid ${pid} -- identity check failed (possible pid reuse)`);
    return;
  }
  process.kill(pid, "SIGTERM");
  const deadline = Date.now() + graceMs;
  while (isAlive(pid) && Date.now() < deadline) {
    await new Promise((r) => setTimeout(r, 100));
  }
  if (isAlive(pid)) process.kill(pid, "SIGKILL");
}
```
For the top-level shutdown wiring, register on every event D-3 names — `SIGTERM`, `SIGINT`, `SIGHUP`,
`uncaughtException`, `unhandledRejection`, and normal `exit` — funnelling all of them into one
idempotent teardown function that calls `verifiedKill()` for every child the broker recorded launching:
```typescript
let shuttingDown = false;
async function shutdown(reason: string) {
  if (shuttingDown) return;
  shuttingDown = true;
  console.error(`vice-broker: shutting down (${reason})`);
  await Promise.all(recordedChildren.map((c) => verifiedKill(c.pid, c.expectedSubstring)));
  process.exit(0);
}
for (const sig of ["SIGTERM", "SIGINT", "SIGHUP"] as const) {
  process.on(sig, () => void shutdown(sig));
}
process.on("uncaughtException", (err) => { console.error(err); void shutdown("uncaughtException"); });
process.on("unhandledRejection", (err) => { console.error(err); void shutdown("unhandledRejection"); });
```
**SIGKILL/SIGSTOP remain uncatchable by construction** (D-3's own kernel fact, re-confirmed here: no
signal handler, `exit` listener, or `finally` block can run once SIGKILL is delivered) — this is
POSIX/kernel behavior, not a Node limitation, so nothing above claims to catch it; §D3/the design note
already accept this and it does not need re-litigating.
**Evidence: direct source read of the bash equivalent; TypeScript translation reasoned from Node's
documented `process.kill`/`process.on` semantics, not independently executed against a real spawned
child in this session (would require driving process launches this research is scoped to avoid).
Confidence: MEDIUM** for the TypeScript code shape; **HIGH** for the bash discipline being ported.

### D2. Concurrency: preserving the single in_flight owner

Confirmed by direct source read: `vice-broker.sh`'s `process_requests()` and `maintain_spares()` share
a single in-flight-launch counter (`count_launching()`, recomputed from the `spares/`/`launching`-state
directory contents on each poll pass) specifically to prevent the 2026-08-01 triple-launch outage
(three simultaneous `x64sc` spawns from `VICE_BROKER_SPARES=3` racing GPU/audio-device contention).
**Evidence: `grep -n "in_flight\|maintain_spares()\|process_requests()"` across `vice-broker.sh`.
Confidence: HIGH.**

The concrete Node idiom that preserves "single owner" with the least new surface: a **plain
module-level boolean flag, checked and set synchronously with no `await` between the check and the
set**, not a library-based async mutex and not a full promise-chaining queue:
```typescript
let launchInFlight = false;

async function tryLaunchOne(): Promise<void> {
  if (launchInFlight) return;      // synchronous check -- no await has run since the last set
  launchInFlight = true;           // synchronous set -- this pair cannot be interleaved by anything
  try {
    await spawnOneInstance();      // the only place awaiting is allowed
  } finally {
    launchInFlight = false;
  }
}
```
This works because JavaScript's single-threaded event loop guarantees no other code runs between two
synchronous statements — the hazard a real mutex exists for (two threads racing the same
check-then-set) cannot occur here as long as the check and the set are never separated by an `await`.
**Recommend against** pulling in an `async-mutex`-style dependency: the invariant needed is exactly
this one flag, adding a library for it is the same class of over-engineering D-3 already rejected for
`PR_SET_PDEATHSIG`/cgroups. **Recommend a promise-chaining queue only if** a future defect shows more
than one broker operation needs strict serialization (not just launches) — that is a heavier, more
general tool than this specific, already-scoped problem needs today.

**The risk to name explicitly in the plan:** any future edit that inserts an `await` between the
`if (launchInFlight)` check and the `launchInFlight = true` set silently reintroduces the exact race
this flag exists to prevent — recommend a dedicated test that fires two concurrent launch requests
and asserts exactly one spawn occurs (directly reproducing the 2026-08-01 scenario's shape, container-
side, with a stubbed spawn function — no real `x64sc` needed).
**Evidence: reasoned from Node's documented single-threaded event-loop model. Confidence: HIGH**
(this is well-established JS runtime semantics, not project-specific speculation).

### D4. `--once` and `VICE_BROKER_PROBE_CMD` — the seams every test drives

## E. Criterion-10 hazard: the load-order landmine that must NOT be tidied

Read `install-resources.mjs` and `repo-root.mjs` in full, then **reproduced the exact hazard live**
in the scratchpad this session (not merely reasoned about it).

**(a) The exact mechanism.** `repo-root.mjs` imports `ensureResourcesInstalled` from
`install-resources.mjs` near the top of its file (before its own `const HERE = ...` line), then calls
`ensureResourcesInstalled({ root: repoRoot() })` at the very **bottom** of its module body — after
`HERE`, `repoRoot()`, and `supervisorDir()` are all fully defined. This ordering is safe today because
ES module semantics evaluate an imported module's entire body to completion **before** any of the
importing module's own top-level statements run — so when `repo-root.mjs` is first loaded,
`install-resources.mjs` finishes evaluating (today, safely — it takes `root` as a parameter and
imports nothing back) before `repo-root.mjs` even reaches its own `const HERE = ...` line.

If `install-resources.mjs` were changed to `import { repoRoot } from "./repo-root.mjs"` (the exact
"cleanup" the header comment forbids) **and** that import were used to compute something at
`install-resources.mjs`'s own top level (e.g. "since we need `repoRoot`, let's just call it here
instead of taking `root` as a parameter"), the resulting cycle crashes. **Verified live, this session,
with a minimal two-file reproduction:**
```
STEP 2: install-resources.mjs body starting to evaluate
STEP 3: about to call repoRoot() -- HERE should NOT be initialized yet in repo-root.mjs
ReferenceError: Cannot access 'HERE' before initialization
    at repoRoot (.../repo-root.mjs:6:30)
    at .../install-resources.mjs:4:22
```
Notably, `repo-root.mjs`'s own **first line of code never even ran** before the crash — confirming
that ESM import resolution fully evaluates the dependency graph before the importing module's own
body starts, not merely "before the specific line that would be affected." This exactly reproduces
the error string install-resources.mjs's own header comment quotes verbatim
("Cannot access 'HERE' before initialization"). **Evidence: live reproduction in
`/tmp/.../scratchpad/tdz2/`, this session. Confidence: HIGH.**

**A second reproduction, also run this session, found an important nuance:** if the reintroduced
import is only *called lazily* — from inside a function body invoked later, rather than at the
importing module's own top level — **it does not crash**:
```
install-resources: root = computed-here
repo-root.mjs: done
exit: 0
```
**This means the hazard is specifically a top-level-synchronous-access hazard, not a "the import
exists at all" hazard** — a future refactor could add the forbidden import and, by sheer luck of
calling it lazily, never trigger the crash today while still leaving the codebase one reordering away
from it. **Evidence: live reproduction, this session. Confidence: HIGH.**

**(b) Does TypeScript compilation make this better, worse, or differently shaped?** **Not
meaningfully better, and arguably a source of false confidence.** Two considerations:
1. TypeScript's module system compiles down to the same CommonJS or ESM runtime semantics `tsc`
   targets — the cycle survives compilation unchanged if the emit target is ESM (`module: "nodenext"`,
   the recommended setting per §A2/§State-of-the-Art). The hazard is a plain JS/ESM runtime property,
   not a types-level concern, so TypeScript neither introduces nor removes it.
2. **A genuine new risk TypeScript introduces:** `import type { repoRoot } from "./repo-root.js"` (a
   type-only import) is **completely erased at compile/strip time** — verified live this session (an
   `import type` of a nonexistent module path caused no error at all, confirming type-only imports
   vanish before module resolution even happens). This means a well-meaning contributor could add
   `import type { ... }` for IDE/type-checking convenience, believing it "doesn't really import
   anything, so it's safe" — and be **right**, by accident, for the wrong reason (it happens to be
   erased, not because the discipline was followed) — while a plain value import of the same specifier
   would reintroduce the exact hazard. This is a **worse** situation than plain JS, because it adds a
   plausible-looking exception ("it's just a type import, that's fine") that happens to be technically
   safe but sends exactly the wrong signal about why the rule exists.
3. **If the emit target were CommonJS instead of ESM**, `require()` cycles have different, generally
   *more forgiving but silently wrong* semantics — a cyclic `require()` returns a possibly-incomplete
   `module.exports` object rather than throwing, so `HERE` could resolve to `undefined` rather than
   crashing loudly. This would be a **strictly worse** outcome for this specific codebase, which has
   an established, explicit preference for loud failures over silent wrong answers (`repo-root.mjs`'s
   own header comment names this exact class of bug — "a broken invariant with no error anywhere" —
   as the thing the whole file exists to prevent). **This is a concrete argument for `module:
   "nodenext"`/ESM output over `"commonjs"` output**, independent of every other reason already
   pointing that way (native Node stripping, `tsc` 7.0's own dropped `moduleResolution` modes).

**(c) How a test can assert the import is never added back.** Recommend a **static source-text
check**, not a runtime-crash-based test — because (per the lazy-call reproduction above) a runtime
test can only catch the specific top-level-call variant of the mistake, while a source-text/AST check
categorically forbids the import regardless of how it would be used:
```typescript
import { readFileSync } from "node:fs";
import test from "node:test";
import assert from "node:assert";

test("install-resources.ts never imports from repo-root -- see its own header comment", () => {
  const src = readFileSync(new URL("./install-resources.ts", import.meta.url), "utf8");
  assert.ok(
    !/from\s+["']\.\/repo-root(\.[jt]s)?["']/.test(src),
    "install-resources.ts must not import from repo-root.ts -- this reintroduces the TDZ " +
      "cycle documented in this file's own header comment; see 01.6-RESEARCH.md §E for the " +
      "live-reproduced crash this guards against."
  );
});
```
**Evidence: reasoned from the live reproduction above, plus the general principle that AST/text-level
checks are more categorical than behavior-level ones for this class of "never do X" rule. Confidence:
HIGH** for the reproduction; **MEDIUM** for the specific test-code recommendation (not itself executed
against the real converted files, which do not exist yet).

## Common Pitfalls

### Pitfall 1: Treating this as a mechanical syntax port

**What goes wrong:** an agent-driven `.mjs` → `.ts` conversion that adds type annotations file-by-file
looks complete when `tsc` passes, but the LARGEST test file (`vice-broker.test.mjs`) verifies bash
subprocess behavior that has no equivalent once state moves in-process — "converting" it by adding
types to code that spawns a script which no longer exists produces a suite that either doesn't
compile, or compiles and asserts nothing meaningful.
**Why it happens:** the conversion inventory (§G) presents this as one file among many, same shape as
every other; nothing in the file itself signals that its test *methodology*, not just its syntax,
needs redesigning.
**How to avoid:** treat `vice-broker.test.mjs`'s redesign as an explicitly separate, separately-sized
task from every other file's conversion (§A5/§D3/§Validation Architecture).
**Warning signs:** a converted `vice-broker.test.mjs` that still calls `execFileP("bash", [...])` —
if the broker is genuinely one TypeScript process now, there should be no bash subprocess left to
spawn for testing its OWN logic (only, perhaps, for testing the one surviving launcher script itself).

### Pitfall 2: Assuming `vice-pool.mjs`/`vice-pool.sh` is broker logic

**What goes wrong:** converting and folding `vice-pool.mjs`/`vice-pool.sh` into the one-process broker
because the design note's own inventory table lists it as retiring, without checking whether it is
actually the SAME "pool" D-1 means.
**Why it happens:** the name overlap ("pool") between `vice-broker.sh`'s internal warm-spares pool and
the separate `vice-pool.mjs`/`.sh` subsystem is genuinely confusing, and the design note's table
conflates them.
**How to avoid:** get an explicit developer decision per §A1 before writing tasks that touch these
files.
**Warning signs:** a plan that references "the pool" without specifying which of the two subsystems it
means.

### Pitfall 3: `enum`/`namespace`/constructor-parameter-properties creeping into converted code

**What goes wrong:** a converted class or config module uses one of these idioms (extremely common in
typical TypeScript code, and nothing about a naive `.mjs`→`.ts` conversion would flag them), and it
either fails under native Node stripping (if tests run directly against `.ts`) or fails under `tsc`
(if `erasableSyntaxOnly` is enabled) — in either case, discovered late, possibly per-file rather than
project-wide.
**Why it happens:** these are default-idiomatic TypeScript patterns; nothing about "convert this
JavaScript file to TypeScript" naturally excludes them.
**How to avoid:** enable `erasableSyntaxOnly: true` from the very first converted file (§tsconfig
recommendation above), so `tsc` itself rejects these constructs at the same file that would fail
native stripping — turning a late runtime surprise into an immediate compile error.
**Warning signs:** any `enum`, `namespace`, or `constructor(public ...)`/`constructor(private ...)` in
a diff touching this conversion.

### Pitfall 4: Silent drift between `resources/` and its TypeScript source

**What goes wrong:** exactly the scenario criterion 3 and criterion 10 both exist to prevent — a
developer edits `.ts` source, forgets (or is interrupted before) rebuilding, and commits a stale
`resources/` tree that looks identical to a fresh one until diffed.
**Why it happens:** `resources/` inverting from hand-authored to generated-but-tracked removes the
"if it looks wrong, someone will notice while editing it" safety net a purely hand-authored directory
has.
**How to avoid:** the sync test described in §F, run as part of every CI/test pass, not just at
release time.
**Warning signs:** a `git diff` touching `.ts` source files with no corresponding change to
`resources/` in the same commit.

## Security Domain

Most classic ASVS web-application categories do not apply to this phase: there is no
authentication/session/access-control surface in the usual sense (a single trusted
container↔host pair on one operator's own machine, not a multi-tenant service), and no
network-facing listener beyond the existing loopback/bind-mount channels this phase does not add to.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---|---|---|
| V2 Authentication | No | Single-operator, single-host trust boundary; no login surface exists or is being added. |
| V3 Session Management | No | The "session" concept here is an MCP/broker lease, already covered by this project's own existing epoch/liveness discipline (D1-D4 above), not a web session. |
| V4 Access Control | Partial | `broker.json`/`grants/`/etc. rely on filesystem permissions and uid parity between container and host (an existing, already-recorded precondition, `D-1.2-D`) — this phase should not weaken that (e.g., don't widen file modes "for convenience" during the conversion). |
| V5 Input Validation | Yes | Every on-disk file the broker/proxy reads is untrusted input from the OTHER side of a trust boundary (host reads container-written request files and vice versa) — the existing "parse in try/catch, malformed is 'not there yet', never throw" discipline (already established project-wide, confirmed by direct source read of `vice-pool.mjs`'s and `vice-broker-client.mjs`'s own header comments) must be preserved verbatim in the TypeScript port, not weakened by, e.g., a naive `JSON.parse()` with no surrounding try/catch. |
| V6 Cryptography | No | No cryptographic operations exist in this subsystem or are being added. |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---|---|---|
| Malformed/half-written state file read as a crash-inducing input | Denial of Service | The existing "never throw on untrusted file read" discipline (parse in try/catch, absent-or-malformed treated as "not there yet") — already established project convention, must be preserved through the TS port, not silently dropped by an agent-driven conversion that "cleans up" a try/catch it doesn't understand the purpose of. |
| Pid reuse leading to a wrong-process kill | Tampering / Elevation of Privilege (of a sort — killing an unrelated process) | The identity-verified kill discipline (`ps -o args=` match before any `kill -TERM`/`kill -KILL`) — already established, must be ported byte-for-byte (§D1), not "simplified" to a bare `process.kill(pid)`. |
| A stray `x64sc` surviving a SIGKILL being handed to a second session as if it were fresh | Tampering (cross-session contamination) | Criterion 7's unconditional reap-on-startup, bumping every epoch — explicitly unaffected by this phase's SIGKILL-orphan acceptance (D-3); must not be weakened or "optimized away" during the conversion. |
