### What PD-06 costs, stated plainly so the discussion can price it

Criterion E says *"a green suite proves language and structural equivalence only."* With five deliberate
behaviour changes inside the same 2,546-line conversion, that claim no longer covers the whole
deliverable. **The discussion must decide, per change, what replaces "it behaves as before" as the
proof** — because for these five, "the test still passes" is either meaningless (the test was rewritten
to expect the new behaviour) or ambiguous (a failure could be a translation bug *or* the intended
change). Concretely, each of the five needs:

1. A test that fails against the OLD behaviour and passes against the NEW one — proving the change
   happened, not just that nothing broke.
2. A named boundary: which parts of the conversion the equivalence claim still covers, and which are
   deliberately excluded. The plan has to state this; a reader must not be able to mistake a green
   suite for whole-deliverable equivalence.

## The agenda — five policy changes needing detailed discussion

Ordered by strength of evidence, strongest first. Each block lists what the discussion has to settle,
not just what the change is.

### D3 — pool floor 3 → 1

**Today:** `VICE_BROKER_SPARES` defaults to 3 (`vice-broker.sh:431`), counted by `count_ready()` over
`spares/*.json` with state `ready`. A claimed instance moves to `grants/` and stops counting toward the
total, so three live sessions put **six** `x64sc` on the host (three granted, three warm replacements).

**Proposed:** floor becomes 1.

**Evidence:** waves arrive as a burst within milliseconds, so spares 2..N buy nothing against that
arrival pattern; `x64sc` is not headless (GTK3 window + OpenGL 4.6 context + PulseAudio handle each);
a machine is never shared between agents, so a spare is only ever a latency optimisation. Boot was
**measured sub-second on 2026-08-02 (~0.65s upper bound)** — so a warm spare buys back under a second.

**To settle:**
- Is the new default 1, or is the *default* 1 with the knob still honouring any N? (The bash `start [N]`
  argument exists today and was itself the subject of a live-outage misdiagnosis — see D6.)
- Does the knob keep its name in this change, or does D6's rename land in the same commit?
- What proves the floor is 1 — a test asserting exactly one warm instance at idle against a stubbed
  spawn, or something more? Note kill-never-recycle stays either way; it is locked at ROADMAP level.
- Any interaction with `VICE_BROKER_MAX=16` (note Decision 5.4), which the note flags as unverified
  and inconsistent with a known crash at 3 concurrent *initialisations*? Spike 005 was meant to
  measure this and has not. Does lowering the floor change whether that matters here?

### D5.2 — the pool target counts files, not processes  *(the proven silent bug)*

**Today:** `grant_from_spare()` was hardened to probe a spare at grant time, but `count_ready()` — the
function that decides whether a replacement needs launching — still trusts the `ready` state recorded
in a JSON file rather than checking the process it describes.

**Proposed:** evaluate the floor over probe-live instances; reap anything that fails the probe rather
than trusting its file record.

**Evidence: proven.** Defect 3 of the defects todo showed such a record surviving a broker stop, a
broker start *and* a full host restart with its `x64sc` long dead. A host with N dead-but-recorded
spares concludes the ready-floor invariant is satisfied and **launches nothing to replace them**.

**To settle:**
- What is the probe, exactly, in the new in-process design? The bash version has
  `VICE_BROKER_PROBE_CMD` (a loopback curl probe). Does that mechanism survive unchanged, or does
  in-process state change what "probe" means?
- **Hard constraint:** `mcp__vice__*` is the only route to the emulator. The probe is host-side broker
  code, not container-side, so it is not the same violation — but the discussion must state explicitly
  why it is permitted and confirm no *test* opens its own connection.
- Reap semantics: does a failed probe delete the record, mark it dead, or both? Does reaping count as
  a kill that must go through the identity-verified kill discipline (criterion D)?
- What proves this? A test where a `ready` record describes a non-existent process, asserting the
  broker launches a replacement — which fails against today's behaviour and passes after.

### D5.1 — no priority between launch reasons

**Today:** `count_launching()` is ONE shared in-flight counter consulted by both `process_requests()`
(a cold launch answering a real waiting request) and `maintain_spares()` (speculative warming toward
the floor). Either blocks the other, so a boot nobody asked for can delay a request an agent is
actively waiting on. Observed log line: `"request $id -- a launch is already in flight, awaiting
readiness"`.

**Proposed:** an explicit launch queue of depth 1 in which a request-driven launch always precedes
warming.

**Critical interaction — this is the one to be most careful about.** Serialising launches was the
fix for the GPU/audio SEGV that launched three `x64sc` simultaneously during the 2026-08-01 outage.
This phase's **criterion C** already requires that the single `in_flight` owner survive the move from
a poll loop to an event loop, with a concurrency race test (two concurrent launch requests, stubbed
spawn, exactly one spawn) as a required deliverable. D5.1 adds *priority on top of the lock* — the
lock itself must not weaken. RESEARCH Pitfall 3 names exactly this: do not "improve" the
serialised-warming `break` into concurrent spawns.

**To settle:**
- Is priority a strict two-tier queue (requests always before warming), or does warming get to
  finish an in-flight boot before yielding?
- What happens to a warming boot already in flight when a real request arrives — abandoned, killed,
  or allowed to complete and then granted to the request?
- Does the criterion-C race test extend to cover priority, or is that a second test?
- Ordering: criterion C's guard must be proven working *before* priority is layered on, so a failure
  is attributable. Does that make these two separate tasks in separate waves?

### D5.3 — no FIFO fairness

**Today:** `process_requests()` iterates the requests directory in glob (lexical) order over ids
shaped `req-832-1785608443993-9c3df302`, so `req-1000-…` sorts ahead of `req-832-…` purely as string
comparison. Each pass re-globs and re-picks from scratch, so a burst of arrivals can jump an unlucky
agent's request repeatedly while its own deadline runs down.

**Proposed:** an arrival-ordered queue instead of a re-glob-and-pick loop.

**Evidence: inferred, not proven.** The note names this as "the mechanism behind wave failures that
look random and have no repeatable pattern" — a hypothesis that fits the symptom, not a reproduction.

**To settle:**
- Is arrival order taken from the id's own embedded timestamp, from file mtime, or from the order the
  broker first observed the file? (The id shape `req-<pid>-<ms>-<hex>` carries a millisecond stamp —
  is it trustworthy as the ordering key?)
- **This touches the protocol boundary.** The request id format is C7's subject and
  `REQUEST_ID_PATTERN` is a shared constant (`vice-broker-client.ts:44`). If ordering now depends on
  parsing a field out of the id, the id format acquires a new consumer — does that count as a
  protocol change the phase goal forbids?
- Since this one is inferred, does the discussion want it reproduced first, or is fixing an obvious
  unfairness acceptable without a reproduction?
- What proves it? A test injecting requests whose lexical order contradicts their arrival order,
  asserting arrival order wins — fails today, passes after.

### D6 — rename `spares`

**Today:** `spares` reads as "extras beyond what is in use," but it denotes the entire ready pool —
the only pool that exists.

**Proposed:** rename to something that says what it is — a warm floor or ready floor. The note insists
this is deliberate, not cosmetic.

**Evidence:** one real incident. During a live outage an operator misdiagnosed a working `start [N]`
argument as broken because the surrounding prose about "spares" was stale and confusing under pressure.

**To settle:**
- The actual new name. "warm floor" / "ready floor" / something else — pick it here, not at plan time.
- **Blast radius, which is the real question.** The name appears in: the `VICE_BROKER_SPARES` env var
  (operator-facing), the `spares/` state directory name (on-disk, and the current test suite inspects
  it directly), `count_ready()`/`maintain_spares()`/`grant_from_spare()` function names, and log text.
  Which of those rename, and which are frozen?
- **`spares/` the directory is the sharp edge.** Is it protocol-facing (container-side code or an
  operator reads it) or broker-internal? RESEARCH §D2 draws that boundary — if it is broker-internal
  and moves in-process per C4, the directory may cease to exist anyway, which dissolves part of this
  question. Settle that first.
- Does `VICE_BROKER_SPARES` keep working as a deprecated alias, or break? An operator with it set in
  a shell profile is the failure mode.

## Non-negotiables the discussion must not trade away

- **`mcp__vice__*` is the only route to the emulator.** No script, module, test or driver may open its
  own connection to host VICE, read broker state to find a port, or import a transport module as a
  library. Every launch/kill/probe test in this phase is **stubbed** — no real emulator.
- **This phase is in "maintaining the `mcp__vice__` implementation" mode**, which is what makes
  editing `.claude/mcp/vice/` legitimate here. Authored TypeScript lives flat in `.claude/mcp/vice/`;
  `resources/` is generated-but-committed (banners, diffed by `resources-sync.test.ts`) with
  `resources/vice-launcher.sh` the sole hand-authored exception; `tools/` is generated and gitignored.
- **Kill-never-recycle** — a released instance is killed, never recycled back into the pool. Locked at
  ROADMAP level; keeps every granted instance a known-clean boot-fresh machine.
- **Identity-verified kill is reused, not re-derived** (criterion D). Phase 01.3 criterion 6 set the
  discipline. RESEARCH Pitfall 2 warns the identity substring needs *correcting* for the new spawn
  topology — a wrong-but-compiling identity string is a real new risk this phase introduces.
- **D-04: the epoch file survives** as the second on-disk exception, written by the broker, format,
  location and semantics unchanged. **Capture a fixture from the real bash-written epoch file BEFORE
  `vice-supervisor.sh` is deleted** — order-dependent and irreversible if missed.
- **C6: exactly one shell script survives** — `resources/vice-launcher.sh`.
- **Criterion E stands regardless:** no live-session tool-surface verification exists until Phase 01.4.
  A green suite here does not prove a live agent session sees the same tool surface.
