## Summary

This phase deletes `resources/vice-broker.sh` (2,103 lines) and `resources/vice-supervisor.sh`
(443 lines) — 2,546 lines of bash, exactly matching the ROADMAP's own scope line — and re-expresses
every function in both as one TypeScript, host-bound, one-process broker that already exists in
skeletal tracer form (`vice-broker.mts`, 191 lines, Phase 01.6 plan 01). This is **not** a syntax
port: every function was read directly from source this session, and roughly a third of them encode
policy that only makes sense against a *poll loop over files* (`count_launching()`,
`grant_from_spare()`'s retry-on-stale-probe loop, `maintain_spares()`'s serialised-warming break,
`sweep_grants()`'s snapshot-then-act ordering) — porting the *policy* (never two simultaneous
`x64sc` boots; a released or stale lease tears down through one code path; a spare is proven live at
grant time, not trusted from its own file) while changing the *mechanism* (an event loop with typed
in-memory state, not a `while true` loop re-reading JSON files) is the actual work.

Three findings should reshape how the planner slices and scopes this work more than anything else:

1. **A design-note/ROADMAP tension exists and must be resolved explicitly before Wave 1, not
   discovered mid-plan.** `.planning/notes/vice-broker-lifecycle-decisions.md` (2026-08-01,
   corrected 2026-08-02) — a pre-ROADMAP `/gsd-explore` design record this phase's own task
   description names as required reading — frames the coming rewrite as a **policy** change, not a
   translation: rename "spares" to something clearer (Decision 6), lower the default warm floor
   from 3 to 1 (Decision 3), add priority between launch reasons so a real request is never blocked
   behind speculative warming (Decision 5.1), evaluate the ready-floor over probe-live instances
   rather than trusting a JSON file's own `state` field (Decision 5.2), and replace glob-order
   request iteration with FIFO fairness (Decision 5.3). **None of these appear anywhere in
   `ROADMAP.md`'s criteria register, `01.6-CONTEXT.md`'s locked decisions, or this group's own
   success criteria A–E.** The phase's actual goal wording — *"2,546 lines of host-side bash become
   one TypeScript process... with... no protocol change"* — and criterion 8's "the existing suite
   passes across the move" (owned by the sibling 01.6.1, but the equivalence *philosophy* is
   shared) both point at faithful behavioral conversion, not policy revision. **Recommendation,
   argued in full in §A1: treat the lifecycle-decisions note as historical rationale for WHY the
   current mechanisms exist (cite it liberally for that), but do NOT implement Decisions 3/5.1–5.4/6
   as part of this phase's scope** unless the developer says otherwise at plan time — each is a
   real, valuable improvement, but each also changes observable broker behavior in a way a
   from-scratch test (this phase's own §F deliverable) cannot prove equivalent to the bash original,
   which directly undermines this phase's own criterion E ("a green suite proves language and
   structural equivalence only").
2. **A file-naming collision exists between the already-landed tracer and the script this phase
   deletes, and CLAUDE.md has already answered which name wins.** The Phase 01.6 tracer created
   `resources/vice-launcher.sh` as a *new*, separate file, deliberately not repointing
   `brokerHostPath()` (`vice-proxy.ts`) or `hostLaunchInstructions()` (`install-resources.ts`) at it
   — both still hardcode `tools/vice-broker.sh`, the bash daemon THIS phase deletes.
   `./.claude/CLAUDE.md`'s own Emulator Access section already documents the answer: *"The one
   exception is `resources/vice-launcher.sh`, which stays hand-authored."* `host-scripts.test.ts`'s
   `EXPECTED_TRACKED_SHELL_SCRIPTS` array (currently 5 entries) must shrink to exactly
   `[".claude/mcp/vice/resources/vice-launcher.sh"]` — not a renamed `vice-broker.sh`. **This phase
   must therefore update every hardcoded `"vice-broker.sh"` host-path string in already-converted,
   already-tested container-side TypeScript** (`brokerHostPath()`, `hostLaunchInstructions()`, and
   their own test assertions) to name `vice-launcher.sh` instead — a small, concrete, easily-missed
   task. See §A6.
3. **`vice-broker.test.mjs`'s 61 tests split unevenly, and the split is now countable, not
   estimated.** `01.6-RESEARCH.md §D3` estimated "nearly all 61" lose their mechanism. Read against
   this phase's actual scope (state-in-process, no protocol change) rather than a generic "state
   moved" description, the real split is: **~14 tests exercise the still-unchanged file *protocol*
   (request/grant/denial/lease file shapes, request-id validation, the recycle-ack contract) and
   survive as black-box tests against the NEW implementation with no rewrite of their assertions,
   only their subprocess-spawn mechanism; ~8 tests exercise `--dry-run`/`--once`/`--detach`/CLI
   parsing, which the new broker either does not need (no more one-pass-per-invocation daemon to
   flag) or needs in a different shape (an in-process broker has no argv to parse per pass); and
   ~39 tests exercise internal bash mechanics with no TypeScript equivalent at all** (spare-file
   `state` transitions, `broker-instances.json`'s exact JSON shape, `next_free_port()`'s
   file-scanning behavior, the atomic-write temp-file convention) **and have no 1:1 port** — they
   must be re-derived against whatever observation surface the in-process implementation exposes.
   See §F for the per-function table this count is built from.

**Primary recommendation:** build one TypeScript module exporting typed, directly-testable
functions for every stateful concept `vice-broker.sh`/`vice-supervisor.sh` encode (a `BrokerState`
class or equivalent holding grants/spares/leases as in-memory maps, a `launchInFlight` boolean per
`01.6-RESEARCH.md §D2`, a `verifiedKill()`/`shutdown()` pair per `01.6-RESEARCH.md §D1`), test it by
**importing the module and calling its functions directly** (dependency-injected `spawn`/clock/
filesystem for the concurrency race test), keep the file-protocol boundary (`requests/`, `grants/`,
`denials/`, `leases/`, `recycle-acks/`, `broker.json`, and the per-instance `epoch.json`) exactly as
`vice-broker-client.ts` already reads/writes it, and treat the epoch file's writer as the one piece
of `vice-supervisor.sh`'s logic this phase's own broker must reproduce byte-for-byte (D-04). Do not
implement the lifecycle-decisions note's policy changes in this phase; file them as a follow-up
todo instead, exactly as this project already treats scaffolding-maintenance work (see the note's
own Decision 7).

### A7. `lib/container-guard.sh` and `lib/repo-root.sh` — the two-part decision C6 requires be deliberate

Both files are sourced by all three retiring scripts (`vice-broker.sh`, `vice-supervisor.sh`, and
today also `vice-launcher.sh` itself). Once the first two are deleted, **only `vice-launcher.sh`
would still source them** — but C6 requires EXACTLY one shell script survive, meaning these two
`lib/` files cannot remain as separate tracked files regardless of who still needs their logic.
Read in full this session (`container-guard.sh`, 184 lines; `repo-root.sh`, 103 lines) — full text
reproduced in the `<files_to_read>`-equivalent section above; the decision:

**`lib/repo-root.sh`'s logic MUST move into the surviving launcher (bash), not TypeScript —
this is not a free choice.** The launcher needs the resolved repo root BEFORE it can `exec node
... --repo-root <path>` — by the time a Node process exists to resolve anything, the shell has
already had to decide what to pass it. `repo-root.sh`'s own header names exactly why a fixed `".."`
hop is wrong (it differs between `tools/` and `resources/`, and gets it wrong silently, with a
permanently-empty state directory as the only symptom) — this reasoning is unaffected by which
language reads the result, so the 4-branch precedence ladder (`CONTAINER_WORKSPACE_PATH` when it
contains the caller → walk up for `.git` → `CONTAINER_WORKSPACE_PATH` as a last resort with a
warning → a location-shaped last resort with a warning) must be **inlined directly into
`vice-launcher.sh`** as a `resolve_repo_root()` function defined in that one file, not sourced from
a sibling. `resources/lib/repo-root.sh` is then deleted outright — its logic, not its file, survives.

**`lib/container-guard.sh`'s logic has a genuine choice, and this document recommends moving it
to TypeScript, for defense-in-depth reasons ROADMAP's own criterion 6 text does not force but does
not forbid either:**

| Option | What it costs | What it buys |
|---|---|---|
| **(a) Inline into `vice-launcher.sh` (bash)** | The launcher grows by ~150 lines (the 5-signal detection + report/enforce functions), all bash, none of it typechecked or unit-testable the way the rest of this phase's deliverable is | Matches today's exact behavior and today's exact failure mode: the guard fires ONLY if the launcher itself is invoked — running the compiled `vice-broker.mjs` directly (bypassing the launcher) inside a container is UNGUARDED, exactly as it is unguarded today if someone runs `node resources/vice-broker.mjs` directly without going through the shell wrapper (untested, because nothing does this today) |
| **(b) Port to TypeScript, checked at the broker's own process startup, before any state read/write or spawn** | A genuine port (not large — the 5 signals are `fs.existsSync`, one `process.env` read, one `execFileSync("systemd-detect-virt", ...)`, one `fs.readFileSync("/proc/1/cgroup")` — all directly Node-portable, no bash-specific construct among them) | **Strictly stronger protection**: the broker refuses to run inside a container even if invoked directly, not only when invoked through the launcher — and the check becomes directly unit-testable via `node:test` (mock `/proc/1/cgroup`'s content, mock env vars) rather than only reachable via a bash subprocess spawn, which is exactly the kind of test-mechanism improvement criterion A's own redesign mandate is about |

**Recommendation: (b).** It costs a real but bounded port (5 independent, already-well-commented
signal checks — see the file's own `_container_guard_record_signal`/`container_guard_evaluate`
structure, which maps cleanly onto a TypeScript function returning a typed signal list), it
STRENGTHENS the guarantee rather than merely relocating it, and it moves the guard into the same
`node:test`-driven, directly-callable observation surface this phase's own criterion A redesign
already requires for everything else. The launcher itself then keeps Decision 2's original,
narrower framing (*"resolve its own directory, verify `node` exists on `PATH`... and `exec` into the
Node entry point. No lifecycle logic lives in the shell file"*) — the guard is lifecycle logic, and
belongs where the rest of the lifecycle logic now lives. **If (a) is chosen instead, that is
equally defensible and equally satisfies C6's literal text** — record whichever is chosen, and why,
in the plan, per criterion 6's own explicit ask ("deliberately either way").

session read `count_launching()` directly (lines 842–852) and its TWO call sites
(`process_requests()` line 1269, `maintain_spares()` line 1409) to confirm the design against the
real mechanism rather than a paraphrase:

```typescript
// Confirmed against vice-broker.sh's count_launching() (lines 842-852) and its two call
// sites, process_requests() (line 1269) and maintain_spares() (line 1409) -- both consult
// the SAME counter so a cold launch and a warming launch can never race (the 2026-08-01
// outage: three simultaneous x64sc spawns, one SEGV/one exit-1/one exit-0 at the identical
// spawn second, per vice-broker-lifecycle-decisions.md Decision 3).
let launchInFlight = false;

async function tryLaunchOne(reason: "cold" | "spare", port: number): Promise<void> {
  if (launchInFlight) return; // synchronous check, no await since the last set
  launchInFlight = true; // synchronous set -- the pair cannot be interleaved
  try {
    await spawnOneInstance(port, reason);
  } finally {
    launchInFlight = false;
  }
}
```

**One nuance the bash version has that a naive port could lose:** `process_requests()`'s in-flight
flag starts from `count_launching() > 0` (a snapshot at the TOP of the pass) but then sets its OWN
local copy to `1` the moment IT ITSELF starts a cold launch (bash line 1315,
`in_flight=1` inside the loop) — so a SECOND pending request later in the SAME pass sees the
just-started launch and defers, without needing to re-query global state. The TypeScript idiom
above achieves the identical property for free (the module-level flag IS the shared state both the
"first request in this pass" and "every later check, in this pass or a future one" observe) — but
the required test is the SAME one `01.6-RESEARCH.md §D2` already specifies: **two concurrent launch
requests against a stubbed spawn, asserting exactly one spawn occurs** (this group's own criterion
C, verbatim). Confirmed here that this is not merely a good idea but a DIRECT reproduction of the
2026-08-01 incident's shape — the test should be understood as regression-testing a real, previously
uncaught outage, not a hypothetical race.

**The "priority between launch reasons" question (`vice-broker-lifecycle-decisions.md` Decision
5.1) is explicitly declined per §A1** — the ported behavior should match today's: whichever of
`process_requests()` or `maintain_spares()` runs first in a given pass gets to launch; there is no
priority queue. Confirm this is stated explicitly in the plan so a reviewer does not mistake its
absence for an oversight.

## D. State Design

### D1. `broker.json` and the epoch file — the two on-disk exceptions (C1, C4, D-04)

**`broker.json`.** `vice-broker.mts` (191 lines, the Phase 01.6 tracer) already implements
`writeBrokerRecord()`, `readBrokerRecordMaybe()`, `parseArgs()`, and a `main()` CLI entry — all
directly reusable. **The one required change**: the tracer's record carries exactly `pid`,
`started_at`, `node_version` and DELIBERATELY omits `heartbeat_at` (its own header: *"DELIBERATELY
OMITS heartbeat_at... Adding a heartbeat field here would make an inert record read as 'alive' to
every session's proxy"*) — correct for a tracer that writes once and exits, WRONG for a real
long-lived broker, which must refresh `heartbeat_at` every pass exactly as `write_broker_json()`
(bash, lines 924–947) does, or `readBrokerLiveness()`'s `alive`/`stale`/`never_started`
classification (already implemented, container-side, unchanged by this phase) permanently reads a
running broker as `never_started`. **This is the single most important thing to get right and the
easiest thing to accidentally carry forward wrong** — the tracer's own code comment about omission
is correct FOR THE TRACER and actively harmful if copied into the real broker without re-reading why
it was there.

The bash version's field set (`version`, `written_by`, `pid`, `started_at`, `heartbeat_at`,
`spares_target`, `max_instances`, `ttl_seconds`, `poll_ms`, `dry_run`) is a reasonable template for
the TS version to match or extend — no consumer parses anything beyond `pid`/`heartbeat_at`
(confirmed: `readBrokerLiveness()` reads exactly those two plus checks `heartbeat_at`'s presence),
so extending the shape is safe; dropping fields other consumers don't read is also safe. Recommend
keeping the full field set for operational visibility (a human reading `broker.json` by hand still
benefits from `spares_target`/`ttl_seconds` etc.), updating `written_by` to name the TS broker
(§A2), and adding `node_version` (already in the tracer, must survive into the real broker — this
is literally C1's deliverable).

**The epoch file (D-04).** Confirmed by direct read this session: `vice-supervisor.sh`'s
`write_epoch()` (lines 289–306) writes `$VICE_SUPERVISOR_DIR/epoch.json`, where
`VICE_SUPERVISOR_DIR` is set by the CALLER (`vice-broker.sh`'s `launch_instance()`, line 1101:
`VICE_SUPERVISOR_DIR="$dir"` where `dir="$VICE_POOL_DIR/$port"`) — so the real, resolved path is
**`.vice-supervisor/<port>/epoch.json`**, one per instance, keyed by port. Fields: `epoch` (int,
monotonic per-instance, incremented on every respawn), `spawned_at` (ISO 8601), `pid` (the `x64sc`
child's own pid — this is the field `handle_recycle_request()` reads via `read_epoch_field()`,
`pid`, per T-01.3-04's rule that recycle targets the CHILD's pid, never the supervisor's own bash
pid), `supervisor_pid` (currently the SUPERVISING BASH PROCESS's own `$$` — **this field's meaning
must be reconsidered**: once there is no separate supervisor process, is this the broker's own pid,
or should it be dropped as meaningless? Recommend dropping it or repointing it at the broker's own
pid — no consumer currently reads it per the grep in §B's `teardown()` row: *"never the recycle
target... there is no reader here for a caller to reach for by accident"*), `vice_bin` (the resolved
binary name, read by `handle_recycle_request()` and by `signal_vice_child_pid()`'s identity check),
`vice_args` (array of strings), `log` (relative path to the boot log), `dry_run` (bool).

**The write must be atomic** (tmp-in-same-dir → `mv`), matching `write_epoch()`'s own comment: *"The
container polls this file on its own schedule and must never observe a half-written JSON document
mid-write."* Container-side `readEpoch()` (`vice.ts:416-439`) already treats this file as
**untrusted, host-written input** — `JSON.parse` in try/catch, `epoch` must decode to a finite
integer, unknown fields ignored, never throws. This phase's broker is now the WRITER of a file the
container already treats defensively; no change needed on the container side, and the contract
(exact field names, exact path shape) must not drift, or the READER (unchanged, still expecting the
current shape) silently stops seeing valid epochs.

### D2. In-process shape — what moves, what stays a file (the corrected version of C4)

Re-derived precisely in §B's `lease_is_stale()` row above — restated here as the governing rule for
the whole phase, since it resolves an ambiguity the ROADMAP's own criterion 4 text leaves open:

**Moves in-process (broker-internal bookkeeping, both writer and reader are the broker):**
- `grants/` — becomes a `Map<string, GrantRecord>` keyed by request id.
- `spares/` — becomes a `Map<number, SpareRecord>` keyed by port (matching the bash version's own
  `spares/<port>.json` keying).
- `broker-instances.json` — likely dropped entirely (§B, `write_instances()` row) or, if kept for
  operational visibility, becomes a derived/computed view over the two maps above, never
  independently maintained (matching the bash version's own "pure projection" comment).
- `BLOCKED_PORTS` — becomes a `Set<number>`.

**Stays a file (protocol boundary — writer and reader are DIFFERENT processes, one of which is not
converting in this phase):**
- `requests/` — container-written, broker-read.
- `denials/` — broker-written, container-read.
- `leases/` — container-written (`vice-broker-client.ts`'s `createLease()`/`touchLease()`/
  `releaseLease()`, unchanged), broker-read (staleness check).
- `recycle-acks/` — broker-written, container-read (`pollRecycleAck()`, unchanged).
- `broker.json` — the confirmed C4 exception.
- Per-instance `epoch.json` — the confirmed D-04 exception.

**This means C4's "in one place, in process" is precisely: the broker's own coordination bookkeeping
(who is a spare, who is granted, which ports are taken) — not the wire protocol it uses to talk to
the container, which criterion 4's own closing sentence already says is out of scope
("Retiring the file *protocol* is Phase 01.7 — this criterion is about where state lives, not how
the proxy talks to it").** State this distinction explicitly in the plan — it is the difference
between "convert everything to in-memory" (wrong; breaks the container's ability to write a request
or a lease at all) and "convert the broker's own private bookkeeping" (correct, and the literal
reading of both C4's text and D-2c's own six-item list, three of whose six items — `requests/`,
`leases/`, and arguably `broker-instances.json` — turn out on close reading to be either
protocol-facing or droppable, not internal state that moves).

### D3. Catchable shutdown — direct application of `01.6-RESEARCH.md §D1`

No new design needed — that document's `verifiedKill()`/`shutdown()` sketch was reasoned from
`vice-broker.sh`'s OWN `signal_recorded_pid()` (confirmed, byte-for-byte matching, in §B above).
**The one adaptation this phase's design requires**: `verifiedKill()`'s identity check needs the
EXPECTED SUBSTRING to be the `x64sc` binary path (or resolved name), not a supervisor script path —
per §B's `teardown()` row, this is a forced consequence of spawning `x64sc` directly rather than via
an intermediate `vice-supervisor.sh` process. Record each child's expected-identity string at spawn
time (mirroring how `signal_vice_child_pid()` already takes an explicit `expected_bin` parameter
rather than a hardcoded constant), and iterate every recorded child on `shutdown()`, exactly as
`reap_all_instances()` does today (§B).

## E. Suggested Slicing — Keeping the Suite Green Continuously

This phase's own scope is smaller and more concentrated than 01.6.1's (one directory of internal
state, one concurrency guard, one shutdown path, one absorbed sibling process) — but it is also the
one place in the whole conversion where the OLD test mechanism (spawn bash, inspect files) has no
replacement to slice INTO gradually; the replacement suite has to exist before any of the new
broker's behavior can be asserted at all. Recommended order:

1. **Wave 0 — the state shape and its own unit tests, no wiring to real spawn yet.** Define the
   typed `GrantRecord`/`SpareRecord` shapes and the pure functions that operate on them
   (`nextFreePort()`, `countReady()`, `countTotal()`, `countLaunching()`) — directly unit-testable
   with in-memory fixtures, zero process spawning, zero filesystem I/O. This is the fastest possible
   feedback loop and de-risks the largest number of §B's "deleted, not ported" rows in one slice.
2. **Wave 1 — the concurrency guard (criterion C) in isolation**, against a STUBBED spawn function
   injected as a parameter (not a real `child_process.spawn` call) — the exact "two concurrent
   launch requests, assert exactly one spawn" test this group's own criteria require, buildable and
   green before any real `x64sc` interaction exists.
3. **Wave 2 — the shutdown/kill discipline (criteria D, D3 above)**, against a stubbed
   `process.kill`/`ps` — reusing `01.6-RESEARCH.md §D1`'s exact sketch, tested the same way its own
   `signal_recorded_pid()`/`signal_vice_child_pid()` bash originals are tested today (per §F, these
   ARE among the survivable tests, re-pointed at the new implementation).
4. **Wave 3 — the file-protocol boundary (broker.json + epoch.json writers, D1/D-04)** — these are
   the two places this phase's code touches the filesystem for real, and both have direct,
   narrowly-scoped tests (byte-for-byte field/mode assertions, matching `vice-broker-launch.test.ts`'s
   own existing style for `broker.json` — extend that file rather than starting fresh).
5. **Wave 4 — wiring it all together behind the real `child_process.spawn`**, with the protocol
   files (`requests/`, `leases/`, `denials/`, `recycle-acks/`) exercised against the UNCHANGED
   container-side `vice-broker-client.ts` — the closest this phase gets to an integration test, still
   with zero real `x64sc` (per the hard rule: no real emulator, `mcp__vice__*` is the only route).
6. **Wave 5 — deletion.** `resources/vice-broker.sh`, `resources/vice-supervisor.sh`,
   `resources/lib/container-guard.sh`, `resources/lib/repo-root.sh`, and `vice-broker.test.mjs`
   itself are removed in the SAME wave the new implementation is proven green — never a wave where
   both the old and new implementations coexist untested against each other (that window is exactly
   where a "looks converted" false confidence would hide).

**Key insight:** every "don't hand-roll" item in this phase is really the same insight applied

expressing it (typed objects instead of grep, `JSON.parse` instead of regex extraction, a boolean
flag instead of a file glob) — never a redesign from scratch.

## Common Pitfalls

### Pitfall 1: Copying the tracer's "no heartbeat_at" comment forward literally

**What goes wrong:** the real broker's `broker.json` writer is built by extending
`vice-broker.mts`'s existing `writeBrokerRecord()`, and the function's own header comment says, in
capital letters, "DO NOT add heartbeat_at" — a contributor who does not re-read WHY (it was correct
for a tracer that writes once and exits; it is wrong for a long-lived daemon) copies the comment's
constraint forward and ships a broker that never reports `alive`.
**Why it happens:** the comment reads as an absolute rule rather than a rule scoped to the tracer's
own narrow behavior.
**How to avoid:** state explicitly in the plan (per §D1) that this phase's broker MUST add
`heartbeat_at`, refreshed every pass, and that the tracer's comment does not apply to it.
**Warning signs:** a converted broker whose `broker.json` never carries a `heartbeat_at` field, or a
test asserting the tracer's own "must NOT carry heartbeat_at" invariant against the REAL broker's
output (that assertion belongs only to `vice-broker-launch.test.ts`'s tracer-specific tests).

### Pitfall 2: Treating the identity-check substring as unchanged

**What goes wrong:** `teardown()`/`signal_recorded_pid()`'s bash identity check matches against
`$SUPERVISOR_SCRIPT`'s own path — a straightforward-looking "port this constant" task silently ships
a broker whose kill discipline checks a process against a script path that no intermediate process
exists to have ever been invoked as, so the identity check ALWAYS fails, `signal_recorded_pid()`
ALWAYS refuses to signal, and every `teardown()`/`shutdown()` call silently orphans its instance
while logging a "possible pid reuse" warning that is actually just a wrong expected-string constant.
**Why it happens:** the constant look like a config value to carry forward, not a design decision
tied to a process topology this phase specifically removes.
**How to avoid:** confirm explicitly in the plan (per §D3/§B's `teardown()` row) that the expected
identity string becomes the `x64sc` binary path/name, recorded at spawn time — never a leftover
reference to a supervisor script this phase deletes.
**Warning signs:** any string literal in the new broker's kill-discipline code that still contains
`vice-supervisor` or `SUPERVISOR_SCRIPT`.

### Pitfall 3: "Improving" the serialised-warming break into concurrent spawns

**What goes wrong:** `maintain_spares()`'s bash loop deliberately `break`s after the FIRST successful
launch per pass, taking N passes to reach a warm floor of N rather than launching all N at once — an
event-loop port using `Promise.all()` over several pending launches "for efficiency" silently
reintroduces the exact GPU/audio race that caused the 2026-08-01 triple-launch outage.
**Why it happens:** `async`/`await` makes concurrent operations look free and idiomatic; nothing
about the code itself signals that concurrency here is actively dangerous rather than merely
unnecessary.
**How to avoid:** the single `launchInFlight` flag from §C already prevents this MECHANICALLY if
every launch path (cold-launch and warming alike) goes through the SAME guarded function — state
this invariant explicitly and test it (criterion C's own required race test) rather than trusting
code review alone to catch a `Promise.all` slipping in later.
**Warning signs:** any call site that launches more than one instance without an `await` between
them, or any code path that does not go through the single guarded launch function.

### Pitfall 4: Deleting `requests/`/`leases/` on shutdown because the bash version's `purge_protocol_state()` did

**What goes wrong:** a line-by-line reading of `purge_protocol_state()` deletes `requests/` and
`leases/` unconditionally on shutdown, exactly as bash does — but per §D2, those directories are
CONTAINER-WRITTEN, and a container session that wrote a lease moments before the broker died still
believes it holds one. Silently deleting it out from under that session (rather than the container
discovering, on its own next call, that the grant/lease relationship no longer holds) is a policy
choice with real consequences, not a mechanical carry-forward.
**Why it happens:** the bash function's own scope (every file it deletes) reads as one atomic,
uncontroversial "clean shutdown" concept, obscuring that three of its five deletions are actually
about DIFFERENT processes' state.
**How to avoid:** treat this explicitly as an Open Question (below) rather than silently porting the
bash behavior; the safest default is likely "delete only what THIS broker owns (in-process state has
nothing to delete by construction; `broker.json` and the epoch files, yes) and leave `requests/`/
`leases/`/`denials/`/`recycle-acks/` for the next broker start (or a container-side timeout) to
reconcile" — but confirm this reasoning explicitly rather than assuming it.
**Warning signs:** a shutdown implementation that calls anything resembling `rm -rf` on

## Open Questions

1. **Does `broker-instances.json` survive this phase at all?**
   - What we know: it is a pure projection with no confirmed consumer outside the bash daemon and
     its own tests (§A2).
   - What's unclear: whether a human operator or a future tool (a status-reporting skill, say) is
     expected to read it.
   - Recommendation: drop it unless the plan finds a concrete consumer; if kept, it must remain a
     pure derived view, never independently maintained, exactly as today.

2. **Does the shutdown path delete `requests/`/`leases/`/`denials/`/`recycle-acks/`, or leave them
   for the next start to reconcile?**
   - What we know: the bash version deletes them unconditionally; those directories are
     container-written, not broker-internal state, once this phase's design (§D2) separates the two.
   - What's unclear: whether a session's in-flight lease/request surviving a broker crash (and being
     silently discarded on the NEXT broker start instead of on shutdown) changes any observable
     container-side behavior in a way that matters.
   - Recommendation: treat as an explicit design decision for the plan (Pitfall 4), not a mechanical
     carry-forward; the safest default is likely "the broker deletes only what it owns" with
     reconciliation (if any is needed) happening at the NEXT start via the same drop-dead-record
     logic §B's `drop_dead_instance_records()` row already notes has no direct equivalent anyway.

3. **Does the surviving launcher need a `--detach`-equivalent mode, or does detaching move entirely
   to whatever process manager (systemd, `nohup`, manual) starts the launcher itself?**
   - What we know: the bash daemon's own `--detach`/`setsid`/recursion-guard machinery (§B,
     `cmd_start()` row) exists because a foreground bash process is fragile to a closed terminal or
     SIGHUP; a Node process invoked via a thin launcher has the exact same fragility if run the same
     way.
   - What's unclear: whether this phase's scope includes reproducing that resilience, or whether it
     is legitimately deferred to "however an operator chooses to run the launcher" (their own
     `nohup`/`setsid`/systemd unit, outside this project's code).
   - Recommendation: recommend deferring to the operator's own process-management choice (matching
     Decision 2's framing that the launcher stays thin) rather than re-implementing bash's own
     recursion-guarded re-exec dance in either bash or TypeScript — but confirm this is a deliberate
     choice, not an oversight, in the plan.

| Pattern | STRIDE | Standard Mitigation |
|---|---|---|
| Malformed/half-written protocol file (a request, a lease) read as a crash-inducing input | Denial of Service | The never-throw discipline, reused verbatim from `vice-broker-client.ts`'s own existing `readJsonMaybe()` posture — this phase's broker is a NEW reader of these files but must inherit the SAME defensive posture the container-side writer already assumes the reader has. |
