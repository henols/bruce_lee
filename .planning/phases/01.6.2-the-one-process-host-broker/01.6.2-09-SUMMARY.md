# Phase 01.6.2 Plan 09: Repoint Every Host-Instruction Message, Delete the Dead-Capability Paragraph, Triage Every Old-Port Reference Summary

**Eight agent-facing/operator-facing messages that would otherwise instruct a human or an agent to run a file this phase deletes now name the one surviving launcher (tools/vice-launcher.sh) with an invocation it actually accepts; the installer's standalone-recovery-pipeline paragraph is deleted rather than repointed; and all 35 references to the port number the emulator band moved away from are individually triaged into four named categories, with the one non-port occurrence left deliberately untouched as the proof that bulk replacement would have been wrong.**

## Performance

- **Duration:** ~1h45min (estimated; no precise start timestamp was captured at session start)
- **Tasks:** 2 (task 1 `type="auto"`, task 2 `type="auto"`)
- **Files modified:** 10 (9 within task 1's declared `files_modified` plus `vice-probe.test.ts`, all within the phase's declared `files_modified` roster)

## Accomplishments

- **Every host-instruction message repointed (task 1):** `supervisorHostPath()` (the retiring per-instance supervisor's host-path helper) is deleted outright. Its three former consumers -- `neverStartedMessage()`, `deadOrHungMessage()`, `aliveButFailedMessage()` -- now resolve `brokerHostPath()`, the SAME single helper the broker-absent triple (`brokerNeverStartedMessage()`/`brokerDeadOrHungMessage()`/`brokerLaunchFailedMessage()`) already used, itself repointed from `tools/vice-broker.sh` to `tools/vice-launcher.sh`. A structural test proves exactly one host-path helper survives.
- **Four prose instructions repointed:** three in `vice.ts` (`rpc()`'s timeout catch, `withReconnect()`'s exhausted-retry throw, `assertSameMachine()`'s no-evidence throw) and one in `vice-sync.ts` (`waitCheckpointHit()`'s never-fired throw) now name `tools/vice-launcher.sh` and describe what its broker actually does: launches a boot-fresh instance on demand, supervises it, and respawns a crashed one with backoff, logging the crash for the same root-cause investigation the original messages already pointed at.
- **The STATED RESIDUAL comment resolved, not merely reworded:** the comment recording that `aliveButFailedMessage()` named a separate supervisor path even under a broker-granted session is now explicitly marked RESOLVED -- that tension dissolved once both messages resolve the identical single launcher, and the comment says so rather than leaving a note describing a state that no longer exists.
- **The installer's dead-capability paragraph deleted, not repointed (task 1):** `install-resources.ts`'s `hostLaunchInstructions()` used to return two paragraphs -- one repointable (the broker launcher) and one advertising a standalone (non-MCP) recovery pipeline whose own scripts (`vice-pool.mjs`/`vice-session.mjs`) were already deleted behind a zero-consumers gate in an earlier phase (`01.6-CONTEXT.md` D-02). The second paragraph is gone entirely; only the broker-launch paragraph survives, repointed at `vice-launcher.sh` and reworded for one script instead of two. This function had NO prior test coverage at all; two new tests now cover it, including one that compares its named exit codes against `containerGuardEnforce()`/`containerGuardReport()`'s own LIVE-computed return values in this containerized environment (2 refuse, 3 report), rather than a second hardcoded literal.
- **New structural gate with proven discriminating power (task 1):** `host-scripts.test.ts` gains a directory-enumerating test (`RETIRING_DAEMON_FILENAMES = ["vice-supervisor.sh", "vice-broker.sh"]`) asserting neither filename appears anywhere in the module directory's non-test TypeScript source, with `//`/`/* */` comments stripped first so a header sentence recording history cannot self-invalidate the gate. Its discriminating power was verified LIVE: a non-comment probe line naming `vice-broker.sh` was temporarily appended to `vice.ts`, the gate was re-run and confirmed to FAIL naming that exact file and filename, the probe was reverted (`diff` confirmed byte-identical), and the gate was re-confirmed passing. The gate's own comment notes `resources/` is deliberately out of scope this wave (the shallow, non-recursive `readdirSync(HERE)` never reaches that subdirectory anyway, since the two retiring scripts' actual bytes survive there until plan 11).
- **Port triage, per-occurrence, into four named categories (task 2):** a fresh count at execution time found 35 occurrences of the old port number across the five files (plan-time estimate was "roughly thirty-four" -- within tolerance, no drift investigation needed):

  | File | Count | Category | Action | Reasoning |
  |---|---|---|---|---|
  | `vice.ts` | 4 (`DEFAULT_ENDPOINT`'s URL literal + `activePort`'s two-branch fallback) | Human-band / fixed-port fallback | KEPT, comment added | Describes an `x64sc` a human launches on the host for their own work in the reserved 6510-6599 band -- under D-18's new convention this is MORE correct than before, not merely unchanged |
  | `vice-probe.test.ts` | 2 | Human-band / fixed-port fallback | KEPT, comment added | Tests the same default endpoint against the real (currently down) host |
  | `vice-proxy.ts` | 1 (`"6510 processor port at $01"`, HIRAM bit comment) | NOT A PORT | Left completely untouched | Names the MOS 6510 CPU's own hardware I/O register, not a TCP port at all -- this occurrence is the concrete illustration of why per-occurrence triage (not bulk replace) was required |
  | `incident-record.test.ts` | 28 | Arbitrary fixture value | Left unchanged (group decision) | The module's `port` field is opaque to every test in this file, which exercises port-value-agnostic filename/frontmatter-rendering logic; moving to 6600+ would falsely suggest the fixtures verify something about a specific band |
  | `vice-broker-client.test.ts` | 0 | -- | Nothing to triage | -- |
