## Decisions Made

- **The five new InstanceRecord fields are OPTIONAL, not required.** `broker-state.test.ts`'s own `makeInstance()` helper constructs full `InstanceRecord` literals directly and is NOT in this plan's `files_modified`; making the fields required would have broken that file's typecheck for a file this plan has no mandate to touch. `superviseChild()` is the one writer that always sets all five together, immediately after every launch — every OTHER record-construction site (plain `tryLaunchOne()`/`acquirePortAndLaunch()` calls, existing tests) remains valid without them by construction.
- **`superviseChild()` computes its own per-respawn log file rather than reusing `vice-broker.mts`'s `makeLoggingSpawn`/`spawnFactory` mechanism for the log path.** `vice-broker.mts` is outside this plan's scope, and a caller-supplied `spawnFactory`'s internal log-opening (established in a prior plan) has no channel to hand its log path back to `broker-launch.mts` across an async respawn boundary that happens long after the original call site returned. Instead, `broker-epoch.mts`'s `instanceLogDirFor()` is called directly, and the log file's existence is guaranteed (touched into being if the injected spawn implementation is a test stub that never itself writes) rather than trusted to whichever spawn implementation the caller happened to supply.
- **The crash-loop give-up threshold mirrors `vice-supervisor.sh`'s own `>= VICE_MAX_RESTARTS` check exactly** (give-up fires on the Nth crash when `maxRestarts=N`), confirmed by direct reading of the retiring script's `while true` loop rather than the plan prose's "one more than the maximum" test-scenario phrasing, which was read as describing a safety-margin test choice (crash `max+1` times to be unambiguously over the line), not a different threshold semantic.
- **The real vs. fake "stub child" choice was made per-assertion, not blanket.** Real short-lived subprocesses (`/bin/true`, `/bin/sleep`) are used wherever a genuine OS pid is the point (the no-orphan liveness check; the plain exits-on-its-own case) — matching `host-scripts.test.ts`'s own cited idiom exactly. A fully test-controlled `EventEmitter` cast as `ChildProcess` is used wherever EXACT ordering control over backoff/crash-window timing is the point, since a real process's exit timing cannot be driven step-by-step.

## Issues Encountered

- **A test-authoring bug during Task 2's own development, caught and fixed before commit, not left in the committed suite.** The first version of the "a stub child that exits on its own is respawned" test used `maxRestarts: 50` with a spawn function that ALWAYS returned a real, instantly-exiting `/bin/true` process. Because the injected `sleepMs` resolves instantly (as intended, for deterministic fast tests) and `/bin/true` exits almost immediately, the crash→respawn cycle raced through all 50 allowed crashes and gave up within milliseconds — far faster than the test's 10ms-interval poll could observe the intermediate "epoch reached 2" state, so the test flaked to a hard timeout (confirmed via a standalone debug script, not a re-run guess). Root cause was the TEST's own design (an unbounded fast cascade against a real, self-perpetuating crash loop), not the implementation. Fixed by having the spawn function return a real `/bin/true` only for the FIRST launch and a long-lived `/bin/sleep 300` for every launch after that, so the chain deliberately settles at epoch 2 instead of continuing to crash. A second, related bug surfaced in the SAME test's own cleanup: killing the settled `/bin/sleep` child without first setting `deliberateKill = true` triggered ANOTHER automatic respawn (correct behavior on the implementation's part — an un-marked exit is a crash by design) that spawned a fresh, untracked `/bin/sleep` the test never accounted for, leaving an orphan process that hung the entire `node --test` process after all individual tests had already reported pass (confirmed via `ps aux` showing a lingering `/bin/sleep 300` and the `node --test` process itself still alive after all test output had printed). Fixed by marking `deliberateKill = true` before the cleanup kill, exactly mirroring the deliberate-kill test's own established pattern. Recorded here because it demonstrates the supervisor working exactly as specified under adversarial-to-the-test conditions, not a defect in `superviseChild()` itself.
