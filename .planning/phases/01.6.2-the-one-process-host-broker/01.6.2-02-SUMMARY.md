## Decisions Made

- **C7's import could not land literally in `broker-state.mts`.** Verified empirically (a scratch `tsc -p tsconfig.build.json` run) that importing `vice-broker-client.ts` — even as a type-only re-export attempt — pulls its transitive dependents (`repo-root.ts`, `install-resources.ts`, `hostpath.ts`) into the same build program, either failing to compile under `tsconfig.build.json`'s `allowImportingTsExtensions:false`, or — if that flag were loosened — forcing `resources-sync.test.ts` to require those unrelated container-side files be committed under `resources/` as if host-bound. `broker-state.mts` has no code path that validates a request id at all, so there is nothing to hand-roll; the shared binding (`REQUEST_ID_PATTERN`/`isValidRequestId`) is proven via a test-only import in `broker-state.test.ts`, plus a structural grep-for-zero-copies test across all six broker `.mts` modules (`broker-state`, `broker-launch`, `broker-control`, `broker-kill`, `broker-epoch`, `vice-broker`) confirming none hand-rolls a second copy of the pattern.
- **`broker-launch.mts`'s runtime dependency on `broker-state`'s VALUES was removed in favour of required, injected deps.** Discovered while writing this module's own unit test: `broker-launch.mts` is the first host-bound module whose test imports it DIRECTLY, unbuilt (native Node type-stripping), rather than spawning the compiled artifact as every prior cross-importing test (`vice-broker-launch.test.ts`, `broker-e2e.test.ts`) does. Node's native resolver does not map a `.mjs` import specifier to a sibling `.mts` source the way `tsc`'s build does (confirmed via a minimal scratch repro), so a value import that compiles fine under the build fails outright at direct execution. `import type` is fully erased under this project's `verbatimModuleSyntax` and was confirmed to sidestep the resolution entirely, so `broker-launch.mts` now imports only TYPES from `broker-state.mjs`, taking `nextFreePort`/`countReady`/`countTotal`/`countLaunching` as required fields on `MaintainWarmFloorDeps`/`AcquirePortAndLaunchDeps` instead. `vice-broker.mts`, which already imports `broker-state.mjs`'s real values, supplies them at the real-broker wiring site.
- **`acquirePortAndLaunch()` added, holding the guard across the async port-allocation step.** `nextFreePort()` was made asynchronous specifically to support a REAL port-in-use probe (a bind-and-release check on 127.0.0.1) rather than a stub — a genuine improvement over the bash original's synchronous `/dev/tcp` check, but one that introduces a race no synchronous allocator has. `tryLaunchOne()` itself is unchanged (its inner spawn+record logic extracted into a private `spawnAndRecordInstance()` both functions now call) — it remains the right primitive for a caller with an already-decided port. `acquirePortAndLaunch()` is the new primitive for a caller that needs a FRESH port; both `handleAcquire` (cold acquire) and `maintainWarmFloor` (warm launch) now route through it.
- **The criterion C race test targets `acquirePortAndLaunch()`, not `tryLaunchOne()` directly.** An early version of this test used `tryLaunchOne()` with two different ports and passed — but this was later recognised as a vacuous test: `tryLaunchOne()` has no internal `await`, so two separate calls to it can never actually overlap in JS's single-threaded, run-to-completion model, and launching two different instances for two different requests on two different ports is correct behaviour, not a race. The corrected test targets the function that genuinely has an async gap, using a shared, deferred port allocator so both concurrent requests are told the identical candidate port is free — the realistic shape of the race.
