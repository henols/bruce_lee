# Phase 01.6.2 Plan 08: D-13/D-14 -- A Dead Machine Costs One Acquisition, Broker Death Gets the Same Discipline Summary

**A granted instance that stops answering costs this session exactly one automatic replacement acquisition (adopted through the same containerizeGrant()/useInstance() seam the ordinary acquisition uses), the triggering call still fails loudly naming the machine as REPLACED/FRESH/GONE, and broker death discovered mid-replacement gets the identical discipline: one fresh-session attempt, then either the same replaced-machine report or an honest "session must be restarted, the broker is the cause."**

## Performance

- **Duration:** ~1h15min
- **Tasks:** 2 (task 1 `type="auto" tdd="true"`, task 2 `type="auto" tdd="true"`)
- **Files modified:** 2 (both within this plan's declared `files_modified`)

## Accomplishments

- **D-13, replace-and-report (task 1):** the retired `brokerGrantedUnreachableMessage()` (report an unreachable granted instance, tell a human to investigate on the host) is replaced by `handleGrantedInstanceUnreachable()`: when the pre-flight probe finds the session's granted instance unreachable, the proxy immediately acquires a replacement over the SAME held control session, adopts it through `adoptGrant()` (the one seam `ensureBrokerLease()` itself now also calls, for its ordinary acquisition), re-baselines the epoch, and returns `machineReplacedMessage()` -- an error, never a result, naming three facts verbatim: the machine was REPLACED, the replacement is a FRESH emulator, and prior state on the old instance is GONE.
- **One shared vocabulary, not invented twice:** `machineReplacedMessage()` builds its epoch-comparison sentence by calling `epochDriftMessage()` directly -- the exact function the pre-existing fixed-port epoch-drift guard already uses -- so a reader meeting this new report recognizes the same discipline this project already had for a voided run, rather than learning a second one. A dedicated structural test asserts this reference exists in the function's own source.
- **Bounded, never a loop:** exactly one replacement attempt per triggering call. A replacement the broker itself refuses (`at_capacity`, etc.) produces `replacementFailedMessage()`, naming both the original unreachability and the failed replacement, and does not retry. Two consecutive calls against a still-unreachable replacement each attempt exactly one MORE replacement (proven by an acquire counter reaching 2 then 3 across two calls) -- nothing is memoised as a sticky negative.
- **D-14, broker death gets the same discipline (task 2):** when the same-session replacement attempt itself resolves `kind: "broker_gone"` (the control connection is gone, not merely the emulator instance), `handleGrantedInstanceUnreachable()` attempts exactly one fresh `openBrokerControl()` -- a genuinely new `broker.json` read, never the stale record the dead session was opened against. If a fresh session opens and can acquire, it replaces and reports through the identical `machineReplacedMessage()` path. If nothing can be opened (or the fresh session's own acquire fails), `sessionMustRestartMessage()` reports that the session must be restarted, naming the broker -- not this proxy -- as the cause.
- **Recycle's placeholder branch discharged, deliberately conservatively:** `handleRecycle()`'s pre-existing `broker_gone` branch (plan 07's distinguishable-but-unworded placeholder) now returns `sessionMustRestartMessage()`'s text instead of a bare transport error string. It deliberately does NOT attempt a fresh-session replacement the way a forwarded call does -- the instance a recycle was trying to kill is of genuinely unknown state when the connection drops mid-request, and silently handing back an unrelated "replacement" under the name of a recycle result would overstate certainty about a kill that may or may not have reached the broker.
- **Accepted regression, recorded in source:** a comment above `handleGrantedInstanceUnreachable()` names broker death as an ACCEPTED, KNOWING regression against the retiring file protocol's own tolerance (before plan 07's transport swap, the only broker dependency surviving past a grant was a silent-no-op file write; under one held TCP connection that safety margin is given up deliberately, per the tolerance decision in `broker-control-plane-over-tcp.md`), so a future reader finds this documented rather than rediscovering it as a defect.
- **Never-cache extended to a third path:** `controlSession` is deliberately left pointing at a known-dead session object on every D-13/D-14 failure branch (never nulled, never replaced with a sentinel) -- proven by two dedicated tests where a second call, after the first call's failure, independently re-attempts the exact same from-scratch sequence (one more replacement acquisition for D-13; one more fresh `openBrokerControl()` for D-14) rather than repeating a cached verdict.
