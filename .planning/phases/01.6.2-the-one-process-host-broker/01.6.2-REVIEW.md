# Phase 01.6.2: Code Review Report

**Reviewed:** 2026-08-04T06:08:50Z
**Depth:** standard
**Files Reviewed:** 33
**Status:** issues_found

## Summary

This phase replaces a 2,546-line bash host daemon with an in-process TypeScript broker and a
TCP control plane. The token-gate, framing, and the single-owner `inFlight` launch guard are all
implemented correctly and match their own extensive header commentary — I could not find a
check-then-act race across an `await` in `tryLaunchOne()`/`acquirePortAndLaunch()`, and the
constant-time token comparison runs before any state is touched, as documented.

However, tracing the actual call graph the real broker entry point (`vice-broker.mts`) wires up
at runtime — as opposed to what `broker-launch.mts`'s own extensive comments and
`broker-launch.test.ts`'s unit tests describe — surfaces two serious defects that both produce
permanent, unbounded resource leaks in the real (non-test) broker process, and one destructive,
session-facing tool (`vice_recycle`) that does not do what its own tool description promises.
Both blockers below are provable by reading the wiring alone; neither requires a live emulator to
demonstrate.

## Critical Issues

### CR-01: Crash-respawn supervision (`superviseChild`) is never wired into the real broker — crashed/recycled instances leak forever and `vice_recycle` never actually respawns

**File:** `.claude/mcp/vice/vice-broker.mts` (the whole file; contrast with `.claude/mcp/vice/broker-launch.mts:820-823`)

**Issue:** `broker-launch.mts` implements a complete per-child supervisor — `superviseChild()` —
with crash-respawn, doubling backoff, a crash-loop give-up threshold, and a `deliberateKill`
marker so a released instance is never respawned. It is described repeatedly in that file's
comments as "absorbing `resources/vice-supervisor.sh` wholesale" and is exhaustively unit-tested
in `broker-launch.test.ts` (`superviseChild: a stub child that exits on its own is respawned...`,
the give-up test, the backoff-doubling test, etc).

`superviseChild` is exported but **never imported or called anywhere in `vice-broker.mts`**
(confirmed by grep — zero references outside its own definition/tests). The real broker's two
launch paths instead are:

- `handleAcquire()` (vice-broker.mts:274-318), which spawns via `acquirePortAndLaunch()` with a
  `spawnFactory` built from `makeLoggingSpawn()` (vice-broker.mts:230-239) — a bare
  `nodeSpawn(cmd, args, {stdio:[...]})` with **no `exit` listener attached at all**.
- `maintainWarmFloorForRealBroker()` (vice-broker.mts:402-429), whose `spawnFactory` wraps the
  same `makeLoggingSpawn()` spawn with equally no exit listener.

Consequences, all provable from the code alone:

1. When a real granted or warm-spare `x64sc` process crashes or is killed, nothing in the real
   broker ever observes the exit. The `InstanceRecord` for that port stays in `state.instances`
   forever, with its state frozen at whatever it was (`"granted"`/`"ready"`/`"launching"`) and its
   `pid` pointing at a dead process.
2. `nextFreePort()` skips any port already present in `state.instances`
   (`broker-state.mts:242`), so that port can never be reallocated — it is permanently lost from
   the allocatable band until the whole broker process restarts.
3. `countTotal()` counts every entry in `state.instances` regardless of liveness
   (`broker-state.mts:265-267`), so each such ghost record silently and permanently shrinks the
   effective `VICE_BROKER_MAX` capacity (`atCapacity()`, broker-state.mts:298-300) — the exact
   "warm floor doesn't grow / capacity is mysteriously full" failure class this rewrite exists to
   prevent.
4. `vice_recycle` (`vice-proxy.ts`'s `RECYCLE_TOOL` description, line ~357) is documented as
   "Kills and **respawns** THIS session's own emulator in place, on the same port, via the host
   supervisor's existing respawn loop." `handleRecycleForRealBroker()` (vice-broker.mts:350-393)
   only calls `verifiedKill()` and returns; it never updates `state.instances`, never clears the
   record, and (per this finding) there is no respawn loop listening for the exit at all. The
   advertised behaviour is false in the current wiring: a recycle permanently kills the instance,
   the port is never freed, and the session's own subsequent forwarded calls fall into the
   probe-fails/replace-and-report path (D-13, `handleGrantedInstanceUnreachable()`), which issues
   a **second** real acquisition on the same connection while the first dead grant/instance is
   silently abandoned (its `state.grants`/`state.instances` entries are never removed, because
   `requestIdForThisConnection` is overwritten by the new grant, and only the *current* value is
   ever released on connection close).
5. `broker-e2e.test.ts` — the one true integration test that spawns the emitted broker artifact —
   proves acquire → spawn → epoch → grant → release/kill, but has no test that kills a granted
   child and asserts a respawn; that gap is exactly why this was never caught.

**Fix:** Wire `superviseChild()` (or an equivalent exit-aware spawn wrapper) into both
`handleAcquire()`'s and `maintainWarmFloorForRealBroker()`'s spawn paths in `vice-broker.mts`, and
delete/replace `makeLoggingSpawn()`'s bare spawn with one that installs the same crash-respawn
exit handler. `handleRelease()` and `handleRecycleForRealBroker()` must also set
`instance.deliberateKill = true` **before** signalling (matching `shutdown()`'s own discipline in
`broker-kill.mts:196`), and must remove the instance from `state.grants`/`state.instances` once
the kill discipline runs (or delegate that removal to the supervisor's exit handler) — otherwise
wiring in supervision alone will cause a released instance to be misclassified as a crash and
respawned, which is the exact "kill-never-recycle" regression `T-01.6.2-21`'s own comment warns
against.

```typescript
// vice-broker.mts, both handleAcquire()'s and maintainWarmFloorForRealBroker()'s
// spawnFactory need to install the same exit-driven respawn superviseChild()
// already implements, e.g.:
import { superviseChild } from "./broker-epoch.mjs"; // (via broker-launch.mjs)
// ...replace the bare makeLoggingSpawn()-based spawn with a call through
// superviseChild()'s launchSupervised() path so an exit is observed and acted on.
```

### CR-02: `attemptAcquire()` launches a real emulator for an already-abandoned connection — permanent instance/grant leak

**File:** `.claude/mcp/vice/broker-control.mts:331-361`

**Issue:** `attemptAcquire()` checks `socket.destroyed` **after** awaiting `opts.onAcquire()`, not
before:

```typescript
function attemptAcquire(requestId: string): Promise<boolean> {
  return opts
    .onAcquire(requestId)
    .then((outcome) => {
      if (socket.destroyed) return true; // nothing left to answer -- drop
      ...
```

When a cold acquire arrives while a launch is already in flight, `handleLine()` enqueues a
`PendingAcquireEntry` whose `attempt` is `() => attemptAcquire(requestId)`
(broker-control.mts:391-395). That entry is retried later by `drainPendingAcquires()`, driven from
`vice-broker.mts`'s periodic evaluation pass (`serveAcquires: () => drainPendingAcquires(...)`).

If the requesting client disconnects **while its acquire is still queued** (timeout, crash,
session restart — anything that closes the socket before the retry runs), nothing removes its
entry from `pendingAcquires`, and `socket.on("close", ...)` does nothing for it either (
`requestIdForThisConnection` was never set, because the acquire never succeeded from that
connection's point of view — broker-control.mts:308-318). On the next drain pass,
`attemptAcquire()` still calls `opts.onAcquire(requestId)` — which, on the real broker, is
`handleAcquire()` (vice-broker.mts:274): this **allocates a real port, spawns a real `x64sc`
child process, writes its epoch record, and records a real grant** in `state.grants` — before the
socket-destroyed check runs and silently drops the (unwritable) response.

The result is a real, running emulator process with a live grant that:
- is never released (no connection holds its `requestId`, so `onRelease` is never invoked for it),
- occupies a port forever (`nextFreePort()` will never reallocate it, per the same mechanism as
  CR-01),
- counts against `atCapacity()` forever,
- and (per CR-01, compounding this) will never even be respawned on its own eventual crash.

This is reachable with completely ordinary client behaviour (a caller that gives up on a slow
acquire and reconnects, or a proxy session that is killed while `ensureBrokerLease()` is waiting)
— no adversarial input is required, and `broker-control.test.ts`'s own queued-acquire test (line
376) only exercises the case where every client stays connected until its grant arrives; the
disconnect-while-queued path is untested.

**Fix:** Re-check `socket.destroyed` immediately before calling `opts.onAcquire(requestId)` (not
just after), and treat a request whose owning socket is already gone as settled without ever
invoking `onAcquire()`:

```typescript
function attemptAcquire(requestId: string): Promise<boolean> {
  if (socket.destroyed) return Promise.resolve(true); // owner already gone -- never launch for it
  return opts.onAcquire(requestId).then((outcome) => {
    if (socket.destroyed) {
      // the launch already started before the disconnect was observed --
      // release/kill whatever was just granted rather than leaking it.
      ...
    }
    ...
```

The narrower race (disconnect landing exactly between the new pre-check and the `onAcquire()`
call) still exists but is now a best-effort minimization rather than an always-reachable leak; a
complete fix also needs the success branch to release/kill a grant discovered after the socket is
already gone, rather than merely dropping the response.

## Warnings

### WR-01: `handleRelease()`/`handleRecycleForRealBroker()` never set `deliberateKill` and never remove the killed instance from state

**File:** `.claude/mcp/vice/vice-broker.mts:350-393` (`handleRecycleForRealBroker`), `:436-447`
(`handleRelease`)

**Issue:** Both functions call `verifiedKill()` directly but never set
`instance.deliberateKill = true` first, and never delete the instance from `state.instances`
(`handleRelease` does delete the *grant* and the instance entry — but `handleRecycleForRealBroker`
does neither). `shutdown()` in `broker-kill.mts:196` treats setting this marker *before* signalling
as load-bearing (T-01.6.2-21): without it, a supervised child's exit handler cannot tell a
deliberate teardown from a crash and will respawn exactly what was just killed. This is currently
dormant only because of CR-01 (no supervisor is wired in to misread it) — fixing CR-01 without
also fixing this will immediately break the kill-never-recycle invariant for every release and
every recycle.

**Fix:** Set `instance.deliberateKill = true` before calling `verifiedKill()` in
`handleRecycleForRealBroker()`, and thread the same discipline through once CR-01's supervision
wiring lands. `handleRecycleForRealBroker()` should also remove or clearly re-key the instance
record after a successful kill so the port becomes reallocatable once the (fixed) supervisor
decides not to respawn, or once a legitimate respawn replaces the record.

### WR-02: Oversize-line guard in the control listener can destroy a well-formed connection whose lines are individually small

**File:** `.claude/mcp/vice/broker-control.mts:294-299`

**Issue:**

```typescript
socket.on("data", (chunk: Buffer) => {
  buffer += chunk.toString("utf8");
  if (Buffer.byteLength(buffer, "utf8") > MAX_LINE_BYTES) {
    socket.destroy();
    return;
  }
  ...
```

The 64KB ceiling is checked against the **whole accumulated buffer**, before any complete,
newline-terminated lines are split off and processed. The header comment states the intent as "A
connection exceeding MAX_LINE_BYTES without a newline is destroyed rather than buffered further"
— i.e., a guard against one line that never terminates. As written, though, a single `data` event
that happens to contain many small, complete, well-formed JSON lines totalling more than 64KB
(e.g. TCP coalescing a burst of otherwise-valid traffic) is destroyed exactly the same way a
single 64KB unterminated line would be, even though every line present is valid and bounded. This
is untested (`broker-control.test.ts` has no test naming `MAX_LINE_BYTES`).

**Fix:** Check the size of the buffer *remaining after* splitting off every complete line (i.e.
after the `while` loop), or track only the length of the current unterminated tail, so the bound
applies to "bytes buffered awaiting a newline" as documented, not to "total bytes seen in one
`data` callback."

### WR-03: Replacement acquisition on an unreachable granted instance overwrites the connection's own grant id, silently abandoning the old grant

**File:** `.claude/mcp/vice/vice-proxy.ts:2313-2327` (`handleGrantedInstanceUnreachable`), cross-
referenced with `.claude/mcp/vice/broker-control.mts:396-402` (release path keys only on the
connection's *current* `requestIdForThisConnection`)

**Issue:** `handleGrantedInstanceUnreachable()`'s same-session replacement path calls
`session.acquire()` again on the connection that already holds a grant, and `adoptGrant()`
overwrites the module-level `grantId` with the new one. On the broker side,
`requestIdForThisConnection` is similarly overwritten to the new request id
(`broker-control.mts:337`). The **old** grant (and its instance record, and its `state.grants`
entry) is never explicitly released — only the connection's *current* id is released on close or
explicit `release`. Combined with CR-01 (no crash-respawn/cleanup path notices the old instance is
now orphaned), every "granted instance stopped answering" replacement permanently leaks the old
grant/instance in addition to whatever CR-01/CR-02 already leak.

**Fix:** Before or as part of adopting a replacement grant, explicitly release the prior grant id
(a `recycle`-shaped or dedicated release-by-id request) rather than relying on the single
per-connection `requestIdForThisConnection`/`grantId` slot to implicitly discard it.

### WR-04: `main()`'s heartbeat and evaluation-pass `setInterval`s are never cleared

**File:** `.claude/mcp/vice/vice-broker.mts:595-632`

**Issue:** Both `setInterval` timers created in `run()` (the heartbeat refresh and the
`runBrokerPass` tick) are never captured or cleared anywhere, including in
`shutdown()`/`registerShutdownHandlers()` (`broker-kill.mts`). In production this is harmless
because the process calls `process.exit()` on every catchable teardown path, which reclaims the
timers along with everything else — but it does mean any future caller that imports `run()`
programmatically (e.g., a test harness that wants to start and then cleanly stop a broker
in-process rather than as a subprocess) has no way to stop these loops without killing the whole
process, and the interval handles are simply discarded (`setInterval(...)` return values are not
even assigned to a variable).

**Fix:** Capture both interval handles and clear them inside `shutdown()`'s sequence (guarded by
`usingRealProcess` the same way `exit()` already is, so real-process behaviour is unchanged but a
future in-process caller can tear down cleanly).

## Info

### IN-01: `handleRecycleForRealBroker`'s `outcome`/`reason` vocabulary only covers a subset of what the container-side renderer switches on

**File:** `.claude/mcp/vice/vice-broker.mts:350-393`, cross-referenced with
`.claude/mcp/vice/vice-proxy.ts:592-614` (`recycleAckOutcomeMessage`)

**Issue:** `recycleAckOutcomeMessage()` in `vice-proxy.ts` has named cases for
`"target_lookup_failed"`, `"grant_lookup_failed"`, `"epoch_lookup_failed"`, `"pid_lookup_failed"`,
and `"identity_refused"`. `handleRecycleForRealBroker()` only ever produces
`"grant_lookup_failed"`, `"pid_lookup_failed"`, `"identity_refused"`, or `"ok"` — it never produces
`"epoch_lookup_failed"` or `"target_lookup_failed"` (both are dead cases in the real wiring,
matching the phase's own broker-control.mts comment that this is a documented, accepted subset).
This is already disclosed in a comment (`broker-control.mts:59-62`) as intentional, so it is not a
defect — noted only because a future maintainer adding a new failure path to
`handleRecycleForRealBroker()` should keep using a value from this existing vocabulary rather than
inventing a sixth one, since `vice-proxy.ts`'s `recycleAckOutcomeMessage()` has a `default` case
that would silently swallow an unrecognised value into generic wording.

**Fix:** None required; recorded for the next maintainer's benefit only.
