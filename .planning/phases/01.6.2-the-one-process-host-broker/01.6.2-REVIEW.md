# Phase 01.6.2: Code Review Report

**Reviewed:** 2026-08-04T10:11:25Z

## Summary

A prior review pass over this same file set (dated 2026-08-04T06:08:50Z, still visible in git history
for this path) recorded two blockers: `superviseChild()` never wired into the real broker, and
`attemptAcquire()` launching for an already-abandoned connection. Both are **confirmed fixed** in the
current source — `vice-broker.mts`'s `handleAcquire()`/`maintainWarmFloorForRealBroker()` now route
every spawn through `withCrashSupervision()`, and `broker-control.mts`'s `attemptAcquire()` now
pre-checks `socket.destroyed` before ever calling `onAcquire()` and releases a grant that settles for a
socket already gone (both carry explicit "gap closure, plan 14" comments naming the fix). That prior
review's WR-01 (missing `deliberateKill` marker on release/recycle) and WR-03 (replacement acquisition
leaking the prior grant) are likewise fixed, with matching gap-closure comments in the current source.
Its WR-02 (oversize-line guard measuring the whole buffer) and WR-04 (heartbeat/eval-pass intervals
never cleared) remain open but are the two issues this workflow run was explicitly told are already
filed as pending todos, so they are **not** re-reported here.

Continuing the same adversarial pass against the current source turned up four new, independent
correctness defects, all in the concurrency/lifecycle core the scope notes flagged as highest risk:
the exit-driven respawn path (crash *and* recycle) shares its launch guard with fresh port allocation
and can be silently dropped by an unrelated concurrent launch (CR-01); a single transient port
conflict permanently and irrecoverably shrinks the allocation band for the life of the broker process
(CR-02); the warm-floor subsystem launches spares that `acquire` never actually consumes, so it
provides no benefit while still consuming ceiling capacity (CR-03); and a refused ("identity_refused")
recycle kill leaves the deliberate-kill marker stuck, misclassifying that instance's next genuine crash
(CR-04). Three warnings and two info items are also recorded.

## Critical Issues

### CR-01: A crash/recycle respawn can be silently dropped by an unrelated concurrent launch

**File:** `.claude/mcp/vice/broker-launch.mts:53, 154-162, 201-226, 688-745, 795-836`
**Issue:** `tryLaunchOne()` and `acquirePortAndLaunch()` share **one module-level `inFlight` boolean**
(line 53). `acquirePortAndLaunch()` — used by both a cold `acquire` and warm-floor maintenance — holds
this guard across an entire asynchronous port scan (`nextFreePort()`, which itself yields via
`setImmediate` under contention, `broker-state.mts:292-294`) plus the spawn itself. Meanwhile
`superviseChild()`/`launchSupervised()` — the exit-driven respawn path used for **both** an unexpected
crash and a `vice_recycle`-ordered relaunch on the same port — spawns through `tryLaunchOne()`
(line 826), which checks the exact same guard.

If a child's `exit` event fires while a cold acquire or warm-floor launch is mid-flight elsewhere,
`tryLaunchOne()` returns `null`, and `launchSupervised()` propagates `null` with **no retry of any
kind** — the exit event that would trigger a second attempt has already fired and will not fire again
for that pid. Two concrete consequences follow directly from `handleExit()`:

- **Crash path** (lines 736-744): `deps.onOutcome?.(respawned ? "respawned" : "given_up", port)`
  reports `"given_up"` even though the crash count never reached `VICE_MAX_RESTARTS` — the stale
  pre-crash `InstanceRecord` (dead pid, wrong `state`) is left in `state.instances` forever, permanently
  occupying its port (`nextFreePort()` skips any port already present in the map) with no process
  behind it and no further respawn attempt ever scheduled.
- **Recycle path** (lines 700-713): a `vice_recycle` request that collides with a concurrent, unrelated
  launch silently fails to relaunch the instance, while the recycle ack the caller already received
  reports a successful kill stage — the session is left holding a grant to a permanently-dead port with
  no way to recover it short of a fresh acquire.

Nothing in `broker-launch.test.ts` exercises an exit event arriving while `inFlight` is already held by
an unrelated launch (`grep`-confirmed: no test names both `inFlight`/concurrency and `handleExit`
together), so this collision window is untested.
**Fix:** Give the exit-driven respawn path its own guard — it never needs port allocation, it always
relaunches on the *same*, already-owned port — or, if `tryLaunchOne()`'s guard is refused, requeue the
respawn attempt (e.g. via `setImmediate`/backoff) instead of treating a transient collision as a
terminal `given_up`/failed-recycle outcome.

### CR-02: A single transient port conflict permanently shrinks the allocation band

**File:** `.claude/mcp/vice/broker-state.mts:236-300`
**Issue:** `nextFreePort()` calls `blockPort(state, port)` (line 290) on any `EADDRINUSE` from the
bind-and-release probe, and `blockedPorts` has no expiry, no TTL, and no un-block path anywhere in this
module tree (confirmed: no `unblockPort` or equivalent export exists). `blockPort()`'s own doc comment
gives the correct rationale for *not persisting* a block to disk — "a port refused now may be free
after the next reboot" — but the in-memory block is exactly as permanent for the life of this
long-lived broker process, which is the whole point of this phase. Ports in this exact 100-wide band
are constantly recycled by this broker's own release/recycle cycle, so a released port briefly sitting
in the OS's `TIME_WAIT` state is a routine, expected occurrence here, not a rare edge case — the very
next `nextFreePort()` scan that happens to probe that port while it is still draining permanently
blacklists it for the rest of the broker's uptime. Over enough acquire/release/recycle churn, the
allocation band can trend toward `no_free_port` even while the host has plenty of genuinely free ports.
**Fix:** Retry a blocked port after a cooldown (a monotonic timestamp per blocked port, re-checked
before permanent exclusion), or re-probe blocked ports periodically / on `no_free_port` rather than
excluding them for the process's entire lifetime.

### CR-03: Warm-floor spares are launched but never actually granted to an acquirer

**File:** `.claude/mcp/vice/broker-launch.mts:439-547`, `.claude/mcp/vice/vice-broker.mts:322-366`
**Issue:** `maintainWarmFloor()` launches and promotes "ready" spare instances specifically so a later
`acquire` can be served faster than a cold launch — the documented purpose of `VICE_BROKER_SPARES`,
advertised directly to users by `install-resources.ts`'s `hostLaunchInstructions()` ("keeping a warm
floor of spare instances ready"). However, `handleAcquire()` (`vice-broker.mts:322`) **never inspects
`state.instances` for an existing `ready` record** — every acquire, warm floor notwithstanding,
unconditionally calls `acquirePortAndLaunch()`, which calls `nextFreePort()`, which **skips every port
already present in `state.instances`** (`broker-state.mts:287`: `if (state.instances.has(port))
continue;`) — i.e. it deliberately avoids every spare rather than consuming one. No
`grant_from_spare()` (or equivalent) implementation exists anywhere in this module tree (confirmed by
search across every reviewed file), even though a comment in `broker-launch.mts:456-458` asserts one
exists and is "a separate, already-correct mechanism this plan does not touch." As written, every
acquisition pays a full cold launch regardless of how many warm spares are sitting ready, while those
same spares still count fully against `VICE_BROKER_MAX` via `atCapacity()` — the warm floor purely
consumes ceiling capacity for zero latency benefit, and can make `at_capacity` errors on *real*
acquisitions more likely, not less.
**Fix:** Before calling `acquirePortAndLaunch()` in `handleAcquire()`, look for an existing
`state.instances` entry with `state === "ready"` and grant that one directly (mark it `granted`, record
the id in `state.grants`), falling back to a cold launch only when no ready spare exists.

### CR-04: A refused ("identity_refused") recycle kill leaves the deliberate-kill marker stuck, corrupting the next real crash

**File:** `.claude/mcp/vice/vice-broker.mts:299-310, 407-451`
**Issue:** `handleRecycleForRealBroker()` calls `markDeliberateDeath(instance, true)` (line 445)
**before** attempting the kill, per T-01.6.2-21's own (correct) ordering requirement. But when
`verifiedKill()` returns `"identity_refused"` (the process was **not** actually signalled — per this
same function's own comment, "the target was NOT killed and is still running"), nothing rolls the
marker back. The still-running instance record is left in `state.instances` permanently carrying
`deliberateKill: true, respawnAfterKill: true`, with no code path anywhere that ever resets it while
that record survives.

If that same, still-alive instance later exits for a genuinely unrelated reason (a real crash), the
exit handler (`broker-launch.mts`'s `handleExit()`) reads `record.deliberateKill === true` and takes
the **"recycled"** branch unconditionally — never the crash-accounting branch — silently bypassing
`VICE_MAX_RESTARTS`/crash-window bookkeeping for that instance's real crash, and restoring a stale
`"granted"` pre-kill state onto the relaunch even though the recycle that set these markers never
actually succeeded. This defeats both the kill-never-recycle invariant's crash accounting and the
recycle ack's own honesty (`identity_refused` is reported to the caller as "NOT killed and is still
running," but the instance's own bookkeeping now silently disagrees with that report).
**Fix:** On any kill outcome other than a successful stop (`identity_refused`, and any future
non-terminal stage), reset `instance.deliberateKill = false; instance.respawnAfterKill = false;` before
returning, so a later, real exit event is classified correctly.

## Warnings

### WR-01: The control listener enforces no "one grant per connection" invariant of its own

**File:** `.claude/mcp/vice/broker-control.mts:355-433`
**Issue:** The design's authorization model is "the TCP connection is the lease" (per this module's own
header comment), and the `recycle` op *does* defensively check ownership
(`requestIdForThisConnection === null || targetId !== requestIdForThisConnection`, lines 449-456)
before ever calling `onRecycle()`. The `acquire` op has no equivalent guard: nothing in `handleLine()`'s
`acquire` branch (lines 427-433) checks whether `requestIdForThisConnection` is already set before
starting a second `attemptAcquire()` on the same socket. If a second `acquire` line arrived on a
connection that already holds a grant, the success path would unconditionally overwrite the single
per-connection slot (`requestIdForThisConnection = requestId;`, line 374) — the first grant's id would
become unreachable from that connection, and since only the *current* value is ever released (on
`release` or on `close`), the first grant's `state.grants` entry and its spawned child would never be
torn down.
This is not currently reachable through the shipped container-side client: every
`BrokerControlSession` method in `vice-broker-client.ts` awaits its own request before issuing the
next, and `handleGrantedInstanceUnreachable()` in `vice-proxy.ts` explicitly releases the old grant
before acquiring a replacement (the fix for the prior review's WR-03). The gap is that the *server*
enforces none of this itself — the invariant holds only by convention, upheld by one client file,
rather than by the same explicit check `recycle` already has.
**Fix:** Refuse a second `acquire` on a connection that already holds one (or has one queued),
mirroring `recycle`'s existing ownership check.

### WR-02: Per-connection response ordering is not enforced by the control listener

**File:** `.claude/mcp/vice/broker-control.mts:401-433`, `.claude/mcp/vice/vice-broker-client.ts:447-553`
**Issue:** `handleLine()` answers `release`/`recycle`/`status`/`host_state` synchronously within the
same tick, but dispatches `acquire` through a fire-and-forget `void attemptAcquire(requestId).then(...)`
(line 429) that can resolve later, out of line — particularly when a launch is already in flight and
the request is queued (`enqueueAcquire`) for a later evaluation pass. The `data` handler keeps
processing subsequent lines on the same socket immediately, with no per-connection serialization. The
container-side client's `createSession()` (`vice-broker-client.ts:447`) assumes strict FIFO
response-to-request ordering (`pending.shift()`), which holds today only because every
`BrokerControlSession` method awaits its own request before issuing the next. Nothing on the server
enforces this — a client that ever pipelines two requests on one connection would receive its `acquire`
grant/error interleaved after a later request's response, silently corrupting the FIFO dispatch on the
client side.
**Fix:** Either serialize request handling per connection (queue and process one op at a time before
starting the next), or have the client match responses by request id instead of arrival order (several
response kinds would need an id added to the wire format for this).

### WR-03: Incident record filename selection has a TOCTOU race

**File:** `.claude/mcp/vice/incident-record.ts:350-367`
**Issue:** `writeIncidentRecord()` picks a non-clobbering filename by looping `while (existsSync(path))`
before calling `writeAtomic()`. Between the `existsSync` check and the eventual `renameSync()` inside
`writeAtomic()`, a second, concurrent recycle sharing the same timestamp/port/epoch stem could compute
the same "next free" suffix, and one write could silently clobber the other (the final `renameSync` has
no exclusivity check of its own). Low likelihood given recycle's own kill-then-wait cadence, but the
whole point of this module is that an incident record must never silently disappear.
**Fix:** Open the target with `O_EXCL` (or equivalent) to claim the filename atomically instead of
probing with `existsSync()` first.

## Info

### IN-01: Redundant absolute-path check in `build.ts`

**File:** `.claude/mcp/vice/build.ts:93-95`
**Issue:** `resolvePath(outDir).startsWith("/") && outDir.startsWith("/")` — `resolvePath()` of any
input on this Linux-only project always returns an absolute (and therefore `/`-prefixed) path
regardless of whether `outDir` itself was relative, so the left-hand side of the `&&` is always `true`
and the whole expression reduces to `outDir.startsWith("/")`. Harmless, but reads as if it were checking
something it is not.
**Fix:** Simplify to `outDir.startsWith("/") ? outDir : join(HERE, outDir)`.

### IN-02: `handleRecycleForRealBroker`'s outcome vocabulary is a documented subset of what the container-side renderer switches on

**File:** `.claude/mcp/vice/vice-broker.mts:407-451`, cross-referenced with
`.claude/mcp/vice/vice-proxy.ts:592-614` (`recycleAckOutcomeMessage`)
**Issue:** `recycleAckOutcomeMessage()` in `vice-proxy.ts` has named cases for `"target_lookup_failed"`,
`"grant_lookup_failed"`, `"epoch_lookup_failed"`, `"pid_lookup_failed"`, and `"identity_refused"`.
`handleRecycleForRealBroker()` only ever produces `"grant_lookup_failed"`, `"epoch_lookup_failed"`,
`"pid_lookup_failed"`, `"identity_refused"`, or `"ok"` — `"target_lookup_failed"` is a dead case in the
real wiring. This is already disclosed as an accepted, documented subset in `broker-control.mts`'s own
header comment, so it is not a defect — recorded only so a future maintainer adding a new failure path
reuses this existing vocabulary rather than inventing a new value that would silently fall into
`recycleAckOutcomeMessage()`'s generic `default` case.
**Fix:** None required; recorded for the next maintainer's benefit only.
