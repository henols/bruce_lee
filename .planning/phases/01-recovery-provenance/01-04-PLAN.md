<objective>
Prove the dumps are complete by looking for on-demand loading with mechanical detectors, and record the result as a claim with its evidence attached — including when the result is zero.

Purpose: a dump that misses a region the game loads later is the exact failure mode that makes every downstream provenance verdict and every Phase 4 round-trip diff quietly wrong. Success criterion 2 does not accept silence: "zero found" only counts if the armed set and the coverage reached are stated alongside it (D-10). Absence of evidence is only evidence of absence when you can show what looked — and when you can show the machine was running while it looked.

This is the second rewrite of a plan whose first execution was reverted (`bb0b1f7`). The **intent** of the original survives intact and is what this plan delivers: earn the armed set, calibrate idle to zero, attribute every hit before classifying it, prove teardown by enumeration, record absence as evidence. On 2026-08-01 a hard project rule landed: the `mcp__vice__*` tools are the only permitted route to the emulator, so emulator-driving work is performed by the executing agent through its own tool calls, and `tools/` holds pure logic only — resolution, attribution, ordering, rendering — over data the agent fetched and passed in. Every CLI verb the previous version of this plan aimed at a live machine is gone; what remains under `tools/` is the pure half, which was always the correct half.

</objective>

## The one route to the emulator

Read `.claude/CLAUDE.md` § "Emulator Access" before starting. In one sentence: **the `mcp__vice__*` tools are the only permitted route to the emulator, and this plan's live work is the executing agent issuing those tool calls in its own turn.** Access is per-session and boot-fresh — an instance is granted on this session's first forwarded tool call and is yours for the session; nothing needs starting by hand and container paths are translated for you.

What that means concretely for every task below:

- **Live work is a tool call you make.** Arming, disassembling, resuming, polling, reading memory, reading the checkpoint list, driving the joystick, taking screenshots — each is a named `mcp__vice__*` call you issue and whose result you record.
- **`tools/` holds pure logic.** Every function this plan writes takes already-fetched data as an argument, or reads a committed file, and returns data. The whole test suite runs to completion with the emulator absent, and that is the mechanical proof of the shape.
- **The boundary between the two is a committed file.** You write your observations into a hit-log JSON as you work; everything downstream of that file is pure logic that can be re-run, tested and diffed offline. That file is also what makes the run auditable after the fact.
- **Take every tool's exact name and parameter set from the live tool schemas in front of you**, never from a document. Where this plan names a tool it is naming the capability; if the schema disagrees with the plan on a parameter name, the schema wins and the deviation is recorded.
- If a step seems to need a Node process to reach the emulator, that design is dead — say so and stop, rather than building a way around it.

Two operational facts that cost a day each when violated, both recorded in `.planning/STATE.md`:

1. **Most state-reading calls pause the machine and do not resume it.** Measured: ~991,000 cycles/s with an explicit `mcp__vice__vice_execution_run` issued last, against ~6,000 cycles/s when polling without re-resuming — which is why a checkpoint once appeared never to fire. Read state first, poll with `mcp__vice__vice_ping` (measured non-pausing), and resume exactly once at the end of a group.
2. **`mcp__vice__vice_run_until`'s `cycles` parameter is documented in its own schema as "timeout, not yet implemented".** There is no safety net against a wrong target address hanging. Every run-to-checkpoint step in this plan therefore states its manual recovery path: if the expected checkpoint has not reported a hit after the stated poll budget, stop polling, issue `mcp__vice__vice_execution_pause`, read `mcp__vice__vice_registers_get` and `mcp__vice__vice_backtrace`, record where the machine actually is, and treat the step as failed rather than extending the budget.

Host VICE has had six unexplained outages, several on resume. Minimise resumes; that is the schedule risk this plan carries more of than any other in the phase.

**The real delta: the dump-production route.**

- **Primary noun:** *the observation record* — the committed file holding what the agent fetched from the emulator (ordered hex chunks, register readings, checkpoint hits), from which every committable artifact is rendered.
- **Decision:** `promote`. The observation record becomes the primary representation of "a capture", and the previously-primary representation — a runnable capture command that both fetched and wrote — is **retired, not kept alongside**. There is no second production route to fall back to, by rule.

## Success criterion 1: what carries it now, stated rather than assumed

Success criterion 1 says re-running the recorded procedure produces a byte-identical dump. The mechanism that carried it — a runnable `reproduce` command — was deleted with the rest of the standalone recovery tooling. This plan **records the change explicitly rather than letting the criterion quietly go unmet**, and Task 2 makes the record honest.

The assessment, made against the committed artifacts rather than inherited from research:

- **For RECOVER-01/02/03 the criterion is satisfied *as executed*, and that evidence is permanent.** The three-run reproducibility proof was performed, and its SHA-256 digests plus comparison verdict are committed in `recovery/danish/NOTES.md`, `recovery/saeger/NOTES.md` and `recovery/RELEASES.json`. Deleting the script does not un-produce the evidence.
- **Both `NOTES.md` files already read as replayable tool-call procedures.** Checked directly: § "Dump trigger" quotes the disassembly at the trigger, § "Boot procedure" lists the ordered calls including the fact that a resume is mandatory after autostart, § "The cracktro gate" records the gate address, the key and the hold-until-trigger release rule with the three measured delivery mechanisms, and § "Clean-slate ritual" lists the reset sequence in order. A different agent session can issue exactly these calls.
- **One thing is genuinely stale and is fixed by this plan.** Each file's § "Reproducing this dump" opens with a command that no longer exists, followed by "That is the whole procedure." Left alone, that is a documented procedure a reader cannot run — the worst of both worlds. Task 2 rewrites that section into the ordered tool-call procedure the rest of the file already documents.
- **A schema check is not a reproducibility proof and must not be recorded as one.** `node tools/recovery-schema.mjs validate` confirms a committed dump's artifact set is complete and internally consistent; it never re-runs anything. Recording it as reproducibility would launder a weaker claim into a stronger one.

**Decision recorded:** the mechanism for criterion 1 going forward is *a documented tool-call procedure, precise enough for a different agent session to replay by issuing the same `mcp__vice__*` calls in the same order*. This is a named downgrade in **convenience** — one shell command becomes a read-and-replay — and not a downgrade in evidentiary weight for the proof already on record. It is written into both `NOTES.md` files by Task 2 so the downgrade is visible where a reader will meet it.

**VERIFY-01 → Phase 3 (a replay driver over the `vice_*` MCP tools): a deliberate deferral, with the reason.** The requirement's literal wording describes software that autonomously drives the emulator, which is exactly the shape the rule forecloses. Recorded as a deferral with its reason, not as a gap. D-12 already points the same way by keeping this phase's input sequence as plain notes rather than as a `verify/scripts/` artifact, and Task 3 keeps it that way.
