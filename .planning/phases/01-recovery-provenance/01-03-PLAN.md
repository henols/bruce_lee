## Phase Goal

See `01-01-PLAN.md` § Phase Goal. ROADMAP's Phase 1 Goal line is not in user-story form and no story was invented.

<objective>
Recover the second cracked release by re-running the already-proven procedure, and prove in the process that the procedure is release-agnostic.

Purpose: RECOVER-03 asks for a capture "under the same recorded procedure", and the developer's N-ready decision asks that adding a third or fourth release cost one registry entry and one invocation. Those are the same requirement seen from two angles, and this plan is where both are tested. If recovering the second image needs a code change, the procedure was never a procedure — it was a script for one disk.

Output: the full four-file artifact set for the second release, twice over for the reproducibility proof, plus its own `NOTES.md`.

**Why this plan is not the tracer.** `01-01-PLAN.md` records the tracer/ROADMAP resolution in full. The short version: the first release proved the architecture end-to-end; this plan is the first *expansion*, and its whole value is that it should be boring.
</objective>

<flagged_assumptions>
**RECOVER-03 / `unclassified`** — the edge probe returned *"unclassified — review manually"* for this requirement, so it stays **`unresolved`** rather than being auto-backstopped, and is recorded here as an explicit flagged assumption.

Assumption being carried: "the same recorded procedure" is well-defined for a release whose loader has a materially different shape. The second image is **uncrunched**, so it has no decrunch stage to step out of — its loader-done point is the transfer of control out of a raw-sector load loop rather than out of a decruncher. The plan assumes that difference is fully absorbed by a different `trigger.address` value in the registry and does not require a differently-shaped trigger *kind*. If it turns out the uncrunched loader has no single clean transfer point — for example if it interleaves loading with execution — then `trigger.kind` needs a second legitimate value and the "same procedure" claim needs qualifying in both `NOTES.md` files. That would be a real finding to record, not a failure to hide.
</flagged_assumptions>

  <action>
Run the recorded procedure against the second release, in this order and with no shortcuts.

First establish the trigger. `node tools/recover.mjs find-entry saeger` boots the image and walks out of its raw-sector loader using bounded `vice_execution_step` batches with a `vice_registers_get` between batches, `vice_backtrace` to confirm control has left the loader's own code, and `vice_disassemble` to confirm the candidate address decodes as plausible game entry. Because this image is uncrunched, expect the loader-done point to be the transfer of control out of the sector-load loop rather than out of a decruncher; the shape of the *evidence* differs, the shape of the *record* does not. Do not fall back to `vice_run_until`'s `cycles` argument as a safety net — it is documented in its own live schema as unimplemented.

Then capture and prove reproducibility with `node tools/recover.mjs reproduce saeger`, which performs its own hard `machine_reset` plus checkpoint teardown plus disk detach before each of the two runs. Confirm the four-file artifact set landed for the primary run label.

Re-confirm the bank-scoped read against this running game as well: one `bank:"ram"` versus `bank:"rom"` comparison at `$E000`, recorded in the capture record. The research finding that `bank:"ram"` reaches RAM beneath ROM and I/O was verified against an idle pre-boot machine, and it must be re-confirmed per game rather than assumed to generalise. Perform no `$01` port write.

**The constraint that makes this plan worth its own existence:** if anything about this release resists the shared procedure, the fix goes into `recovery/RELEASES.json` as data, never into a file under `tools/` as a conditional. Concretely — if `vice_autostart` fails against this disk's faked directory and the keyboard `LOAD"*",8,1` plus `RUN` fallback is needed, that is recorded as `boot.method` and `boot.fallback_used` on the release entry and the fallback is already generic code from plan 01-01. If a different chunk size is needed, it is a `chunk_size` field. If the trigger address is found differently, that is the `trigger.how_located` prose. Adding a release-name conditional to any tool is the failure mode this plan exists to catch, and `check-parameterisation` is the gate that catches it.

Record the release's `snapshot_names` entry using the same explicit convention — a descriptive versioned name, never a bare default. The `.vsf` remains host-side and uncommittable per the D-07 correction recorded in plan 01-01; this release records a name, not a fourth file.

| Boundary | Description |
|----------|-------------|
| capture session N → capture session N+1 | This plan is the first time the shared VICE instance carries state from a *different release's* session. Residual checkpoints, an attached disk, or RAM left by the previous capture would contaminate this one and produce a dump of a hybrid machine. |
| container tooling → host VICE MCP | Unchanged; the deny-list in the client seam remains the only guard against the shared-instance crash. |
| emulated 6510 → captured evidence | This release is uncrunched, which makes it tempting to trust a statically-reasoned entry point rather than an observed one. A guessed trigger produces a dump nobody can falsify. |

**ASVS L1 applicability:** unchanged — no network service, no untrusted input path, no auth, session, access-control or cryptographic-control surface. The modelled risk class is evidence integrity.
