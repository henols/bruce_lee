## Tracer / ROADMAP tension — resolved explicitly

ROADMAP.md prescribes a horizontally-sliced 5-plan breakdown in which 01-01 resolves bootstrap and boots both images but produces **no dump**, and the first `.bin` appears only in 01-02. TRACER_MODE and WALKING_SKELETON require the opposite.

**Resolution: option (a) — restructured.** Plan 01-01 *is* the end-to-end tracer for exactly one release:

> cold hard `machine_reset` → one image attached and autostarted over MCP → loader-done detected by a **PC-reached exec checkpoint** (a signal, never a timeout) → bank-scoped RAM captured across all 65536 addresses → bytes plus a machine-readable capture record written under `recovery/danish/` → **`reproduce` re-runs the whole recorded procedure and proves the two dumps byte-identical**.

Reasoning recorded for the future reader:

1. That chain exercises every architecturally risky mechanism in the whole project in one pass — container→host path translation, the MCP client transport, signal-based (not duration-based) synchronisation, `bank:"ram"` reads under ROM/IO, and the determinism proof. A dead end in any of them is discovered after one commit instead of after five.
2. It agrees with ROADMAP's own note that 01-01 is *"strictly first; everything else in this phase depends on it"* — it simply makes "first" mean *proven*, not *surveyed*.
3. It turns the second release (now 01-03) into a **pure re-run of an already-proven procedure**, which is exactly what RECOVER-03 asks for ("under the same recorded procedure") and what the N-ready decision demands.

Consequences: the plan count is 6, not 5, and the plan↔requirement mapping differs from ROADMAP's list. ROADMAP will be re-annotated after planning. The tracer is **production-quality, not a prototype**: `tools/vice.mjs`, `tools/releases.mjs` and `tools/recover.mjs` are the tools Phase 3's `verify/runner.mjs` builds on, not scaffolding to be thrown away.

## Research correction to D-07 — surfaced, do not lose this

CONTEXT.md D-07 says the `.vsf` snapshot is *"committed alongside"* the `.bin`, making the per-dump set four files. **That is not achievable and the plan does not attempt it.** `01-RESEARCH.md` verified against the live server that `vice_snapshot_save` accepts only a `name` (plus `description`/`include_roms`/`include_disks`), stores snapshots under the **host's** `~/.config/vice/mcp_snapshots/`, and that no tool in the 64-tool surface exports snapshot bytes back through MCP.

Therefore:
- The committed per-dump set is **three** files: `.bin` + `.capture.json` + `.state.json` (the last one lands in plan 01-02). There is no fourth file.
- A snapshot is recorded **by name** (`danish_gameentry_v1`, never `snapshot.vsf`) as a field in the capture record and in `NOTES.md`, together with the host directory it lives in, and is treated as a host-side non-portable convenience.
- Success criterion 1's reproducibility is satisfied through the **recorded procedure** (`node tools/recover.mjs reproduce danish`), not through a replayed blob. This is strictly stronger, because the procedure is re-runnable by someone who does not have the host's snapshot directory.

<assumption_delta_decision>
**Primary noun:** `release`.

**Decision:** `promote`.

**Rationale:** the phase's own artifacts are plural in three independent directions at once — N cracked releases (the user has more `.d64` files to supply), a *set* of artifacts per release (primary RAM image + zero-or-more supplementary on-demand-load dumps + a chip-state sidecar + a range manifest + a capture record), and an N-way rather than pairwise agreement vote. Keeping "the canonical image" as the primary noun and adding releases alongside it would contradict all three. So `release` is promoted to the primary entity in `recovery/RELEASES.json`, each release owns a *set* of dumps rather than one `.bin`, and **`canonical` is demoted to a single boolean field on one release entry**. `recovery/clean/bruce-lee.bin` and `recovery/clean/README.md` survive as locked paths (D-01, success criteria 1 and 5 name them), but they are documented and validated as a *projection* of the registry — a byte-identical copy of whichever release carries `canonical: true` — not as an independent privileged artifact.

**Invariant encoding the generalized intent (implemented as a real task in plan 01-02, task 3):** `node tools/recovery-schema.mjs validate` fails when any release directory under `recovery/` does not conform to the single registry schema, when more than one entry carries `canonical: true`, or when `recovery/clean/bruce-lee.bin` exists and is not byte-identical to the canonical release's primary dump. A future phase that reintroduces the singular assumption fails loudly instead of quietly.
</assumption_delta_decision>

**Layer 3 — `tools/recover.mjs`, the procedure.** Verbs `reset`, `boot`, `find-entry`, `capture`, `recover`, `reproduce`.

- `reset` is the clean-slate ritual, and it is a **step of `recover`**, not an optional courtesy: enumerate with `vice_checkpoint_list` and `vice_checkpoint_delete` each returned id one at a time (no bulk-clear tool exists in the 64-tool surface), `vice_disk_detach` units 8 through 11, then `vice_machine_reset({mode:"hard", run_after:false})`.
- `boot` resolves the release's `disk_image` to a host path through `tryHostPaths`, calls `vice_disk_attach({unit:8, path})`, then `vice_autostart({path})`, then asserts progress with `vice_registers_get` — PC must have left the reset/READY region — and captures a `vice_display_screenshot` into the release's dumps directory as boot evidence. If PC has not moved or the screenshot still shows a READY prompt, fall back to `vice_keyboard_type` with the `LOAD"*",8,1` sequence and then `RUN`, gated on a checkpoint rather than any delay, and use `vice_keyboard_petscii` if the ASCII conversion mangles the quote or comma bytes. Record which path worked in the registry's `boot.method` and `boot.fallback_used`.
- `find-entry` locates the loader-done signal empirically per D-06: from the booted state, walk out of the loader with bounded `vice_execution_step({count:N})` batches and a `vice_registers_get` between batches, using `vice_backtrace` to confirm control has left the loader's own code and `vice_disassemble` to confirm the candidate address decodes as plausible game entry rather than mid-decruncher. Do **not** lean on `vice_run_until`'s `cycles` argument for safety — its own live schema documents it as "timeout, not yet implemented", so a wrong address hangs the call rather than failing; the bounded-step batches are the actual safety net. Write the chosen address and a prose `how_located` into the registry's `trigger` as `{kind:"pc-exec-checkpoint", address, how_located}`. Print the recorded manual-recovery path in the tool's own output: if a `run_until` appears hung, the recovery is a host-side VICE restart, and that fact belongs in `NOTES.md`.
- `capture` arms `vice_checkpoint_add({start:triggerAddress, exec:true, stop:true})` first and only then calls `vice_run_until({address:triggerAddress})` — belt and suspenders, so the stop is a checkpoint event and not a dependence on `run_until`'s semantics. Once stopped, read all 65536 addresses with `vice_memory_read({address, size, bank:"ram", encoding:"hex"})`. Try a single large read first; on truncation or error fall back to a chunk size of 4096 and record the chunk size actually used. Export `assembleChunks(chunks)` and `captureImage({call, ranges, chunkSize})` as pure-ish functions taking an injectable `call`, so the assembly contract is testable without the emulator. `assembleChunks` copies each chunk into a `Buffer.alloc(65536)` at its own start address, so response processing order cannot affect the result, and it throws when any chunk's decoded byte length differs from its requested size. Assert the final length is exactly 65536 before any write, and write nothing at all if the assertion or any chunk check fails.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| container tooling → host VICE MCP (`http://host.docker.internal:6510/mcp`) | Container-side Node crosses into a host process that owns the single shared emulator. One specific request (`vice_disk_list`) is known to crash that process, and there is no second instance to fall back to. |
| emulated 6510 → captured evidence | Bytes are read out of a running, deliberately obfuscated program (crack loader plus cruncher) and become the project's ground truth. Anything mis-sampled becomes a documented "fact" that every later phase inherits. |
| capture session N → capture session N+1 | One shared instance. Residual checkpoints, watches, attached disks or RAM contents from a previous session can contaminate the next capture. |
| `disks/*.d64` (immutable evidence) → tooling | The two disk images are the only source material in existence for this project. A tool with a write path there destroys provenance irrecoverably. |

**ASVS L1 applicability, judged rather than copied.** `01-RESEARCH.md` § Security Domain argues the standard ASVS categories are inapplicable here, and that judgement holds: this phase builds no network-facing service, accepts no untrusted user input, and has no authentication, session, access-control or cryptographic-control surface — it is offline binary forensics against two already-possessed files through one trusted local endpoint. Enumerating web-application threats would be fabrication. The real risk class is **evidence integrity**, and it is modelled below because every later phase inherits it.
