## Phase Goal

See `01-01-PLAN.md` § Phase Goal. ROADMAP's Phase 1 Goal line is not in user-story form and no story was invented.

<objective>
Complete the per-dump artifact *set* so a recovered release is described by more than a bare `.bin`, gather the disk-directory evidence for both images without ever touching the forbidden tool, and encode the promoted release-centric data model as a runnable invariant.

Purpose: the assumption-delta check on this phase found that a release's recovered artifact is a *set*, not one file — primary RAM image plus a chip-state sidecar plus a range manifest plus a capture record, and later zero-or-more supplementary dumps. A data model that assumes one release equals one `.bin` breaks on the first on-demand-load event plan 01-04 exists to find. This plan makes the set the unit and makes the assumption mechanically enforced.

Output: `tools/chip-state.mjs`, `tools/d64-parse.mjs`, `tools/d64-parse.test.mjs`, `tools/recovery-schema.mjs`, the two sidecars for the first dump, and directory evidence for both images.
</objective>

The sidecar this writes, per D-04, has two halves and both are mandatory.

*Raw half*: `registers.vicii` from `vice_vicii_get_state` including its full 45-byte `registers` array covering `$D000`-`$D02E`; `registers.sid` from `vice_sid_get_state`; `registers.cia1` and `registers.cia2` from `vice_cia_get_state`; `sprites` as the eight `vice_sprite_get({sprite:N})` results for N in 0 through 7; `cpu` from `vice_registers_get`.

*Derived half* — the facts that matter and are not in RAM, each recorded next to the raw byte it came from:
- `derived.port01` — the byte at `$01` plus its LORAM, HIRAM and CHAREN decoding.
- `derived.dd00_raw` and `derived.vic_bank` — CIA2 port A's low two bits select the 16 KB VIC bank and the mapping is inverted, so `%11` is bank 0 at `$0000`-`$3FFF`. Take the raw byte from `vice_cia_get_state().cia2.port_a` and cross-check it against a plain `vice_memory_read` of `$DD00`; record both and fail if they disagree.
- `derived.d018_raw`, `derived.screen_base`, `derived.charset_base` — `$D018` is `vice_vicii_get_state().memory_pointers`; resolve both bases against the selected VIC bank rather than against absolute address zero.
- `derived.sprite_pointers` — eight bytes read with a single `vice_memory_read` at the resolved screen base plus `$3F8`, size 8. Do not take these from `vice_sprite_get`, which returns position, colour and mode flags and never the pointer byte. `vice_sprite_inspect` is a reasonable human cross-check but is not the source of record.
- `derived.sprite_data_addresses` — each pointer byte multiplied by 64 and offset into the selected VIC bank.
- `snapshot_name` — copied from the capture record so the sidecar is self-contained.

Also write the D-02 range manifest as `<release>-<label>.map.json` with `schema_version: 1`, `image_bytes: 65536`, `offset_equals_address: true`, `classification_state: "ranges-only"`, and a `ranges` array whose union covers `$0000` through `$FFFF` with no gap and no overlap. Each range carries `start`, `end`, `kind`, `source` and `note`. At this stage `kind` takes the D-02 enum values that are already determinable — `io` for the `$D000`-`$DFFF` window whose RAM the image holds beneath the I/O block, and `unused` for any range the capture found entirely uniform in the C64 power-on `$00`/`$FF` run pattern — and the transient value `unclassified` for everything awaiting the three-bucket partition. `unclassified` is a sixth, explicitly transient value on top of D-02's five; `recovery-schema.mjs validate --final` rejects it, so it cannot survive to the end of the phase. Record that fact in the manifest's own `note` on the schema.

Then modify `tools/recover.mjs` so its `recover` verb calls `captureChipState` and the manifest writer as part of the same run, before it records the dump in the registry. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| container tooling → host VICE MCP | Chip-state reads cross into the host process; the deny-list in the client seam is the only thing standing between a careless call and a shared-instance crash. |
| emulated 6510 → captured evidence | The chip registers and the derived VIC bank, screen base and sprite pointers are facts that exist *only* at the dump instant and are not in RAM. If they are wrong, Phase 3's checkpoint design is built on them. |
| `disks/*.d64` (immutable evidence) → `tools/d64-parse.mjs` | The parser opens the only source material in existence. A write path there is unrecoverable. |
| `recovery/` registry → every later plan | `RELEASES.json` becomes the description Phases 1 through 4 read. A schema that permits two canonical releases, or a dump entry pointing at a missing file, silently corrupts everything downstream. |

**ASVS L1 applicability:** unchanged from `01-01-PLAN.md` — no network service, no untrusted input path, no auth, session, access-control or cryptographic-control surface. The modelled risk class is evidence integrity.
