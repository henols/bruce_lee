# Phase 01.2 Plan 03: Broker Diagnostics and Client-Side Thresholds Summary

**Three distinct broker-absent messages (never-started/dead-or-hung/launch-failed) replace the single generic one, classified before any request or lease is written so a missing broker fails fast and never orphans files; `.mcp.json` now commits a per-server timeout ordered above the proxy's own 25s grant-poll deadline; `MAX_MCP_OUTPUT_TOKENS`'s absence is made observable on stderr since the file that would set it is gitignored.**

## Performance

- **Duration:** ~25 min
- **Completed:** 2026-07-31
- **Tasks:** 2
- **Files modified:** 4 (plus one new deferred-items.md)

## Accomplishments

- `vice-proxy.mjs`'s `ensureBrokerLease()` now calls `readBrokerLiveness()` **first**, before writing any request: `never_started` and `stale` both return their own message immediately, with zero filesystem side effects. Only an `alive` classification writes a request+lease and polls; a denial returns `brokerLaunchFailedMessage(reason)` (verbatim relay, no restart advice) and a poll timeout returns `brokerWarmingMessage(elapsedMs)` (explicit retry, not a hang) -- both clean up the request and lease they created via the new `removeRequestFile(id)` helper (built from `vice-broker-client.mjs`'s already-exported `requestsDir()`, no new export needed).
- Four new message builders (`brokerNeverStartedMessage`, `brokerDeadOrHungMessage`, `brokerLaunchFailedMessage`, `brokerWarmingMessage`) replace the single `brokerUnavailableMessage()` plan 01 left as a placeholder, mirroring the existing host-unreachable triple's wording register and sharing the one `ONLY_ROUTE_NOTE` definition.
- The never-cache-a-negative-result comment block above `ensureViceSession()` is extended to name the broker classification explicitly: liveness is re-read fresh on every acquisition attempt, never memoised.
- `.mcp.json`'s `vice` entry gained a numeric `timeout: 60000` -- comfortably above the 25000ms grant-poll default and comfortably below the measured >=150s tool-call floor. No other property changed; the docs-gate's single-entry/no-url/one-arg assertion still passes unchanged.
- `warnOnceAboutOutputLimit()`: one stderr line at startup naming `MAX_MCP_OUTPUT_TOKENS`, the required value (25000), and where to set it, when the proxy's own inherited environment shows it absent or insufficient. Never a refusal, never repeated across a process's lifetime (proven across several tool calls in the same process).
- `tools/README.md` gained a new "Per-machine setup" section documenting the exact setting, value, and location, without naming any shell verb of the transport module (the durable docs gate's own pattern stays unmatched).
- A code comment records two client behaviours this proxy deliberately does not rely on: `MCP_TIMEOUT` for the startup handshake (genuinely open, not settled -- moot anyway since `initialize` does zero host I/O) and automatic backgrounding of long tool calls (excludes subagent-originated calls, which is this project's dominant pattern).
- 6 new tests in `vice-proxy.test.mjs` (broker three-states, broker never-cache, malformed broker.json x3 shapes, broker warming, timeout ordering, output-limit warning) plus one pre-existing helper fix; full file is 41/41.

## Decisions Made

- **`brokerLaunchFailedMessage()` quotes `brokerHostPath()` descriptively, mirroring `aliveButFailedMessage()`'s `hostRef` pattern.** Required so all three broker-absent messages satisfy "quotes an absolute path", while still carrying no restart instruction -- restarting a broker that is demonstrably alive and correctly answering would be the wrong fix.
- **`.mcp.json`'s `timeout` set to 60000ms.** 2.4x the 25000ms grant-poll default, comfortably below the measured >=150s floor -- chosen so the proxy's own cold-path messaging is what a caller sees, never the client's own cutoff.
- **`REQUIRED_MAX_MCP_OUTPUT_TOKENS` set to 25000.** A concrete, defensible floor rather than a value derived from a precisely-measured token-to-byte ratio for this specific client (that ratio was not independently measured in the spike set).
- **`acquireLeaseViaBroker()` (the shared test helper from plan 01.2-01) now plants a `broker.json` with a fresh heartbeat before sending its `tools/call`.** A direct, necessary consequence of this task's classify-before-write change -- see Deviations below.

No ROADMAP criterion for this phase covers chunk sizing, so resolving this here would be unscoped -- recorded instead, per this task's own explicit instruction. **The one question that settles it:** does a per-tool `anthropic/maxResultSizeChars` override in `_meta` actually change the client's inline-response ceiling, or is 40-60KB a hard client-side floor regardless of what a tool declares?
