# Phase 01.2: Code Review Report

**Reviewed:** 2026-08-01
**Depth:** standard
**Files Reviewed:** 11
**Status:** issues_found

## Summary

Reviewed the on-demand host-side broker (`resources/vice-broker.sh`), the
container-side broker client (`vice-broker-client.mjs`) and its consumer in
the stdio MCP proxy (`vice-proxy.mjs`), plus their test suites and the two
docs (`SKILL.md`, `tools/README.md`). The `vice_disk_list` deny-list and the
`kill-never-recycle` structural guarantee (a torn-down grant is never reset
to a re-grantable state; only a fresh `launch_instance()` call ever produces
a grantable instance) both check out — I traced every path that removes a
grant and found no route back to a re-grantable state, and no route by which
the deny-listed tool could reach the host.

Three BLOCKER-level issues remain, all in the concurrency/correctness space
the phase's own hazard notes flag as the highest-risk area:

1. Nothing prevents two `vice-broker.sh start` daemons from running at once,
   and `grant_from_spare()`'s read-then-remove sequence is not atomic across
   processes — two racing brokers can hand the *same* ready spare to two
   different sessions.
2. The pid-identity guard in `teardown()`/`cmd_stop()` that is supposed to
   protect against pid reuse only checks that `ps` reports the supervisor
   *script path* in the command line — since the port/working-directory are
   passed to `vice-supervisor.sh` via environment variables, not argv, this
   check cannot actually distinguish between two different, both-legitimate,
   concurrently-running supervisor instances, only "some vice-supervisor.sh
   process, we don't know which."
3. `tools/README.md`'s "Interactive (agent-facing) use" section still
   describes the *pre-01.2* behavior (`vice-proxy.mjs` forwards to the fixed
   port 6510 and "never leases a pooled instance and never redirects") and
   never mentions `vice-broker.sh` anywhere — directly contradicting the
   on-demand leasing this phase ships.

Three WARNING-level races/gaps and three INFO items follow below.

## Critical Issues

### CR-01: No protection against two concurrent broker daemons — `grant_from_spare()` can double-grant the same instance

**File:** `.claude/mcp/vice/resources/vice-broker.sh:1269-1306` (`cmd_start()`), `.claude/mcp/vice/resources/vice-broker.sh:932-980` (`grant_from_spare()`)

**Issue:** `cmd_start()` never checks `broker.json` for an existing live
heartbeat before writing its own `pid`/`started_at` and entering its poll
loop — there is no lock file, no pid check, nothing stopping a human (or a
second terminal, or a restarted service unit that didn't confirm the old one
exited) from running `tools/vice-broker.sh start` twice concurrently against
the same `.vice-supervisor/` directory.

If that happens, `grant_from_spare()` is not safe under concurrent
invocation: it scans `spares/*.json` for the lowest-port entry in state
`ready`, reads its fields, writes `grants/$id.json`, *then* removes the spare
file and the request file as three separate steps with no locking:

```bash
[ -n "$lowest_file" ] || return 1
... read fields from $lowest_file ...
write_json_atomic "$GRANTS_DIR/$id.json" "$grant_content"
rm -f "$lowest_file"
rm -f "$REQUESTS_DIR/$id.json"
```

Two broker processes racing on the same pool dir can both observe the same
`spares/<port>.json` in state `ready` (neither has removed it yet), and both
write a `grants/<idA>.json` and `grants/<idB>.json` pointing at the *same*
port/url/epoch_file for two different sessions. This is exactly the
"recycling would leak one session's emulator state into the next" hazard
this phase's own header comments treat as a structural invariant
(kill-never-recycle) — except here it is two *live* sessions sharing one
instance simultaneously, which is worse: both proxies believe they hold an
exclusive lease and neither backs off.

**Fix:** Add a singleton guard to `cmd_start()` (e.g., refuse to start if
`broker.json` exists with a heartbeat newer than some small multiple of
`VICE_BROKER_POLL_MS` and its pid is alive, mirroring the pid-liveness
pattern already used elsewhere in this file), and/or take an flock-style
exclusive lock on a dedicated lock file for the duration of each
`broker_once()` pass so `grant_from_spare()`'s read-then-remove is atomic
across processes even if a second daemon is accidentally started.

### CR-02: The supervisor pid-identity guard cannot distinguish between two different live supervisor instances

**File:** `.claude/mcp/vice/resources/vice-broker.sh:1190-1216` (`teardown()`), `.claude/mcp/vice/resources/vice-broker.sh:1318-1344` (`cmd_stop()`)

**Issue:** Both `teardown()` and `cmd_stop()` guard against pid reuse the
same way:

```bash
args="$(ps -o args= -p "$supervisor_pid" 2>/dev/null || true)"
case "$args" in
  *"$SUPERVISOR_SCRIPT"*)
    kill -TERM "$supervisor_pid" 2>/dev/null || true
    ;;
  ...
```

`launch_instance()` spawns the supervisor as
`VICE_SUPERVISOR_DIR="$dir" VICE_ARGS="$resolved_args" nohup "$SUPERVISOR_SCRIPT" ...`
— i.e. every per-instance identifier (the port, the working directory) is
passed via **environment variables**, not argv. `ps -o args=` reports the
command line, not the environment, so every `vice-supervisor.sh` invocation
launched by this broker (or by `vice-pool.sh`, or run by hand) reports the
*same* `args` string regardless of which port or directory it is actually
supervising. The guard therefore only proves "the pid currently names some
`vice-supervisor.sh` process" — it can never prove "the pid names *this
grant's* supervisor process."

Combined with CR-01 (and with ordinary pid recycling on a host that churns
through many short-lived `x64sc` processes over a long-running broker's
life), a stale or misattributed `supervisor_pid` recorded in one grant can
end up matching a pid that is currently a live, unrelated, still-serving
supervisor instance for a *different* port/session. The guard will pass and
`kill -TERM` a working instance that some other session is actively using —
the exact kind of "possible pid reuse" scenario this guard exists to
prevent, except it cannot actually detect the collision it is documented to
guard against. There is no existing test for this: the current test
(`"teardown: a supervisor pid whose ps output does not name the supervisor
script is refused"`) only covers the *non-matching* case (a pid belonging to
something that isn't `vice-supervisor.sh` at all), never the case where the
pid genuinely is a *different* `vice-supervisor.sh` instance.

**Fix:** Record something instance-specific and verifiable in the grant
(e.g. have `vice-supervisor.sh` write its own pid/port into a per-instance
marker file under `supervisor_dir`, and have `teardown()` read that marker
back and compare it to the recorded port before signalling), rather than
trusting a bare command-line substring match.

### CR-03: `tools/README.md` still documents the pre-01.2 fixed-port behavior and never mentions the broker

**File:** `tools/README.md:386-398` ("Interactive (agent-facing) use takes no pool lease at all")

**Issue:** This section states, unqualified:

> As of Phase 01.1 (§3 above), `.mcp.json` registers `vice-proxy.mjs`, which
> forwards every `mcp__vice__*` call to the FIXED port from decision D-A
> (6510, the single supervised instance) — it never leases a pooled instance
> and never redirects.

This directly contradicts the code this very phase ships:
`vice-proxy.mjs`'s `ensureBrokerLease()` (lines 994-1057) writes a request,
polls for a broker grant, and calls `useInstance()` with the *broker-granted*
(non-fixed, boot-fresh) port and URL — i.e. it does lease a (broker-managed)
instance and does redirect, on the first forwarded call of every session.
Nowhere in `tools/README.md` (all 496 lines) is `vice-broker.sh` mentioned,
nor is the on-demand per-session leasing model this phase introduces. An
operator following this doc would have no way to learn that the broker needs
to be started at all, and would be actively told the opposite of what
actually happens when a session's first tool call is forwarded.

**Fix:** Update §5's "Interactive (agent-facing) use" paragraph to describe
the on-demand broker path (boot-fresh instance granted on first forwarded
call, released at session end, `tools/vice-broker.sh start [N]` as the
host-side launch command), and add the broker to the doc alongside the
existing supervisor/pool sections — `vice-mcp-selector-docs.test.mjs`
enumerates `tools/README.md` for the shell-invocation-pattern check but has
no assertion that would have caught this staleness.

## Warnings

### WR-01: `sweep_grants()`'s stale-lease check is a check-then-act race, not atomic against a concurrent heartbeat refresh

**File:** `.claude/mcp/vice/resources/vice-broker.sh:1225-1242` (`sweep_grants()`), `.claude/mcp/vice/resources/vice-broker.sh:480-496` (`lease_is_stale()`)

**Issue:** `lease_is_stale()` stats the lease file once, computes `age` at
that instant, and returns true/false. `sweep_grants()` then acts on that
verdict unconditionally:

```bash
elif age="$(lease_is_stale "$lease" "$VICE_BROKER_TTL_S")"; then
  rm -f "$lease"
  teardown "$id" "swept (stale ${age}s, ttl ${VICE_BROKER_TTL_S}s)"
```

If the container-side proxy's heartbeat timer (`startHeartbeat()` in
`vice-broker-client.mjs`, default every 60s) calls `touchLease()` in the
narrow window between the `stat` inside `lease_is_stale()` and the `rm -f`
above, the refresh is silently discarded — the broker still removes the
just-refreshed lease and tears the instance down, destroying a session's
live emulator state even though that session proved itself alive moments
earlier. The default TTL (180s, three heartbeat intervals) makes this a
low-probability window in practice, but nothing in the code structurally
prevents it, and the consequence (loss of an actively-used instance) is
exactly the kind of failure this phase's checkpoint/lease design otherwise
takes great care to avoid.

**Fix:** Re-stat the lease immediately before `rm -f` and skip the teardown
if the mtime advanced past the staleness threshold since the first check, or
combine the check-and-remove into a single atomic step (e.g. `mv` the lease
to a "condemned" name and only proceed if that succeeds, using the rename's
atomicity to settle the race).

### WR-02: `writeRequest()` then `createLease()` are still two separate synchronous writes, not one atomic step

**File:** `.claude/mcp/vice/vice-proxy.mjs:1016-1022` (`ensureBrokerLease()`)

**Issue:** The comment above `ensureBrokerLease()` states the lease is
created "BEFORE awaiting the grant, not after" specifically so a broker pass
landing in the window between request and grant can never see "a grant with
no lease yet" and tear it down. That reasoning holds for the
request-vs-grant window, but `writeRequest({...})` and `createLease({...})`
are still two independent synchronous filesystem operations with no atomic
grouping between them:

```js
writeRequest({ id, sessionId, clientPid });
createLease({ id, sessionId, clientPid }); // BEFORE pollGrant() -- see comment above
```

Between these two calls there is a real (if very short) window during which
`requests/<id>.json` exists but `leases/<id>` does not yet. A broker pass
that happens to land exactly here could grant the request via
`grant_from_spare()` and then, in the very same pass, tear it straight back
down via `sweep_grants()` (lease absent → "released"), because both run
sequentially inside the same `broker_once()` call. The effect is
self-healing (the proxy's `pollGrant()` will simply see neither a grant nor
a denial and eventually report the warming-and-retry message, and a retried
`tools/call` starts a fresh request), so this is far lower severity than
CR-01/CR-02, but it is the same class of race the plan's own comment
believed it had fully closed.

**Fix:** Either write both files as a pre-lease-first pair from one combined
helper that is documented as covering this exact residual, or accept and
explicitly record this window is a "self-healing, first-call-only, extremely
narrow" residual rather than implying (as the current comment does) that the
ordering alone eliminates the race class entirely.

### WR-03: `containerizeGrant()` only re-validates fields that were actually translated; an untranslated ("passthrough") field is trusted verbatim

**File:** `.claude/mcp/vice/vice-proxy.mjs:887-978` (`containerizeGrant()`)

**Issue:** The workspace-containment re-check is gated on
`changedFields.has(field)`:

```js
if (changedFields.has("epoch_file") && !isInsideWorkspace(resolve(record.epoch_file), root)) {
  record.epoch_file = fallbackEpochFile;
  substituted.epoch_file = true;
}
```

If `containerpath.mjs` decides a field was "already container-shaped" (i.e.
it matched no known host root and was left unchanged — the documented D-7
passthrough case), that field is never checked for workspace containment at
all; it is trusted exactly as written in the grant file. Separately, the
final `url`'s validation (`T-ccn-02`) only checks that its **port** matches
the grant's own validated port — the **host** portion of the URL is never
independently validated against a known-good alias or the workspace at all,
which is a narrower check than the "derive purely from the validated port,
never trust a path/host string read out of the file" posture
`vice-pool.mjs`'s `instanceFor()` uses elsewhere in this same codebase for
the analogous problem. In the current single-trusted-broker deployment model
this is low risk, but it is an inconsistency with the stricter pattern used
elsewhere for the same class of "host-written, therefore should be treated
as untrusted" data.

**Fix:** Apply the containment check (or an explicit "derive from validated
port only" rule, matching `instanceFor()`) unconditionally to every field,
not only to fields `containerizeRecord()` happened to translate; validate
the URL's host component against the expected alias, not just its port.

## Info

### IN-01: `probe_ready()`'s no-mechanism fallback is broader than its own stated justification

**File:** `.claude/mcp/vice/resources/vice-broker.sh:1105-1130` (`maintain_spares()` step 1), `.claude/mcp/vice/resources/vice-broker.sh:674-708` (`probe_ready()`)

**Issue:** `probe_ready()`'s "trust the launch" unconditional-success branch
(reached only when neither `VICE_BROKER_PROBE_CMD` nor `curl` is available)
is justified in its own comment specifically for "an ALREADY-pending request's
cold instance." In `maintain_spares()`, however, step 1 calls `probe_ready()`
for *every* spare currently in state `launching`, regardless of `reason` —
so a leftover `reason:"spare"` entry (e.g. from before an operator removed
`curl`, or from a config change mid-run) would also get trust-the-launch
promoted, which the design comment implies should only apply to `cold`
entries. Low impact (step 2 already stops *creating* new speculative spares
in this mode; this only affects an already-existing one), but worth aligning
code and stated intent.

### IN-02: `BLOCKED_PORTS` never shrinks for the life of one broker daemon

**File:** `.claude/mcp/vice/resources/vice-broker.sh:531-542`, `.claude/mcp/vice/resources/vice-broker.sh:550-578` (`next_free_port()`)

**Issue:** Once `next_free_port()`/`maintain_spares()` observes a port bound
by something outside the broker's own bookkeeping, `block_port()` adds it to
`BLOCKED_PORTS` for the remaining lifetime of that daemon process — there is
no corresponding "unblock" once the external process releases the port. On a
long-running broker this can only ever narrow the usable port window over
time, requiring a full broker restart to reclaim a transiently-bound port.
Documented as a deliberate choice in the code's own comment, but worth
flagging as a maintainability/robustness tradeoff rather than a pure
non-issue, since the effect compounds silently over a long uptime.

### IN-03: Startup log line reports the pre-lease default instance, not the eventual broker-granted one

**File:** `.claude/mcp/vice/vice-proxy.mjs:1344`

**Issue:**

```js
console.error(`vice-proxy: ready, forwarding to ${activeInstance().url} (port ${activeInstance().port})`);
```

This runs at module load, before any broker lease is ever requested (leases
are deferred to the first forwarded `tools/call`, per this phase's own
design). Under the on-demand broker path, the URL/port printed here is
whatever the default/env-configured instance happens to be — not the
instance the session will actually be forwarded to once
`ensureBrokerLease()` runs. This is purely a diagnostic/log-message
accuracy issue (nothing downstream depends on this line), but it can mislead
someone reading proxy stderr while troubleshooting a broker-granted session.
