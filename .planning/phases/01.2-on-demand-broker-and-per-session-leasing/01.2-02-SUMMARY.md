# Phase 01.2 Plan 02: One Teardown Path, Real Daemon, Kill-Never-Recycle Summary

**`vice-broker.sh` is now a real `start`/`stop`/`status` daemon whose released-lease and TTL-stale-sweep branches converge on one `teardown()` function, whose torn-down grants are structurally unrecyclable (proven by a test confirmed to fail when relaxed), and whose request-id validation is pinned byte-for-byte to the container-side client by a corpus-driven parity test (also confirmed to fail when the two patterns diverge).**

## Performance

- **Duration:** ~45 min
- **Completed:** 2026-07-31
- **Tasks:** 2 (Task 1: single teardown path + daemon lifecycle; Task 2: kill-never-recycle + id parity)
- **Files modified:** 2 (`resources/vice-broker.sh`, `vice-broker.test.mjs`) -- no files created

## Accomplishments

- **`teardown(id, reason)`** is the single function reached from two call sites inside `sweep_grants()`'s loop body: a grant whose lease is absent is torn down as `"released"`; a grant whose lease is present but stale is torn down as `"swept (stale ${age}s, ttl ${ttl}s)"` after `sweep_grants()` removes the stale lease itself first, converting stale-but-present into missing. A dedicated test writes the two scenarios into separate temp pool directories and asserts the resulting directory listings are identical (no grant, no lease, in both cases), differing only in the logged reason string.
- **A real daemon.** `cmd_start` writes `broker.json` once with a fixed `started_at`, then (absent `--once`) loops forever: refresh `heartbeat_at`, run one `broker_once()` pass, sleep `VICE_BROKER_POLL_MS` -- with the same consecutive-failure backoff shape `vice-supervisor.sh`'s own respawn loop uses. `trap cleanup INT TERM` removes `broker.json` and exits 0 without touching any granted instance (the broker stopping is not a session ending). `cmd_stop` verifies the recorded pid's `ps` output names `vice-broker.sh` before signalling, matching `vice-pool.sh`'s own `cmd_stop` idiom.
- **`broker-instances.json`** is rebuilt as a pure projection of `grants/*.json` at the end of every `broker_once()` pass, via a new `write_instances()`/`read_instance_field()` pair (no `jq`, same grep-against-known-shape idiom as `read_registry_ports`/`read_registry_pids`). `cmd_status` reports the broker's own liveness (pid, heartbeat age via the file's own mtime) plus one line per instance naming its port. The broker never writes `registry.json` -- verified with a grep that excludes comment lines.
- **Kill-never-recycle is structural, not incidental.** `teardown()` unconditionally `rm -f`s the grant entry (matched-kill or refused-mismatch alike); because `broker-instances.json` is a from-scratch projection, a removed grant simply stops appearing on the next write. Dry-run grants now record a nanosecond-epoch value as both the synthetic `supervisor_pid` and `launched_at`, replacing a constant `"null"` that would have made the "no recycling" test pass vacuously.
- **Request-id validation moved to the body.** `process_requests()`'s operative id is now `extract_id_field()`'s read of the request's own `"id"` JSON field, validated against the allow-list pattern before any path construction -- never the filename. A request whose id fails validation, or whose body can't be parsed that far, is skipped with a logged reason (`vice-broker: skipping request <file> -- invalid or missing id: "<id>"`); the rest of the pass continues.
- **A real bug found and fixed along the way:** `extract_id_field()`'s `grep | head | sed` pipeline exits non-zero when grep finds no match (any malformed request body) -- under this script's own `set -euo pipefail`, that silently killed the *entire* broker pass with no error output at all, discovered when the malformed-body test's `execFileP` call failed with exit code 1 and empty stderr. Fixed with `|| true` on every grep-based field extraction that can legitimately find nothing (not just the new one -- `write_instances()`'s and `read_instance_field()`'s equivalent reads carried the same latent hazard).

## Decisions Made

- **Dry-run synthetic launch id is a nanosecond epoch timestamp, not a constant.** Both the synthetic `supervisor_pid` and `launched_at` fields under `--dry-run` use `date +%s%N`, which is monotonically increasing and virtually guaranteed distinct between any two separate grants. A constant placeholder would have let the kill-never-recycle test pass vacuously regardless of whether the underlying rule held.
- **`broker-instances.json` is fully rebuilt from `grants/*.json` every pass, not incrementally maintained.** This makes kill-never-recycle structural: a torn-down grant simply isn't there to project on the next write, with no separate "mark reusable" step that a later change could accidentally skip or a bug could accidentally leave set.
- **The operative request id comes from the body's own `"id"` field, not the filename.** This was necessary for the id-pattern parity test to be meaningful in the first place: several corpus entries (an empty id, an absolute-looking name, a name containing `..` and a separator) cannot exist as real filenames at all. Reading id from the body lets the test drive the actual validation logic under a safely-named outer file, rather than being limited to whatever the filesystem itself would tolerate as a filename.
- **`|| true` added to every grep-based field extraction that can legitimately find no match**, not only the one directly implicated by the malformed-body test's failure. `write_instances()`'s and `read_instance_field()`'s equivalent extractions carried the identical latent hazard (a `set -e`/`pipefail` abort with zero error output) even though no test had yet exercised the code path that would trigger it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `extract_id_field()`'s pipeline aborted the entire broker pass under `set -euo pipefail`**
- **Found during:** Task 2, writing the "malformed request body is skipped" test
- **Issue:** `grep -o '"id": *"[^"]*"' "$1" | head -1 | sed ...` exits with grep's own non-zero status when grep finds no match (a garbage/unparseable request body) -- exactly the case this function exists to handle gracefully. Under `set -euo pipefail`, `pipefail` propagates that as the whole pipeline's exit status, and since the calling assignment (`id="$(extract_id_field "$req_file")"`) is a plain statement (not the condition of an `if`), the script aborted immediately with exit code 1 and **no error message at all** -- confirmed via `bash -x` tracing, which showed execution stopping mid-`process_requests()` right after `id=` was assigned an empty string.
- **Fix:** Added `|| true` to `extract_id_field()`'s own pipeline, and audited every other grep-based field extraction in the file for the same hazard -- `write_instances()`'s `supervisor_pid`/`dry_run_field` reads and `read_instance_field()`'s three branches carried the identical latent risk (they always matched in practice, against this script's own well-formed writes, but a single malformed/hand-crafted file would have silently killed the whole broker loop with zero diagnostic output).
- **Files modified:** `.claude/mcp/vice/resources/vice-broker.sh`
- **Verification:** `node --test .claude/mcp/vice/vice-broker.test.mjs` -- all 12 tests pass, including the malformed-body test that surfaced this.
- **Committed in:** `bfcf1dc` (Task 2 commit)

**2. [Rule 1 - Bug] Test scenarios initially omitted the lease that real usage always writes alongside a request, causing false negatives**
- **Found during:** Task 2, first run of the parity and malformed-body tests against the real implementation
- **Issue:** `vice-proxy.mjs`'s own `ensureBrokerLease()` calls `createLease()` immediately after `writeRequest()`, **before** polling for a grant (see `vice-proxy.mjs:696-699`) -- so under real usage a lease always exists by the time the broker grants a request. My first draft of the parity/malformed-body tests wrote only request files with no accompanying lease, so a single `--once` pass would grant the request AND immediately sweep it (lease absent) within the same call -- a technically-correct outcome that made every valid id in the corpus indistinguishable from a rejected one purely due to the test's own setup, not the code under test.
- **Fix:** Every test scenario that expects a grant to survive one `--once` pass now also writes a matching lease file, mirroring the real ordering.
- **Files modified:** `.claude/mcp/vice/vice-broker.test.mjs`
- **Verification:** `node --test .claude/mcp/vice/vice-broker.test.mjs` -- parity and malformed-body tests both pass with correct, non-vacuous assertions.
- **Committed in:** `bfcf1dc` (Task 2 commit)

   ```
   AssertionError [ERR_ASSERTION]: the released grant must be torn down
   true !== false
   ```
   The fix was reverted (`diff` against a pre-patch backup confirmed byte-identical restoration) and the test passed again before commit.

2. **Request-id pattern parity.** `vice-broker-client.mjs`'s `REQUEST_ID_PATTERN` was temporarily loosened from `[0-9a-f]{8}` to `[0-9a-fA-F]{8}` (accepting uppercase hex). Re-running the parity test failed exactly as expected, at its own corpus-sanity assertion (the earliest point the divergence becomes detectable):
   ```
   AssertionError [ERR_ASSERTION]: sanity: the corpus's own expected verdicts must match
   isValidRequestId() before comparing against the shell side
   [ ..., false, true, false ]  (actual)
   [ ..., false, false, false ] (expected)
   ```
   The fix was reverted (`diff` against a pre-patch backup confirmed byte-identical restoration) and the full test suite passed again before commit.
