## 8. Output-ceiling behaviour on a large read

`mcp__vice__vice_memory_read`, address `$0400`, size **16384**, default `array` encoding, from
session 1's leased instance on port 6512.

**Outcome: the result arrived INLINE.** Named unambiguously against the three candidates: it was
*not* split across a continuation sequence, and the client did *not* report the result too large or
name a spilled file path. One response carried all 16,384 bytes.

Response shape, head and tail (the body is 16,384 two-byte hex strings and is not reproduced in
full):

```json
{"address":1024,"size":16384,"encoding":"array","data":["20","20","20","20", … ,"FF","FF"]}
```

The payload is coherent, not padding: it opens with the C64 screen RAM at `$0400` holding the
familiar boot banner in screen codes — `2A 2A 2A 2A` (`****`), then `03 0F 0D 0D 0F 04 0F 12 05`
(`COMMODORE`), `36 34` (`64`), `02 01 13 09 03` (`BASIC`) — and runs on into the `$D000`-region
byte pattern. So a real machine's memory was read end to end, not a truncated or synthetic buffer.

### What this settles, and what it corrects

At 5 characters per array element (`"XX",`), 16,384 elements plus the wrapper is approximately
**82,000 characters** in a single inline response.

That figure sits **above** the 40–60 KB inline ceiling recorded as a measured constant in the
project's spike findings, and far **below** the 500,000-character ceiling the proxy declares. The
recorded discrepancy the procedure set out to settle is therefore resolved in this direction:

- The **500,000-character declared ceiling is honoured** — nothing spilled, so no follow-up on
  chunk sizing is triggered by the failure mode item 8 was watching for.
- The **standing 32 KB chunking rule is more conservative than the transport requires.** A single
  16 KB read produced ~82 KB inline without difficulty.
- The **40–60 KB inline ceiling from the spike findings did not bind here.** Either it is
  route-dependent — the spike measured a different path than the broker-granted proxy — or it is
  lower than the true limit. This is a correction worth carrying forward, but a single observation
  at ~82 KB establishes only that the limit is *above* 82 KB on this route, not where it actually
  falls. Finding the real boundary needs a deliberate bisection, which this procedure did not do
  and which is not required by criterion 13.
