<objective>
Prove the whole request → grant → forward → release seam end-to-end on one path, with
production-quality release wiring present from the first commit.

Purpose: the ~490ms graceful window and the two-different-handler correction (finding 8) are the
constraints that decide whether per-session leasing works at all. Retrofitting release onto a
working forward path is how a whole class of session ending silently starts leaking leases. The
tracer therefore carries the full five-trigger teardown, not a stub.

Output: a host-side broker script that can satisfy one request in a single pass, a container-side
broker protocol client, the proxy wired to acquire on first forwarded call and release on every
ending path, and tests that drive all of it with no host emulator and no live x64sc.
</objective>

<assumption_delta_decision>
The assumption-delta detector fired on this phase (`pluralization`, `optional`). It is right to: the
phase ends the monopoly of two singular assumptions.

**1. Primary noun: the emulator claim was identified by PORT; it is now identified by REQUEST ID.
Decision: `promote`.**

Before this phase there was one emulator at one fixed port, and port *was* identity — the classic
lease lives at `leases/<port>.lease`, and `tools/recover.mjs`'s snapshot names are namespaced by
port. Under on-demand launch, ports are recycled across sessions, so a port no longer names a claim:
two different sessions minutes apart can legitimately both be "6511". The request id is promoted to
primary — requests, grants and leases are all keyed by it, and the port demotes to an attribute *of a
grant*. Consequences taken deliberately: the lease filename is `leases/<id>`, not `leases/<port>`;
`CLAUDE_CODE_SESSION_ID` is metadata rather than the key, because one proxy process per session means
process identity already is session identity; and snapshot names must be namespaced by something
session-scoped rather than by port, which plan 01.2-05 writes into the skill document.

**2. Second lease mechanism alongside the first. Decision: `add-alongside`, as accepted debt.**

The classic port-keyed process/session lease (`vice-pool.mjs`'s `acquire()`) keeps running unchanged
for the non-MCP recovery pipeline, whose remaining Phase 1 plans are unexecuted and still depend on
it. So two lease mechanisms coexist in one `.vice-supervisor/` tree. This is genuinely
add-alongside rather than promote, and it is debt: two mechanisms means two places a future change
must land. **What would force the promote:** once Phase 1's plans 01-04 through 01-06 have executed
and the standalone pipeline's emulator access is separately settled, the classic pool becomes
retirable and the broker protocol becomes the single mechanism. Until then, deleting it would
silently break in-flight work this phase has no mandate to touch.

**3. `inotify` as an optional accelerator. Decision: `no-change`.** Polling is the contract and the
only thing built. Same-inode bind-mount behaviour is a property of this particular host, not of the
design, and the existing acquire path already polls at 500ms, so the latency floor is acceptable
without watching.

**Invariant test encoding the generalized intent (accepted, built in plan 01.2-02):** the request-id
pattern parity test drives one shared corpus through both the host and container validators. It goes
red the moment either side reintroduces an id shape the other rejects — which is the concrete way the
"id, not port, is the key" generalization can silently regress.
</assumption_delta_decision>
