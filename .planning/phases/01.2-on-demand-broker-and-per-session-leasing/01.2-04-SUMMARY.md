# Phase 01.2 Plan 04: Warm Spares, Readiness Proof, and Denial Semantics Summary

**`vice-broker.sh` now carries an explicit `launching`/`ready`/`leased` instance state machine driven by an injectable readiness probe (default: host-side curl POST of `vice_ping`), with `maintain_spares()` as the single function owning both the spare target and the instance ceiling, and `grant_from_spare()`/`deny()` completing the "not yet" vs "never" distinction the container-side proxy's polling loop depends on.**

## Performance

- **Duration:** ~100 min
- **Completed:** 2026-07-31
- **Tasks:** 2 (Task 1: readiness state machine + `maintain_spares`; Task 2: grant/refill/deny)
- **Files modified:** 2 (`resources/vice-broker.sh`, `vice-broker.test.mjs`) -- no files created

## Accomplishments

- **An explicit instance state machine.** Every launched instance now lives in one of three states: `launching` (just spawned, or dry-run-pretended, never grantable), `ready` (a real MCP round-trip succeeded), or `leased` (granted to a session, tracked in `grants/<id>.json` exactly as plan 02 left it). Spare state lives in a new `spares/<port>.json`, keyed by port since a spare has no request id until it is granted.
- **`launch_instance(port, reason)`** allocates the supervisor dir, spawns (or, under `--dry-run`, pretends to spawn) a supervised instance, and records `spares/<port>.json` in state `launching`. `port_in_use()` is checked only outside `--dry-run` (preserving the tracer test's dry-run-grant-against-an-already-bound-port pattern from plan 01); the supervisor-script-missing check applies unconditionally, since it is safe and side-effect-free.
- **`probe_ready(port)`** is the injectable readiness seam: `VICE_BROKER_PROBE_CMD` invoked as `"$CMD" "$port"` (a positional argument, never interpolated into a command string -- no injection surface), or, by default, a single curl POST of a `vice_ping` `tools/call`, matched against the bare words `version`/`machine` in the response (not quoted JSON keys -- see Decisions below for why). A bare TCP accept is explicitly never sufficient.
- **`maintain_spares()`** is the single function reading both `VICE_BROKER_SPARES` (the ready-spares target) and `VICE_BROKER_MAX` (the total-instance ceiling) for the purpose of the spare invariant: it promotes existing `launching` entries whose probe now succeeds, then launches new spares while a deficit remains and the ceiling has room. Called once at the end of every `broker_once` pass, after grants and after teardowns.
- **`grant_from_spare(id)`** selects the lowest-port `ready` spare, flips it to leased by writing `grants/<id>.json`, and removes the spare entry -- instant, same-pass grant. **`deny(id, reason)`** writes `denials/<id>.json` for the three genuinely unsatisfiable cases: ceiling reached, port already bound, supervisor script missing -- each reason naming the concrete obstacle and current counts.
- **The cold path defers, deliberately.** With zero ready spares, `process_requests()` launches a cold instance and writes **neither** a grant nor a denial -- the request stays pending until a later pass, once `maintain_spares()` promotes the new instance, grants it. `count_cold_launching()` prevents a still-pending request from triggering a second, redundant cold launch on every subsequent pass while its own instance is still warming up.
- **A real bug found and fixed via this plan's own tracer test:** `probe_ready()`'s first draft matched literal quoted JSON keys (`"version"`, `"machine"`) in the curl response body -- but a real MCP `tools/call` result wraps its payload as an escaped JSON string inside `result.content[0].text`, so those substrings arrive backslash-escaped (`\"version\"`) and never match literally. Loosened to bare-word matching, which is correct against both the escaped-string shape and any hypothetical unwrapped shape.
- **28/28 tests pass** in `vice-broker.test.mjs` (12 pre-existing + 16 new), plus `vice-broker-client.test.mjs`'s own 14 unmodified tests (42/42 combined).

## Decisions Made

See the `key-decisions` frontmatter above for full rationale on: `port_in_use()`'s dry-run gating, the unconditional supervisor-script check, the bare-word probe match (and the real bug it fixes), the "trust the launch" degradation for a pending request under a probe-less host, `count_cold_launching()`'s duplicate-launch prevention, and the four pre-existing test adaptations.

**On the maintain_spares "one snapshot, local counters" launch loop:** the plan's own prose describes `maintain_spares()` as launching "while `count_ready < spares_target` and `count_total < max_instances`." Implemented literally with live-recomputed counts, this would either never launch anything in a single pass (since a freshly-launched spare never becomes ready within the same pass its own probe hasn't run) or launch until the ceiling regardless of the deficit (since `count_total` would keep rising while `count_ready` stayed frozen at its initial value). The implementation therefore takes ONE snapshot of both counts after promotion, then launches while a LOCAL copy of `ready` (incremented per launch, representing "spares now accounted for toward the target," not a re-probed truth) stays below target and `total` stays below the ceiling. This is what produces the exactly-right numbers in every row of the invariant table and the "two passes to reach steady state" behavior this plan's own tests require, while still reading both bounds only inside this one function.

## Issues Encountered

- **The plan's own literal grep recipe for "the ready target and the ceiling are read only inside `maintain_spares`"** (`grep -cE 'max_instances|MAX_INSTANCES'`) does not match this codebase's actual variable name, `VICE_BROKER_MAX` (established in plan 01/02, not introduced here) -- the literal pattern returns only the pre-existing, unrelated `"max_instances"` JSON key inside `write_broker_json()`'s informational status output. The SUBSTANCE of the criterion holds in spirit for the spare-target-pursuit logic (`maintain_spares()` is the only place the `ready < target && total < max` DEFICIT decision is made), but `process_requests()`'s own denial-producing ceiling check (`if [ "$total_now" -ge "$VICE_BROKER_MAX" ]`, task 2's own requirement) necessarily reads `VICE_BROKER_MAX` too, since denying an unsatisfiable request is a DIFFERENT decision (request satisfiability) from the spare invariant `maintain_spares()` maintains. This is a reasoned, necessary expansion task 2's own denial requirement introduces, not an oversight -- recorded here rather than silently narrowing task 2's own required behavior to fit a grep pattern that predates it.
- **This project's `curl`-escaping pitfall (see Deviations #2) is the kind of thing worth flagging for anyone extending `probe_ready()` further**: any future tightening of the response-matching heuristic should account for the fact that a real MCP tool-call result's payload arrives as an escaped JSON string, not a flat object.
