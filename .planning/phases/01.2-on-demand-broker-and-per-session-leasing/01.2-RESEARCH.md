### Locked Decisions

- **Three components, already named:** a static, never-rewritten `.mcp.json` `vice` entry; the
  existing `vice-proxy.mjs` (server+client stdio↔HTTP hybrid, built in 01.1); a new host-side
  broker daemon that owns emulator lifecycle (launch on demand, kill on release, sweep orphans).
- **File IPC only**, under the **existing** `.vice-supervisor/` directory — no new port, socket,
  mount, or gitignore entry (decision D-2, carried from 01.1). Every write is tmp-file +
  `rename()` in the same directory, never in place.
- **Acquisition is deferred to the first `tools/call`.** `initialize`/`tools/list` never launch or
  request an emulator (finding 6: spawn is eager, so acquiring at `initialize` launches `x64sc` for
  every session that never touches VICE).
- **Release is wired to BOTH `SIGINT`/`SIGTERM`/`SIGHUP` AND stdin `end`/`close`.** Neither alone is
  sufficient (finding 8, corrected): graceful teardown delivers SIGINT first and never closes
  stdin; abrupt client death closes stdin and never signals.
- **The shutdown handler does exactly one synchronous local filesystem operation** — `unlinkSync`
  on the lease file — and awaits nothing. ~490ms budget, ~0.1ms cost, ~3000-7000x headroom.
- **One lease file does three jobs:** existence = lease, mtime = heartbeat, removal = release.
  Release is a delete, never a write.
- **The lease records `CLAUDE_CODE_SESSION_ID` and `CLAUDE_PID` as diagnostic metadata, not as the
  lease key.** One proxy subprocess per session (finding 4) with subagents riding it (finding 5)
  means process identity already *is* session identity.
- **A released instance is killed, never returned to the spare set.** Non-negotiable; a warm spare
  preserves the "fresh power-on" property only while never used. This is the rule that must not be
  relaxed for efficiency, and it needs a test that fails if it is violated.
- **Warm spares are a latency optimisation, not a correctness requirement** (finding 15: default
  tool-call budget is ≥150s; the cold path is seconds). `ready_spares == N` subject to
  `total_instances <= MAX` (MAX=16). Readiness is proven by a real MCP round-trip, never a socket
  probe.
- **Broker-absent reporting is three states, three messages** (never started / dead-or-hung /
  alive-but-launch-failed), each quoting the absolute host path via `hostpath.mjs`, each explicitly
  forbidding "route around it" workarounds, failing fast rather than waiting out a timeout.
- **The proxy never exits and never caches a negative result** (finding 7: a dead stdio server is
  never auto-reconnected).
- **`MAX_MCP_OUTPUT_TOKENS` and `MCP_TOOL_TIMEOUT` are set explicitly, not inherited.**
  `MCP_TIMEOUT` is not to be relied on for the startup handshake.
- **A forwarded memory read is chunked at 32KB by the proxy** (already built in 01.1 — this phase
  does not touch chunking, listed here only because MANIFEST.md restates it as a standing
  non-negotiable).
- **CLI surface mirrors the existing pool:** `vice-broker.sh start [N]`, default `N=3`, range
  `1..16`, matching `vice-pool.sh start 3` muscle memory.

## Summary

The design in `.planning/notes/vice-mcp-selector-design.md` is unusually complete: three
components, a file-IPC protocol with a concrete directory layout, a warm-spares model, and 16
researched findings — 4 of them promoted from MEDIUM to MEASURED by a dedicated spike set that ran
2026-07-31 and closed the gate on this phase. Two of those findings were *corrected*, not merely
confirmed: the shutdown ladder is inverted from what the design assumed (graceful teardown is the
constrained ~490ms path via SIGINT; abrupt client death is the *unconstrained* path via stdin EOF),
and the inline-output ceiling is roughly half what was assumed (40-60KB, not ~100KB). Both
corrections are already written back into the design note and the `spike-findings-bruce-lee`
skill; this phase's plan should treat that skill as mandatory reading, not optional background.

Given that, this research does not re-derive the design — it resolves the concrete gap between
"the design says X" and "how X gets built against the actual bash/Node code already in this repo."
The single largest structural finding: **the broker should be a new, bash script
(`vice-broker.sh`) that reuses `vice-supervisor.sh` unchanged as its per-instance launch primitive
and shares `container-guard.sh`/`repo-root.sh` verbatim, while `vice-pool.sh`'s own fixed-N
`start`/`stop`/`status` entry point should be left running, untouched, as a still-needed path for
the non-MCP standalone recovery pipeline** (`tools/recover.mjs`, `chip-state.mjs`,
`watch-loads.mjs`), because Phase 1's plans 01-04/01-05/01-06 are not yet executed and still depend
on it. Retiring `vice-pool.sh` outright would silently break in-flight Phase 1 work that this
phase has no mandate to touch.

The second largest finding, not in the design note at all: the existing `vice-proxy.mjs` has **zero
signal handlers today**. Its only exit path is `stdin.on("end"/"close")`. Wiring
`SIGINT`/`SIGTERM`/`SIGHUP` alongside the existing stdin handlers is not an incremental addition to
existing shutdown logic — it is new code, and the file's own header comment ("Claude Code's
termination ladder is stdin EOF -> SIGTERM -> SIGKILL") is the *pre-spike, now-disproven* model and
must be corrected in the same change, not left to drift.

Third: current official Claude Code docs (fetched live, 2026-07-31) refine two of the spike's
findings for a client version newer than what was measured (v2.1.220): automatic backgrounding of
long tool calls (v2.1.212+, 2-minute default threshold) mostly does not apply to this project's
actual usage pattern, because it explicitly excludes subagent-originated calls — and GSD executor
waves are exactly that. And there is now a documented, official per-server `"timeout"` field
directly in `.mcp.json`, which is a cleaner mechanism for setting the vice server's own tool-call
timeout than a global `settings.json` edit.

**Primary recommendation:** build `vice-broker.sh` as a new bash daemon sharing
`container-guard.sh`/`repo-root.sh`/`vice-supervisor.sh` with the existing pool scripts, leave
`vice-pool.sh` running unmodified for the non-MCP pipeline, wire `vice-proxy.mjs`'s shutdown to all
five signals plus stdin end/close with a single idempotent `unlinkSync`, and correct the file's own
header comment and this project's `ROADMAP.md`/`vice-mcp-selector` skill in the same change.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Emulator process lifecycle (launch, supervise, kill) | Host (bash daemon) | — | Only the host can spawn/kill `x64sc`; the container guard makes this structural, not advisory. |
| Request/grant/lease/denial protocol | Shared filesystem (bind mount) | Host (writer of grants/denials), Container (writer of requests/leases) | File IPC is the only channel available across the container/host boundary (no socket, no new port, per D-2). |
| Session-to-instance binding (which emulator a session's calls reach) | Container (`vice-proxy.mjs`, via `vice.mjs`'s `useInstance()`) | — | The proxy is the only component that knows "this stdio process is this session's one connection"; the broker never knows sessions exist, only lease files. |
| Deny-list / epoch / path-translation hazard enforcement | Container (`vice-proxy.mjs` seam) | — | Already built in 01.1; 01.2 must not weaken it when redirecting `useInstance()` at a granted port instead of the fixed default. |
| Warm-spare invariant maintenance (`ready_spares == N`, `total <= MAX`) | Host (broker loop) | — | Spare readiness requires an MCP round-trip against a live `x64sc`, which only the host can perform. |
| TTL sweep / orphan reclaim | Host (broker loop) | — | Same code path as graceful release (criterion 7); must live where the kill happens. |
| Broker-absent diagnosis and host-path translation for the human-facing message | Container (`vice-proxy.mjs`, via `hostpath.mjs`) | — | The proxy is what the agent talks to; the broker cannot report on itself if it is the thing that's absent. |
| Standalone (non-MCP) recovery pipeline instance acquisition | Container (`vice-pool.mjs`'s existing `acquire()`) | — | Unaffected by this phase — see the compatibility finding below. Do not route `tools/recover.mjs` through the new broker protocol in this phase. |

### Pattern 1: Reuse `vice-supervisor.sh` as the per-instance launch primitive, unchanged

**What:** The broker's job is never "know how to launch `x64sc`" — that already exists, is already
tested (crash-loop backoff, epoch writing, `trap cleanup INT TERM`), and is already how
`vice-pool.sh`'s own `cmd_start` launches each of its N instances today.
**When to use:** Every time the broker needs a new instance — whether for a warm spare or an
on-demand grant when the spare set is empty — the *launch* step is identical: spawn
`vice-supervisor.sh` with `VICE_SUPERVISOR_DIR=<pool dir>/<port>` and `VICE_ARGS` set, detached.
**Example (adapted directly from `vice-pool.sh:369-381`, the exact idiom to copy):**
```bash
# Source: tools/vice-pool.sh cmd_start(), lines 369-381 (this repo)
resolved_args="-mcpserver -mcpserverhost $VICE_POOL_MCP_HOST -mcpserverport $port"
VICE_SUPERVISOR_DIR="$dir" VICE_ARGS="$resolved_args" \
  nohup "$SUPERVISOR_SCRIPT" >"$supervisor_log_abs" 2>&1 &
spawned_pid=$!
disown "$spawned_pid" 2>/dev/null || true
```
The broker's delta over the pool is entirely in *when* this runs (on-demand + to maintain
`ready_spares == N`, not once at a fixed count) and *what happens after* (grant/deny files,
lease-driven teardown) — not in how an instance itself is launched.

### Pattern 2: A single `teardown(id)` function fed by two triggers, for criterion 7's "exactly one path"

**What:** Graceful release and TTL sweep must converge on identical code, not two branches that
drift.
**When to use:** In the broker's main loop, on every iteration.
**Example:**
```bash
# Pseudocode for the broker's main loop body, illustrating the single-path property
for id in "${GRANTED_IDS[@]}"; do
  lease="$LEASES_DIR/$id"
  if [ ! -e "$lease" ]; then
    teardown "$id" "released"          # proxy unlinked it -- normal path
  elif lease_is_stale "$lease" "$TTL_S"; then
    rm -f "$lease"                     # broker converts stale-but-present into "missing"
    teardown "$id" "swept (stale ${TTL_S}s)"
  fi
done
```
`teardown()` itself does exactly one thing regardless of which branch called it: identity-verified
`kill -TERM` on the recorded `x64sc` pid (never a name match — mirror `vice-pool.sh`'s existing
`cmd_stop` verification via `ps -o args=` before signalling), then remove `grants/<id>.json`, then
re-evaluate the warm-spare invariant.

### Pattern 3: Testing a host-only bash daemon from inside the container — reuse the existing idiom exactly

**What:** `vice-pool.sh`/`vice-supervisor.sh` are tested today, from Node's `node --test`, by
spawning the *real* shell script as a child process via `execFile` and asserting on its
`--dry-run`/`--check-container`/`--print-paths` output (`vice-pool.test.mjs:1-24`, `:906-965`,
already 1768 lines of exactly this). There is no `.bats` framework in this repo and none needs to
be introduced.
**When to use:** For `vice-broker.sh`'s protocol-level logic (request scanning, grant/denial
writing, spare-invariant bookkeeping) — none of which requires a live `x64sc`.
**Recommendation:** give `vice-broker.sh` the same three testability flags its siblings already
have, plus one new one:
- `--check-container` / `--print-paths` / `--help` — copy verbatim, same shared `container-guard.sh`.
- `--dry-run` — mirror `vice-supervisor.sh`'s own (write records, spawn nothing).
- **`--once`** (new, not present on either existing script) — run exactly one loop iteration
  (scan `requests/`, satisfy/deny them, evaluate the spare invariant, sweep stale leases) then exit,
  rather than looping forever. This is the seam that makes the broker's *protocol* testable via
  `execFileSync` from `node --test` without managing a live background daemon in CI — an `--once`
  pass over a temp `.vice-supervisor/`-shaped directory, with `--dry-run` so no real `x64sc` spawns,
  gives a deterministic, synchronous assertion point exactly like the existing pool/supervisor
  tests already get from `--dry-run` alone.
```js
// Recommended test idiom, directly modeled on vice-pool.test.mjs's own pattern
const { stdout } = await execFileP(brokerScript, ["--once", "--dry-run"], {
  env: { ...process.env, VICE_POOL_DIR: tmpDir, VICE_SUPERVISOR_ALLOW_CONTAINER: "1" },
});
// assert on the resulting grants/<id>.json, denials/<id>.json, registry.json contents
```
Warm-spare invariant maintenance and TTL sweeping over *time* (not a single pass) are not directly
unit-testable this way — document that gap explicitly (see Validation Architecture below) rather
than force a fake clock into a bash script.

### Anti-Patterns to Avoid

- **Re-deriving the stdio-server framing or the deny-list/epoch-check seam.** Both already exist in
  `vice-proxy.mjs` (01.1) and must only be *extended* (new acquisition path feeding `useInstance()`),
  never rewritten.
- **Forking `container-guard.sh` or `repo-root.sh` into a second copy for the broker.** Both files'
  own header comments record exactly this mistake happening once already (the removed mountinfo
  signal); source them, do not copy them.
- **Treating `registry.json`'s existing single-shot `write_registry()` writer as fixed-schema-only.**
  The schema (array of `{port, url, epoch_file, supervisor_dir, supervisor_pid, started_at}`) can
  stay; only the *cadence* changes (continuous reconciliation instead of one-shot at `start`). Do
  not invent a new schema when the existing one already fits.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Detecting "is this the host or the container" | A new guard | `tools/lib/container-guard.sh`, sourced | Already has documented failure history (the removed mountinfo signal); a second copy WILL drift. |
| Atomic JSON writes (grants/denials/leases/registry/broker.json) | A bespoke write pattern | tmp-file + `mv` in the same directory, exactly as `write_registry()`/`write_epoch()` already do | `mv` within one filesystem is atomic; a direct `>` redirect is not, and the existing scripts already prove the idiom works without `jq`. |
| Identity-verified process kill | A pid-only `kill` | `ps -o args= -p "$pid"` matched against the known script path BEFORE signalling, exactly as `vice-pool.sh`'s `cmd_stop` already does | A stale registry entry can point at a recycled pid; killing blind risks killing an unrelated process. |
| Unique, non-repeating IDs for requests/grants/leases | A counter or the session id reused as a filename | `randomUUID()`-based token, exactly as `vice-pool.mjs`'s existing `tryAcquirePort()`/lease-token pattern already does | Reusing an existing, already-tested idiom rather than inventing a second ID scheme in the same codebase. |

**Key insight:** almost everything this phase needs already exists in this repo in a slightly
different shape (fixed-N launch instead of on-demand, one-shot instead of continuous, process/session
lease instead of request/grant/lease). The work is re-composition of proven primitives under a new
loop shape, not new invention — the one genuinely new piece of code is the request-queue loop
itself and the proxy's lease-acquisition client.

## Common Pitfalls

### Pitfall 1: `vice-proxy.mjs` has NO signal handlers today — this is not an incremental change

**What goes wrong:** A plan that reads "wire release to both signals and stdin" as "the signal half
already exists, just add the lease-unlink line" will under-scope the work. Verified by direct
read of `.claude/mcp/vice/vice-proxy.mjs` (836 lines, current as of 01.1): the only shutdown code
is
```js
function shutdown() { process.exit(0); }
process.stdin.on("end", shutdown);
process.stdin.on("close", shutdown);
```
There is no `process.on("SIGINT"/"SIGTERM"/"SIGHUP", ...)` anywhere in the file.
**Why it happens:** 01.1 correctly scoped signal handling out (leasing didn't exist yet, so there
was nothing to release), but the file's own header comment states an already-superseded model as
fact: *"Claude Code's termination ladder is stdin EOF -> SIGTERM -> SIGKILL"* — this is the
pre-spike assumption spike 002 disproved (finding 8).
**How to avoid:** Treat this as new code, not a one-line addition. Add `SIGINT`/`SIGTERM`/`SIGHUP`
handlers per the spike's exact snippet (see Code Examples below), and correct the header comment
in the same change — a stale comment describing a wrong termination ladder right above the actual
handler is exactly the kind of drift this project's own conventions warn against elsewhere
(ROADMAP's confidence-marker convention, the provenance-ledger rule).
**Warning signs:** A plan task that only mentions "add lease release to the shutdown handler"
without a task to add the signal listeners themselves.

### Pitfall 2: Two lease mechanisms will coexist, and conflating them will break something

**What goes wrong:** `vice-pool.mjs`'s existing `acquire()`/`releaseLeaseByToken()` (process/session
kinds, files at `leases/<port>.lease`) is a DIFFERENT mechanism from the new broker protocol's
`leases/<id>` (id = request id, written by the proxy on behalf of an MCP session, meaning-per-file
= "this session's claim on this granted instance"). Both will exist in the same `.vice-supervisor/`
tree after this phase ships. `tools/recover.mjs`, `chip-state.mjs`, and `watch-loads.mjs` — none of
which route through MCP, all of which are still needed because Phase 1's plans 01-04/01-05/01-06
are unexecuted (`STATE.md`, current as of 2026-07-31) — depend on the OLD mechanism continuing to
work exactly as-is.
**Why it happens:** The design note's own "Lifecycle" section describes the NEW protocol only from
the proxy's point of view; it does not mention the old pool's callers at all, because they are out
of this phase's stated scope. A plan that reads "the broker replaces the pool" too literally could
delete or repurpose `vice-pool.sh`/`vice-pool.mjs`'s existing entry points, silently orphaning the
standalone recovery pipeline mid-milestone.
**How to avoid:** Keep `vice-pool.sh` and `vice-pool.mjs`'s `acquire()` running exactly as they are.
Build the broker as an ADDITIONAL, independent daemon and an ADDITIONAL, independent container-side
client module (`vice-broker-client.mjs`, not a new mode bolted onto `vice-pool.mjs`). Do not delete
`vice-pool.sh`'s `cmd_start` in this phase even though ROADMAP frames the fixed pool as "superseded"
conceptually — superseded-in-intent for new (proxy) work is not the same as safe-to-delete while
other code still calls it.
**Warning signs:** Any task that edits `tools/recover.mjs`, `chip-state.mjs`, or `watch-loads.mjs`,
or that removes `vice-pool.sh`'s `start`/`stop` subcommands. None of those files are in this
phase's stated scope (ROADMAP names only `tools/vice-broker.sh` vs `.claude/mcp/vice/vice-proxy.mjs`
as the two touched paths).

### Pitfall 3: `port_in_use()` / TCP-accept readiness is not the same as MCP-ready

**What goes wrong:** A spare that answers a bare TCP `connect()` may still be mid-boot — the C64
has not finished its power-on sequence, and `x64sc -mcpserver` can accept a socket before the
emulated machine itself is usable. Advertising such a spare as `ready` hands a session a half-alive
machine, which presents as a flaky emulator, not as an obvious race (criterion 9, explicit in
ROADMAP).
**Why it happens:** `vice-pool.sh`'s own `port_in_use()` (used only to *refuse launching on an
already-bound port*, never to prove readiness) is the closest existing code, and it is tempting to
reuse it for the wrong question.
**How to avoid:** Prove readiness with an actual `mcp__vice__vice_ping` round-trip (the tool
already exists and is exactly what `vice-probe.mjs`'s `probeInstance()` — already built, already
imported by `vice-proxy.mjs` — performs). A spare only becomes `ready` after this succeeds once, not
after the port merely accepts a connection.
**Warning signs:** A spare marked `ready` immediately after spawning `vice-supervisor.sh`, with no
probe in between.

### Pitfall 4: `MCP_TIMEOUT`'s effect on startup was measured only in the mode most likely to mislead

**What goes wrong:** Spike 003's own `g1c` experiment (`MCP_TIMEOUT=60000` against a 10s init
delay, "changed nothing") is cited in the design note as proof `MCP_TIMEOUT` does not govern
startup. But setting a 60-second cap and testing it against only a 10-second delay cannot
distinguish "the cap is honored but never reached" from "the cap does nothing" — and current
official docs (`code.claude.com/docs/en/mcp`, fetched live 2026-07-31) state plainly: *"Configure
MCP server startup timeout using the `MCP_TIMEOUT` environment variable (for example,
`MCP_TIMEOUT=10000 claude` sets a 10-second timeout)"* `[CITED: code.claude.com/docs/en/mcp]`.
**Why it happens:** The spike's own `g1c` used print mode for part of its testing (the exact mode
its own conventions call the least reliable for timing), and the one long-lived (`stream-json`)
success case (`g1d`) only proves "no deadline within 10 seconds," not "no deadline at any value of
`MCP_TIMEOUT`."
**How to avoid:** This is a genuine, open discrepancy — record it as such (see Assumptions Log),
but note it is **not load-bearing for this phase's design**: the vice proxy answers `initialize`
with zero host I/O (criterion 3/finding 6, unconditionally true regardless of `MCP_TIMEOUT`), so
whatever `MCP_TIMEOUT` actually governs cannot affect this proxy's handshake latency. Do not spend
plan effort re-litigating this constant; it is moot for 01.2's own correctness, only worth flagging
so nobody later cites "no startup deadline, ever, unconditionally" as a fact broader than what was
actually shown.

### Pitfall 5: Automatic backgrounding of long tool calls mostly does not help this project's actual usage pattern

**What goes wrong:** Current docs describe a real, useful-sounding feature (Claude Code v2.1.212+):
a main-conversation MCP tool call still running after 2 minutes (default,
`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS`) moves to a background task automatically rather than blocking
the turn `[CITED: code.claude.com/docs/en/mcp]`. It would be easy to assume this smooths over any
residual cold-boot latency for the "warming, retry" UX.
**Why it happens:** The docs are explicit that **"Calls from subagents; Claude Code backgrounds
only main-conversation calls"** never move to the background. This project's actual VICE-touching
work runs overwhelmingly through GSD executor waves — subagent-driven, per 01.1's own measured
finding that a GSD worktree executor shares its parent session's single proxy connection. Those
calls get NO benefit from auto-backgrounding; they simply block for the full duration, same as the
spike measured pre-feature.
**How to avoid:** Design the "warming, retry" cold-path UX (the `MCP_TOOL_TIMEOUT`/per-server
`"timeout"` cutoff message) as the primary mechanism, not as a fallback for cases auto-backgrounding
"should" handle — because for this project's dominant call pattern, it won't. Auto-backgrounding is
a genuine bonus for a human's own interactive main-conversation calls, not something the executor
wave path can rely on.
**Warning signs:** A plan task that designs the cold-path UX around "the call will just background
itself" without checking whether the call in question originates from a subagent.

## Code Examples

### The five-signal shutdown handler (verbatim from the spike's validated snippet)

```js
// Source: .claude/skills/spike-findings-bruce-lee/references/shutdown-and-lease-release.md
// Measured 3/3 identical: SIGINT -> +100ms SIGTERM -> ~490ms SIGKILL (graceful);
// stdin_end -> stdin_close, unbounded time (abrupt). Both paths call the SAME onTeardown().
let teardownRan = false;

function releaseLease(trigger) {
  if (!leaseFile) return;
  try { unlinkSync(leaseFile); }        // the ENTIRE release. ~0.1ms measured.
  catch (err) { console.error(`vice-proxy: lease_unlink_failed trigger=${trigger}: ${err.message}`); }
}

function onTeardown(trigger) {
  if (teardownRan) return;              // idempotent -- several triggers can arrive
  teardownRan = true;
  releaseLease(trigger);                // FIRST, before anything interruptible
}

process.stdin.on("end",   () => onTeardown("stdin_end"));      // abrupt client death
process.stdin.on("close", () => onTeardown("stdin_close"));    //   "
for (const sig of ["SIGTERM", "SIGINT", "SIGHUP"]) {           // graceful -- SIGINT arrives FIRST
  process.on(sig, () => onTeardown(sig));
}
```
This replaces the current, signal-free `shutdown()` in `vice-proxy.mjs` — the existing
`stdin.on("end"/"close")` lines are kept but redirected to call `onTeardown`, not
`process.exit(0)` directly (nothing in the graceful path needs an explicit `process.exit()`; SIGKILL
finishes the job ~390ms after SIGTERM regardless, and the abrupt path already exits normally on its
own once the pipe closes and there's nothing left listening).

## Open Questions

1. **Broker implementation language: bash or Node?**
   - What we know: `vice-supervisor.sh`/`vice-pool.sh` are bash, tested via real-subprocess
     `execFile` from `node --test`; `vice-proxy.mjs` and its transport modules are Node, with a real
     test suite (1410+1768 lines across the two existing test files). Host-side Node availability
     is unconfirmed (no host access this session); host-side bash is a given (the existing scripts
     already require it).
   - What's unclear: whether the project would accept a new host-side runtime dependency (Node) in
     exchange for safer JSON handling and one fewer language in the stack for this one component.
   - Recommendation: **bash**, extending `vice-supervisor.sh`'s exact shape, per the concrete
     reasoning in Architecture Patterns/Standard Stack above. Confirm during planning if there is a
     reason to override this (e.g., if the host is already confirmed to run Node for some other
     purpose this research did not surface).

2. **Does the broker replace `vice-pool.sh` or wrap it?**
   - What we know: `container-guard.sh`, `repo-root.sh`, and `vice-supervisor.sh`'s per-instance
     launch are all directly reusable, unchanged. `vice-pool.sh`'s own `cmd_start`/`cmd_stop` entry
     points are the part whose *model* (fixed-N, pre-launched, long-lived) is superseded.
   - What's unclear: whether the plan should formally mark `vice-pool.sh` deprecated (comment-only,
     no behavior change) or leave it entirely untouched.
   - Recommendation: **leave `vice-pool.sh` entirely untouched in this phase.** It is still load-
     bearing for the non-MCP recovery pipeline (Pitfall 2). Revisit retirement only once that
     pipeline's own emulator-access story is separately settled — out of scope here.

3. **What is the request-id scheme?**
   - What we know: must never repeat across sessions, doubles as the snapshot-name prefix (ports
     recycle under the broker, so port-prefixing breaks). `vice-pool.mjs`'s existing lease-token
     generation already uses `randomUUID()`.
   - Recommendation: generate one fresh id **per acquisition attempt** (not per session — a session
     could in principle need a second grant if its first instance dies, per the design note's
     "can request a replacement" property), e.g. `req-${process.pid}-${Date.now()}-${randomUUID().slice(0,8)}`,
     mirroring the existing token idiom exactly. Store `CLAUDE_CODE_SESSION_ID`/`CLAUDE_PID` inside
     the request/grant/lease JSON body as separate metadata fields, never as the id itself.

4. **What TTL, relative to the 60s heartbeat?**
   - What we know: heartbeat measured rock-stable (60.1s min/max, zero drift, 39 ticks over 40
     minutes). Nothing reaps an idle *session*, so the TTL only needs to protect against the
     broker's own sweeper reclaiming a thinking session too eagerly.
   - Recommendation: **TTL = 3x the heartbeat interval (180s at the default 60s heartbeat).**
     Tolerates one or two missed ticks (a transient host hiccup, GC pause) without falsely sweeping
     a live session, while bounding an orphaned instance's lifetime to a few minutes. This is a
     reasoned default (Assumption A5), not a measured constant — revisit once the broker exists and
     real orphan/sweep behavior can be observed.

5. **Does `registry.json` stay `0600`?**
   - Recommendation: **yes, keep `0600`**, and state uid-parity (container `vscode` and host
     `henrik`, both uid 1000, already verified in the design note) as an explicit, documented
     precondition of the whole broker design, rather than widening the mode defensively for a
     multi-user scenario that does not exist today.

6. **Does the proxy absorb the pause-on-state-read polling discipline, or stay documented?**
   - Carried unresolved from ROADMAP's own "Decisions to resolve here" list; 01.1 decided
     "documented" (D-F). Not flagged as a specific research target for this phase (see
     `<additional_context>`'s explicit research-scope list, which does not include it) — the
     planner should treat 01.1's precedent as the default unless there is a specific reason to
     revisit it now that on-demand instances change the blast radius of getting it wrong.

| Pattern | STRIDE | Standard Mitigation |
|---|---|---|
| Request-id reuse enabling grant/lease hijack or snapshot-name collision | Spoofing / Tampering | Generate ids via `randomUUID()`-based scheme (Open Question 3), never a predictable counter; never derive the id from a value an attacker-adjacent process could guess or replay. |
| TOCTOU between "lease file observed absent" and "broker acts on it" | Tampering | Not a realistic multi-tenant attack here (uid-parity precondition means only the container's own proxy or the host's own broker can write these files) — but still worth a single-pass, read-once-then-act discipline in the broker loop (read the lease's mtime/existence once per iteration, act on that snapshot, don't re-check mid-action) to avoid the broker's own internal races. |
| Path traversal via a malformed request id used to build a file path | Tampering | Validate the id against a strict allow-list pattern (e.g. `^req-[0-9]+-[0-9]+-[0-9a-f]{8}$`) before using it in any path construction, exactly mirroring `vice-pool.mjs`'s existing "accept only integer ports in 1..65535" discipline for `registry.json`. |
| Unbounded warm-spare growth exhausting host resources | Denial of Service | The `MAX` ceiling (16, already specified) is the control — enforce it in the SAME invariant-check function that maintains `ready_spares == N`, never as a separate, independently-maintained limit that could drift out of sync. |
| A malformed/hostile `denials/<id>.json` reason string relayed verbatim to the agent | Information Disclosure (low severity) | Already the existing posture for host-error relaying (`aliveButFailedMessage()` in `vice-proxy.mjs` relays the host's message verbatim by design) — acceptable here since both sides are the same trust domain (uid-parity precondition), not attacker-adjacent. |
| `VICE_ARGS`-style argument injection into a spawned `x64sc` | Elevation of Privilege | Not new to this phase — `vice-supervisor.sh` already documents this exact concern (T-jty-02) and mitigates by treating `VICE_ARGS` as a single space-separated string split exactly once, printed before spawn for visibility. The broker inherits this by reusing `vice-supervisor.sh` unchanged (Pattern 1) rather than re-implementing the spawn itself. |
